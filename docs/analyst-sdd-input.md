# Analyst-owned OpenSpec input: результат адаптации

Дата: 8 октября 2026 года.

Обновление к аудиту от 5 октября: по решению аналитика ответственность за
proposal и delta specs перенесена на аналитическую сторону. Design, tasks,
реализация и технические проверки остаются у разработки. Исходный аудит
сохраняет историю прежнего решения; актуальный договор — `core/sdd-input.md`.

## Основание и границы

Источник формата — предоставленный `sdd-integration-contract.md`, прочитанный
как отчёт о среде разработки. Он описывает обычный OpenSpec `spec-driven`,
отдельные backend/frontend roots одного кодового репозитория, backend CLI 1.5.0
и frontend/skills 1.6.0. Store не зарегистрирован, references не объявлены.
Это сведения из отчёта, а не проверка действующей среды разработчиков.

Адаптация выполнена в analyst-harness и coda-analyst-harness. Общие проверки
и формат одинаковы; инструкции GigaCode и его skill изменены только в coda.
Продуктовые требования, baseline и обычные кодовые клоны не изменялись.
Реальная поставка и эксперимент GigaCode в эту работу не входят.

## Точка входа и состав

Точка входа сохранена:

```text
requirements-exchange/<delivery-key>/
  manifest.json
  revisions/NNN/
    requirements.md
    sdd/
      package.json
      backend/<change-id>/
        .openspec.yaml
        proposal.md
        specs/<capability>/spec.md
      frontend/<change-id>/
        .openspec.yaml
        proposal.md
        specs/<capability>/spec.md
    returns/
      receipt.json
      tasks.md
      tasks/<task-id>.md
      summary.md
```

Создаются только затронутые контуры. Аналитик готовит `sdd/` в рабочей ветке
выбранной поставки до принятия в analytics/main. Новый профиль —
`openspec-spec-driven-v1`. Схема манифеста 5 сохраняет прежние редакции;
квитанция версии 2 добавляет хеш полного SDD-входа. Самостоятельный change
в разработке не становится отдельной бизнес-поставкой.

## Реализованные проверки

- Proposal/spec/package связаны с точными байтами requirements, исходным commit,
  config/context, main specs и картой REQ → requirement → scenario.
- Поддержаны ADDED, MODIFIED, REMOVED, RENAMED. Для MODIFIED проверяются существующие
  имена и сохранение сценариев; намеренное удаление требует отдельного основания.
  Полнота смысла проверяется содержательным аудитом.
- Аудит и подтверждение связывают весь SDD-вход. Правка только proposal/spec
  обнаруживается, требует регистрации источника, нового аудита и новой редакции.
- Публикация использует прежнюю изолированную review-ветку. Подтверждение принятия
  и повтор после слияния учитывают SDD; неопределённая публикация не превращается
  в резервное размещение. Обычный code checkout остаётся только для чтения.
- Приёмник по умолчанию проверяет без записи. В сессии разработки `--apply`
  переносит точные файлы в указанные OpenSpec changes. Проверяются все цели до
  записи, конфликты путей и редакций, повторный импорт; частичный сбой откатывает
  только созданные этим запуском каталоги. Существующие design/tasks сохраняются.
- Новый вход не перезаписывает change прежней редакции. Для исправления выбирается
  отдельный согласованный change-id. Приёмник не запускает реализацию, CLI,
  коммиты или публикацию и не создаёт квитанцию автоматически.

Отсутствие кода блокирует готовность нового SDD-входа даже при резервной передаче
через analytics. Прежний requirements-only профиль сохранён для старых клиентов
и согласованного legacy-процесса, автоматического понижения профиля нет.

## После реализации и релиза

Разработка возвращает квитанцию, согласованные задачи, фактические результаты
и общий summary по всем REQ. Реализация, проверка, аналитическая приёмка и
внедрение остаются разными фактами.

Подтверждённый внедрённый релиз запускает разбор результатов и обновление baseline.
Обязательная проверка доменной модели охватывает сущности, связи, правила,
жизненные циклы, процессы и диаграммы; для каждого аспекта сохраняется основание
обновления либо отсутствия изменений. Полный обмен, включая `sdd/`, архивируется
в `releases/<release-id>/exchange-archive/<delivery-key>/`. Очистка допускается
после принятия baseline и архива в analytics/main и подтверждается отдельно
после принятия удаления. Частичные поставки остаются в рабочем обмене.
Локальный OpenSpec archive не заменяет этот релизный процесс.

## Проверка и следующий эксперимент

Целевые проверки охватывают структуру и трассировку, актуальность источников,
подмену и изменение входа, исторические схемы и квитанции, публикацию через
временные Git remotes, повторный импорт, сохранение design/tasks и отказ при
коллизиях. Отдельно проверен полный цикл SDD-возврата, закрытия, baseline,
неизменяемого архива и принятой очистки.

Локальный валидатор проверяет профиль обмена и не заменяет установленный
OpenSpec validator. Эксперимент должен проверить фактические правила и версии
backend/frontend, dry-run и приём входа, строгую валидацию change, переход
GigaCode к design/tasks без повторной генерации proposal/spec и возврат точной
квитанции. Готовность артефакта tasks для apply не означает завершения чекбоксов.

Результаты проверки:

| Проверка | Результат |
|---|---|
| Полная регрессия analyst-harness | 767 тестов, OK, один пропуск |
| Полная регрессия coda-analyst-harness | 798 тестов, OK, один пропуск |
| Все SDD-тесты после последнего исправления приёмника | 51 тест в каждой обвязке, OK |
| Целостность ссылок и доступность договоров | 3 теста в каждой обвязке, OK |
| Проверка diff и пробельных ошибок новых файлов | OK в обеих обвязках |

Единственный пропуск полной регрессии — отрисовка PlantUML: не настроен
`PLANTUML_JAR`. Последнее исправление приёмника запрещает создавать Python-кэш
в кодовом checkout; отдельный тест запускает доставленный helper непосредственно
из принятого `requirements-exchange/` и проверяет отсутствие любых записей.

Изменения подготовлены в `codex/analyst-sdd-input` для публикации и эксперимента
на стороне аналитика. Тестовые публикации использовали только временные
Git-репозитории; реальная передача требований проверяется отдельно.
