# Аналитическая обвязка АС КОДА

`coda-analyst-harness` разворачивает и обслуживает рабочую область аналитика АС КОДА. Обвязка, проектные данные и исходный код разделены между независимыми Git-репозиториями. Это позволяет обновлять инструменты без служебных файлов в `documents`, исследовать код в ограниченном объёме и синхронизировать `documents` с `changeswork-copy` через проверяемую обратную заплату.

## Главное правило

В корне обвязки находятся инструкции, режимы, шаблоны, программы и местное состояние. Назначение репозитория задаётся ролью, а не именем каталога. Штатное соответствие фиксировано и не запрашивается при запуске: `analytics = documents`, `code = coda`, `source = changeswork-copy`. Переназначение допускается только по прямой команде аналитика.

Рабочее дерево проектных данных есть только у роли `analytics`. Репозиторий роли `source` хранится как скрытое служебное bare-зеркало без рабочего дерева. Их коммиты должны описывать одну структуру и после применения обратной заплаты давать одинаковое Git-дерево.

В дереве `documents` и в Git-дереве `changeswork-copy` запрещены:

- `.workflow/`;
- `.vscode/`;
- отслеживаемый Git файл `AGENTS.md` как копия аналитической обвязки.

Программа развёртывания создаёт в корне роли `analytics` местный `AGENTS.md` с точкой входа в корневую обвязку. Он исключён через `.git/info/exclude`, не входит в Git и не нарушает равенство проектных деревьев. Файлы `AGENTS.md` внутри самодостаточных пакетов передачи разработчикам также не являются копией аналитической обвязки: это договор принимающей SDD, который входит в сам пакет.

## Рабочая область

После развёртывания получается один каталог с тремя независимыми репозиториями:

```text
coda-analyst-harness/
├── AGENTS.md
├── core/
├── modes/
├── scripts/
├── skills/
├── templates/
├── .workspace-state/          # местное состояние, не версионируется
│   ├── repositories/
│   │   └── changeswork-copy.git/ # bare-зеркало, рабочего дерева нет
│   └── retired-repositories/  # сохранённые старые клоны, не используются
├── reverse-diffs/             # обратные заплаты, не версионируются
├── documents/                 # роль analytics; внутри местный игнорируемый AGENTS.md
└── coda/                      # исходный код, только чтение
```

Это не единый репозиторий. `documents` и `coda` являются независимыми клонами с рабочими деревьями. `changeswork-copy.git` является независимым bare-репозиторием: в нём есть только база Git, но нет извлечённых файлов, которые могла бы изменить LLM или нормализовать файловая система macOS. Корневой репозиторий обвязки их не отслеживает.

| Роль | Штатный репозиторий | Назначение | Права обвязки |
|---|---|---|---|
| `analytics` | `documents/` | требования, планы, пакеты, фактическое выполнение | изменение и отправка |
| `source` | `.workspace-state/repositories/changeswork-copy.git/` | служебное получение внешних аналитических изменений | только `fetch` программой обмена, рабочего дерева нет |
| `code` | `coda/` | серверный и клиентский код | только чтение |

Для `coda` и bare-зеркала `changeswork-copy` при развёртывании устанавливается запрещающий адрес отправки. Зеркало не включается в рабочую область редактора. Обвязка отправляет изменения только в `documents`.

## Первый запуск

Клонируйте обвязку и запустите LLM в её корне. Корневой `AGENTS.md` требует автоматически развернуть отсутствующие репозитории до содержательной работы:

```bash
git clone https://github.com/shuhart75/coda-analyst-harness.git
cd coda-analyst-harness
python3 scripts/workspace.py bootstrap
```

Команда:

1. клонирует `documents` и `coda` с рабочими деревьями;
2. создаёт скрытое bare-зеркало `changeswork-copy` без рабочего дерева;
3. проверяет адреса и запрещает отправку из `coda` и зеркала `changeswork-copy`;
4. записывает роли в `.workspace-state/workspace.json` и реестр кода в `.workspace-state/code-repos.json`;
5. создаёт в `documents` местный игнорируемый `AGENTS.md`, который ведёт LLM к корневой обвязке;
6. создаёт `coda-analyst.code-workspace` без зеркала `changeswork-copy`.

Если остался старый корневой клон `changeswork-copy/`, повторный `bootstrap` переносит его целиком в `.workspace-state/retired-repositories/`, включая незакоммиченные файлы, но больше никогда не использует его для обмена. Это позволяет обновить старую установку, не потеряв случайные изменения. После проверки содержимого устаревшую копию можно удалить вручную.

Повторный запуск безопасен: действующие репозитории проверяются, но не создаются заново. Состояние рабочей области:

```bash
python3 scripts/workspace.py status
```

Если в `documents` ещё находится старая отслеживаемая обвязка, `bootstrap` не перезаписывает её. Он помечает необходимость перехода, а команда синхронизации получает из `source` штатный коммит удаления обвязки, объединяет истории и только после успешного слияния создаёт местную точку входа. Изменённые служебные файлы вызовут обычный конфликт Git; автоматического удаления или выбора стороны нет.

## Откуда запускать LLM

После первого `bootstrap` аналитик может запускать LLM:

- из корня `coda-analyst-harness`;
- непосредственно из репозитория роли `analytics`, штатно из `documents`.

В обоих случаях модель обязана определить `HARNESS_ROOT`, получить `PROJECT_ROOT` командой `python3 scripts/workspace.py project-root` и записывать `baseline/`, `context/`, `planning/`, `features/` и `releases/` только в `PROJECT_ROOT`. При запуске из `documents` местный игнорируемый `AGENTS.md` содержит абсолютные `HARNESS_ROOT`, `PROJECT_ROOT` и `CODE_ROOT` этой машины. Поэтому маршрутизация не зависит ни от имени репозитория, ни от текущего вложенного каталога, а исследование роли `code` выполняется через единую корневую обвязку.

Существующую задачу, начатую в `documents` до обновления, можно продолжить там же после обновления корневой обвязки, `bootstrap` и успешной команды `синкани репы`.

Обновление кода выполняется только отдельной командой:

```bash
python3 scripts/workspace.py update-code
```

Она останавливается при изменённом рабочем дереве, отделённом `HEAD` или невозможности выполнить только быстрое перемещение ветки вперёд.

## Где что хранится

### В обвязке

- `AGENTS.md` - обязательный договор LLM для всей рабочей области;
- `core/` - общие правила качества, исследования, контекста, передачи и циклов;
- `modes/` - режимы планирования, требований, прототипирования, фактического выполнения и завершения выпуска;
- `scripts/` - проверки, генераторы и служебные команды;
- `templates/` - шаблоны проектных документов и пакетов;
- `skills/` - договоры повторяемых циклов;
- `.workspace-state/active-mode.md` - текущий режим;
- `.workspace-state/runs/` - состояния циклов;
- `.workspace-state/run-state/` - производные местные сводки и индекс трассировки.

### В проектных репозиториях

```text
Git-дерево documents или changeswork-copy
├── README.md
├── baseline/
│   ├── current/               # подтверждённое текущее состояние системы
│   └── versions/              # сохранённые версии состояния
├── context/
│   ├── source-materials/      # исходные материалы
│   ├── current-system/        # обработанное описание текущей системы
│   ├── change-requests/       # обработанные запросы на изменение
│   ├── project-rules/         # особенности конкретного проекта
│   ├── evals/                 # проектные проверочные сценарии
│   └── analysis-log.md        # журнал аналитических решений
├── planning/
│   ├── team.md                # состав, интервалы недоступности, коэффициенты
│   ├── consistency-backlog.md # известные хвосты согласованности
│   ├── approved-plans/        # контрольные снимки утверждённых планов
│   └── <YYYY-QN>/
├── features/
└── releases/
```

Проектные правила, состав команды, утверждённые планы и журнал анализа являются данными продукта, поэтому хранятся одинаково в обоих аналитических репозиториях. Текущий режим, состояния циклов и производные индексы зависят от конкретной машины и в проектные репозитории не попадают.

## Короткие команды пользователю

LLM должна понимать команды без путей и самостоятельно выбирать нужную программу:

| Команда пользователя | Действие |
|---|---|
| `синкани репы` | обновить оба аналитических клона, влить `changeswork-copy` в `documents`, проверить обратную заплату и отправить только `documents` |
| `сделай обратный дифф` | построить и проверить обратную заплату без её применения и отправки |
| `покажи состояние репозиториев` | показать ветки, коммиты, чистоту и наличие встроенной обвязки |
| `обнови код` | безопасно обновить `coda` быстрым перемещением ветки вперёд |
| `сходи в код`, `посмотри в коде`, `проверь по коду` | провести ограниченное исследование выбранного контура |
| `планируем`, `обнови план` | включить режим планирования и работать с черновиком плана |
| `делаем требования` | включить режим требований |
| `сформируй пакет для разработки` | проверить требования и выпустить самодостаточный пакет функциональности |
| `обнови реальный прогресс` | изменить только представление фактического выполнения |
| `актуализируй доменную модель` | перенести подтверждённый результат в текущее состояние и оформить версию |

Точные варианты коротких команд перечислены в `templates/workflow/command-catalog.template.md` и `templates/workflow/command-cheatsheet.template.md`.

## Сквозной процесс

### 1. Текущее состояние системы

`documents/baseline/current/` описывает только уже подтверждённое поведение: доменную модель, правила, данные, API, интерфейсы, решения и ограничения. Будущая работа туда не включается.

Аналитик может уточнять текущее состояние по документам и по коду. Код является техническим доказательством реализации, но не источником новых бизнес-решений.

### 2. Планирование

Квартальные работы разбиваются по функциональностям. Одна функциональность - законченный пользовательский или системный результат. Для неё может быть до четырёх плановых историй: `AN`, `BE`, `FE`, `QA`; отсутствующая роль не создаётся искусственно.

Основные правила:

- приоритетные функциональности располагаются выше и начинаются раньше;
- цель - максимальная, но не превышающая 100 процентов загрузка доступных ресурсов;
- на квартальном и командирском уровне трудоёмкость роли распределяется по доступному составу команды с учётом ограничений параллельности;
- коэффициенты роли по умолчанию: `AN = 0.80`, `BE = 0.70`, `FE = 0.65`, `QA = 0.80`, если проектный документ не задаёт иное;
- персональные коэффициенты и закрытые интервалы задаются в `PROJECT_ROOT/planning/team.md` (штатно `documents/planning/team.md`);
- клиентская работа может начаться не раньше чем через три рабочих дня после начала связанной серверной работы;
- базовый запас риска не менее 20 процентов, но отдельной полосой на руководительской диаграмме не показывается;
- основной артефакт - диаграмма Ганта PlantUML;
- утверждает план только пользователь-владелец;
- утверждённые квартальные и командирские планы неизменяемы.

После утверждения фактические задачи отражаются на диаграммах фактического выполнения. По итогам квартала оценка сравнивается с фактом, а коэффициенты производительности и риска уточняются для следующего планирования.

### 3. Требования

Главный документ функциональности: `documents/features/<feature>/requirements.md`. Он описывает изменение относительно `baseline/current/` и создаётся по практическому профилю, основанному на ISO/IEC/IEEE 29148:2018.

Обязательные свойства требований:

- полнота границ, участников, данных, состояний, ошибок и отрицательных случаев;
- атомарность и однозначность нормативных формулировок;
- проверяемость и устойчивые идентификаторы `REQ-*`, `SCN-*`, `IMP-*`;
- явная трассировка от источника до среза, проверки, пакета и квитанции;
- отдельный раздел доработок затронутых функциональностей;
- отсутствие противоречий с текущим состоянием и соседними требованиями;
- русский язык; английский допускается для кода, путей, API, полей, статусов и необходимых специальных терминов.

Пока аналитик прорабатывает функциональность, LLM изменяет только `features/<feature>/requirements.md`. Она не создаёт и не обновляет после каждой правки срезы, подробные требования клиентской и серверной частей, кандидаты задач или пакет передачи. Возможные границы и порядок срезов до передачи фиксируются внутри корневого документа.

Срезы в `features/<feature>/slices/<slice>/` создаются как производная аналитическая декомпозиция только при явной подготовке пакета и затем служат основной единицей тестирования. Существующие срезы между передачами являются снимком последней отправленной редакции и могут намеренно отставать от живого `requirements.md`.

Состояние хранится в `features/<feature>/requirements-state.json`. После правки LLM фиксирует один из источников:

- `analyst` - изменение по инициативе аналитика;
- `developer-receipt` - изменение принято из зарегистрированной квитанции SDD.

Изменение по квитанции не пересобирает срезы, не создаёт новую редакцию и не вызывает предложения её создать. После аналитического изменения уже переданных требований LLM один раз предлагает подготовить новую редакцию и пересмотреть срезы. Если аналитик отказывается, отказ сохраняется; повторных предложений и пересборок не будет до явной команды подготовки.

Служебные переходы, которые LLM выполняет сама:

```bash
python3 scripts/requirementsctl.py status documents <feature>
python3 scripts/requirementsctl.py record-change documents <feature> --origin analyst
python3 scripts/requirementsctl.py record-change documents <feature> --origin developer-receipt --receipt <путь>
python3 scripts/requirementsctl.py mark-offered documents <feature>
python3 scripts/requirementsctl.py decline-revision documents <feature>
python3 scripts/requirementsctl.py begin-preparation documents <feature>
python3 scripts/requirementsctl.py mark-published documents <feature> --package-id <id> --revision <N>
```

Аналитику эти команды помнить не требуется. Файл состояния нужен для переноса решения между задачами LLM и рабочими машинами. `handoffctl add-revision` технически блокирует создание редакции, пока `begin-preparation` не зафиксировал явное разрешение.

Перед изменением существующей функциональности LLM проверяет состояние. Если файл состояния создаётся впервые и живые требования уже расходятся с последней отправленной редакцией, обвязка требует сначала классифицировать расхождение. LLM не угадывает источник, а задаёт аналитику один вопрос: это инициативная правка или результат зарегистрированной квитанции.

Перед выпуском пакета LLM сначала проверяет полноту, непротиворечивость, проверяемость, влияния, трассировку, язык и устаревшие хвосты корневого документа. Затем один раз строит срезы и подробные требования контуров, проверяет их покрытие и публикует редакцию. Однозначные редакционные исправления вносятся автоматически. Если решение меняет смысл или допускает несколько вариантов, LLM задаёт аналитику по одному вопросу и ничего не придумывает.

### 4. Ограниченное исследование кода

Код не загружается в контекст целиком. Проход выполняется по одному контуру:

1. зафиксировать ветку, коммит и чистоту `coda`;
2. выбрать `backend` или `frontend`;
3. прочитать локальные инструкции SDD выбранного контура;
4. найти точные сущности, поля, маршруты или символы;
5. открыть только найденные модули и соседние проверки;
6. сохранить краткие доказательства с относительными путями;
7. проверить, что код за время исследования не изменился.

Команды низкого уровня:

```bash
python3 scripts/code-inspect.py doctor documents
python3 scripts/code-inspect.py locate documents '<строка>' --contour backend
python3 scripts/code-inspect.py begin documents --contour backend --feature <feature> --query '<цель>'
python3 scripts/code-inspect.py verify <файл-состояния>
```

Если реализация отличается от ожиданий, это не отменяет требования автоматически. Аналитик фиксирует наблюдение, а разработческая SDD всё равно повторяет сверку на своей актуальной ветке перед изменением кода.

### 5. Передача функциональности разработчикам

Пакет хранится в проектном репозитории:

```text
features/<feature>/handoffs/<package-id>/
├── README.md
├── AGENTS.md
├── handoff.json
├── .control/
└── revisions/
    └── NNN/
        ├── package/
        │   ├── README.md
        │   ├── request.md
        │   ├── manifest.json
        │   ├── requirements.md
        │   └── slices/
        └── returns/
            ├── development-tasks/
            ├── decomposition-snapshots/
            ├── implementation-results/
            └── test-results/
```

`package-id` обозначает поток поставки функциональности, обычно `<feature>-delivery`. Номер редакции хранится отдельно. `handoff.json` содержит состояние каждой редакции и единственное `next_sdd_action`, поэтому принимающая SDD не угадывает актуальную редакцию по дате или имени каталога.

В `request.md` используются разделы:

- `Goal` - требуемый результат;
- `Constraints` - обязательные ограничения и явно исключённая работа;
- `Context` - только необходимый предметный контекст;
- `Examples` - однозначные примеры;
- `Acceptance Criteria` - наблюдаемые критерии.

Полный документ требований и срезы остаются источником предметного объёма. Манифест фиксирует состав, контрольные суммы и трассировку. Опубликованный `revisions/NNN/package/` неизменяем.

### 6. Декомпозиция разработки

Получив пакет, разработчик передаёт SDD ссылку на корень пакета и короткую команду `обработай пакет`. SDD читает `AGENTS.md`, `handoff.json`, активную редакцию, затем исследует только нужные участки `coda`.

SDD формирует в `returns/development-tasks/` карточки будущих задач Jira:

- одна карточка - один законченный технический результат, который можно отдельно проверить и закоммитить;
- серверные и клиентские работы всегда разделены;
- целевой размер - 1-3 рабочих дня одного исполнителя;
- максимум - 5 дней для серверной и 10 дней для клиентской задачи;
- превышение требует явного обоснования;
- оценка и ключ Jira необязательны;
- разработчик меняет карточки короткими командами из самой карточки: объединяет, делит, переименовывает, переносит, меняет зависимости или отменяет;
- после команды подтверждения создаётся неизменяемый снимок декомпозиции.

Подтверждённая декомпозиция сразу становится доступна аналитику, но передача является фоновым процессом и не блокирует начало разработки. Аналитик сам решает, кто заведёт задачи в Jira и как использовать оценки в фактическом плане.

### 7. Реализация, тестирование и квитанции

Разработческая SDD выполняет то, что однозначно и уместно для фактического кода. Уже реализованное, иначе реализованное или перенесённое поведение не считается сбоем всего пакета. Работа продолжается по следующим пунктам.

Квитанция реализации фиксирует:

- исходную и итоговую ревизии кода;
- коммиты и проверки;
- результат каждого требования и сценария;
- уже существовавшее поведение;
- отклонения от входных ожиданий;
- оставшуюся или дополнительную работу;
- рекомендуемое последующее действие аналитика.

Тестировщик работает по тем же срезам и сохраняет результаты в `returns/test-results/`. Квитанция тестирования связывает срез, карточки разработки и квитанции реализации.

После получения квитанций аналитик:

1. переносит подтверждённое реализованное поведение в `baseline/current/`;
2. уточняет требования, если фактическое решение принято как новое ожидаемое состояние;
3. оставшуюся работу отменяет, откладывает или переносит в другую доработку;
4. сохраняет трассировку решения;
5. не переписывает задним числом неизменяемый входной пакет и утверждённый план.

Если пункт 2 выполняется непосредственно по квитанции, новая редакция пакета и новые срезы не формируются. Такая актуализация фиксирует принятый фактический результат в живых требованиях и текущем состоянии. Новая передача появляется только по отдельному решению аналитика.

## Синхронизация аналитических репозиториев

Штатно аналитик работает только в роли `analytics`, то есть в `documents`. Команда:

```bash
python3 scripts/repository-exchange.py sync
```

выполняет под межпроцессной блокировкой:

1. обновление скрытого bare-зеркала роли `source`;
2. проверку рабочего дерева роли `analytics` и быстрое перемещение его ветки `main` из собственного удалённого репозитория;
3. узкое безопасное сопоставление известного ошибочного Unicode-имени на macOS, только если содержимое файла совпадает с Git и входящий коммит удаляет старый путь;
4. локальное слияние `source/main` в `analytics/main`;
5. остановку и полный откат незавершённого слияния при конфликте;
6. проверку Unicode NFC и отсутствия отслеживаемой встроенной обвязки после слияния;
7. создание местной игнорируемой точки входа `AGENTS.md` в роли `analytics`;
8. построение и проверку обратной заплаты от дерева `source` к дереву `analytics` во временном индексе Git;
9. доказательство совпадения итоговых идентификаторов деревьев;
10. отправку только `analytics/main`.

Поэтому при накопившихся независимых коммитах в `documents` и `changeswork-copy` порядок для аналитика остаётся коротким: обновить корневой `coda-analyst-harness` и сказать LLM `синкани репы`. Команда не переписывает историю и не копирует каталоги: обе линии объединяются обычным Git merge. Конфликт требует отдельного осознанного решения.

Обратная заплата и сведения проверки сохраняются в `reverse-diffs/`:

```text
reverse-diffs/
├── reverse-diff-latest.patch
├── reverse-diff-latest.json
└── <временная-метка>-<source>-to-<target>.patch
```

Только построить заплату без обновления и отправки:

```bash
python3 scripts/repository-exchange.py reverse-diff
```

Показать состояние:

```bash
python3 scripts/repository-exchange.py status
```

До применения заплаты коммиты и деревья репозиториев могут различаться. Критерий корректности обмена: применение проверенной заплаты к указанному коммиту `changeswork-copy` создаёт дерево, полностью совпадающее с указанным деревом `documents`.

## Проверки

Основная проверка проектного репозитория запускается из корня обвязки:

```bash
PROJECT_ROOT="$(python3 scripts/workspace.py project-root)"
python3 scripts/harnessctl.py doctor "$PROJECT_ROOT"
```

Отдельные проверки:

```bash
python3 scripts/validate-structure.py "$PROJECT_ROOT"
python3 scripts/validate-links.py "$PROJECT_ROOT"
python3 scripts/validate-context.py "$PROJECT_ROOT"
python3 scripts/validate-language.py "$PROJECT_ROOT" --all
python3 scripts/validate-requirements-profile.py "$PROJECT_ROOT"
python3 scripts/validate-planning.py "$PROJECT_ROOT"
python3 scripts/validate-trace.py "$PROJECT_ROOT" --strict
python3 scripts/evaluate-harness.py "$PROJECT_ROOT"
```

Проверка структуры отвергает встроенные `.workflow`, `.vscode` и отслеживаемую копию корневого `AGENTS.md`, но разрешает созданную программой местную игнорируемую точку входа.

Проверки самой обвязки:

```bash
python3 -m compileall -q scripts tests
python3 -m unittest discover -s tests -v
git diff --check
```

## Архивы

ZIP не является состоянием пакета и запрещён в `coda-analyst-harness`, `documents`, `changeswork-copy` и каталогах `features/*/handoffs/`. Транспортный ZIP создаётся только по прямому требованию пользователя и только в `~/Downloads`. Обычная передача выполняется ссылкой на каталог пакета.

## Версия

Версия обвязки находится в `VERSION`. Проектные репозитории не содержат копию версии и не обновляются путём установки служебных файлов: новая версия начинает действовать после обновления корневого `coda-analyst-harness`.
