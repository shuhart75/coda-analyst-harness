# Аналитическая обвязка АС КОДА

`coda-analyst-harness` разворачивает и обслуживает рабочую область аналитика АС КОДА. Обвязка, проектные данные и исходный код разделены между независимыми Git-репозиториями. Это позволяет обновлять инструменты без служебных файлов в `documents`, исследовать код в ограниченном объёме и синхронизировать `documents` с `changeswork-copy` через проверяемую обратную заплату.

## Главное правило

В корне обвязки находятся инструкции, режимы, шаблоны, программы и местное состояние. Назначение репозитория задаётся ролью, а не именем каталога. Штатное соответствие фиксировано и не запрашивается при запуске: `analytics = documents`, `code = coda`, `source = changeswork-copy`. Переназначение допускается только по прямой команде аналитика.

Рабочее дерево проектных данных есть только у роли `analytics`. Репозиторий роли `source` хранится как скрытое служебное bare-зеркало без рабочего дерева. Их коммиты должны описывать одну структуру и после применения обратной заплаты давать одинаковое Git-дерево.

В дереве `documents` и в Git-дереве `changeswork-copy` запрещены:

- `.workflow/`;
- `.vscode/`;
- отслеживаемый Git файл `AGENTS.md` как копия аналитической обвязки.

Программа развёртывания создаёт в корне роли `analytics` местный `AGENTS.md` с точкой входа в корневую обвязку. Он исключён через `.git/info/exclude`, не входит в Git и не нарушает равенство проектных деревьев. Формальный договор принимающей SDD хранится отдельно в корне `requirements-exchange/AGENTS.md`.

Тот же местный файл исключений защищает `.codex/`, `.gigacode/`, `.gigaide/`, `.idea/`, `GIGACODE.md`, `*.iml` и `*.orig`. Это предотвращает случайное добавление новых локальных настроек, но намеренно не скрывает уже отслеживаемые файлы: такое загрязнение должно быть явно удалено из Git.

## Рабочая область

После первого развёртывания получается один каталог с тремя независимыми репозиториями:

```text
coda-analyst-harness/
├── AGENTS.md
├── core/
├── modes/
├── scripts/
├── skills/
├── templates/
├── .workspace-state/          # местное состояние, не версионируется
│   ├── repositories/
│   │   └── changeswork-copy.git/ # bare-зеркало, рабочего дерева нет
│   ├── analytics-snapshots/ # местные защитные снимки обновлений analytics
│   └── retired-repositories/  # сохранённые старые клоны, не используются
├── reverse-diffs/             # обратные заплаты, не версионируются
├── documents/                 # роль analytics; внутри местный игнорируемый AGENTS.md
└── coda/                      # исходный код, только чтение
```

Это не единый репозиторий. `documents` и `coda` являются независимыми клонами с рабочими деревьями. `changeswork-copy.git` является независимым bare-репозиторием: в нём есть только база Git, но нет извлечённых файлов, которые могла бы изменить LLM или нормализовать файловая система macOS. Корневой репозиторий обвязки их не отслеживает.

| Роль | Штатный репозиторий | Назначение | Права обвязки |
|---|---|---|---|
| `analytics` | `documents/` | требования, планы, резервный каталог передачи, фактическое выполнение | изменение и отправка |
| `source` | `.workspace-state/repositories/changeswork-copy.git/` | служебное получение внешних аналитических изменений | только `fetch` программой обмена, рабочего дерева нет |
| `code` | `coda/` | серверный и клиентский код | чтение, защищённый `git pull --ff-only` и изолированная публикация только в заранее созданный `requirements-exchange/**` |

Для `coda` и bare-зеркала `changeswork-copy` при развёртывании устанавливается запрещающий адрес обычной отправки. Зеркало не включается в рабочую область редактора. Исключение кодового репозитория ограничено защищённой передачей в заранее согласованный `requirements-exchange/**`; при недоступности используется `documents/requirements-exchange/`.

Корневой репозиторий `coda-analyst-harness` на машине аналитика является установленной обвязкой, а не рабочим репозиторием проектных данных. В штатной работе его разрешено только обновлять командой `git pull --ff-only`: LLM не изменяет, не коммитит и не отправляет его отслеживаемые файлы. Создаваемые на месте `.workspace-state/`, `reverse-diffs/`, `documents/`, `coda/` и файл рабочей области исключены из Git, поэтому не загрязняют корневое рабочее дерево и не препятствуют обновлению. Исключение возможно только при явно поставленной задаче на разработку самой обвязки.

После первого успешного развёртывания роли `code` и `source` становятся необязательными локальными источниками. Пользователь может удалить `coda/`, скрытое зеркало `.workspace-state/repositories/changeswork-copy.git/` или оба каталога. Повторный запуск не восстанавливает их самовольно: состояние становится `degraded`, но это рабочий, а не аварийный режим. Роль `analytics` обязательна; её удаление блокирует автоматическое развёртывание, поскольку в удалённом рабочем дереве могли остаться неотправленные изменения.

## Первый запуск

Клонируйте обвязку и запустите LLM в её корне. Корневой `AGENTS.md` требует автоматически развернуть отсутствующие репозитории до содержательной работы:

```bash
git clone https://github.com/shuhart75/coda-analyst-harness.git
cd coda-analyst-harness
python3 scripts/workspace.py bootstrap
```

Команда:

1. клонирует `documents` и `coda` с рабочими деревьями;
2. создаёт скрытое bare-зеркало `changeswork-copy` без рабочего дерева;
3. проверяет адреса, при первом клонировании запрещает отправку из `coda`, при повторном запуске проверяет этот запрет и запрещает отправку из зеркала `changeswork-copy`;
4. записывает роли в `.workspace-state/workspace.json` и реестр кода в `.workspace-state/code-repos.json`;
5. создаёт в `documents` местный игнорируемый `AGENTS.md`, который ведёт LLM к корневой обвязке;
6. создаёт `coda-analyst.code-workspace` без зеркала `changeswork-copy`.

Если остался старый корневой клон `changeswork-copy/`, повторный `bootstrap` переносит его целиком в `.workspace-state/retired-repositories/`, включая незакоммиченные файлы, но больше никогда не использует его для обмена. Это позволяет обновить старую установку, не потеряв случайные изменения. После проверки содержимого устаревшую копию можно удалить вручную.

Повторный запуск безопасен: действующие репозитории проверяются, а ранее подготовленные, но затем удалённые `code` и `source` не создаются заново. Состояние рабочей области:

```bash
python3 scripts/workspace.py status
```

Если в `documents` ещё находится старая отслеживаемая обвязка, `bootstrap` не перезаписывает её. Он помечает необходимость перехода, а команда синхронизации получает из `source` штатный коммит удаления обвязки, объединяет истории и только после успешного слияния создаёт местную точку входа. Изменённые служебные файлы вызовут обычный конфликт Git; автоматического удаления или выбора стороны нет.

## Откуда запускать LLM

После первого `bootstrap` аналитик может запускать LLM:

- из корня `coda-analyst-harness`;
- непосредственно из репозитория роли `analytics`, штатно из `documents`.

В обоих случаях модель обязана определить `HARNESS_ROOT`, получить `PROJECT_ROOT` командой `python3 scripts/workspace.py project-root` и записывать `baseline/`, `context/`, `planning/`, `features/` и `releases/` только в `PROJECT_ROOT`. При запуске из `documents` местный игнорируемый `AGENTS.md` содержит абсолютные `HARNESS_ROOT` и `PROJECT_ROOT` этой машины, а `CODE_ROOT` указывается только при наличии роли `code`. Поэтому маршрутизация не зависит ни от имени репозитория, ни от текущего вложенного каталога. Если `code` отсутствует, модель продолжает аналитическую работу, не ищет другой клон и не пытается исследовать код.

Существующую работу, начатую в `documents` до обновления, можно продолжить из того же каталога. После обновления корневой обвязки первый запрос о начале работы над функциональностью сам запускает описанную ниже одноразовую миграцию. Если есть местные изменения или неопубликованные коммиты, миграция сохраняет их в отдельной рабочей ветке до любого полного обмена репозиториев.

LLM общается с аналитиком по-русски: по-русски задаёт вопросы, сообщает о ходе работы и формулирует итог. Английский сохраняется только в точном коде, путях, идентификаторах, закреплённых названиях и необходимых специальных терминах либо по прямой просьбе аналитика. Общее правило редактора `output-language.md` не является решением проекта перейти на английский; если платформа навязывает его с более высоким приоритетом, это отдельная настройка платформы, а не поведение обвязки.

Кодовый репозиторий принадлежит внешнему процессу разработки. Аналитическая обвязка разрешает первоначальное клонирование, защищённый `git pull --ff-only` и отдельную публикацию только в заранее созданный разработчиками `requirements-exchange/**`. Публикация выполняется во временной копии актуальной ветки, проверяет точный состав путей, создаёт отдельный коммит и отправляет его; обычный клон `coda` не меняется. Если каталога, чтения или права отправки нет, роль `code` не изменяется, а редакция создаётся в `documents/requirements-exchange/`. Любое другое изменение блокирует исследование до вмешательства владельца кодового репозитория.

## Где что хранится

### В обвязке

- `AGENTS.md` - обязательный договор LLM для всей рабочей области;
- `core/` - общие правила качества, исследования, контекста, передачи и циклов;
- `modes/` - режимы планирования, требований, прототипирования, фактического выполнения и завершения выпуска;
- `scripts/` - проверки, генераторы и служебные команды;
- `templates/` - шаблоны проектных документов и пакетов;
- `skills/` - договоры повторяемых циклов;
- `.workspace-state/active-mode.md` - текущий режим;
- `.workspace-state/runs/` - состояния циклов;
- `.workspace-state/run-state/` - производные местные сводки и индекс трассировки.

### В проектных репозиториях

```text
Git-дерево documents или changeswork-copy
├── README.md
├── baseline/
│   ├── current/               # подтверждённое текущее состояние системы
│   └── versions/              # сохранённые версии состояния
├── context/
│   ├── source-materials/      # исходные материалы
│   ├── current-system/        # обработанное описание текущей системы
│   ├── change-requests/       # обработанные запросы на изменение
│   ├── project-rules/         # особенности конкретного проекта
│   ├── evals/                 # проектные проверочные сценарии
│   └── analysis-log.md        # журнал аналитических решений
├── planning/
│   ├── team.md                # состав, интервалы недоступности, коэффициенты
│   ├── consistency-backlog.md # известные хвосты согласованности
│   ├── approved-plans/        # контрольные снимки утверждённых планов
│   └── <YYYY-QN>/
├── features/
└── releases/
```

Проектные правила, состав команды, утверждённые планы и журнал анализа являются данными продукта, поэтому хранятся одинаково в обоих аналитических репозиториях. Текущий режим, состояния циклов и производные индексы зависят от конкретной машины и в проектные репозитории не попадают.

## Короткие команды пользователю

LLM должна понимать команды без путей и самостоятельно выбирать нужную программу:

| Команда пользователя | Действие |
|---|---|
| `пишем требования по фиче <feature>`, `работаем с фичой <feature>`, `беру фичу <feature> в работу`, `начинаем работу над требованиями по <feature>` | при первом использовании выполнить одноразовую миграцию, затем создать от актуальной `origin/main` и включить рабочую ветку этой функциональности; неоднозначный идентификатор не угадывать |
| `сохрани`, `зафиксируй изменения`, `закоммить` | проверить и зафиксировать все и только точные изменённые пути, затем отправить активную рабочую ветку; `main` не изменять |
| `обнови`, `синкани`, `подтяни изменения` | при активной работе объединить актуальную `origin/main` с рабочей веткой и отправить эту ветку; полный обмен репозиториев не выполнять |
| `требования готовы к объединению`, `отправь требования на проверку`, `вливаем в основную ветку` | проверить требования, сохранить и обновить рабочую ветку, затем отправить её; явно сообщить, что запрос на слияние не создан, а возвращённая ссылка открывает форму его создания; пакет не формировать |
| `запрос на слияние принят`, `MR принят`, `ветка влита в main` | доказать включение отправленного коммита в `origin/main`, выполнить `collaboration.py finish` и закрыть местную рабочую сессию |
| `отправь требования в разработку`, `передай разрабам`, `сформируй пакет для разработки` | только после принятия рабочей ветки в `origin/main` проверить требования и передать `requirements.md` с `manifest.json`; сообщить фактическое место |
| `синкани репы`, `обнови репы`, `обнови репозитории` | если выбрана отправленная рабочая ветка, сначала доказать её принятие через `finish` и автоматически перейти на `main`; затем обновить всё доступное. Если принятие не доказано, остановиться до обновления `code` и `source` |
| `сделай обратный дифф` | при наличии `source` построить и проверить обратную заплату без её применения и отправки; без `source` сообщить, что проверка недоступна |
| `покажи состояние репозиториев` | показать ветки, коммиты, чистоту и наличие встроенной обвязки |
| `обнови код`, `обнови coda`, `обнови репу с кодом` | при наличии `code` выполнить только защищённый `git pull --ff-only`; без `code` ничего не восстанавливать |
| `сходи в код`, `посмотри в коде`, `проверь по коду` | при наличии `code` провести ограниченное исследование выбранного контура; без `code` сообщить о недоступности сверки |
| `включи совместную работу`, `мигрируй на веточную работу` | включить местный многопользовательский режим; существующую работу сначала сохранить в рабочей ветке без автоматического коммита и отправки |
| `планируем`, `обнови план` | включить режим планирования и работать с черновиком плана |
| `делаем требования` | включить режим требований |
| `обнови реальный прогресс` | изменить только представление фактического выполнения |
| `актуализируй доменную модель` | перенести подтверждённый результат в текущее состояние и оформить версию |

Точные варианты коротких команд перечислены в `templates/workflow/command-catalog.template.md` и `templates/workflow/command-cheatsheet.template.md`.

## Сквозной процесс

### 1. Текущее состояние системы

`baseline/current/` описывает подтверждённое работающее состояние. Требования функциональности описывают изменение относительно него. Наблюдение из кода само по себе не становится бизнес-правилом: аналитик отделяет факт реализации от ожидаемого поведения.

### 2. Планирование

Функциональность является законченным квартальным результатом. Для неё создаётся не более одной плановой истории на `AN`, `BE`, `FE` и `QA`. Утверждённые квартальные и командирские планы неизменяемы; фактические задачи позднее отражаются отдельно.

### 3. Требования

Главный и единственный авторский документ:

```text
features/<feature>/requirements.md
```

Документ оформляется как компактная спецификация в духе SDD, но остаётся бизнес-контрактом, а не техническим `spec.md`. ISO-подобный и прежний многораздельный последовательный форматы больше не используются для новых передач.

При явно порученной миграции прежний документ можно один раз переименовать в `requirements_iso.md`. Это неизменяемая архивная копия: она не является источником требований, не проходит проверки живого документа и не передаётся разработчикам.

Обязательные свойства:

- назначение, законченный результат и явные границы;
- правила `REQ-*` в естественном порядке процесса;
- хотя бы один вложенный сценарий с ключевыми словами `Когда` и `Тогда` у каждого правила;
- необязательное связное описание процесса, данных и состояний только когда оно помогает чтению;
- трассировка по устойчивым `REQ-*` без обязательной таблицы, повторяющей полный текст;
- обязательный раздел влияния на соседние функциональности, включая необходимые доработки;
- явная подчистка устаревшего поведения и неотслеженных хвостов;
- отсутствие противоречий с текущим состоянием и соседними требованиями;
- наглядные диаграммы только в PlantUML, дополняющие текст, но не вводящие самостоятельных правил;
- русский язык с английским только для кода, путей, API, полей, статусов, форматов и необходимых специальных терминов.

Каждое правило и каждый сценарий дополнительно проходят договор контролируемых
формулировок из `core/requirements-wording.md`. Количества и области действия
задаются явно; `Когда` называет конкретное состояние и событие, а `Тогда` -
наблюдаемый результат без повторения `система должна`. Команды
`проверь формулировки требований`, `проверь однозначность требований`,
`найди плохо составленные требования` и `убери неоднозначные формулировки`
запускают эту проверку без создания редакции передачи.

Пока аналитик прорабатывает функциональность, LLM изменяет только корневой `requirements.md`. Срезы, отдельные требования клиентской и серверной частей, предварительные задачи разработки и редакции передачи не создаются.

Сам `requirements.md` не содержит поля `Статус`: оно создало бы неоднозначность с
исполняемой статусной моделью. Авторская готовность и аудит хранятся в
`requirements-state.json`, а состояние передачи конкретной неизменяемой редакции —
в `manifest.json` каталога обмена.

После каждого изменения `requirements-state.json` фиксирует источник:

- `analyst` — инициатива аналитика;
- `developer-result` — принятое уточнение из возврата разработческой SDD с устойчивым `return_id`.

Результат разработчиков не создаёт новую редакцию. После инициативного изменения ранее переданных требований LLM один раз предлагает новую редакцию; отказ действует до следующей явной команды передачи.

### 4. Ограниченное исследование кода

Когда для требований нужен факт текущей реализации, LLM:

1. получает зарегистрированную роль `code`;
2. фиксирует ветку, коммит и чистоту;
3. выбирает один контур;
4. читает его местные инструкции;
5. ищет точные сущности и открывает только найденные модули и соседние проверки;
6. сохраняет относительные пути доказательств;
7. доказывает неизменность кода после исследования.

Разработческая SDD повторяет сверку по своей актуальной ветке.

### 5. Передача разработчикам

Канонический каталог:

```text
requirements-exchange/
├── README.md
├── AGENTS.md
└── <feature>/
    ├── manifest.json
    └── revisions/
        └── 001/
            ├── requirements.md
            └── returns/
                ├── tasks.md
                ├── tasks/
                │   └── <task-id>.md
                └── summary.md
```

Вход конкретной функциональности состоит только из `manifest.json` и неизменяемого `requirements.md`. Корневые `README.md` и `AGENTS.md` являются общим договором каталога. Переданный файл является бизнес-контрактом. Разработческая SDD не копирует его целиком в локальный `spec.md`: она сверяет требования с кодом, выделяет техническую дельту каждого контура и создаёт собственные `proposal/spec/design/tasks` либо их местные аналоги.

Выбор места выполняется автоматически:

1. если репозиторий роли `code` существует, обвязка создаёт его временную копию и проверяет корневой `requirements-exchange/` в актуальной ветке;
2. если каталог существует, обвязка формирует только `requirements-exchange/**`, проверяет точные пути, создаёт коммит и отправляет его в ту же ветку;
3. обычный клон роли `code` остаётся неизменным, а корневой каталог в нём обвязка сама не создаёт;
4. если репозитория, каталога, чтения или права отправки нет, создаётся `PROJECT_ROOT/requirements-exchange/`;
5. структура резервного каталога полностью совпадает со структурой приёма;
6. итоговый ответ содержит фактическую роль и номер редакции, а также удалённую ветку и путь для `code` либо абсолютный путь для `analytics`.

Команда `сформируй пакет для разработки` и её синонимы запускают обязательный аудит, а не немедленную публикацию. Полный алгоритм закреплён в `core/requirements-audit.md`.

Аудит выполняется в три уровня:

1. каждое `REQ-*` отдельно проверяется на один смысл, однозначность и проверяемость;
2. весь набор проверяется как единая система ролей, действий, состояний, данных, сценариев, зависимостей и влияний;
3. проверяется готовность к передаче: формат, покрытие сценариями, трассировка, язык, PlantUML, хвосты и контрольная сумма.

На втором уровне LLM обязана рассуждать между требованиями, а не только читать их по очереди. После каждого ответа аналитика повторно проверяются затронутые связи, а после последнего исправления все три уровня выполняются заново по полному документу.

Исправления без изменения смысла вносятся автоматически. При содержательной неопределённости LLM показывает связанные места, проблему, последствия и допустимые варианты, затем задаёт аналитику один вопрос и ничего не придумывает. Итоговый отчёт содержит метод аудита, состояние трёх уровней, все замечания и решения, исправления, принятые риски, блокировки, предположения и контрольную сумму. Затем задаётся прямой вопрос: `Подтверждаете результат аудита и отправку требований в разработку?`

До явного положительного ответа редакция не создаётся. Исходная команда передачи не считается подтверждением аудита. Подтверждение связано с контрольной суммой `requirements.md`; любое последующее изменение требует нового аудита. После подтверждения редакция сразу получает состояние `sent`; промежуточный пакет `ready` и ZIP не создаются.

### 6. Декомпозиция, реализация и тестирование

`returns/tasks.md` содержит уже согласованную разработчиками разбивку. Как и когда разработчики её согласуют, не относится к аналитическому процессу.

Для каждой задачи указываются:

- устойчивый идентификатор и название;
- ровно один контур и содержание;
- связанные `REQ-*`;
- локальное изменение SDD и созданные технические материалы;
- зависимости;
- необязательная оценка;
- необязательный ключ Jira.

Клиентская и серверная работа не смешиваются в одной задаче; одно требование может быть связано с несколькими задачами разных контуров. Аналитик не подтверждает `tasks.md`, а его обработка не блокирует разработку. Изменение согласованной декомпозиции оформляется новой редакцией и записью в журнале самого файла.

По мере выполнения задач SDD создаёт `returns/tasks/<task-id>.md`. Отчёт фиксирует локальное изменение SDD, уже существовавшее поведение, выполненную работу, отличия, остаток, коммиты, пути и проверки.

Уже реализованное, иначе реализованное или частично реализованное правило не обрушает обработку всей функциональности. SDD описывает факт и продолжает независимую работу.

`returns/summary.md` покрывает каждый `REQ-*` активной редакции и показывает:

- фактическое состояние;
- реализованное поведение;
- отличия от ожиданий;
- оставшуюся работу;
- доказательства.

### 6.1. Чтение SberTrek и Jira

Команды `прочитай задачи из трекеров`, `проверь задачи в трекерах`,
`сверь SberTrek и Jira` и `покажи текущее состояние по трекерам` запускают
безопасную сверку без изменения трекеров и аналитического репозитория.

При незавершённой первичной настройке это не команда немедленного поиска. LLM
задаёт ровно один вопрос дословно, без вступления, примеров и подсказок, сохраняет
ответ и последовательно задаёт следующие. Конечные и исключающие статусы
настраиваются отдельно для SberTrek и Jira.
До завершения настройки она не читает задачи и не показывает предварительную
сводку. `config-status` запускается отдельно, без `head`, `tail`, `grep`, `jq` и
других фильтров; код `3` и `must_stop: true` запрещают любые MCP-вызовы. Чтение
выполняет только главный агент после `begin`, а итог показывается только после
успешного `reconcile` с тем же `run_id`, `workflow_complete: true` и
`final_response_allowed: true`. Ошибка `reconcile` запрещает ручную сводку по уже
прочитанным данным.

Процесс:

1. При первом запуске по одному уточняются проекты, типы единиц разработки и
   конечные и исключающие статусы. Встреченные account id затем последовательно
   связываются только с `team_id` из `planning/team.md`; роль выводится из префикса
   `AN`, `BE`, `FE` или `QA`. Короткие формы `A`, `B`, `F`, `Q` равнозначны.
2. После готовой настройки LLM находит MCP-инструменты SberTrek и Jira по возможностям, а не по имени сервера.
3. Уже известные реальные задачи читаются из SberTrek; Jira заполняет отсутствующие
   оценки и другие поля и дополняет историю.
4. После каждого MCP-ответа LLM сохраняет данные штатными командами
   `snapshot-metadata`, `snapshot-issue`, `snapshot-not-found`, `snapshot-history`
   и `snapshot-collection`; утверждения полноты содержат доказательство MCP-вызова,
   а `run-status` показывает незаполненные части.
5. Разные заполненные значения показываются как конфликт. SberTrek остаётся
   эффективным источником.
6. Для каждого найденного эпика читается ограниченный список остальных задач.
   Прямо связанные с функциональностью задачи предлагаются к включению; по
   сомнительным задачам LLM задаёт аналитику один вопрос.
7. Один набор показывается отдельно по эпикам и по релизам. Отсутствующие на
   actual-progress релизы показываются как предложения.
8. Завершение разработки определяется по явному статусу либо по подтверждённому
   историей переназначению с участника роли `developer` на участника другой роли.
   Правило действует для настроенных типов, включая Story, если она является
   единицей разработки проекта.

Первый запуск полностью управляется коротким пользовательским промптом. Внутри LLM
выполняет `trackerctl.py config-status`, задаёт недостающие вопросы строго по одному
и подтверждает настройку до `begin`. `begin` создаёт шаблоны снимков с проверяемым
паспортом чтения истории, связей, прямых Jira-пар, эпиков и релизов. Неполная
настройка, состояние `pending`, незакрытый seed, неизвестный участник,
неоднозначная пара или недочитанная прямая пара блокируют `reconcile`;
недоступная возможность MCP явно попадает в ограничения только после реальной
неуспешной попытки вызова.
Прямые результаты MCP не показываются как итог: сначала `run-status` должен вернуть
`tracker-run-ready`, затем `reconcile --run-id ...` формирует проверенный отчёт.
Каждый исходный seed-ключ ссылается на аналитический источник и обязан завершиться
найденной задачей своего провайдера либо доказанным `not-found`; результат
текстового поиска без такого источника остаётся кандидатом и не выдаётся за
известную задачу. SberTrek/Jira counterpart является взаимно однозначным.

Итоговые количества и ограничения берутся непосредственно из `trackerctl` и
`report.md`. LLM не пересчитывает их вручную и не может сообщить об отсутствии
ограничений при неполном сборе.

Старый пустой конфиг первой версии распознаётся автоматически и возвращается в
состояние незавершённой настройки; фиктивный тип `development-task` не наследуется.
Старые свободные маппинги участников очищаются один раз и повторно собираются через
обязательные вопросы текущего запуска.

Снимки и отчёты находятся только в игнорируемой
`.workspace-state/tracker-runs/`. Включение найденных задач и релизов в
actual-progress будет отдельной подтверждаемой операцией.


### 7. Получение и обработка возвратов

После обновления доступного кодового репозитория команда `проверь результаты разработки` ищет новые файлы по пути и контрольной сумме.

- по умолчанию показываются функциональности текущего аналитика;
- чужие результаты открываются только по явной команде просмотра всех;
- просмотр не меняет владельца;
- обработка чужого результата начинается только по явной команде;
- требования не меняются автоматически;
- принятое решение фиксируется в `features/<feature>/development-results-state.json`.

По результату аналитик отдельно решает, нужно ли изменить требования, обновить `baseline/current/`, отложить, отменить или перенести остаток. Историческая входная редакция и утверждённый план не переписываются.

## Совместная работа аналитиков

Если в `documents` работают несколько аналитиков, используется один общий репозиторий и отдельные рабочие ветки. Форки не требуются: они добавили бы отдельные адреса получения и отправки, усложнили бы определение роли `analytics` и перенесли бы ту же проблему объединения на дополнительный уровень.

Общая модель:

- `main` содержит принятую командой версию требований;
- `feature/<feature>/<analyst>` содержит первый цикл работы аналитика; последующие
  циклы той же функциональности получают свободный суффикс `-2`, `-3`, поэтому
  принятую историческую ветку не требуется удалять или перезаписывать;
- новую рабочую ветку обвязка создаёт от актуальной `origin/main`, а не от возможной устаревшей местной `main`;
- один корневой `features/<feature>/requirements.md` имеет одного ответственного редактора;
- человек принимает рабочую ветку в `main` через запрос на слияние;
- пакет для разработки создаётся только после такого принятия и только из актуальной `main`;
- полный обмен с `source` и формирование обратной заплаты выполняются только для `main`.

Многопользовательский режим включается локально на каждой машине. Состояние хранится в `.workspace-state/collaboration.json`, не входит в `documents` и не передаётся другим аналитикам. Если файла ещё нет, это означает необходимость одноразовой миграции, а не разрешение работать непосредственно в `main`.

### Команды аналитика

| Действие | Равнозначные фразы |
|---|---|
| Начать работу | `начинаю работу над фичей <feature>`, `пишем требования по фиче <feature>`, `работаем с фичой <feature>`, `беру фичу <feature> в работу`, `берём фичу <feature> в работу`, `начинаем работу над требованиями по <feature>`, `начинаем работы над требованиями по <feature>` |
| Сохранить | `сохрани работу`, `сохрани`, `зафиксируй`, `зафиксируй изменения`, `закоммить`, `закоммить изменения`, `сделай коммит` |
| Обновить рабочую ветку | `обнови мою ветку`, `обнови`, `синкани`, `подтяни изменения`, `синкани мою ветку`, `обнови рабочую ветку` |
| Передать на проверку и слияние | `требования готовы к объединению`, `отправь требования на проверку`, `подготовь требования к слиянию`, `отправь ветку на слияние`, `вливаем в основную ветку`, `влей в основную ветку` |
| Завершить после принятия | `запрос на слияние принят`, `MR принят`, `PR принят`, `ветка принята в main`, `ветка влита в main`, `слияние выполнено` |
| Передать разработке | `сформируй пакет для разработки`, `отправь требования в разработку`, `передай требования разработчикам`, `передай разрабам`, `отдай требования разрабам`, `отправь разрабам`, `отдаём в разработку`, `передаём в разработку` |

Короткие `обнови` и `синкани` имеют веточный смысл только при зарегистрированной активной работе. Фразы `синкани репы`, `синхронизируй репозитории`, `обнови код` и `обнови coda` имеют отдельный закреплённый смысл. Вне активной работы голая команда без объекта считается неоднозначной: LLM задаёт один вопрос и ничего не изменяет.

### Процесс с точки зрения аналитика

1. Аналитик пишет `беру фичу <feature> в работу`, `начинаем работу над требованиями по <feature>` или использует другой синоним начала.
2. До чтения требований LLM выполняет `bootstrap` и проверяет состояние совместной работы.
3. Если это первый запуск после обновления, LLM запрашивает короткий идентификатор аналитика и выполняет одноразовую миграцию. Отсутствие `collaboration.json` не переводит процесс в однопользовательский режим.
4. LLM находит существующий идентификатор функциональности. Если подходят несколько функциональностей, она задаёт один вопрос. Затем обвязка создаёт `feature/<feature>/<analyst>` от актуальной `origin/main` и регистрирует активную работу.
5. Аналитик обсуждает и меняет один корневой `features/<feature>/requirements.md`. Срезы и отдельные приложения по контурам не создаются.
6. По фразе `сохрани`, `закоммить` или синониму LLM просматривает все изменённые пути, запускает относящиеся к ним проверки и отдельно спрашивает о непонятных файлах. Обвязка принимает только полный точный набор путей, создаёт смысловой коммит и отправляет рабочую ветку. `main` не меняется.
7. По фразе `обнови` или `синкани` обвязка получает актуальную `origin/main`, создаёт защитный снимок и объединяет её с рабочей веткой. Бесконфликтный результат отправляется в ту же ветку. При конфликте исходные версии сохраняются, попытка обвязки отменяется, а LLM запрашивает решения по одному пути.
8. Когда требования готовы, аналитик пишет `требования готовы к объединению` или `вливаем в основную ветку`. LLM выполняет полную проверку требований, сохраняет остаточные изменения, обновляет ветку, повторяет проверки и отправляет только рабочую ветку. `collaboration.py submit` возвращает `merge_request_created=false`: запрос на слияние и пакет для разработки на этом шаге не создаются. Адрес из `merge_request_create_url` является формой создания запроса, а не ссылкой на существующий запрос.
9. Ответственный сотрудник создаёт, проверяет и принимает запрос на слияние в `documents/main`. Разбиение этой организационной роли и права в Bitbucket находятся вне обвязки.
10. После принятия аналитик пишет `запрос на слияние принят` или синоним. LLM выполняет `collaboration.py finish`, который доказывает включение отправленного коммита в `origin/main`, безопасно возвращается на актуальную `main` и закрывает местную рабочую сессию. Последующая команда `передай разрабам` проверяет требования и публикует только `requirements.md` с `manifest.json` как `sent`, после чего сообщает фактическое место.
11. Инициативные последующие изменения начинают новую рабочую ветку и при необходимости новую редакцию передачи. Изменения по принятому результату разработки также проходят через рабочую ветку и запрос на слияние, но сами по себе не создают новую редакцию.

В одной локальной рабочей области ведётся одна активная функциональность. Для двух одновременно открытых функциональностей одному аналитику нужны два независимых клона рабочей области. Это исключает смешение незакоммиченных изменений и неоднозначность коротких команд.

### Миграция существующей установки

Миграция выполняется отдельно на каждой машине. Она не создаёт коммиты из незакоммиченных файлов, не отправляет `main`, не удаляет ветки и не применяет rebase, reset или force push.

1. Аналитик открывает корень `coda-analyst-harness`, выполняет `git pull --ff-only` либо просит LLM обновить только корневую обвязку этой командой.
2. Аналитик начинает новый диалог с LLM в корне или в `documents`. Можно написать `включи совместную работу`, но отдельная команда не обязательна: любая команда начала работы над функциональностью запускает миграцию автоматически.
3. LLM запускает `workspace.py bootstrap`. Обновляются местные инструкции, описание ролей и точка входа; проектные файлы не коммитятся.
4. LLM запускает `collaboration.py status` и проверяет текущую ветку, незакоммиченные пути и наличие `MERGE_HEAD`.
5. Если уже выполняется слияние, миграция останавливается без отмены. LLM сохраняет защитный снимок через штатную диагностику, показывает один конфликтующий путь и спрашивает решение. Только после осознанного завершения текущего слияния миграция начинается заново.
6. LLM спрашивает один раз короткий идентификатор аналитика, например `ivanov`. Допустимы строчные латинские буквы, цифры и дефисы. Идентификатор сохраняется только локально и используется в именах веток.
7. LLM выполняет `collaboration.py migrate --analyst <id>`.
8. Если `documents/main` чиста и совпадает с `origin/main`, режим включается без изменения проектного дерева.
9. Если чистая местная `main` только отстаёт, обвязка быстро обновляет её с защитным снимком. Старый коммит остаётся достижимым через снимок.
10. Если найдены незакоммиченные файлы, локальные неопубликованные коммиты, расхождение с `origin/main` или работа в другой ветке, команда возвращает `feature-required` и ничего не переносит.
11. LLM спрашивает, к какой одной функциональности относится найденная локальная работа. Она не угадывает функциональность, если состав файлов допускает несколько трактовок.
12. После ответа LLM повторяет миграцию с `--feature <feature>`. Обвязка создаёт `feature/<feature>/<analyst>` на текущем локальном коммите и переключается в неё. Все незакоммиченные файлы остаются с теми же байтами и статусом; автоматического коммита и отправки нет. Старая местная `main` не переписывается.
13. LLM показывает аналитику найденные пути. По подтверждённой команде сохранения она проверяет их, фиксирует точным списком и отправляет только рабочую ветку.
14. LLM выполняет обновление рабочей ветки. Актуальная `origin/main` объединяется уже с защищённой веткой функциональности, а не непосредственно с общей `main`.
15. При конфликте обвязка возвращает чистое рабочее дерево на локальном коммите, сохраняет базовую, локальную и входящую версии файлов и ожидает последовательных решений аналитика.
16. После проверок рабочая ветка отправляется на слияние и принимается человеком в `documents/main`.
17. LLM выполняет `collaboration.py finish`. Команда сначала доказывает, что рабочий коммит является предком `origin/main`, затем переключается на `main` и быстро обновляет её с новым защитным снимком.
18. LLM повторно запускает `collaboration.py status`. Ожидаемое состояние: текущая ветка `main`, `active_work = null`, незакоммиченных путей нет.

Если в одном незакоммиченном наборе смешаны изменения нескольких функциональностей, автоматическая миграция прекращается. Аналитик сначала определяет границы, после чего изменения переносятся отдельными осознанными коммитами. Обвязка не пытается разделить такой набор по именам каталогов.

## Синхронизация рабочей области

Штатно аналитик работает только в роли `analytics`, то есть в `documents`. По фразе `синкани репы` LLM сначала выполняет:

```bash
python3 scripts/workspace.py bootstrap
python3 scripts/workspace.py sync
```

Первый шаг обновляет местное описание ролей, точку входа, реестр кода и файл рабочей области редактора. Если в `analytics` есть понятные намеренные изменения, LLM до второго шага просматривает их, запускает относящиеся к ним проверки, индексирует только точные пути и создаёт смысловой коммит. Обвязка не создаёт такой коммит автоматически. При смысловой неоднозначности LLM задаёт аналитику один вопрос и ждёт решения; `git add -A` и `git add .` запрещены.

В настроенном многопользовательском режиме незакоммиченные изменения в `main` считаются незавершённой рабочей миграцией: LLM не фиксирует их непосредственно в `main`, а сначала сохраняет их в ветке функциональности по процессу миграции выше.

Сам полный обмен выполняется только при выбранной `analytics/main`. Если выбрана рабочая ветка `feature/<feature>/<analyst>` со статусом `awaiting-merge`, `workspace.py sync` сначала запускает штатный `finish`. Когда `origin/main` уже содержит отправленный коммит, обвязка автоматически обновляет местную `main`, закрывает рабочую сессию и продолжает тот же полный обмен. Если включение коммита не доказано либо работа ещё не отправлена, команда прекращается до обновления `code` и `source`. Это исключает случайное смешение обновления рабочей ветки и полного обмена, но не требует отдельной команды после уже принятого запроса на слияние.

Дальнейшее поведение определяется фактически доступными ролями.

**Все роли доступны.** Команда под межпроцессной блокировкой выполняет:

1. проверку чистоты, ветки, адреса получения и запрета отправки роли `code`;
2. защищённый `git pull --ff-only` текущей ветки роли `code` с отключёнными Git-перехватчиками;
3. обновление скрытого bare-зеркала роли `source`;
4. проверку рабочего дерева и получение `analytics/origin/main`;
5. создание местного защитного снимка обеих линий перед быстрым перемещением или слиянием, затем быстрое перемещение, если локальная ветка отстаёт, сохранение локальной ветки, если она впереди, либо обычный merge-коммит при бесконфликтном расхождении двух линий;
6. остановку с отменой только начатого обвязкой merge при конфликте между локальным и удалённым `analytics`; уже существующий незавершённый merge не отменяется и не перезапускается;
7. узкое безопасное сопоставление известного ошибочного Unicode-имени на macOS, только если содержимое файла совпадает с Git и входящий коммит удаляет старый путь;
8. проверку состава обоих аналитических деревьев до слияния: разрешены только корневые пути `.gitattributes`, `.github`, `.gitignore`, `LICENSE`, `README.md`, `assets/`, `baseline/`, `context/`, `features/`, `planning/`, `releases/`; непосредственно в `features/` разрешены только `README.md` и `.gitkeep`; содержимое `context/source-materials/` считается непрозрачным исходным материалом и не классифицируется по именам вложенных файлов;
9. блокировку локальных настроек инструментов и любого неподтверждённого удаления файла, унаследованного из `source`;
10. создание отдельного защитного снимка и локальное слияние `source/main` в `analytics/main`;
11. сохранение базовой, локальной и входящей версий каждого конфликтующего файла, затем остановку и полный откат незавершённого слияния при конфликте с `source`;
12. повторную проверку состава, Unicode NFC и отсутствия отслеживаемой встроенной обвязки после слияния;
13. создание местной игнорируемой точки входа `AGENTS.md` в роли `analytics`;
14. построение и проверку обратной заплаты от дерева `source` к дереву `analytics` во временном индексе Git;
15. доказательство совпадения итоговых идентификаторов деревьев и повторную проверку непосредственно перед отправкой;
16. проверку, что обе исходные линии являются предками каждого автоматически полученного результата;
17. отправку только `analytics/main`.

**Нет `source`.** Команда:

1. обновляет `code` защищённым `git pull --ff-only`, если роль доступна;
2. проверяет чистоту и ветку `analytics/main`;
3. безопасно объединяет её с `analytics/origin/main` по тем же правилам;
4. проверяет Unicode NFC, структуру, отсутствие местных настроек и встроенной обвязки;
5. обновляет местный `AGENTS.md`;
6. удаляет устаревший `reverse-diff-latest.patch`;
7. записывает `reverse-diff-latest.json` со значениями `status=unavailable`, `reason=source-role-absent`, `verified=false`;
8. отправляет только `analytics/main`.

Старые заплаты с временными метками сохраняются как история, но не считаются текущими. Обвязка не восстанавливает `source` и не заявляет о совпадении аналитических деревьев без новой проверки.

**Нет `code`.** Любой из двух режимов обмена продолжает работу, но обновление и исследование кода пропускаются. В реестре кода остаётся пустой список репозиториев, `coda-analyst.code-workspace` не содержит кодовый каталог, а местный `AGENTS.md` прямо сообщает, что код недоступен. Если одновременно нет `source`, выполняется только проверка, обновление и отправка `analytics`.

Поэтому при накопившихся независимых коммитах в `documents` и `changeswork-copy` порядок для аналитика остаётся коротким: обновить корневой `coda-analyst-harness` и сказать LLM `синкани репы`. Команда не переписывает историю и не копирует каталоги: обе линии объединяются обычным Git merge. Конфликт требует отдельного осознанного решения.

Если локальный `documents/main` и удалённый `origin/main` содержат разные коммиты, обвязка сохраняет обе линии. Бесконфликтное расхождение завершается служебным merge-коммитом автоматически. При конфликте команда отменяет только собственную пробу, оставляет реальный `documents` чистым и возвращает `analytics-origin-merge-conflict`. Для диагностики используется:

```bash
python3 scripts/workspace.py inspect-analytics-origin-conflict
```

Команда воспроизводит конфликт во временной копии и показывает базовую, локальную и удалённую версии каждого пути. LLM запрашивает решения аналитика по одному, после чего выполняет обычный merge `origin/main`, индексирует только точно разрешённые пути, запускает проверки, создаёт merge-коммит и повторяет синхронизацию. `reset`, rebase, force push и выбор одной истории целиком запрещены.

До изменения `analytics/main` обвязка создаёт защитный снимок локального и входящего коммитов. Если возникает конфликт, она до отмены своей попытки слияния отдельно сохраняет все три версии каждого конфликтующего файла: базовую, локальную и входящую. Поэтому ошибочный последующий выбор версии не делает исходный текст недоступным.

Снимки находятся только на машине аналитика:

```text
.workspace-state/analytics-snapshots/<id>/
├── snapshot.json
└── files/
    └── <номер-конфликта>/
        ├── base
        ├── local
        └── incoming
```

Дополнительно исходные коммиты удерживаются локальными ссылками Git `refs/coda-analyst-harness/analytics-snapshots/<id>/...`. Команда отправки указывает только `analytics/main`, поэтому эти ссылки не попадают в `documents`. Каталог `.workspace-state/` исключён из корневой обвязки и не мешает её обновлению.

Просмотр доступных снимков:

```bash
python3 scripts/workspace.py list-analytics-snapshots
python3 scripts/workspace.py inspect-analytics-snapshot --snapshot <id>
```

Точечное восстановление выбранной версии файла:

```bash
python3 scripts/workspace.py restore-analytics-snapshot-file \
  --snapshot <id> \
  --side local \
  --path features/<feature>/requirements.md
```

Вместо `local` можно явно выбрать `base` или `incoming`. Команда требует чистого рабочего дерева, принимает только один точный относительный путь, существовавший хотя бы в одной стороне снимка, ничего не индексирует и не создаёт коммит. Аналитик сначала проверяет получившееся изменение и отдельно решает, следует ли его фиксировать. Автоматический выбор стороны и автоматическое восстановление запрещены.

Если пользователь уже запустил `pull` или merge и репозиторий находится в конфликтном состоянии, синхронизация возвращает `analytics-origin-merge-in-progress`. Обвязка не отменяет такое слияние. Та же команда диагностики читает текущие стадии конфликта; после последовательного разрешения путей создаётся merge-коммит и повторяется `синкани репы`.

Успешное выполнение этой команды означает, что доступные репозитории обновлены, входящие изменения объединены с `analytics`, а результат `analytics` отправлен. Если сформирована непустая заплата, состояние остаётся `source_analytics_state=reverse-diff-pending`: на этой машине `source` не изменяется. Результаты `source_analytics_state=identical` и `repositories_identical=true` допустимы только когда полученное дерево `source` уже совпадает с деревом `analytics`. Применение заплаты на машине с рабочим `source` является отдельным этапом обмена.

Машинный результат дополнительно содержит `all_repositories_synchronized` и готовую строку `report_message`. LLM обязана начать ответ с этой строки дословно. Утверждать, что все репозитории синхронизированы, разрешено только при `all_repositories_synchronized=true`; успешное завершение местного этапа обмена не равнозначно полной синхронизации.

После конфликта безопасно просмотреть обе стороны без изменения реальных репозиториев:

```bash
python3 scripts/workspace.py inspect-source-analytics-conflict
```

Команда воспроизводит слияние во временной копии, перечисляет конфликтующие пути и различает двустороннее изменение, удаление в `source` и удаление в `analytics`. Если `source` удаляет изменённый путь старой встроенной обвязки (`.workflow/`, `.vscode/` или корневой `AGENTS.md`), отчёт рекомендует принять удаление: такой путь запрещён в репозитории роли `analytics`. Для содержательных проектных файлов LLM последовательно запрашивает решение аналитика и ничего не выбирает самостоятельно.

Обратная заплата и сведения проверки сохраняются в местном каталоге `reverse-diffs/`. Каталог целиком исключён из Git: он не попадает в коммиты корневой обвязки, не мешает `git pull --ff-only` и не удаляется при обычном обновлении репозитория.

Каждое формирование создаёт неизменяемую пару с одним идентификатором и сохраняет её независимо от следующих запусков. Файлы `reverse-diff-latest.*` являются только удобными копиями последнего результата и могут заменяться:

```text
reverse-diffs/
├── reverse-diff-latest.patch
├── reverse-diff-latest.json
├── reverse-diff-<идентификатор>.patch
└── reverse-diff-<идентификатор>.json
```

Только построить заплату без обновления и отправки:

```bash
python3 scripts/repository-exchange.py reverse-diff
```

Показать состояние всей рабочей области, в том числе сокращённое:

```bash
python3 scripts/workspace.py status
```

Команда `python3 scripts/repository-exchange.py status` показывает детальное сравнение двух аналитических деревьев только при наличии `source`.

Файл сведений использует схему 2. До записи транспортной пары программа выполняет `git diff --check` между точными исходным и целевым коммитами. Завершающие пробелы и другие ошибки оформления заплаты блокируют формирование: их исправляют в `analytics`, а уже созданную транспортную пару не редактируют. Поле `verified=true` допустимо только вместе с `diff_check_verified=true`, `tree_verified=true` и `content_policy_verified=true`; дополнительно квитанция содержит `artifact_id`, контрольную сумму `patch_sha256`, исходную и целевую ветки, коммиты и деревья, `changed_path_count`, полный `changed_paths`, `included_analytics_commits`, `included_features` и `approved_source_deletions`. Список коммитов и функциональностей сохраняет происхождение агрегированной заплаты, хотя на принимающей стороне она фиксируется одним интеграционным коммитом. Эта проверка подтверждает техническую корректность и допустимый состав дерева, но не означает утверждение черновых требований. Без `source` поля проверки имеют значение `false` и не подменяются старыми данными: создаётся отдельная квитанция со статусом недоступности, а ранее созданные пары с идентификаторами сохраняются.

До применения заплаты коммиты и деревья репозиториев могут различаться. Критерий корректности обмена: применение проверенной заплаты к указанному коммиту `changeswork-copy` создаёт дерево, полностью совпадающее с указанным деревом `documents`.

### Передача и подтверждение применения

Для передачи используется именно неизменяемая пара с идентификатором, а не файлы `latest`: `reverse-diff-<artifact-id>.json` и `reverse-diff-<artifact-id>.patch`. Способ доставки между машинами не является частью Git-обмена; файлы можно передать разрешённым рабочим каналом. Корневой репозиторий обвязки на машине аналитика остаётся только для чтения, поэтому пара не коммитится в него и не используется как средство синхронизации самой обвязки.

На машине, где `changeswork-copy` является рабочим репозиторием, принимающая аналитическая обвязка:

1. находит пару в своём местном каталоге входящих файлов или в `~/Downloads`;
2. проверяет схему, SHA-256, исходные коммит и дерево, полный состав путей и воспроизводимость целевого дерева;
3. выполняет защищённый `git pull --ff-only` и блокирует применение, если `source/main` уже ушла вперёд;
4. создаёт один интеграционный коммит с деревом `analytics_tree` и отправляет его в `origin/main`;
5. сохраняет местную квитанцию применения с итоговым коммитом и деревом.

Следующая команда `синкани репы` на машине с `coda-analyst-harness` получает этот коммит через fetch роли `source`. Если после объединения новых изменений нет, отчёт подтверждает `source_analytics_state=identical`, `repositories_identical=true` и `all_repositories_synchronized=true`. Только этот результат завершает полный круг обмена. Если за время передачи в `documents` появились новые изменения, будет сформирована следующая заплата; это не отменяет квитанцию применения предыдущей пары.

Одна агрегированная заплата создаёт один коммит в рабочем `changeswork-copy`. Происхождение не теряется: `included_analytics_commits` перечисляет вошедшие коммиты `documents`, а `included_features` — затронутые функциональности.

### Блокировка недопустимого содержимого

При причине `analytics-content-policy` обвязка не создаёт заплату и не отправляет `documents`. LLM обязана показать точные пути. Локальные настройки и файлы вне структуры удаляются только точечными командами; `git add -A` и `git add .` запрещены.

Если отчёт содержит `unapproved_source_deletions`, для каждого пути аналитик выбирает одно из двух действий: восстановить файл из `analyst-source-local/main` либо подтвердить намеренное удаление. Подтверждение выполняется только после явного решения аналитика:

```bash
python3 scripts/repository-exchange.py approve-deletion --path <точный-путь>
```

Подтверждение хранится только в `.workspace-state/`, связано с содержимым файла в текущем `source` и перестаёт действовать при его изменении. Команду запрещено использовать как способ обойти проверку.

## Проверки

Основная проверка проектного репозитория запускается из корня обвязки:

```bash
PROJECT_ROOT="$(python3 scripts/workspace.py project-root)"
python3 scripts/harnessctl.py doctor "$PROJECT_ROOT"
```

Отдельные проверки:

```bash
python3 scripts/validate-structure.py "$PROJECT_ROOT"
python3 scripts/validate-links.py "$PROJECT_ROOT"
python3 scripts/validate-context.py "$PROJECT_ROOT"
python3 scripts/validate-language.py "$PROJECT_ROOT" --all
python3 scripts/validate-requirements-profile.py "$PROJECT_ROOT"
python3 scripts/validate-requirements-wording.py "$PROJECT_ROOT"
python3 scripts/validate-planning.py "$PROJECT_ROOT"
python3 scripts/validate-trace.py "$PROJECT_ROOT" --strict
python3 scripts/evaluate-harness.py "$PROJECT_ROOT"
```

Проверка структуры отвергает встроенные `.workflow`, `.vscode` и отслеживаемую копию корневого `AGENTS.md`, но разрешает созданную программой местную игнорируемую точку входа.

Проверки самой обвязки:

```bash
python3 -m compileall -q scripts tests
python3 -m unittest discover -s tests -v
git diff --check
```

## Архивы

ZIP не является состоянием передачи и запрещён в `coda-analyst-harness`, `documents`, `changeswork-copy` и `requirements-exchange/`. Транспортный ZIP создаётся только по прямому требованию пользователя и только в `~/Downloads`. Обычная передача выполняется через каталог обмена.

## Версия

Версия обвязки находится в `VERSION`. Проектные репозитории не содержат копию версии и не обновляются путём установки служебных файлов: новая версия начинает действовать после обновления корневого `coda-analyst-harness`.
