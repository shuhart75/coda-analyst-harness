# coda-analyst-harness

`coda-analyst-harness` - распространяемая рабочая обвязка аналитика АС КОДА. Она разворачивает три независимых репозитория, связывает аналитическую работу с чтением кода и предоставляет контролируемый обмен изменениями между внешним источником аналитических материалов и корпоративным репозиторием.

Репозиторий рассчитан на терминальные инструменты на базе языковых моделей и обычную ручную работу в проекте. Служебные правила и контракт агента живут в `AGENTS.md` и `.workflow/*`, а сам `README.md` нужен как понятная точка входа для человека.

## Первый запуск

Клонируйте этот репозиторий в каталог, который станет рабочей областью, и откройте его корень в LLM-инструменте:

```bash
git clone <url-coda-analyst-harness> coda-analyst-harness
cd coda-analyst-harness
```

При первом запуске LLM читает `AGENTS.md` и автоматически выполняет:

```bash
python3 scripts/workspace.py bootstrap
```

Команда идемпотентно клонирует отсутствующие репозитории по заранее заданным адресам:

| Каталог | Адрес | Назначение и доступ |
|---|---|---|
| `documents/` | `ssh://git@stash.delta.sbrf.ru:7999/rscon/documents.git` | основная работа аналитика, получение и отправка изменений |
| `coda/` | `ssh://git@stash.delta.sbrf.ru:7999/rscon/coda.git` | точечное исследование кода, без отправки изменений |
| `changeswork-copy/` | `https://github.com/shuhart75/changeswork-copy.git` | получение внешних аналитических изменений, без отправки |

После подготовки создаётся следующая структура:

```text
coda-analyst-harness/
├── AGENTS.md
├── coda-analyst.code-workspace
├── documents/
├── coda/
├── changeswork-copy/
├── reverse-diffs/                 # локальные проверенные обратные заплаты
└── .workspace-state/              # локальное состояние и блокировка операций
```

Каталоги репозиториев, обратных заплат и локального состояния исключены из Git самого `coda-analyst-harness`. Для `coda` и `changeswork-copy` на уровне локальной настройки Git устанавливается запрещающий адрес отправки. Проверить готовность можно командой:

```bash
python3 scripts/workspace.py status
```

Штатная работа с требованиями, планами, пакетами и фактическим выполнением ведётся в `documents/`. Код читается в `coda/` по правилам ограниченного исследования. `changeswork-copy/` вручную не редактируется.

## Обмен аналитическими репозиториями

Каноническое направление получения изменений:

```text
origin changeswork-copy/main
        ↓ fast-forward
локальный changeswork-copy/main
        ↓ обычное Git-слияние
локальный documents/main
        ↓ push
origin documents/main
```

После слияния строится обратная заплата:

```text
дерево changeswork-copy@<commit>
        ↓ reverse-diff-*.patch
дерево documents@<commit>
```

Обвязка проверяет заплату во временном индексе Git: результат её применения обязан иметь тот же идентификатор дерева, что и `documents`. Только после этого заплата считается пригодной для передачи владельцам `changeswork-copy`.

### Короткие команды

| Команда пользователя | Действие LLM |
|---|---|
| `синкани репы` | обновить обе локальные копии, влить `changeswork-copy` в `documents`, проверить обратную заплату и отправить только `documents` |
| `синкани без отправки` | выполнить тот же процесс без `push` |
| `сделай обратный дифф` | сравнить текущие чистые коммиты и сформировать проверенную заплату без обновления и слияния |
| `покажи состояние репозиториев` | показать ветки, коммиты и чистоту `documents` и `changeswork-copy` |
| `обнови код` | отдельно обновить чистый `coda` только fast-forward |

Прямые служебные вызовы:

```bash
python3 scripts/repository-exchange.py sync
python3 scripts/repository-exchange.py sync --no-push
python3 scripts/repository-exchange.py reverse-diff
python3 scripts/repository-exchange.py status
python3 scripts/workspace.py update-code
```

Операция останавливается при незакоммиченных изменениях, неподходящей ветке, невозможности fast-forward, конфликте слияния, неприменимой заплате или ошибке отправки. Ошибки не подавляются. Копирование файлов между репозиториями, автоматический выбор стороны конфликта и принудительная отправка запрещены. Подробный договор находится в `core/repository-exchange.md`.

## Как и что здесь устроено

- правила процесса хранятся в репозитории;
- сердцем проекта является доменная модель в логике DDD;
- каноническое текущее состояние в `baseline/current/` отделено от запланированных изменений;
- работа делится на режимы: планирование, требования, прототипирование, исполнение и финализация релиза;
- артефакты группируются по функциональности; срезы остаются аналитической и тестовой единицей, а техническую декомпозицию определяют разработчики внутри общего пакета функциональности;
- прототипы делаются как одиночный `prototype.html` без сборки;
- все ключевые действия описываются короткими командами на русском.

## Сквозной процесс

Обвязка разделяет продуктовое знание, планирование и код, но связывает их проверяемыми пакетами работ. Требования не обязаны лежать в одном репозитории с кодом. Базовая модель такая:

- в репозитории продуктового знания хранится источник истины: текущее состояние, планы, требования, срезы, пакеты передачи и фактическое выполнение;
- кодовый репозиторий `coda` подключается как независимый соседний клон через `.workflow/code-repos.json`; аналитическая LLM исследует его точечно и только для чтения;
- разработке передаётся не копия всего знания, а автономная редакция пакета одной функциональности с требованиями, срезами и контрольными суммами;
- разработчик и языковая модель сверяют этот пакет с реальным кодом, тестами и архитектурой;
- если код показывает уже реализованное, частично реализованное или отличающееся поведение, принимающая обвязка фиксирует это по каждому требованию, продолжает работу с оставшейся дельтой и возвращает сведения аналитику;
- после подтверждения декомпозиция фоново возвращается аналитику, а результаты реализации и тестирования поступают независимыми квитанциями;
- по обработанным квитанциям факт попадает в диаграмму фактического выполнения, релизный пакет и затем в `baseline/current/`.

### Принципы асинхронного взаимодействия с разработкой

Коммиты и разработка не являются перепиской аналитической и разработческой обвязок. Согласования между людьми проходят в обычном рабочем порядке, в том числе устно, и не оформляются обязательными остановками машинного процесса.

Контур строится на следующих принципах:

1. Аналитик передаёт однозначную, самодостаточную и неизменяемую редакцию требований по функциональности вместе со срезами. Пакет фиксирует требуемый результат, границы, зависимости и проверки, но не диктует внутреннее устройство кода без необходимости.
2. Разработчики с помощью SDD исследуют актуальный код и локальные спецификации нужных контуров, затем определяют окончательную разбивку будущих задач Jira. Оценка и ключ Jira необязательны.
3. Подтверждение декомпозиции создаёт неизменяемый снимок и сразу делает его доступным аналитику. Ответ аналитика не является условием начала разработки.
4. SDD выполняет доступный объём каждой подтверждённой карточки. Неясность или отсутствующая зависимость одного пункта не останавливает независимую работу.
5. По каждой карточке SDD возвращает квитанцию реализации: что существовало до работы, что поставлено, что сделано иначе, что осталось, какие дополнительные результаты появились, какие коммиты и проверки выполнены.
6. Тестировщик работает по срезу из той же входной редакции. Карточки и квитанции реализации служат контекстом, а результат тестирования сохраняется отдельной квитанцией среза.
7. Квитанции не меняют требования автоматически. Аналитическая сторона решает, что изменить в требованиях, что после поставки перенести в `baseline/current/`, а что оставить, отложить, перенести в другую доработку или отменить.
8. Утверждённый квартальный план не переписывается под фактический результат. Изменившийся состав поставки отражается в фактическом выполнении и используется в последующей калибровке планирования.

Таким образом, входная редакция отвечает на вопрос «что требовалось на момент передачи», снимок декомпозиции - «как разработчики разделили работу», квитанции - «что фактически реализовано и проверено», а аналитическая обработка - «как продуктовый контур принимает и распределяет результат».

### Рабочая область аналитика с кодом

Репозитории `documents` и `coda` разворачиваются автоматически внутри корня обвязки. Путь к коду определяется из `documents/.workflow/code-repos.json`: сначала может использоваться `CODA_REPO`, затем стандартный относительный путь `../coda`.

Во время исследования `coda` обвязка не выполняет `fetch`, `pull` или переключение ветки автоматически. Обновление кода является отдельной командой. Исследование всегда сообщает фактически проверенные ветку и коммит. При необходимости проект может закрепить `expected_branch` в `.workflow/code-repos.json`.

По командам `сходи в код`, `посмотри в коде`, `проверь по коду` модель фиксирует ветку и коммит, выбирает один контур, читает его локальные инструкции, находит ограниченный набор файлов и после чтения проверяет неизменность `coda`. Этот же проход запускается автоматически, когда без фактического API, данных, статусов, ролей или существующего поведения нельзя корректно сформулировать требования. Обновление `coda` выполняется только отдельной явной командой `обнови код`.

Если код влияет на требования, краткие доказательства сохраняются в `features/<feature>/.research/code-evidence.yaml` с коммитом, относительными путями и символами. Код не становится источником бизнес-решений, а разработческая SDD повторяет сверку на своей актуальной ветке перед реализацией.

### Хранение и актуальность пакетов

Пакеты хранятся рядом с функциональностью и доступны обеим сторонам по одному пути:

```text
features/<feature>/handoffs/<package-id>/
├── README.md
├── handoff.json
├── .control/
│   ├── handoffctl.py
│   └── validate-handoff.py
└── revisions/
    ├── 001/
    │   ├── package/
    │   │   ├── request.md
    │   │   ├── manifest.json
    │   │   ├── requirements.md
    │   │   └── slices/
    │   └── returns/
    │       ├── development-tasks/
    │       ├── decomposition-snapshots/
    │       ├── implementation-results/
    │       └── test-results/
```

`package-id` обозначает общий поток поставки функциональности и обычно совпадает с её устойчивым коротким идентификатором либо строится как `<feature>-delivery`. Номер входной редакции в него не включается. `handoff.json` хранит состояния всех редакций и единственную команду `next_sdd_action`. SDD всегда сначала читает этот файл и не определяет актуальность по имени каталога, дате или наличию архива. Самодостаточные команды в `.control/` позволяют принять редакцию, подтвердить декомпозицию, подготовить и зарегистрировать квитанции, имея только ссылку на общий каталог и доступ к `coda`.

Каталог `revisions/NNN/package/` после отправки неизменяем. Служебная команда `.workflow/tools/handoffctl.py publish` проверяет редакцию, фиксирует контрольные суммы входных файлов и сразу разрешает SDD обработку. ZIP запрещено хранить внутри репозитория. Только по явному требованию команда `handoffctl transport` создаёт транспортную копию в `~/Downloads`; она не входит в состояние пакета и не нужна SDD для штатной работы. Рабочая декомпозиция хранится в `returns/development-tasks/`, её подтверждённые снимки - в `returns/decomposition-snapshots/`, квитанции реализации - в `returns/implementation-results/`, результаты тестирования - в `returns/test-results/`.

Явная команда аналитика `собери транспортный ZIP редакции <NNN>` соответствует служебному вызову `handoffctl transport <root> <NNN>`. Без такой команды архив не создаётся.

Если требования изменились до начала работы, прежняя редакция переводится в `paused`, `superseded` или `cancelled`, ожидание квитанции снимается, а новой редакции выдаётся `next_sdd_action.action = process`. Если SDD уже начала работу, переключение выполняется явно с фиксацией причины. Приостановленную редакцию можно возобновить командой `handoffctl resume`: невзятая редакция снова получает `process`, а уже взятая - `continue` с сохранением исполнителя.

### 1. Текущее состояние системы

`baseline/current/` описывает уже реализованную систему:

- доменную модель и словарь;
- текущие бизнес-правила;
- текущие API, данные и интерфейсы;
- принятые решения и ограничения.

Это не план будущих работ. Если новая функциональность ещё не поставлена, она не попадает в `baseline/current/`. После финализации релиза подтверждённое изменение переносится в текущее состояние.

### 2. Планирование

`planning/` хранит входящие заметки, квартальные планы, командирские планы, приоритеты, состав команды, закрытые интервалы и план-факт. Функциональность планируется как законченный пользовательский или системный результат. На неё создаются ролевые плановые истории: AN, BE, FE и QA, если соответствующая роль действительно участвует.

Утверждённые квартальный и командирский планы не меняются. Новая обнаруженная работа после утверждения появляется на диаграмме фактического выполнения как черновик задачи или фактическая задача, чтобы в конце квартала можно было честно сравнить оценку с реальным выполнением.

### 3. Требования и дельта

`features/<feature>/requirements.md` является главным документом требований по функциональности. В нём описывается изменение относительно `baseline/current/`, включая:

- пользовательский и системный результат;
- бизнес-правила;
- изменения данных, API и интерфейсов;
- доработки затронутых соседних функциональностей;
- критерии приёмки и проверки.

Новые корневые документы создаются по профилю АС КОДА, основанному на ISO/IEC/IEEE 29148:2018. Профиль использует критерии атомарности, однозначности, проверяемости и трассировки, но не воспроизводит служебную структуру стандарта целиком и не заявляет полного соответствия. Облегчённый и подробный форматы имеют одно обязательное смысловое ядро. Существующие документы переводятся только при существенной переработке или по явному решению пользователя.

Срезы в `features/<feature>/slices/<slice>/` являются производной аналитической декомпозицией. Они помогают проверить целостные пользовательские сценарии, прототипы и покрытие и остаются основной единицей тестирования.

Аналитик не утверждает техническую нарезку заранее. Окончательные карточки будущих задач Jira создаются разработчиками в `returns/development-tasks/` после сверки требований с реальным кодом и локальными SDD серверного и клиентского контуров.

### 4. Передача в разработку

Для разработки создаётся общий пакет функциональности:

- корневой `README.md` — краткая памятка разработчику;
- корневой `AGENTS.md` — формальный обязательный договор для принимающей SDD;
- корневой `handoff.json` — состояние редакций, следующее действие и явная ссылка на `AGENTS.md`;
- `package/request.md` - краткий паспорт в форме «Цель / Ограничения / Контекст / Примеры / Критерии приёмки»;
- `package/manifest.json` - состав редакции, способ трассировки, идентификаторы требований, сценариев и влияний, срезы и контрольные суммы;
- `package/requirements.md` - полный документ требований;
- `package/slices/*/slice.md` и `package/slices/*/requirements/*.md` - карточки срезов и подробные требования контуров для декомпозиции и тестирования;
- `returns/` - единая область возврата разработчиков и тестировщиков.

SDD исследует только нужный контур кода и формирует самодостаточные карточки `DEV-BE-*` и `DEV-FE-*`. Карточка описывает одну будущую задачу Jira и один законченный технический результат. Целевой размер - 1-3 рабочих дня одного исполнителя; максимум 5 дней для серверной и 10 дней для клиентской задачи. Превышение требует обоснования. Оценка и ключ Jira необязательны.

Подтверждённый снимок декомпозиции неизменяем. Если состав задач изменился, создаётся следующая редакция снимка, а предыдущая остаётся в истории. Подтверждение автоматически передаёт сведения аналитику, но не блокирует реализацию.

Квитанция реализации отдельно фиксирует исходную и итоговую ревизии кода, коммиты, проверки и результат каждого требования и сценария карточки. Уже реализованное или иначе реализованное поведение не считается сбоем всего пакета. Квитанция тестирования отдельно фиксирует результат среза и может ссылаться на несколько карточек и квитанций реализации. Полный договор закреплён в `.workflow/developer-handoff.md`.

Новый ISO-подобный документ использует атомарные `REQ-*` и `SCN-*`. Для прежних документов генератор применяет только явную совместимость `traceability.mode = legacy-sections`: единицей результата становится раздел с устойчивым идентификатором и ссылкой `Карточка среза`. Обвязка не придумывает отсутствующие идентификаторы, а манифест прямо предупреждает SDD и тестировщика о более грубой секционной трассировке. Валидатор заново извлекает состав из фактических файлов и не позволяет удалить идентификатор из манифеста при сохранённых требованиях.

### Что всегда видит разработчик

В `returns/development-tasks/index.md` постоянно находятся порядок работы, список предлагаемых и подтверждённых будущих задач Jira, проверка покрытия и основные короткие команды. Каждая `DEV-BE-*` или `DEV-FE-*` карточка содержит полный предметный объём и неизменяемый блок команд для уточнения, переименования, переноса, объединения, разделения, изменения зависимостей, отмены, подтверждения, связи с Jira и начала реализации.

SDD обязана создавать карточки по вложенному шаблону и сохранять этот блок при каждой правке. Подтверждение невозможно, если отсутствует обязательный раздел, остаётся незаполненная заглушка, потерян назначенный идентификатор, карточка исчезла из индекса или сокращена инструкция разработчика.

### Как SDD ограничивает контекст

Принимающая SDD не читает весь кодовый репозиторий. Обязательная последовательность:

1. формальный договор по `handoff.json.agent_contract.path`;
2. `handoff.json` и единственное `next_sdd_action`;
3. компактные `request.md`, `manifest.json` и инструкция активной редакции;
4. один выбранный контур и только связанные с ним разделы требований, срезы и подробные требования;
5. локальная SDD выбранного контура в `coda`;
6. поиск точных сущностей, полей, маршрутов и символов;
7. только найденные модули и соседние проверки.

Второй контур открывается только по обнаруженной зависимости. Пути исходного аналитического репозитория и абсолютные пути машины аналитика внутри полного документа являются сведениями о происхождении материала и не должны открываться на машине разработчика.

Заготовка квитанции реализации создаётся автоматически из подтверждённой карточки и уже содержит точные идентификаторы, номер снимка декомпозиции и необязательный ключ Jira. Заготовка тестовой квитанции создаётся по срезу и содержит номер того же снимка, точные требования и сценарии, связанные карточки и зарегистрированные квитанции реализации. SDD и тестировщик заполняют фактический результат, но не собирают служебную структуру вручную.

### Команда передачи аналитика

Каноническая команда: `сформируй пакет для разработки`. Также распознаются `передаём в разработку`, `передаем в разработку`, `отдаём требования разработчикам`, `отдаем требования разработчикам`, `подготовь требования для разработки`, `собери пакет для разработчиков` и прежняя длинная формулировка про пакет технической декомпозиции.

Команда запускает не только сборку. LLM проверяет полноту, однозначность, непротиворечивость и проверяемость корневых требований, соответствие относящемуся к функциональности текущему состоянию, границы, данные, состояния, ошибки, отрицательные случаи, влияния, срезы, подробные требования контуров, трассировку, устаревшие остатки и русский язык. Однозначные исправления без изменения смысла вносятся автоматически.

Если требуется предметное решение, LLM ничего не предполагает и задаёт аналитику ровно один вопрос. После ответа исправляется соответствующий участок, повторяется проверка и при необходимости задаётся следующий вопрос. Пока остаётся хотя бы одна содержательная неопределённость или блокирующая ошибка, пакет не создаётся.

После успешного прохода обвязка создаёт следующую неизменяемую редакцию, проверяет её и сразу публикует в состоянии `sent` с `next_sdd_action.action = process`. Транспортный ZIP при этом не создаётся. Аналитик проверяет требования, а не внутреннее устройство пакета, поэтому состояния `ready` и отдельного ручного шага отправки в пользовательском процессе нет.

При существенной правке уже переданных требований аналитическая сторона не переписывает карточки разработчиков. Она формирует новую входную редакцию пакета, а состояние прежней редакции явно меняет в `handoff.json`.

После получения квитанции аналитическая сторона создаёт отдельный разбор. Только по результатам этого разбора новое правило, ограничение или расхождение переносится в корневые требования, релиз, `baseline/current/` и производные файлы. Исходный пакет и квитанция разработчика задним числом не редактируются.

### 5. Работа с кодом

Идеальная интеграция с кодом строится без дублирования требований:

- репозиторий продуктового знания остаётся главным источником требований;
- кодовый репозиторий использует собственные SDD серверного и клиентского контуров; аналитическая обвязка не копируется в `coda`;
- передаваемый пакет имеет автономный идентификатор, версию и контрольные суммы собственных файлов; связь с исходными путями и ревизией требований хранится внутри аналитического контура;
- языковая модель начинает с `handoff.json`, читает только активную редакцию, затем открывает относящиеся к ней локальные спецификации и код нужного контура;
- если реальный код или уместная реализация отличаются от ожиданий пакета, обвязка описывает фактический результат и его влияние в квитанции;
- однозначные независимые пункты продолжаются, а неоднозначный или зависимый остаток не скрывается и возвращается как невыполненный;
- после приёма квитанции аналитическая сторона отдельно решает, как синхронизировать текущее состояние, требования и производные материалы.

Практически это может выглядеть так:

```text
repo-product-knowledge/
  baseline/current/
  planning/
  features/<feature>/
    requirements.md
    slices/
    handoffs/<package-id>/            # общий каталог для аналитика и SDD

repo-code/
  src/
  tests/
```

Разработчику передаётся ссылка на `features/<feature>/handoffs/<package-id>/`. Для обработки нужны этот общий каталог и целевой кодовый репозиторий; остальное содержимое аналитического репозитория SDD читать не обязана. Если требования и код когда-либо окажутся в одном монорепозитории, договор редакций и квитанций сохраняется, но физическое копирование пакета не требуется.

### 6. Реализация, проверки и возврат факта

Цикл имеет один входной пакет, но несколько независимых результатов:

1. SDD принимает неизменяемую редакцию и фиксирует ревизии исследованного кода.
2. Разработчики подтверждают декомпозицию; снимок сразу становится доступен аналитику.
3. Каждая подтверждённая карточка отдельно сверяется с кодом, реализуется и получает квитанцию фактического результата.
4. Тестировщик проверяет срез и возвращает отдельную квитанцию, не меняя состояния карточек.
5. Аналитик обрабатывает снимок декомпозиции для фактического планирования и квитанции для требований, релиза и текущего состояния.
6. Невыполненный объём оставляется, откладывается, переносится или отменяется явным аналитическим решением.

## Кто чем занимается

### Аналитик

- разбирает входящие материалы;
- отделяет текущее поведение от новой дельты;
- выделяет функциональность и срезы;
- ведёт планирование, требования и презентационные прототипы;
- формирует и сопровождает редакции общего пакета;
- получает подтверждённую декомпозицию фоново и сам решает, что материализовать в фактическом плане.

### Разработчик

- исследует требования по реальному коду своего контура;
- определяет и подтверждает карточки будущих задач Jira;
- может указать оценку и ключ Jira, но их отсутствие не блокирует работу;
- реализует подтверждённые карточки и возвращает отдельные квитанции.

### Тестировщик

- готовит проверки по срезу;
- собирает негативные и граничные сценарии;
- сверяет проверки с требованиями;
- фиксирует пробелы и возвраты в требования.

### Служебные режимы

- `planning` - квартальное и командирское планирование;
- `requirements` - требования по фиче и срезам;
- `scope-prototype` - быстрый демонстрационный прототип для уточнения формы решения;
- `delivery-prototype` - точный прототип для передачи в разработку;
- `execution-update` - актуализация факта выполнения;
- `release-finalization` - финализация релиза и перенос результата в текущее состояние.

Утверждённые квартальный и командирский планы являются неизменяемым базовым состоянием планирования. Позднее обнаруженный объём работ отображается через черновики задач реализации и диаграмму фактического выполнения.

## Команды по ролям

Работать здесь удобнее через языковую модель: человек называет команду, а модель сама переключает режим и при необходимости запускает нужные скрипты.

### Аналитик

- `новая фича` - разобрать входные материалы и выделить дельту;
- `занимаемся планированием` - собрать оценки, риски и квартальный план;
- `делаем требования` - оформить требования по фиче;
- `сформируй пакет для разработки` - проверить и при необходимости уточнить требования, затем создать и сразу отправить новую редакцию со срезами;
- `делаем презентационный прототип` - собрать общий прототип для согласования;
- `создай прототип среза для фронта` - подготовить прототип передачи в разработку для конкретного среза.

### Разработчик

- `подготовь декомпозицию серверной части` - исследовать серверный контур и предложить `DEV-BE-*`;
- `подготовь декомпозицию клиентской части` - исследовать клиентский контур и предложить `DEV-FE-*`;
- `проверь декомпозицию` - проверить размеры, зависимости и покрытие;
- `декомпозиция подтверждена разработкой` - создать неизменяемый снимок для аналитика и сразу продолжить работу;
- `подготовь список для Jira` - показать подтверждённые карточки без обязательного изменения Jira;
- `возьми DEV-* в разработку` - реализовать одну подтверждённую карточку и вернуть квитанцию.

### Тестировщик

- `возьми срез <id> в тестирование` - проверить срез из активной редакции и вернуть квитанцию;
- `подготовь проверки по срезу` - собрать тестовый замысел;
- `собери негативные сценарии` - выделить отрицательные и граничные случаи;
- `сверь проверки с требованиями` - проверить покрытие;
- `проверь прототип по срезу` - оценить прототип;
- `проверь реализацию по срезу` - оценить готовую реализацию;
- `зафиксируй найденные пробелы` - вернуть расхождения в требования или план.

## Что лежит в репозитории

- `core/` - постоянные правила и концептуальная модель;
- `modes/` - правила каждого режима;
- `prompts/` - готовые текстовые заготовки под роли и режимы;
- `templates/` - шаблоны для планирования, требований, прототипов и исполнения;
- `scripts/` - скрипты создания структуры и проверки;
- `adapters/cli/` - shell-помощники для переключения режима и старта сессии;
- `adapters/vscodium/` - настройки, задачи и сниппеты для VSCodium;
- `examples/demo-project/` - пример раскладки готового проекта;
- `AGENTS.md` - служебный контракт корня рабочей области;
- `templates/workflow/project-agents.template.md` - отдельный контракт аналитического проекта, который устанавливается как его `AGENTS.md`.

### 1. Создайте новый проект

Рекомендуемый путь - использовать скрипт создания структуры:

```bash
bash scripts/scaffold-project.sh /path/to/project
```

Он создает структуру проекта и кладет в нее:

- `.workflow/llm-contract.md`;
- `.workflow/agent-delegation.md`;
- `.workflow/skills-policy.md`;
- `.workflow/tooling-policy.md`;
- `.workflow/context-policy.md`;
- `.workflow/research-policy.md`;
- `.workflow/active-mode.md`;
- `.workflow/modes/*.md`;
- `.workflow/overrides/`;
- `.workflow/command-catalog.md`;
- `.workflow/command-cheatsheet.md`;
- `.workflow/consistency-backlog.md`;
- `.workflow/team.md`;
- `.workflow/tools/`;
- `.workflow/run-state/`;
- `.workflow/templates/`;
- `baseline/current/`;
- `baseline/versions/`;
- `context/`;
- `features/`;
- `planning/intake/`;
- `releases/`;
- `AGENTS.md`.

Не используйте копию корня `coda-analyst-harness` как аналитический проект: корневой `AGENTS.md` управляет тремя репозиториями и намеренно отличается от проектного контракта. Проект создаётся только через `scaffold-project.sh`, а штатная рабочая область КОДА — через `python3 scripts/workspace.py bootstrap`.

### 2. Заполните команду

В новом проекте заполните `.workflow/team.md`:

- кто входит в команду;
- какая у каждого роль;
- какой lane ему назначен;
- какая у него capacity.

Если для проекта нужны собственные формулировки команд, поправьте:

- `.workflow/command-catalog.md`;
- `.workflow/command-cheatsheet.md`.

### 3. Сформируйте доменную модель

До разгона планов и срезов стоит зафиксировать предметную область:

- какие сущности существуют;
- какие у них границы и связи;
- какие бизнес-правила неизменны;
- какие состояния и переходы считаются каноническими;
- что уже находится в `baseline/current/`, а что является новым изменением.

В этой обвязке это центральная точка старта: сначала доменная модель, потом планирование и требования.

Каноническое текущее состояние доменной модели хранится в `baseline/current/domain/`:

- `baseline/current/domain/ubiquitous-language.md`;
- `baseline/current/domain/bounded-contexts.md`;
- `baseline/current/domain/aggregates.md`;
- `baseline/current/domain/business-rules.md`;
- `baseline/current/domain/state-machines/README.md`.

Когда появляется новое изменение, его сначала описывают в функциональности, а затем переносят в текущее состояние после релиза. Для формирования доменной модели удобно опираться на уже существующие требования и команду языковой модели, например:

- `делаем требования` - если нужно собрать или обновить требования по фиче на основе текущих материалов;
- `новая фича` - если сначала надо выделить дельту и только потом расписать доменную модель;
- `занимаемся планированием` - если нужно связать доменную модель с квартальным планом и рисками;
- `делаем требования` + `разложи требования на срезы` - если доменную модель уже надо разнести на проверяемые срезы.

Если пользователь уже знает путь к требованиям системы, можно просить языковую модель сформировать доменную модель прямо по ним:

- `Сформируй доменную модель по требованиям из /path/to/requirements`;
- `Возьми требования из /path/to/project/features/deployments/requirements и собери по ним доменную модель`;
- `Посмотри требования в /path/to/project/baseline/current/requirements и опиши по ним доменную модель текущей системы`;
- `По требованиям из /path/to/project/features/deployments/slices/form-editing/requirements собери доменную модель и перечисли, что должно попасть в baseline/current/domain/`.

### 4. Попросите языковую модель переключить режим

Например:

- `переведи проект в режим планирования`;
- `переведи проект в режим требований`;
- `подготовь старт сессии для проекта`.

Если нужно, языковая модель сама вызовет `switch-mode.sh` или `start-session.sh`.

### 5. Начните работу

Дальше можно просить языковую модель поднимать квартал, функциональности и срезы:

- `создай квартал 2026-Q2`;
- `создай фичу deployments`;
- `создай срез form-editing для фичи deployments`.

При необходимости языковая модель сама вызовет соответствующие скрипты создания структуры из корня `coda-analyst-harness`.

## Исполняемая обвязка

Внутренний командный интерфейс не заменяет ролевые команды, а делает правила проверяемыми:

```bash
python .workflow/tools/harnessctl.py doctor .
python .workflow/tools/harnessctl.py session-brief . --feature <feature> --slice <slice>
python .workflow/tools/harnessctl.py run-init . planning --feature <feature>
```

Черновые квартальный и командирский планы генерируются из ролевых историй:

```bash
python .workflow/tools/sync-planning-gantt.py . 2026-Q3
```

После перевода `planning/<quarter>/plan-state.md` в `approved` эти планы больше не пересобираются. Новая фактическая работа появляется на диаграмме фактического выполнения.

### Версия и управляемые файлы

Текущая версия обвязки хранится в `VERSION`. При создании структуры проекта создаётся `.workflow/harness.json`, где фиксируются:

- версия схемы;
- версия и Git-идентификатор обвязки;
- признак изменённого исходного репозитория;
- хеши установленных управляемых файлов;
- список путей, принадлежащих проекту.

Управляемые файлы включают контракты, режимы, внутренние навыки, шаблоны и инструменты. Они обновляются только через `harnessctl upgrade`. Файлы проекта принадлежат конкретному проекту и не перезаписываются обновлением:

- `.workflow/active-mode.md`;
- `.workflow/team.md`;
- `.workflow/code-repos.json`;
- `.workflow/evals/`;
- `.workflow/overrides/`;
- `.workflow/run-state/`;
- `.workflow/runs/`;
- `README.md` проекта.

Проверить различия перед обновлением:

```bash
python /path/to/coda-analyst-harness/scripts/harnessctl.py diff /path/to/project \
  --source /path/to/coda-analyst-harness
```

Выполнить обновление с защитой от конфликтов:

```bash
python /path/to/coda-analyst-harness/scripts/harnessctl.py upgrade /path/to/project \
  --source /path/to/coda-analyst-harness --apply
```

Если управляемый файл был изменён локально, команда обновления сообщает `CONFLICT` и ничего не перезаписывает. Проектное отличие нужно либо перенести в обвязку, либо оформить в `.workflow/overrides/`.

### Безопасное создание структуры

Команды создания структуры не перезаписывают существующие знания по умолчанию:

```bash
bash scripts/scaffold-project.sh /path/to/project
bash scripts/scaffold-project.sh /path/to/project --merge
bash scripts/scaffold-feature.sh /path/to/project feature-slug --merge
bash scripts/scaffold-slice.sh /path/to/project feature-slug slice-slug --merge
```

- обычный запуск требует пустой целевой каталог;
- `--merge` добавляет только отсутствующие файлы обвязки;
- `--force` является явной операцией перезаписи файлов создаваемой структуры;
- слияние с проектом не создаёт файлы-заглушки внутри существующих `baseline/`, `features/`, `planning/` и `context/`.

## Подробная модель планирования

### Функциональность и плановые истории

Функциональность является законченной пользовательской или системной ценностью квартала. Плановая история — не функциональный срез, а ролевой поток работ внутри функциональности.

На одну функциональность допускается максимум четыре плановые истории:

- `STORY-<FEATURE>-AN`;
- `STORY-<FEATURE>-BE`;
- `STORY-<FEATURE>-FE`;
- `STORY-<FEATURE>-QA`.

Если работа конкретной роли не нужна, соответствующая история отсутствует. Функциональная декомпозиция выполняется позднее в режиме требований через срезы.

### Оценка и длительность

Для каждой ролевой истории сохраняются:

- опорная оценка аналитика;
- оценка команды;
- явно согласованная оценка;
- допустимый параллелизм;
- коэффициент эффективности;
- зависимости;
- ограничение `not before`.

Итоговая оценка не вычисляется усреднением. Она считается принятой только после явного согласования.

Длительность рассчитывается так:

```text
ceil(agreed effort / effective parallel capacity)
```

Коэффициенты по умолчанию:

- `AN = 0.80`;
- `BE = 0.70`;
- `FE = 0.65`;
- `QA = 0.80`.

Коэффициент роли может быть переопределён в истории, а персональный коэффициент — в `.workflow/team.md`.

### Ресурсы и приоритет

- `gantt/order.txt` хранит приоритет фич сверху вниз;
- готовая работа более приоритетной фичи первой получает подходящие ресурсы;
- свободная роль может перейти к следующей фиче, пока в верхней фиче для неё нет готовой работы;
- нижняя фича не должна задерживать ставшую доступной работу верхней;
- автоматическое прерывание уже начатой работы не выполняется;
- загрузка ресурса не превышает 100%;
- отпуска и другие закрытые интервалы задаются в `.workflow/team.md`;
- плановая история может использовать несколько ресурсов до `max_parallelism`;
- фактическая задача всегда назначается одному человеку.

Стандартные зависимости: `AN -> BE`, `AN -> FE`, `BE + FE -> QA`. FE стартует не раньше трёх открытых рабочих дней после старта BE. Если BE отсутствует, FE стартует после AN либо в первое доступное окно.

### Квартальный и командирский планы

Квартальный план строится по согласованным оценкам без командирского резерва. Командирский план использует тот же объём работ, порядок и зависимости, но добавляет резерв риска:

- минимум 20%;
- 30% для высокого риска или внешней зависимости;
- 40% для нескольких высоких рисков, новой интеграции или неясной модели данных;
- 50% для критической неопределённости или неподтверждённой архитектуры;
- более 50% требует ручного решения.

Резерв влияет на длительности и даты командирского плана, но не показывается руководству отдельной полосой.

### Утверждение и неизменяемость

План имеет состояния `draft` и `approved`. Только владелец проекта утверждает план:

```bash
python .workflow/tools/harnessctl.py plan-approve . 2026-Q3 --by <owner>
```

При утверждении сохраняются хеши основных PlantUML-файлов, включаемых файлов функциональностей и базовых колонок карт фактического выполнения. После этого:

- квартальный и командирский планы не пересобираются;
- базовые даты начала и длительности в картах фактического выполнения не меняются;
- новый объём работ появляется как черновики задач реализации или фактические задачи;
- диаграмма фактического выполнения остаётся единственным изменяемым представлением реального положения дел;
- `validate-planning.py` обнаруживает любую правку утверждённого базового плана.

### Ретроспектива

После квартала:

```bash
python .workflow/tools/calibrate-planning.py . 2026-Q3
```

Инструмент сравнивает оценку роли с длительностью фактических задач и предлагает новые значения коэффициента эффективности и риска. Предложения применяются только к будущим черновым планам и никогда не переписывают историю.

## Требования, влияния и техническая декомпозиция

### Язык требований

Описательная часть требований пишется на русском языке. Английская форма допускается только там, где перевод нарушит точность:

- код и команды;
- пути к файлам;
- методы и поля API;
- таблицы и поля базы данных;
- значения перечислений и статусов протокола;
- закреплённые названия внешних систем;
- общепринятые технические сокращения вроде HTTP, JSON, SQL, API, FE, BE и QA.

В остальных случаях используются русские формулировки: «объём работ» вместо scope, «текущее состояние» вместо baseline, «срез» вместо slice, «передача в разработку» вместо handoff, «влияние» вместо impact.

Проверка изменённых требований:

```bash
python .workflow/tools/harnessctl.py language-check . --feature <feature>
python .workflow/tools/harnessctl.py requirements-check . --feature <feature>
```

Полный аудит всех требований выполняется только явно:

```bash
python .workflow/tools/harnessctl.py language-check . --all
```

Языковой контроль входит в обязательный второй проход вместе с поиском смысловых хвостов.

Корневые требования являются главным авторским источником. Карточки срезов, пакеты требований к клиентской и серверной части, входные редакции, техническая декомпозиция, планы реализации и тестовое покрытие являются производными.

После изменения требований выполняются два прохода:

1. Обновление корневых требований и всех непосредственно производных срезов.
2. Поиск устаревших маршрутов API, полей, статусов, ролей, терминов, прототипов и соседних правил.

Локальный необъяснённый хвост блокирует завершение. Работа на стыке режимов может быть отложена только конкретной записью в журнале несогласованностей.

Обязательные изменения соседних функциональностей включаются в объём работ инициирующей функциональности и раздел `Доработки затронутых функциональностей`. Каждая строка должна быть покрыта `REQ-*`, включена во входной пакет и связана с проверкой либо иметь явную пометку `неприменимо` с причиной.

После завершения требований аналитик формирует общий пакет функциональности. Разработчики определяют карточки будущих задач Jira по фактическим границам кода:

- одна карточка относится только к серверному или только к клиентскому контуру;
- один смыслово законченный и отдельно фиксируемый технический результат;
- полные ссылки и формулировки связанных `REQ-*`, `SCN-*` и `IMP-*`;
- зависимости и обязательные проверки;
- целевой размер 1-3 рабочих дня одного исполнителя;
- максимум 5 дней для серверной и 10 дней для клиентской задачи;
- оценка необязательна, но превышение максимума при указанной оценке требует обоснования;
- ключ Jira необязателен.

Подтверждённые карточки не меняются задним числом. Новое решение разработчиков создаёт следующий снимок декомпозиции. Передача снимка аналитику выполняется автоматически и не является согласованием начала разработки.

## Исполнительские циклы

Состояние каждого цикла хранится в `.workflow/runs/<run-id>/run.json`. Общая петля выполнения:

```text
сориентироваться -> спланировать -> выполнить ограниченное действие -> проверить
                 -> независимо пересмотреть -> зафиксировать контрольную точку -> продолжить/завершить/эскалировать
```

Создание циклов:

```bash
python .workflow/tools/harnessctl.py run-init . planning --feature <feature>
python .workflow/tools/harnessctl.py run-init . requirements --feature <feature>
python .workflow/tools/harnessctl.py run-init . implementation --feature <feature> --slice <slice> --role BE
python .workflow/tools/harnessctl.py run-init . qa --feature <feature> --slice <slice> --role QA
```

`implementation` и `qa` используют `.workflow/code-repos.json`. Цикл сохраняет хеши входных требований. Если они меняются во время работы, `run-verify` возвращает ошибку свежести и требует обновить рабочий пакет.

Проверка задаётся массивом аргументов без интерпретации командной оболочкой:

```json
{
  "name": "targeted tests",
  "argv": ["pytest", "tests/test_slice.py"],
  "cwd": "."
}
```

Запуск:

```bash
python .workflow/tools/harnessctl.py run-verify .workflow/runs/<run-id>/run.json
```

Повторяющаяся ошибка после заданного лимита переводит цикл в `escalated`.

## Диагностика и проверки

`harnessctl doctor` объединяет проверки структуры, процесса, ссылок, контекста, планирования и трассировки. `--strict` переводит предупреждения по контексту и трассировке в ошибки.

Синтетические проверки контролируют чистое создание проекта, несоответствие режима, защиту от разрушительного создания структуры и подмену утверждённого плана:

```bash
python scripts/evaluate-harness.py
```

Проектные эталонные сценарии живут в `.workflow/evals/golden-scenarios.json`:

```bash
python .workflow/tools/evaluate-harness.py .
```

Они предназначены для низкодрейфовых доменных инвариантов, а не для копирования полного набора требований в eval-конфигурацию.

## Типовой рабочий цикл

1. `новая фича` - разобрать исходные материалы и выделить дельту.
2. `занимаемся планированием` - подготовить оценки, риски и квартальный план.
3. `делаем требования` - оформить требования по фиче.
4. `делаем презентационный прототип` - собрать прототип для согласования.
5. `делаем прототип для разработки` - подготовить прототип передачи в разработку для среза.
6. `сформируй пакет для разработки` - проверить полноту, непротиворечивость, влияния, срезы, трассировку и язык; исправить однозначное, задать по одному все необходимые предметные вопросы и после успешной проверки сразу отправить неизменяемую редакцию.
7. Разработчики подтверждают декомпозицию и могут сразу начать реализацию карточек.
8. Аналитик фоново получает снимок и при необходимости отражает карточки в фактическом плане.
9. `возьми DEV-* в разработку` - реализовать карточку и вернуть квитанцию.
10. `возьми срез <id> в тестирование` - проверить срез и вернуть отдельную квитанцию.
11. Аналитик обрабатывает квитанции и затем выполняет `финализируем релиз`.

## Как читать структуру проекта

- `baseline/current/` - текущее каноническое состояние системы;
- `baseline/versions/` - предыдущие версии текущего состояния;
- `features/` - папки по отдельным функциональностям;
- `planning/` - квартальные планы и входящие заметки;
- `planning/intake/` - заметки предварительного разбора перед созданием структуры новой функциональности;
- `context/` - исходные материалы и описания текущей системы;
- `releases/` - неизменяемые релизные пакеты перед переносом в текущее состояние.

## Коротко о том, как не запутаться

- сначала создается или копируется проект;
- потом фиксируется команда и активный режим;
- затем функциональность проходит через планирование, требования, прототипы, исполнение и релиз;
- `baseline/current/` обновляется только после финализации релиза;
- в спорных случаях источником истины остается markdown в репозитории.
