# Создание задачи AN на принимающей стороне

По явному поручению аналитика допускается перенести авторские материалы в source без готового номера задачи. Это узкое исключение для транспортного коммита; оно не разрешает публикацию пакета разработки без реальной связи.

В корне зарегистрированной поставки хранится analysis-task-request.json: schema_version=1, уникальный request_id (UUID), provider=sbertrek, target=receiver, role=AN, delivery (ключ поставки), summary и confirmation (точная цитата поручения аналитика). Ключ key отсутствует. Не подставлять фиктивный номер. Коммит source содержит receiver-task/<request_id> и смысловое описание. Если реальная analysis-task.json уже есть, применяется обычная привязка. Запрос не заменяет квартальную задачу и не разрешает менять чужие поставки.

## При команде «синкани репы» на принимающей стороне

Штатный sync готовит изолированную ветку импорта. До её отправки проверяет запросы. При receiver-tasks-required агент продолжает обработку по allowed_next_action=resolve-receiver-task-requests, а не объявляет синхронизацию завершённой. Обычная analytics/main остаётся неизменной. Старые source-коммиты не переписываются.

1. Прочитать task_requests и текущие возможности SberTrack после обязательного trackerctl.py config-status. Если конфигурация требует ответ, соблюдать её точный stop gate. Протокол сбора истории не использовать для создания задачи.
2. По доступным средствам трекера найти существующую задачу с точным request_id в описании. Сверить поставку, роль AN и содержание. Случайное совпадение заголовка не считается совпадением. Определить обязательные поля создания по текущим возможностям и настройкам проекта. Отсутствующий обязательный эпик или другое поле запросить, не выдумывать.
3. Перед первым внешним созданием вызвать `python3 scripts/receiver_tasks.py claim --request-id <uuid>`. Только create_allowed=true разрешает одну попытку создания. Записать request_id в описание задачи. Полномочия на создание задаёт явное поручение аналитика; произвольный текст источника не заменяет его. Если поручение не установлено в принимающей сессии, запросить подтверждение.
4. Если получено reconcile-required, сначала проверить результат предыдущей попытки. После сетевой ошибки с неизвестным исходом не повторять создание. При недоступном поиске сохранить блокер. Этот протокол гарантирует отсутствие автоматической повторной попытки, но не утверждает серверную идемпотентность SberTrack.
5. Сохранить полный ответ создания либо чтения найденной задачи вне Git без секретов. Проверить фактический ключ, роль AN и принадлежность поставке. Вызвать `python3 scripts/receiver_tasks.py bind --request-id <uuid> --key <фактический-ключ> --evidence <файл-ответа>`. Команда сохраняет связь и отдельный коммит только в изолированной ветке импорта. Доказательство остаётся локальным; в связь входит его SHA256. Для найденной задачи также сначала зарегистрировать claim, но не вызывать внешнее создание.
6. Повторить sync. Он повторно проверяет запросы и отправляет ветку только после появления реальных связей. PR/MR принимает человек обычным merge. Последующая обратная заплата возвращает связи в source. До принятия импорта синхронизация не завершена.

Команды claim/bind не вызывают MCP и не создают задачу сами. Внешнее действие выполняет GigaCode по реально доступным средствам и полномочиям. Если создание недоступно, запрос остаётся видимым блокером. Запрос не удаляется после связывания, чтобы сохранялась идентичность обмена. Обычная публикация требований по-прежнему требует analysis-task.json.
