# Запрос создания задачи на принимающей стороне

`analysis-task-request.json` в корне поставки сохраняет явное поручение аналитика создать задачу на принимающей стороне. Это транспортные метаданные, не связь с готовой задачей и не разрешение обойти проверку коммитов.

Поля схемы 1: schema_version=1, request_id (постоянный UUID), provider=sbertrek, target=receiver, role=AN, delivery (ключ зарегистрированной поставки), summary и confirmation (цитата поручения). Поле key отсутствует. Значение role=AN описывает историческое поручение; вид задачи коммита определяется действующим договором: для поставки kind=delivery, suit=task, префикс [SA][PR]. Не создавать отдельную общую задачу AN вместо задачи в эпике поставки.

## Продолжение «синкани репы»

1. Sync проверяет задачи по будущему дереву слияния и при `awaiting-analysis-task` возвращает `task_requests` затронутых поставок вместе с `resolve-commit-task`. Обычная main не меняется. При повторном запуске сохраняются тот же импорт и идентификатор запроса.
2. Обработай поручение по `core/commit-task-resolution.md`: сначала config-status, затем текущие возможности MCP, подтверждённый владелец и эпик, поиск подходящей задачи и при отсутствии создание. Известный эпик не требует ручного номера задачи от аналитика. Неизвестный эпик нужно уточнить; не выводить его из названия или текущего квартала.
3. Используй штатный `commit-taskctl.py` и тот же файл продолжения для сочетания владельца и вида работы. request_id помогает связать поручение с этой работой, но не заменяет поиск по виду работы, точному названию и эпику. После неизвестного исхода создания выполняй сверку по действующему протоколу, без автоматического повторного создания. Новый идентификатор запроса не разрешает завести дубликат для того же владельца.
4. При `resolved` выполни возвращённый `bind_task_command`, заменив STATE путём продолжения: `repository-exchange.py bind-import-task --task-state STATE --expected-source SOURCE --expected-base BASE`. Команда проверяет текущий импорт, владельца и checksum ответов, затем сохраняет связь схемы 2 в `task_decisions_file`, сохраняя решения других владельцев. Повтор с тем же решением безопасен; другая связь или версия блокируется. Для старой схемы используй процедуру ниже. Не собирай JSON вручную и не изучай исходники для подбора формата. Обычная main и bare source не меняются.
5. Повтори sync. Он проверит связи, включит их в тот же импорт и отправит ветку для человеческого принятия. Обратная заплата вернёт metadata в source после принятия. До него не объявляй синхронизацию завершённой.

Запрос не разрешает публикацию требований в разработку без реальной задачи. Внешние вызовы выполняет агент по штатному договору и доступным средствам, а не программа синхронизации. Недоступность MCP остаётся видимым блокером. Само наличие произвольного текста в source не заменяет поручение аналитика.

## Отсутствующая или старая связь без запроса

`task_binding_targets` показывает поставки, затронутые будущим слиянием, пути их
связей и состояния `missing`, `legacy` или `existing`. Это диагностика импорта,
не выдуманное поручение `analysis-task-request.json`. Отсутствие такого запроса
не требует нового source-коммита или отправки незавершённой локальной аналитики.

При `missing` разреши задачу по обычному договору и выполни команду из выбранного
элемента `task_binding_targets`. При `legacy` сначала покажи `previous_binding`
и подтверждённую задачу замены. Используй уже данное решение аналитика о замене,
если оно однозначно относится к этой поставке и связи; иначе запроси его.
Передай в возвращённую команду точный `binding_sha256` через
`--expected-binding-sha256` и цитату решения через `--confirmation`, заменив
`ANALYST_CONFIRMATION`. Согласие на создание задачи само по себе не отменяет
прежнюю привязку. Повторный поиск и создание не нужны, если сохранённое продолжение
уже имеет `resolved` и проверяемые ответы MCP.

Замена доступна только для распознаваемой схемы 1 (`provider=sbertrek`, `role=AN`,
реальный ключ и confirmation). Связи схемы 2, повреждённые данные, разные прежние
связи в source и base, другой владелец или изменившийся импорт остаются блокерами.
Команда не снимает проверки остальных владельцев, baseline/context и квартала.
Задача `[BASELINE]` не подменяет `[SA][PR]` поставки.

В `task_decisions_file` сохраняются прежняя связь, её SHA256, решение аналитика,
путь продолжения и доказательства MCP. Метаданные записываются только при следующем
sync в ту же изолированную ветку импорта. История source, обычная analytics/main
и опубликованные пакеты не переписываются. После принятия импорта связь возвращается
в source обычной обратной заплатой. Не редактируй файл решений вручную и не создавай
искусственный request для обхода проверки существующей связи.

## Общие пути baseline и контекста

`task_work_targets` перечисляет изменённые пути baseline, releases и context,
для которых нет связи задачи. Вид работы возвращается в `kind`, но владелец
не выбирается автоматически. Согласуй, какой поставке или кварталу принадлежат
точные пути, и используй разрешённое продолжение соответствующего вида
`baseline` или `context`. Уже созданную задачу повторно не создавай.

Выполни `bind-import-task` с теми же source/base, `--task-state STATE`,
`--path PATH` для каждого выбранного файла и `--confirmation` с решением о владельце.
Готовая команда есть у каждого элемента `task_work_targets`; несколько `--path`
можно объединить. Каталоги и пути вне текущего списка не принимаются. Если решение
о владельце и путях уже дано, используй его без повторного вопроса.

Команда сохраняет точные ассоциации в `work-task-bindings.json` через тот же файл
решений импорта. Существующие ассоциации и решения других владельцев сохраняются;
их замена, несколько владельцев одного пути и миграция старых общих связей этим
узким путём не поддерживаются. После добавления связи повтори sync: все задачи
поставки и baseline/context попадут в заголовок одного проверенного коммита.
Проверки владения, эпика, содержимого, конфликтов и человеческого принятия остаются.
