# Груминг перед передачей требований

Команды «грумим <фичу>», «проведём груминг <фичи>», «нарежем на задачи после
груминга» запускают этот процесс в режиме requirements. Авторская работа над
требованиями сама по себе его не запускает. Для новых передач после груминга
этот договор определяет состав story вместо прежнего самостоятельного выбора
задач принимающей SDD. Старые входы без tasks/grooming.json сохраняют свой договор.

## Диалог с аналитиком

1. Разрешить PROJECT_ROOT, точную квартальную поставку и текущий открытый этап.
   Использовать project_layout.py; при неоднозначности задать один вопрос.
   Прочитать requirementsctl.py status. Незарегистрированное расхождение исходника
   сначала разобрать по обычному договору требований. Работать в зарегистрированной
   ветке поставки; main, чужая ветка и чужой этап запрещены.
2. Взять из сообщения аналитика названия задач и оценки. Оценки всегда в
   человеко-днях, поле estimate_unit всегда person-days. Значение 3 означает
   3 человеко-дня. Не спрашивать единицы, не переводить в story points или
   командо-дни. Префикс FE определяет клиентскую работу, BE серверную;
   AN и QA сохраняют свои роли. Не определять роль по исполнителю.
3. Сопоставить названия задач с действующими требованиями своего контура.
   Для общего требования выделить ответственность каждой задачи, сохранив REQ.
   Показать ровно одну задачу: название, оценку в чел.-дн., названия требований,
   конкретную часть работы, сценарии, критерий приёмки и зависимости с названиями.
   Не выводить REQ-номера вместо названий. Неясное название требует уточнения,
   а не автоматического включения всех требований контура.
4. Принять исправления аналитика. Сохранить его подтверждение именно показанного
   состава и перейти к следующей задаче. Изменение состава или оценки снимает
   прежнее подтверждение этой задачи. Уже согласованные неизменившиеся задачи
   повторно не спрашивать. Служебный JSON составляет агент, не аналитик.
5. Проверить весь объём: каждое требование и сценарий, FE/BE-состав, общие ошибки,
   права доступа, данные/миграции, зависимости и сквозные проверки. Пересечения
   допустимы с отдельной ответственностью; потерянное требование блокирует передачу.
   Отдельно зафиксировать решение по QA: отдельные задачи и оценки либо явно
   согласованный иной способ учёта без двойного включения оценки. Не придумывать
   оценку QA, исполнителей и сроки. Проверить отсутствие циклов зависимостей.
6. Показать сводку задач, сумму человеко-дней, эпик и результат проверки покрытия.
   Получить одно подтверждение итогового состава. Отдельное подтверждение аудита
   и передачи сохраняется; согласование груминга его не заменяет.

## Исходник и документы задач

Корневой requirements.md остаётся единственным авторским бизнес-контрактом.
Согласованный реестр лежит в tasks/grooming.json выбранной поставки. Из него и
корневых требований воспроизводимо строятся tasks/<task-id>/requirements.md.
Не редактировать производные документы отдельно. При повторном груминге preview показывает добавленные, изменённые и исключённые
задачи. Для исключённых в removed_tasks сохраняются id и decision с решением
аналитика; это не команда удаления или отмены story в трекере.
Идентификаторы задач устойчивы
между исправлениями и ревизиями; переименование не создаёт новую идентичность.
При разделении/объединении определить судьбу прежних story явно, с учётом их
фактического состояния. Отмена не выполняется автоматически. Новый этап получает
новые привязки; задачи прежнего этапа не переиспользуются молча.

Реестр схемы 1 содержит delivery (канонический ключ), stage_id,
requirements_sha256, epic_key, estimate_unit=person-days, coverage_review,
qa_review, tasks и confirmation. У каждой задачи:

- id, summary с префиксом AN/BE/FE/QA, role, положительная estimate;
- description, acceptance, depends_on (локальные id);
- source_sha256 выбранных правил и сценариев через grooming.task_source_hash;
- sdd_changes: пути вида backend/<change-id> или frontend/<change-id>;
- requirements: req_id, scope (ответственность), scenarios (точные заголовки);
- confirmation: text с точной цитатой решения и sha256 показанного состава.

confirmation.sha256 вычисляет grooming.approval_hash для объекта без его
confirmation. Общее подтверждение включает подтверждения отдельных задач.
Не выставлять эти поля по догадке. Шаблон: templates/grooming/plan.template.json.
Дробные оценки допустимы; отсутствие оценки не заменяется нулём.

Внутренние команды агента:

```text
python3 scripts/grooming.py preview PROJECT_ROOT DELIVERY --plan PLAN_JSON
python3 scripts/grooming.py build PROJECT_ROOT DELIVERY --plan PLAN_JSON
python3 scripts/grooming.py check PROJECT_ROOT DELIVERY
```

preview не записывает файлы и показывает следующую неподтверждённую задачу.
Он возвращает source_sha256 выбранного текста и confirmation_sha256 состава;
агент записывает их с точной цитатой после ответа аналитика. Изменение текста
выбранного правила или сценария требует нового подтверждения этой задачи.
Общие разделы и определения проверяются при итоговом согласовании и аудите.
Черновик PLAN_JSON можно сохранять в локальном состоянии до полного согласования.
build проверяет рабочую ветку и режим до записи, подтверждения, покрытие и SDD;
затем формирует реестр и документы. Проверка структуры не заменяет смысловой
проверки распределения. Если исходные требования изменились, снова сверить
затронутые задачи и общий состав с аналитиком.

## SDD, аудит и публикация

Пакет сохраняет общий sdd/ с proposal/delta specs. Задачи связываются с этими
изменениями; одна story не обязана равняться одному change. FE-задача не может
получить backend change и наоборот. Технические design/tasks создаёт разработка.

sdd/package.json использует схему 3. Она требует соседний tasks/ и допускает
materials/ по прежнему договору SHA256SUMS. sdd_input включает точный состав и
хеш tasks наряду с sdd и materials. Аудит, подтверждение, публикация и квитанция
связывают весь этот вход. Старые схемы 1/2 не принимают tasks молча.

Сохранить и принять исходники в analytics/main обычным процессом. После полного
аудита и подтверждения передать пакет через requirements-exchange.py prepare.
В ревизию входят requirements.md, tasks/, sdd/ и материалы, если они есть.
Изменение любого входа после аудита требует нового аудита; после публикации
создаётся новая ревизия, прежние файлы и возвраты сохраняются.

Принимающая SDD проверяет пакет и использует утверждённые задачи с теми же id.
Технические подзадачи допустимы внутри story. Изменение её объёма, оценки или
распределения требований возвращается аналитику на повторный груминг. Для нового
входа returns/tasks.md отражает эту привязку и локальные технические шаги;
результат story записывается под тем же id, summary охватывает весь вход.

## Story в SberTrack

Создание выполняет основной агент по текущим возможностям SberTrack. До первого
обнаружения инструментов или чтения отдельно выполнить trackerctl.py config-status
и соблюдать его stop gate. Не запускать direct-tracker-v1 сбор или актуализацию
для создания story. Не изобретать имена MCP и обязательных полей. Если запись
недоступна, сохранить готовый пакет и показать конкретный блокер.

Перед созданием повторить штатную проверку публикации и mark-published. Требуются
publication_confirmed=true, назначение code и точная ревизия в целевой ветке.
awaiting-merge и резервный каталог analytics не разрешают ссылки на отсутствующие
файлы coda. Эпик должен быть подтверждён; его ключ не угадывать по названию.

Для КОДА база браузерных ссылок:
https://onework.sigma.sbrf.ru/sc/RSCON/coda

Это адрес браузера репозитория, а не адрес API трекера. Для другого проекта база
явно задаётся по его репозиторию. Проверить соответствие базы фактическому месту
публикации и доступность ссылки получателю. Путь кодируется целиком в path:
requirements-exchange/<delivery>/revisions/<NNN>/tasks/<task-id>/requirements.md.

```text
python3 scripts/grooming_tracker.py preview PROJECT_ROOT DELIVERY --web-url URL
python3 scripts/grooming_tracker.py status PROJECT_ROOT DELIVERY --web-url URL --task TASK_ID
python3 scripts/grooming_tracker.py claim PROJECT_ROOT DELIVERY --web-url URL --task TASK_ID --confirmed-batch HASH
python3 scripts/grooming_tracker.py bind PROJECT_ROOT DELIVERY --web-url URL --task TASK_ID --evidence RAW_RESPONSE --mapping JSON_POINTERS
```

preview готовит Story, точный эпик, название с префиксом, оценку в человеко-днях,
краткое описание, критерий приёмки и ссылку. RSCON_dev является меткой, добавляется
к каждой создаваемой story. При обновлении сохранять остальные существующие метки.
Показать итоговый список и получить одно разрешение на создание/обновление; этот
ответ разрешает обработать весь неизменившийся список. Общая команда «грумим»
сама по себе не разрешает внешнюю запись до согласования конкретного результата.

Перед claim искать существующую story по точному grooming/<request_id> в описании,
включая завершённые карточки. Совпадение названия недостаточно. Для существующей
story сверить поля и связать найденный ключ; при расхождении показать обновление.
claim разрешает одну внешнюю попытку. Повторный claim после неизвестного исхода
возвращает reconcile-required и запрещает новую попытку. Найти карточку и проверить
её поля. При недоступном поиске остановить внешние записи по этой задаче.
Нельзя удалять журнал или менять id ради повторного создания.

bind получает полный неизменённый JSON создания или чтения. JSON_POINTERS
содержит пути в ответе к key (родной ключ SberTrack, не внешнее issue_key), type,
summary, epic_key, estimate, labels и description. Путь requirements_url
необязателен, если ссылка хранится только в описании; проверяется её наличие
вместе с согласованным описанием и критерием приёмки. Не изобретать отдельное
поле трекера ради проверки. При коротком
ответе создания дочитать карточку. Проверяются поля, метка и постоянный маркер.
Единица выбранного поля оценки проверяется агентом по текущей схеме трекера.
Не переписывать raw и не подменять факты ожидаемым payload.

Журнал хранится вне Git в .workspace-state/grooming-tracker/. Он блокирует повторную
локальную попытку, но не даёт серверной гарантии идемпотентности. На другой машине
обязателен поиск по постоянному маркеру. После сбоя продолжить оставшиеся задачи,
сохранив созданные ключи. При новой ревизии тот же id сохраняет Story; обновление
также проходит подтверждение, claim и проверку результата. Удалённые из состава
задачи показать отдельно и запросить их судьбу. Завершённые story не переоткрывать
автоматически. Перенос ключей в execution и пересчёт Ганта выполняются отдельно
по правилам актуализации, с историей и application-preflight.
