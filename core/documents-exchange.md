# Передача через documents и самостоятельная проверка результата

Этот договор действует для новых передач и имеет приоритет над прежними
описаниями публикации в code и обязательных returns. Договор поддерживается
в analyst-harness и coda-analyst-harness. Старые редакции сохраняют свой договор.
В универсальной обвязке documents обозначает репозиторий роли analytics;
его URL и каталог берутся из настройки workspace, а не задаются этим именем.

## Владение

Единственное место новой публикации: requirements-exchange/ репозитория роли
analytics (documents). Кодовый репозиторий аналитик читает. Команда prepare
проверяет вход, создаёт отдельную review-ветку documents в изолированном клоне
и сообщает awaiting-merge. Человек принимает PR/MR. Повтор prepare проверяет
точные байты принятого входа; затем mark-published регистрирует публикацию.
Локальный файл, отправленная ветка и опубликованная редакция различаются.
При недоступности documents отправка останавливается без резервной записи в code.
Существующие операции обновления кода сохраняют свой отдельный договор.

send-by-decision сохраняет явное решение аналитика и прежние ограничения
транспортной безопасности, но также публикует исключительно в documents.
Никакие новые пакеты или инструкции обмена в code не записываются. Developer-side
sdd-receive --apply остаётся действием разработки в её рабочем пространстве.

## Вход

Manifest schema 6 и returns_contract_version 3 определяют новый договор.
Вход редакции неизменяем: requirements.md, sdd/, tasks/ после груминга и
materials/ при наличии. SDD package schema не меняется: схема 3 сохраняет
согласованные задачи и их покрытие, схемы 1/2 остаются читаемыми.
Не требуется receipt.json, returns/tasks.md или returns/summary.md.
Разработка читает пакет documents и сохраняет технические материалы в своей SDD.

Требования разбиты по согласованным задачам груминга. Их id, объём, сценарии
и оценки сохраняются; технические шаги SDD находятся внутри этой нарезки.
Номера Story связываются с локальными id по проверенному журналу создания
или явному решению аналитика. Не восстанавливай владельца задачи по роли
исполнителя, названию change или случайному упоминанию ключа в тексте.

Для подготовки читаются релевантные main specs на известном текущем коммите
кода. Это исходная база до разработки, а не будущий коммит реализации.
package.json закрепляет repository, code_commit, target_root, base_specs и
context_files; proposal/specs содержат согласованную дельту и трассировку.
При необходимости в materials/ можно включить автоматически полученный
неизменяемый снимок выбранных specs с происхождением и SHA256SUMS. Полная
независимо редактируемая копия openspec/specs не создаётся. Получатель сверяет
затронутые источники со своей версией; движение остальных файлов само по себе
не является конфликтом. Незавершённые changes проверяются на пересечения,
но их объём не включается в требования автоматически.

Story создаются после подтверждённой публикации по core/grooming.md. Ссылка
ведёт в documents на путь конкретной неизменяемой редакции. Коммит публикации
указывается рядом. Адрес браузера проверяется по фактическому репозиторию;
прежняя база coda не используется для нового пакета.

## Сбор доказательств

Основная цепочка: задача груминга -> требования и сценарии -> коммиты по номеру
задачи -> связанные изменения SDD и код -> собственный разбор аналитика.
Одной задаче могут соответствовать несколько changes и коммитов.

Перед чтением кода действуют route/begin/verify из core/code-inspection.md.
Прочитай инструкции выбранного контура. Сборщик использует зарегистрированный
code, чистое дерево и полный SHA исследуемого коммита. Он не выполняет fetch,
checkout, сборку или тесты в продуктовой копии. Обновление кода выполняется
отдельной зарегистрированной операцией до начала инспекции.

Внутренние команды агента:

```text
python3 scripts/analyst_results.py collect PROJECT_ROOT DELIVERY --revision N --commit FULL_SHA --target-commit TARGET_SHA --contour backend --bindings BINDINGS_JSON
python3 scripts/analyst_results.py record-analysis PROJECT_ROOT DELIVERY --revision N --report REPORT_JSON
```

BINDINGS_JSON содержит объект task-id -> {key, evidence}. Все id взяты из
переданного tasks/grooming.json; key содержит проверенный родной номер
SberTrack, evidence указывает подтверждённое основание связи. Файл составляет
агент из проверенного журнала grooming_tracker или решения аналитика. Не
просить аналитика заполнять JSON. После сохранения анализа связи входят в его
неизменяемый снимок в documents. Отсутствующие связи требуют сверки, а не догадки.

collect возвращает JSON только в stdout; сохраняй полный результат в локальный
файл, не пересказывай его в терминале. Он содержит коммиты с точным префиксом
ключа, архивные changes, пути и хеши. Это кандидаты, не подтверждение выполнения.
Используется история, достижимая из выбранного коммита; --all не применяется.
Первое появление архива в истории выбранной ветки отделяется от позднего
добавления файла в каталог. При squash/merge тема входного коммита может не
содержать ключа: изучи коммиты задачи и содержимое, сохрани неоднозначность.
Дата в имени архива означает архивацию; created в .openspec.yaml означает
создание change. Ни одно из этих значений не задаёт сроки выполнения задачи.
Опечатки RSON и неизвестные ключи не исправляются автоматически.

## Собственный разбор

Агент исследует каждый сценарий переданного входа. Проверяет код по цепочке
пользовательского действия, общие контракты и зависимости компонентов. Архивные
дельты сопоставляет с исходной базой и результатом соответствующих изменений,
не применяет повторно к сегодняшним specs. Чекбоксы tasks, архивирование и main
specs не доказывают успешный запуск тестов или внедрение.

REPORT_JSON по templates/exchange/analyst-analysis.template.json содержит
точный вход, bindings, полные снимки collect и оценки каждого сочетания
задача/REQ/сценарий. Для входа без груминга task_id пустой, покрываются сценарии
корневого документа. Различаются implementation, conformity, verification,
merge, deployment. Каждая оценка содержит ожидаемое и фактическое поведение,
ограничения и ссылки на файлы конкретного снимка. passed/failed требуют
сохранённого результата запуска, deployed требует записи о внедрении.
Статический анализ не заменяет эти доказательства. Отсутствие отчёта означает
unknown/not-run; не требуй от разработки новый отчёт ради нашего формата.

record-analysis повторно сверяет снимки с Git, проверяет полноту и безопасные
пути, затем сохраняет revisions/NNN/analysis/<content-hash>.json в documents.
Запись разрешена в активной ветке владельца в requirements/release-finalization.
Повтор неизменного анализа идемпотентен; новая версия доказательств создаёт новый
файл, прежний не перезаписывается. Сначала синхронизируй принятый пакет в documents.
При нескольких контурах собери все необходимые доказательства и общую проверку;
успех backend сам по себе не означает готовность frontend.

scan показывает analysis-present или awaiting-analysis отдельно от бизнес-приёмки.
После анализа агент готовит решение по каждому REQ и использует существующий
record-processed --decision reviewed --review-file с полученным return_id.
Принятие, остаток и внедрение требуют прежних оснований и решений аналитика.
Закрытие этапа принимает идентификатор собственного анализа. Неизвестные сценарии
блокируют закрытие. Архив релиза сохраняет исходные редакции, прежние возвраты,
собственные анализы и решения; baseline обновляется лишь по подтверждённому
внедрению. Процесс не собирает и не применяет историю трекера автоматически.

## Совместимость

Схемы manifest 1–5 и contracts 0–2 читаются по прежнему договору. Обновление
корневых инструкций не меняет старые редакции и их идентификаторы. Новая схема
не принимается старым клиентом молча: обновить обвязку и получатель до использования.
Действующая передача в code требует явного переноса истории в documents перед
новой редакцией. Незавершённый кандидат нельзя молча переиздать в другом месте.
Существующий code exchange не удаляется в ходе миграции.

Явный перенос принятой истории выполняется в активной ветке владельца:

```text
python3 scripts/requirements-exchange.py migrate-code-exchange PROJECT_ROOT DELIVERY --analyst-confirmed --reason "Точная формулировка решения"
```

Команда копирует неизменяемую историю и сохраняет исходные идентичности и хеши.
Она не удаляет пакет в code и не подтверждает публикацию в documents. Сохранить
ветку и принять перенос обычным процессом аналитики; лишь затем prepare создаёт
новую редакцию с новым договором. Пока есть неподтверждённый кандидат, перенос
заблокирован. Повтор команды не перезаписывает скопированную историю.

TARGET_SHA означает наблюдаемый полный коммит целевой ветки. Без него состояние
merge остаётся unknown. Несколько контуров исследуются отдельными вызовами;
снимки объединяются в одном анализе поставки. Collect возвращает активные и
архивные changes, связанные с коммитами выбранных задач. При отсутствии SDD
пакета можно указать проверенный --openspec-root из зарегистрированного контура.

Для runtime-доказательств REPORT_JSON допускает external_evidence: path внутри
PROJECT_ROOT, точные content и sha256, kind=test-result/deployment-record,
source_commit исследуемого кода, environment, procedure и result. Агент сохраняет
исходный лог без пересказа. Сценарий ссылается на него через {artifact: sha256,
reason: основание}; статическое доказательство использует {snapshot: хеш полного
collect JSON, path: путь кода, reason: наблюдение}. При записи исходные байты
проверяются; в архиве остаётся полный снимок лога. Это не автоматическая проверка
смысла лога: соответствие команды, среды и сценария проверяет агент.

Файл analysis/current указывает на действующий неизменяемый анализ. Новый отчёт
указывает supersedes с хешем предыдущего. Повтор старого отчёта не откатывает
указатель. Закрытие по прежнему разбору после новой проверки блокируется.
