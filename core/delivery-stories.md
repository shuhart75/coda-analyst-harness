# Задачи при передаче требований

Запрос «передай требования в разработку» включает оформление согласованных
задач в SberTrack после принятия пакета в documents. Агент сам выполняет поиск,
создание или обновление и проверяет результат. Не спрашивай повторно разрешение
на каждую запись. Если аналитик явно поручил только подготовку, запись не выполняй.
Новый бизнес-объём и неизвестную связь задачи с фичей не определяй самостоятельно.
Не требуй оценки: они опциональны и не блокируют передачу.

## Какие задачи обрабатывать

Источник состава: согласованный tasks/grooming.json текущей поставки.
Указанные аналитиком номера сохраняются в необязательном tracker_key задачи.
Если номера переданы после публикации, агент сохраняет отдельный локальный JSON
`{"be-01": "RSCON-8201"}` и передаёт его через --task-keys во всех вызовах.
Не переписывай опубликованный груминг ради добавления номера. Не проси аналитика
составить JSON. Номер должен однозначно относиться к локальной задаче; при реальной
неоднозначности задай один вопрос. Не сопоставляй список по случайному порядку.

- Номер указан: найди точную карточку и обнови её. Отсутствие карточки или доступа
  не разрешает создать замену. При противоречии с ранее сохранённой связью выясни
  владельца; не перепривязывай молча.
- Номер не указан: сначала проверь журнал и поиск по постоянному маркеру
  grooming/<request_id>, включая завершённые карточки. Найденную задачу переиспользуй.
  Если совпадений нет, создай Story. Одного похожего названия недостаточно.
- Если задача уже удовлетворяет текущему входу, сохрани подтверждённую связь
  без повторной записи. При новой редакции обновляй тот же блок описания и номер.

Новые задачи создаются только типа Story. Тип, название, статус, исполнитель,
оценки и остальные посторонние поля существующей карточки не меняются этой
операцией. Не переоткрывай завершённые задачи. Удаление из груминга не является
поручением отменить задачу в трекере.

## Обязательные поля у каждой задачи

| Поле | Значение |
|---|---|
| Эпик | Подтверждённый эпик фичи, указанный в груминге |
| Метки | Добавить RSCON_dev, сохранить остальные |
| КЭ | ПКАП1200 АС КОДА (CI07642362) |
| Архитектурные изменения | Не влияет на архитектуру |
| Требуется НТ | Нет |

Эпик берётся из проверенной связи с фичей, а не из названия или случайного
упоминания номера. Сначала используй сохранённые подтверждения и доступные данные;
только при отсутствии однозначного эпика спроси аналитика. При неверном эпике
существующей задачи установи подтверждённый эпик фичи в рамках этой операции.

Перед первым MCP discovery/read отдельно выполни trackerctl.py config-status
и соблюдай stop gate. Не запускай execution-run или актуализацию ради оформления.
Названия инструментов, идентификаторы custom fields, справочников и вариантов
значений определи по текущим возможностям SberTrack. Семантические имена полей
из preview не являются готовыми аргументами MCP. КЭ проверь по CI07642362 и
указанному названию. Не создавай новые справочные значения.

## Описание, три ссылки и SDD

Используй проверенный формат корпоративных ссылок:
`https://onework.sigma.sbrf.ru/sc/RSCON/documents?path=<полностью URL-кодированный путь>`.
Аналитик подтвердил работоспособность этого формата. Не требуй повторного ручного
подтверждения формата в каждой передаче. При изменении хоста или репозитория
проверь новое соответствие. Все пути должны существовать в принятой редакции.

В каждую задачу включаются объём, критерии приёмки и:

1. Ссылка на requirements-exchange/<delivery>/revisions/<NNN> с пояснением
   «Все данные для разработки по фиче находятся в этой папке».
2. Ссылка на requirements.md в корне этой редакции с пояснением
   «Общие требования по фиче».
3. Ссылка на tasks/<task-id> той же редакции с пояснением
   «Требования по текущей задаче находятся в этой папке».

Добавь готовый промпт SDD и подпиши папку входа. Входом служит вся редакция,
а не только папка задачи: нужны общий контекст, tasks, sdd и materials. Промпт
указывает конкретную задачу, редакцию, коммит публикации и её sdd_changes;
он не поручает реализовать соседние задачи. Для sdd-receive.py --packet указывает
родительский каталог поставки с manifest.json, --revision выбирает точную редакцию.
Не путай его с каталогом revisions/NNN. Корневые инструменты и договоры exchange
должны быть доступны получателю. Сначала dry-run, затем обычный разработческий
процесс приёма, дизайна и реализации. Аналитическая обвязка код не реализует.

preview воспроизводимо формирует ссылки и промпт. Блок передачи имеет устойчивые
начальную и конечную метки. resolve заменяет только этот блок, сохраняет текст
до и после него, остальные метки и название. Если описание редактировали после
подготовки записи, перечитай его и пересобери обновление; при поддержке API используй
версию карточки для защиты от параллельного изменения. Повреждённые границы блока
разбери без удаления пользовательского текста.

## Команды и продолжение после сбоя

Перед оформлением проверь принятие пакета через requirements-exchange.py status
--refresh и регистрацию публикации. Не создавай ссылки на review-ветку.

```text
python3 scripts/grooming_tracker.py preview PROJECT_ROOT DELIVERY --web-url URL [--task-keys FILE]
python3 scripts/grooming_tracker.py status PROJECT_ROOT DELIVERY --web-url URL [--task-keys FILE]
python3 scripts/grooming_tracker.py resolve PROJECT_ROOT DELIVERY --web-url URL --task ID --evidence RAW --mapping POINTERS [--task-keys FILE]
python3 scripts/grooming_tracker.py claim PROJECT_ROOT DELIVERY --web-url URL --task ID --confirmed-batch HASH [--task-keys FILE]
python3 scripts/grooming_tracker.py bind PROJECT_ROOT DELIVERY --web-url URL --task ID --evidence RAW --mapping POINTERS [--task-keys FILE]
```

HASH берётся из текущего preview. Это проверка неизменности подготовленного
набора под действующим поручением аналитика, а не требование нового разрешения.
Не имитируй подтверждение бизнес-состава этим техническим хешем.

Для существующей задачи сначала resolve с полным ответом чтения. Он закрепляет
родной номер, проверяет совпадение с указанным и готовит write_fields. Только
затем claim допускает обновление. Для новой задачи после поиска claim допускает
одну попытку создания. Внешние действия выполняет LLM через доступные средства
SberTrack; утилита сама в сеть не обращается.

После записи перечитай карточку и передай полный неизменённый JSON в bind.
JSON_POINTERS указывает поля key (родной ключ, не внешнее issue_key), type,
summary, epic_key, labels, description, configuration_item, architecture_changes,
load_testing_required. Для новой задачи estimate нужен только если он задан.
Сопоставляй указатели с фактической схемой: configuration_item может указывать
на код CI07642362 или полное отображаемое значение, НТ на «Нет» или JSON false.
Если ответ содержит лишь внутренний ID варианта, дочитай данные справочника
штатными средствами. В mapping вместо простой строки можно задать проверяемую
связь с отдельным полным ответом:

```json
{
  "configuration_item": {
    "path": "/data/custom_field",
    "lookup": {
      "evidence": "/absolute/path/to/raw-options.json",
      "id": "/values/0/id",
      "value": "/values/0/code"
    }
  }
}
```

Пути в примере условные; выбери реальные указатели. Инструмент проверяет равенство
ID карточки и записи справочника, затем её значение; хеш ответа справочника
сохраняется в журнале. Это позволяет проверять нативные enum/reference-поля
без требования несуществующего текстового поля и без исправления сырого ответа.
Короткого ответа создания с одним ключом недостаточно для подтверждения полей.

claim/bind защищает от повторного создания после неизвестного исхода. При
reconcile-required сначала найди и прочитай фактическую карточку. resolve может
подтвердить её готовность или разрешить исправление той же найденной карточки.
Не удаляй журнал и не меняй request_id ради повтора. При недоступном поиске сохрани
неопределённость по этой задаче и продолжай независимые задачи.

status без --task показывает completed/total и следующую незавершённую задачу.
Это итог по сохранённым фактическим ответам, не непрерывная проверка трекера.
В финале отдельно укажи публикацию/регистрацию пакета и число проверенных задач,
их номера, ссылки и оставшиеся ограничения. Принятый пакет при незавершённых
карточках остаётся опубликованным, но весь процесс передачи ещё не завершён.
Execution, сроки и Гант обновляются отдельной операцией с историей и preflight.
