# Вход аналитика для OpenSpec spec-driven

## Владение и точка входа

Канонический обмен остаётся `requirements-exchange/`: одна поставка, одна
активная редакция, один ответственный за общий возврат. Аналитик не записывает
артефакты в рабочие `openspec/changes/` кодового репозитория.

`requirements.md` — единственный авторский бизнес-контракт. Аналитик готовит
производные proposal/delta specs по этому контракту и проверенному состоянию
кода. Разработчики принимают готовые файлы, проверяют реализуемость, создают
design/tasks и реализуют согласованное поведение. Противоречие между requirements
и производными файлами блокирует передачу; разрешается изменение источника
или исправление производного представления, а не выбор удобной версии.

## Профиль и совместимость

`openspec-spec-driven-v1` фиксирует формат входного пакета, а не версию CLI.
Основание — предоставленный 8 октября 2026 года отчёт об установленном OpenSpec:
отдельные backend/frontend roots одного репозитория, схема `spec-driven`,
backend CLI 1.5.0 и frontend/skills 1.6.0. Это наблюдения отчёта, не подтверждение
совместимости версий и не сертификат среды получателя. Перед каждой подготовкой
проверяй действительные config, context, main specs и относящийся к задаче код
каждого затронутого контура. Backend-инструкции не заменяют frontend-инструкции.

Новая подготовка явно выбирает
`begin-preparation --input-profile openspec-spec-driven-v1`. Профиль сохраняется
при возобновлении. `requirements-only-v1` оставлен для прежних клиентов и
согласованного legacy-процесса; отсутствие кода или ошибка SDD не разрешает
молча понизить профиль. Схемы манифеста 1–4 и их входы остаются неизменяемой
историей. Схема 5 связывает новый SDD-вход и квитанцию версии 2.

## Подготовка до аудита передачи

В режиме требований и рабочей ветке выбранной поставки подготовь:

```text
<delivery-root>/
  requirements.md
  sdd/
    package.json
    backend/<change-id>/
      .openspec.yaml
      proposal.md
      specs/<capability>/spec.md
    frontend/<change-id>/
      .openspec.yaml
      proposal.md
      specs/<capability>/spec.md
```

Создавай только затронутые контуры. Каждому change соответствуют точные target
root, источник и покрытие требований. Это части одной редакции поставки,
а не независимые бизнес-срезы. Шаблоны находятся в `templates/sdd/`.
Не создавай design/tasks от лица разработки, не вызывай `opsx-propose` или
`opsx-ff`: они могут сгенерировать весь набор артефактов. Не устанавливай CLI
или Store ради аналитической подготовки.

Источник кода разрешается через роль `code` и зарегистрированное чтение по
`core/code-inspection.md`. Не меняй обычный кодовый клон, его настройки или
корневые инструкции. Исследуй наблюдаемое поведение, API, данные, жизненные
циклы, ограничения и смежные процессы. Код доказывает исходное состояние;
целевое поведение утверждает аналитик. Отсутствие проверяемого источника блокирует
готовность SDD-входа; резервный каталог обмена не снимает этот блокер.

## package.json

Схема `1` содержит:

- `profile: openspec-spec-driven-v1`;
- `requirements_sha256` — SHA-256 точных байтов текущего requirements;
- непустой `changes`, каждая запись содержит:
  - `contour`: `backend` или `frontend`; `change_id`: kebab-case;
  - `target_root`: относительный путь OpenSpec root от корня code;
  - `repository`: точная идентичность Git origin без секретов;
  - `code_commit`: полный исходный commit SHA;
  - `context_files`: относительный путь от корня code → SHA-256 всего файла;
  - `base_specs`: точная capability → SHA-256 всего main spec, либо `null`
    только для подтверждённо новой capability;
  - `coverage`: записи `req_id`, `capability`, `requirement`,
    `scenarios` с точными именами заголовков delta spec.

`context_files` обязательно закрепляет `<target_root>/config.yaml`. Сюда также
включаются реально использованные местные правила, контекст, схемы/шаблоны
и файлы кода. Формальная проверка не способна сама определить весь необходимый
контекст: полноту выбора проверяет аудит. Не ограничивайся config ради прохождения
валидатора. Каждый входной `REQ-*`, каждый блок delta и каждый его сценарий
должны иметь трассировку. Одно требование может покрываться несколькими контурами.

Изменение исходного commit допустимо только как проверяемый потомок при
неизменности выбранных файлов context/main specs. Изменённые источники требуют
пересмотра пакета. Все пути относительные, без выхода за корень и симлинков;
секреты и абсолютные пути рабочей станции в пакет не попадают.

## Proposal и delta specs

Proposal сохраняет обязательные `## Why`, `## What Changes`,
`## Capabilities`, `## Impact`; внутри Capabilities — оба подзаголовка
`### New Capabilities` и `### Modified Capabilities`. Записи имеют вид
`- \`exact-capability\`: описание`. Имя совпадает с каталогом spec.

Укажи цель и общий E2E-сценарий поставки, границы и исключения, затронутые
подсистемы, контракты, данные, доступ, интеграции, совместимость, риски и план
проверки в пределах обязательных разделов. Фиксируй наблюдаемые обязательства;
конкретный способ реализации выбирается в design разработчиков.

Delta содержит только применимые верхние секции:
`ADDED Requirements`, `MODIFIED Requirements`, `REMOVED Requirements`,
`RENAMED Requirements`. Точные синтаксические маркеры остаются английскими;
описание требований и сценариев — по-русски:

```text
## ADDED Requirements

### Requirement: Наблюдаемое поведение
Система SHALL выполнять согласованное действие.

#### Scenario: Конкретное условие
- **WHEN** наступает указанное событие
- **THEN** наблюдается указанный результат
```

New capability использует ADDED; отсутствие main spec не позволяет придумать
MODIFIED. При MODIFIED перенеси весь существующий requirement block со всеми
сценариями и затем внеси согласованную дельту. Проверка имён сценариев не
доказывает сохранение смысла: аудит сравнивает полный текст с main spec.
Удаление сценария требует явного бизнес-решения и основания в
`removed_scenarios[capability][requirement][scenario]` соответствующего change.

REMOVED сохраняет точное имя существующего requirement и обязательные строки
`**Reason**: ...`, `**Migration**: ...`. RENAMED содержит только пары
`- FROM: \`### Requirement: Старое имя\`` /
`- TO: \`### Requirement: Новое имя\``.
Если одновременно меняется поведение, нужен MODIFIED с новым именем.
Для REMOVED и чистого RENAMED в coverage указывается пустой список scenarios;
для rename+MODIFIED — новое имя и все действующие сценарии.

## Аудит, публикация и возврат

Прими requirements и производный sdd в актуальную analytics/main и заверши
collaboration до аудита передачи. Три уровня аудита проверяют смысл, межконтурную
согласованность, полноту REQ/сценариев, точность источников и готовность всего
входа. `record-audit` использует зарегистрированное чтение кода для проверки
источников. Самостоятельно записанный хеш не является доказательством чтения.
Покажи полный результат и получи отдельное подтверждение аудита и передачи.

`scripts/sdd_bundle.py` проверяет структуру, состав, трассировку и закреплённые
источники. Он не заменяет содержательный аудит и живой OpenSpec validator.
Подтверждение связывает весь набор байтов; любая правка proposal/spec/package
или requirements требует повторного аудита. Prepare копирует принятый
`sdd/` побайтно в `revisions/<NNN>/sdd/`; не генерирует файлы после аудита.

В манифесте запись `sdd_input` содержит `profile`, общий `sha256` и `files`
(путь относительно sdd → SHA-256). При `returns_contract_version: 2` квитанция
имеет `schema_version: 2` и содержит также `sdd_sha256`; используй
`templates/exchange/receipt-sdd.template.json` (в exchange — `receipt-sdd.template.json`). Стабильные return_id, этапы, привязки квартальной
поставки и остальные возвраты не меняют смысла.

Получатель использует поставленные в корень exchange `sdd-receive.py` и
`sdd_bundle.py`. По умолчанию проверка без записи; `--apply` выполняется
только по явному разрешению разработчика. Она не перезаписывает другой change,
новую редакцию поверх прежней, design/tasks или исходники кода. Порядок и команда
даны в `templates/exchange/SDD-WORKFLOW.template.md`. Это инструмент нашего
обмена, а не утверждение о существовании native import в OpenSpec.

После приёма разработка проверяет фактическую схему и строгую валидацию change,
продолжает с design/tasks и возвращает полный результат. Существующие ошибки
общей валидации main specs не освобождают от проверки нового входа. Готовность
артефакта tasks для apply отличается от выполнения чекбоксов задач.
Эксперимент на установленном GigaCode/OpenSpec проводится отдельно; локальные
проверки обвязки не доказывают успешный прогон в среде разработки.

## Релиз

OpenSpec main specs могут фиксировать реализованный код. Аналитический baseline
и доменная модель обновляются по подтверждённому внедрённому релизу с обязательной
проверкой сущностей, связей, правил, жизненных циклов, процессов и диаграмм.
Технический archive не заменяет внедрение. Порядок `core/quarter-deliveries.md`
сохраняется: разбор → baseline/домен → архив точного обмена → принятие в
analytics/main → очистка. Частичные поставки остаются активными; sdd входит
в неизменяемый релизный архив вместе со всей редакцией.
