# Актуализация задач по трекерам

## Назначение

Команда «актуализируй задачи» включает сбор, сверку, применение подтверждённых
фактов к исполнению и проверку actual-progress. Это не команда изменения
утверждённого плана и не синоним чтения трекеров.

Доступ к MCP и настройки трекеров принадлежат конкретной установке, а не ОС.
Разработка и автономные тесты обвязки не требуют доступа к трекерам. При
выполнении актуализации недоступный обязательный MCP останавливает сбор;
нельзя подменять его старой выгрузкой, другим провайдером или настройкой с
другой машины. Не меняй установленную обвязку ради прохождения актуализации.

## Сбор и разрешение на применение

### По фиче

Если аналитик уже назвал провайдер и эпик/ключи, используй их без повторного
предпросмотра. Эпик позволяет обнаружить новые входящие задачи в пределах
лимита ответа. Если названа только фича, после готового `config-status`
подготовь список существующих задач:

```sh
python3 scripts/trackerctl.py scope-preview --project-root "$PROJECT_ROOT" --feature <feature> --provider <jira|sbertrek>
```

### По кварталу

После готового gate и уточнения провайдера используй:

```sh
python3 scripts/trackerctl.py scope-preview --project-root "$PROJECT_ROOT" --quarter <YYYY-QN> --provider <jira|sbertrek>
```

Это локальный предпросмотр, не обращение к трекерам. Фичи выбираются по union
`FEATURE-*.puml` в quarter-plan, commander-plan и actual-progress, а также
явной конфигурации квартала. Учитываются mapping, сохранённые прогнозы и
исключения без изменения их решений. При передаче `--quarter` вместе с
`--feature` фича должна входить в выборку квартала.

Предпросмотр читает корневые и legacy slice execution-реестры. Для Jira берёт
только колонку `Jira`, для SberTrek только явную колонку `SberTrek`, если она
есть. `Task ID` не доказывает внешний ключ. Legacy `Jira = KEY/ROLE`
нормализуется с проверкой роли. Несколько ролевых строк дают один запрашиваемый
ключ, но все ссылки сохраняются. Статусы и даты строк не фильтруются:
завершённая работа и неизвестные интервалы остаются предметом проверки.

Покажи `features`, `scope.ids`, источники, `omitted`, `shared_keys` и
`limitations`, затем одним вопросом подтверди область. Если явных ключей
выбранного провайдера нет, спроси эпик или ключи; не назначай провайдера
по внутреннему ID. Не создавай пустой run и не подменяй SberTrek Jira.
При существующем незавершённом run предпросмотр возвращает его действие,
не сканируя новую область; продолжи старый run по общему протоколу.

Квартальная выборка означает текущие задачи известных реестров фич квартала,
не глобальный поиск незавершённых задач и не поиск неизвестных членов всех
эпиков. Новые задачи из эпика требуют отдельно заданной области.
После подтверждения один `tasks` run получает все выбранные ключи через
повторяемый `--scope-id`; не запускай отдельный run на каждую фичу.
Выборка свыше 50 ключей не обрезается в предпросмотре, но требует обсуждения
охвата перед сбором. Не разбивай её на самовольные запросы или новые run.
Предложи явно сузить область или продолжить с видимым ограничением полноты.
Отсутствующие в ответе задачи не считаются закрытыми или отменёнными.

### Общий переход

1. Выполни gate и весь протокол из `core/tracker-reading.md` с intent
   `update-planning`. Уточни провайдер и область, если они не подтверждены.
   Название фичи или квартала само по себе не задаёт ключ эпика.
2. Продолжай существующий незавершённый run, а не начинай повторный сбор.
   Ошибка ingest требует исправленного полного ответа на тот же шаг.
3. Дождись успешного `result-status`. Выведи его `response_contract.text`
   отдельным сообщением дословно. Этот отчёт завершает только фазу чтения.
4. При `planning_application_allowed: true` продолжи по
   `planning_update.next_action` в рамках исходной команды актуализации.
   Не требуй повторного разрешения на уже порученную актуализацию.
   Для `read-only` действие отсутствует: закончи работу без правок.

Перед применением повторно проверь `result-status`, если работа прерывалась.
Не меняй intent завершённого read-only run или его разрешения вручную.
Проверенные результаты чтения не являются доказательством записи в проект:
`workflow_complete` относится к сбору и сверке, а
`planning_update.actualization_complete: false` означает, что tracker-команда
не выполняла актуализацию. Не выдавай её отчёт за обновлённый Гант.

## Контекст и сопоставление

Разреши `PROJECT_ROOT` через `workspace.py project-root`. Прочитай режим,
Git-статус и `collaboration.py status`. До записи используй
`execution-update` и допустимую рабочую ветку по `core/collaboration.md`.
Не переключай и не закрывай чужую активную работу. Если текущая работа
несовместима с целевой фичей, задай один вопрос о продолжении.

Читай только подтверждённые целевые фичи: их execution-реестры, поддерживающие
карточки, `planning/actualization.md`, `execution-context.md`, а также
`planning/team.md` и конфигурацию actual-progress выбранного квартала.
Используй компактный файл из `planning_update.next_action.reconciled`, а не
повторную интерпретацию ответов MCP.

Составь проверяемое сопоставление каждой исходной задачи:

- найденная строка реестра и её внутренний ID либо новая подтверждённая работа;
- фича и основание принадлежности: существующая явная связь или ответ аналитика;
- отдельные work item для всех ролевых оценок, включая QA;
- связь с существующей историей, если она подтверждена;
- известные факты, изменения и один следующий вопрос о недостающих данных.

Не считай эпик или релиз фичей без явного соответствия. Не выводи принадлежность
по названию. Совпадение ключа между провайдерами не является связью:
используй только пару, уже установленную reconciliation.

## Применение фактов

- Обновляй существующие строки по подтверждённому ключу и роли, сохраняя
  внутренние ID и связи. Ищи также в legacy slice-реестрах: не создавай
  дубликат в корневом реестре. Не создавай новые slices ради генератора.
- Новую работу добавляй только после подтверждения принадлежности к фиче.
  Локальные задачи без ключа трекера сохраняются; сходное название не
  разрешает заменить их внешней карточкой.
- В квартальном обновлении сохрани сопоставление каждой задачи с её фичей.
  Ключ в нескольких фичах требует проверки владения, не копирования всего
  результата во все реестры. Подтверди одну владеющую рабочую ветку для
  согласованного набора правок; не создавай и не переключай ветки на каждую
  строку. Один общий запуск `--actual-only` выполняется после подготовки
  всех выбранных фич, а не после каждой отдельной записи.
- Переноси ролевые оценки в человеко-днях без повторного учёта общей оценки.
  Неизвестную роль или несовместимую единицу уточняй. Отсутствующая оценка в
  ответе не обнуляет ранее подтверждённую оценку.
- QA относится к фиче целиком. Источник оценки в FE-карточке не доказывает,
  что QA выполняет её FE-исполнитель. Сохрани отдельную подтверждённую связь
  QA с ресурсом или уточни её. Несколько QA-задач не объединяй.
- Словарь завершённых и исключающих статусов берётся из настройки run.
  Неизвестный статус не означает ни 0%, ни начало работы. Завершённый статус
  не сообщает точные даты. Различай статус карточки и подтверждённое состояние
  каждой ролевой работы; не переноси факты FE на QA только из-за общей карточки.
- `created_at` и `updated_at` не являются датами выполнения. Сохраняй ранее
  подтверждённые интервалы и `Completed By`; при противоречии уточняй факт.
  Не вычисляй прошлое начало из оценки. Не придумывай текущий процент.
- В `excluded` и исходных `issues` проверяй причины исключения. Отсутствующая
  Jira-контрпара не доказывает отмену существующей локальной работы.
  Не удаляй строки, которые не вернулись из запроса, особенно при ограничении
  выдачи. Подтверждённая отмена остаётся записью, не удалением.
- Сохрани в execution-контексте run ID, контрольную сумму результата,
  применённые факты и нерешённые вопросы. Не копируй туда полный ответ MCP.
  Повторное применение тех же фактов не создаёт новых задач или записей.

## Генерация и завершение

Следуй source gate в `modes/execution-update.md`. Сначала проверь готовность
к генерации по всей выбранной выборке, включая сохранённые FORECAST и ролевые
источники PLAN. Не создавай пустые карты и не назначай `Baseline State = absent`
ради прохождения. Недостающие сведения уточняй по одному вопросу.

Запусти из HARNESS_ROOT:

```sh
python3 scripts/sync-quarter-gantt.py "$PROJECT_ROOT/planning/<quarter>/gantt" --actual-only
```

Проверь diff исходных execution-документов и производных файлов, неизменность
утверждённых quarter/commander планов и защищённых FORECAST. Разверни includes
через `expand-plantuml-includes.py <input.puml> <output.puml>` и сравни результат
с `actual-progress-confluence.puml`.

При блокировке генерации сохрани существующий Гант, покажи причину и отдельно
укажи, какие execution-документы уже изменены. Не объявляй весь процесс
завершённым по одному успешному отчёту трекеров.

После успешной генерации сообщи применённые изменения, результаты проверок и
оставшиеся ограничения охвата. Это отдельный отчёт актуализации, не правка
дословного отчёта сверки. Коммит, push, submit и слияние выполняются только по
соответствующей команде аналитика.
