# Заказчики поставок и учёт трудозатрат

Заказчик принадлежит **поставке**, не долгоживущей фиче. Две поставки одной фичи
могут иметь разных заказчиков. Единый источник — `PROJECT_ROOT/planning/customers.json`.
Паспорт `features/<feature_id>/README.md` показывает таблицу поставок с заказчиками
и ссылку на реестр; нельзя заменять её общим заказчиком фичи. Заказчик не выводится
из автора карточки, исполнителя, названия или заказчика соседней поставки.

## Реестр

Схема 1: `schema_version`, `customers` (ID -> объект `name`), `deliveries`
(каждый delivery_key из delivery-index.json ровно один раз). Legacy-проект без
индекса использует feature key как операционный ключ единственной поставки;
это совместимость, а не наследование заказчика будущими поставками.

Подтверждённая запись в deliveries:

```json
{"state":"confirmed","allocations":[{"customer_id":"customer-a","share":1}],
 "source":"quarters/2026-Q3/reports/decisions.md","evidence":"Точная цитата решения аналитика"}
```

Неизвестная запись: `{"state":"unknown","allocations":[],"source":"","evidence":""}`.
Несколько заказчиков требуют подтверждённых положительных долей с суммой 1.
Делить поровну без решения нельзя. Внутренние инициативы учитывай отдельно,
если распределение их затрат не согласовано. Неизвестный заказчик остаётся
отдельной категорией. Смена текущего заказчика не переписывает прошлые поставки.

При регистрации новой поставки добавляй её запись и уточняй заказчика; прежний
заказчик той же фичи автоматически не наследуется. При явной миграции покрывай
весь индекс, неизвестные отмечай unknown. Старые проекты без реестра автоматически
не мигрируются. Перед утверждением плана проверяй привязки включённых поставок.
`--require-confirmed` требует подтверждения для всех поставок проекта.

## Единицы и периоды

Разделяй предварительные объёмы, оценки задач, оценки задним числом и фактические
человеко-дни. Длительность командной полосы не равна труду без состава и загрузки.
`SP = человеко-дни` допустимо только по решению проекта. Неизвестное значение —
null, не ноль. Сумма оценок закрытых задач — выпуск в оценённых единицах, не факт
затраченного труда. Отмена не стирает подтверждённые уже понесённые затраты.

Для recorded-working-days нужно явное решение аналитика о соответствии интервала
времени роли. Без него даты показывают календарное прохождение. Completed By не
задаёт интервал. Прямые подтверждения труда приоритетнее интервала. Даты,
восстановленные из оценки, не служат независимым фактом точности этой оценки.
QA/AN учитываются отдельно. Разработчик хранится независимо от владельца карточки
и ресурсной дорожки. Подтверждённые назначения имеют приоритет.

Период: completion-quarter (завершение), delivery-quarter (портфель поставки) или
work-date (даты труда). Объявляй основание и не смешивай его. При делении интервала
фактические доли не пересекаются; оценка записывается один раз. Неизвестный период
— unknown. Удалённые выполненные карточки сохраняются как исторический труд
при проверке отсутствия дублей.

## Производительность команды

Показывай отдельно выпуск (завершённые задачи и их первоначальные оценки),
калибровку (факт/оценка на сопоставимой выборке), доступную ёмкость и покрытие
данными. При нормировании выпуска на доступные дни называй единицу «оценённых
дней закрытого объёма на доступный день», не процентом загрузки. Неполный квартал
нельзя сравнивать с полным без одинакового окна и ёмкости. Проверяй согласованность
суммы длительностей задач с ёмкостью команды; пересечения не доказывают параллельную
работу. Не выдавай противоречивые длительности за табель или фактическую утилизацию.
Изменение состава работ и заказчиков может менять метрику без изменения людей.

## Проверяемый расчёт

customerctl только читает реестр и подготовленный аналитиком ledger; не собирает
трекер, не меняет исполнение, Гант или baseline.

```sh
python3 scripts/customerctl.py --project PROJECT_ROOT validate
python3 scripts/customerctl.py --project PROJECT_ROOT validate --require-confirmed
python3 scripts/customerctl.py --project PROJECT_ROOT report --ledger LEDGER.json
```

Ledger в `quarters/<quarter>/reports/effort-ledger.json` (legacy: planning/...):
верхний уровень schema_version=1, as_of, period_basis, policy, sources, records.
sources — относительный путь -> SHA256 доказательства. Изменившиеся источники,
внешние пути и символьные ссылки блокируют расчёт. policy описывает календарь,
выборку, допущения и размещение оценки при разделении факта по периодам.

Запись содержит ровно: work_id, feature_id, delivery_key, role, period,
estimate_days, estimate_basis, actual_days, actual_basis, status, developer,
source, evidence. Устойчивый work_id уникален в периоде. role = AN/BE/FE/QA.
Поставка должна принадлежать фиче, заказчик определяется только delivery_key.
estimate_basis: task-estimate/posthoc/unknown. actual_basis:
explicit-confirmation/recorded-working-days/unknown. status:
completed/in-progress/not-started/unknown/cancelled. developer — подтверждённое
имя для BE/FE или null. source входит в sources; evidence поясняет факт.

Отчёт сохраняет снимок связей всех поставок с заказчиками и его SHA256, суммы по
периоду/заказчику/роли и число работ без факта/оценки. Доли не умножают труд.
При пробелах показывай «учтённые затраты», не «все затраты». posthoc не участвует
в оценке точности первоначального плана. Пересчёт старого отчёта при новых связях
делай явно, с сохранением истории Git.

## Сохранение

Метаданные, паспорта и отчёты разрешены в execution-update при явном поручении
аналитика. Работай в активной ветке с set-execution-scope. Реестр проверяется по
каждой изменённой поставке, включая поставки переименованного заказчика. reports/*.md
и reports/*.json принадлежат зарегистрированным кварталам. Это не разрешает менять
утверждённые планы. Перед записью — application-preflight; перед сохранением —
customerctl validate/report и collaboration save-preview с точными путями.
