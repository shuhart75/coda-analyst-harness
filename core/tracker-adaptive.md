# Гибкий сбор и проверяемая история

Для релиза следуй `core/tracker-release.md`: MCP-инструмент и формат ответа
не зафиксированы. Членство через связи/запрос участников оформляется отдельным
манифестом доказательств, а не добавлением полей в исходные карточки. Новая
аналитическая фича без Ганта проходит подтверждение владельца и проверку истории
до регистрации исполнения, не повторный intake существующих требований.

## Порядок

### Восстановление текущего запроса

Цель текущего запроса (трекер, релиз/задачи/эпики, intent) имеет приоритет над
старыми артефактами. После потери контекста сначала обязательный `config-status`,
затем при готовой конфигурации:

```bash
python3 scripts/trackerctl.py resume --scope-kind release --scope-provider sbertrek --scope-id <release> --intent update-planning
```

Если известен сохранённый run_id, добавь `--run-id <exact-run>`. Команда ничего
не пишет и не вызывает MCP: находит только совпадающий запрос, проверяет связь
с завершённой collaboration и возвращает точный `run_json`, `scope` и следующий
шаг. Для combined укажи также `--epic-id`; для нескольких задач повтори scope-id.
Несколько кандидатов требуют выбора точного run, а не выбора самого нового.
Отсутствие совпадения не разрешает перейти к другому релизу или автоматически
создать замену. Сначала разберись с целью и сохранёнными идентификаторами.

`tracker-active-run.json` относится к сбору и снимается после reconciliation;
его отсутствие не означает, что актуализация завершена. `completed_work` — архив,
его execution_scope нельзя принимать за активную цель при `active_work: null`.
Каталог ответов вроде `tracker-responses/rscon7088` не является run_id; не ищи
`tracker-runs/rscon7088/run.json` и не подставляй другой run при неудаче поиска.
Игнорирование каталога инструментом glob не доказывает отсутствия файлов.

Для нового релизного `begin` `--intent` обязателен: «актуализируй» означает
`update-planning`, «покажи/прочитай» — `read-only`. Не перезапускай прежний run
из-за потери его номера. Явное решение аналитика о прекращении сбора остаётся
обязательным для abandon. Согласованные исключения ролей и владельцы сохраняются
для исходных задач; не переносись к другой фиче ради удобного execution_scope.

После доказанного слияния и `collaboration.py finish` применение считается
`applied`, `planning_application_allowed=false`, `actualization_complete=true`.
Исходный completion-status фиксирует этап сбора и не переписывается; текущее
состояние показывает `result-status`. Старые merged-записи также распознаются
как завершение. Повторное применение такого run запрещено, чтение отчёта доступно.
Новая актуализация того же релиза — отдельный запрос и новый run, а не отмена finish.

Просьба дать резюме не разрешает продолжать сбор, применять данные или менять
цель. После явной остановки выполняй только отдельно разрешённую диагностику.

Новый `begin` по умолчанию адаптивный и работает только с указанным `--scope-provider`.
`--adaptive` остаётся совместимым явным обозначением. `--legacy` предназначен
только для совместимости со старым протоколом, не для обычной актуализации.
Факты второго трекера не читаются, даже для заполнения пробелов. Только явная команда
сравнить два трекера разрешает `--compare-trackers`. В однотрекерном режиме
`reconcile` нормализует один источник, не ищет пары. Режим старого run не меняется.

## Область и соответствия

Явный запрос по релизу использует `core/tracker-release.md`, не выбор эпиков.
Во всех сценариях роль задачи определяется префиксом AN/BE/FE/QA, не специализацией
назначенного человека. `[FE][DevOps]` относится к FE; один `[DevOps]` — вне области.
Неподдерживаемые и неоднозначные префиксы показываются в `skipped`; по умолчанию
не создавай для них строки, не требуй владельца, историю или оценку. Явное
исключение аналитиком не разрешает переименовать роль ради прохождения проверки.

Перед новой актуализацией предложи три варианта: по номерам задач в фиче;
по эпикам; и по эпикам и по задачам. Явный выбор в исходной команде уже является
ответом, не спрашивай повторно. Ассоциация эпиков необязательна. В вариантах
с эпиками покажи сохранённые ключи выбранного трекера и спроси, верны ли они,
нужно ли дополнить или заменить; если их нет, попроси указать. Не подменяй
прямой вопрос о номерах эпиков дополнительным «вы укажете номера?». Не подменяй
отсутствующий список поиском по названию. Отсутствие эпиков не мешает варианту задач.

Необязательный источник: `features/<feature>/execution/tracker-scope.json`:

```json
{"schema_version": 1, "epics": {"jira": ["EXAMPLE-1", "EXAMPLE-2"], "sbertrek": []}}
```

`scope-preview` показывает `scope_choices`, `epics`, `identity_requests`.
Сохраняй выбранные эпики только после подтверждения, в допустимой рабочей ветке.
В single/adaptive `begin --scope-kind epic` принимает повторяемый `--scope-id`.
Для объединения используй `--scope-kind combined`: `--scope-id` для задач и
`--epic-id` для эпиков. Один запрос объединяет область без повторного учёта карточек.
Ограничения полноты/лимита сохраняются. Не интерпретируй отсутствие карточки
в эпике как удаление. В квартале сохраняй порядок фич и показывай их области отдельно.

Поиск идентичности не является сравнением фактов. Если известны только ключи
другого трекера, выполни `identity-lookup --source-provider <jira|sbertrek> --key KEY`
после готового config gate. Команда задаёт точную область чтения SberTrek:
для Jira ищется `issue_key`, для SberTrek читается его собственный ключ и `issue_key`.
Инструмент выбирается по актуальным возможностям MCP. Передай полный ответ и
реальный вызов через `--response-file` и `--call-file`; `selection` равен
`query_semantics`. Используй только проверенные `pairs`, не сроки, оценки или статусы
второго трекера. Нет пары/доступа или несколько соответствий означает неопределённость,
не удаление. Не ищи Jira-номер как собственный номер SberTrek и наоборот.
Не сравнивай по названию или совпадению номеров. Затем подтверди полученную область
выбранного провайдера. При применении сохрани обе колонки ключей у того же Task ID,
не создавай вторую задачу; повтори execution-preview после просмотра такого diff.

## Защита записи

До первой записи в аналитику, включая регистрацию новых BE/FE, QA, эпиков и ключей,
выполни `collaboration.py status`, разреши активную чужую сессию штатным порядком,
начни/возобнови работу над нужной фичей и переключись в execution-update.
Для записи зарегистрируй одну область актуализации через
`collaboration.py set-execution-scope` по `core/collaboration.md`: все подтверждённые
фичи, кварталы и текущий run. Затем обязателен
`trackerctl.py application-preflight --project-root PROJECT --feature FEATURE`.
Одна ветка обслуживает всю область; сдвиги производного Ганта соседних фич
не требуют их отдельных веток. Исходные реестры вне области не меняются.
Повторяй его после смены ветки/HEAD и перед применением. Успешный просмотр владельцев
не является разрешением записи. Не предлагай direct-commit в main, ручную ветку
в обход collaboration или удаление состояния как варианты решения блокировки.
Чтение и обсуждение допустимы без записи; текущий режим аналитики не меняется
ради разработки самой обвязки.

До предложения дат обязателен `execution-preview -> collect-history -> history-review`.
Это обязательная часть каждой актуализации, даже когда статусы совпали или даты
ранее подтверждены аналитиком. Приоритет подтверждений запрещает тихую перезапись,
а не сбор истории. Не предлагай завершить актуализацию «без правок» до этой проверки.
Приоритет: подтверждение аналитика (включая legacy), затем история назначений
и переходов; текущий статус даёт состояние, но не дату. Нельзя переходить
от отчёта карточек прямо к заполнению дат или генерации.
`history-collection-incomplete` требует продолжить сбор. Если история недоступна,
укажи `unavailable_history: {"KEY/BE": "причина"}` в манифесте. Даты остаются
неизвестными: не выводи их из статуса, created/updated, оценки или даты ответа.
История читается в выбранном трекере.

«Ответ не сохранён» не означает «история недоступна». Полный inline JSON сохраняй
дословно вне run, как и файл MCP; JSON-строка в обёртке поддерживается путями.
Если клиент показал обрезанный ответ, получи полный доступным read-only способом
из текущих capabilities, не восстанавливай события по памяти и не дописывай поля.
Текстовый ответ, который адаптер не умеет читать, — ограничение формата, а не
доказательство отсутствия истории в трекере. Сначала проверь доступные способы
получить полный ответ; `unavailable_history` оставляй для реальной недоступности
с конкретной причиной, а не для обхода сохранения файла или отсутствия реестра.
Не проси аналитика выбирать способ захвата MCP или технический порядок команд.

Правило относится и к состояниям/процентам, не только к датам. `created`/`todo`
не разрешает записать planned/0 при назначении разработчику. Для регистрации
нового владельца не придумывай нулевой прогресс. В релизном сценарии используй
подтверждённые предложения без записи реестра по `core/tracker-release.md`;
история проверяется до регистрации. Новые FE/BE-задачи изменяют
состав QA: прежнее утверждение «все прошли тестирование» нужно пересмотреть
для расширенного состава, не копировать в новую сводку.
Просьба показать FE/BE/QA-оценки колонками относится к таблице сравнения в чате.
Она не разрешает менять схему execution/tasks.md: сохраняй `Estimate (дн)`.

## Удалённые задачи и единая QA

`missing_task_candidates` — кандидаты на проверку, не доказательство удаления.
До сверки `verify-missing-tasks` блокирует пропуск неполученных исходных ключей.
Для повторного чтения выполни возвращённый `retry-missing` в том же run; старые
ответы сохраняются. При подтверждённом удалении используй `confirm-absence`.
Отсутствие в выдаче, отказ в доступе, лимит и ошибка сервера не разрешают удаление.
Проверь точный ключ read-only инструментом того же трекера, сохрани полный ответ
и вызов. Ответ «не существует или нет доступа» требует подтверждения аналитика.
Не отменяй run самовольно и не используй `--analyst-confirmed` без ответа пользователя.

Для однотрекерного run с областью `tasks`, до `reconcile`, после явного
подтверждения аналитиком отсутствия используй:

```text
trackerctl.py confirm-absence --run-id RUN --key KEY --response-file FULL_RESPONSE --call-file ACTUAL_CALL --decision-source CONFIRMATION --analyst-confirmed
```

Команда привязывает ключ к исходной области, контрольной сумме ответа и реальному
вызову, сохраняет подтверждение и возвращает чтение оставшихся ключей в том же run.
Она не трактует произвольную ошибку как удаление: семантику отсутствия подтверждает
аналитик. Для epic отсутствие среди участников не доказывает удаления карточки;
этот случай не поддерживается командой. Старые/завершённые run не переписываются.
`delete-current-execution` в предпросмотре — предложение удаления, не запись файлов.

Подтверждённо удалённые задачи включи в diff удаления текущих execution-записей,
отдельных карточек и ссылок actualization. После просмотра и команды применения
удали их из текущего исполнения и перегенерируй actual-only. Запиши ключ,
доказательство и решение в execution-контекст. Локальные QA/AN без внешнего ключа,
архивы и утверждённые планы не удаляются. Отмена задачи не равна удалению.
Неполученные карточки не разрешают объявлять охват QA полным.

По умолчанию на фичу одна текущая QA-работа. При подтверждённом разбиении по
релизам используются непересекающиеся группы из `core/tracker-release.md`;
их нельзя объединять при последующей актуализации фичи или квартала.
`feature_qa_proposals` содержит сумму
заполненных QA-оценок всех полученных карточек фичи, каждую карточку учитывает
один раз. Отсутствующие оценки перечислены отдельно, это не нули. При неполной
выборке сумма не является полной оценкой фичи. Не прибавляй прежнюю локальную
QA-оценку к новой сумме. Обнови существующую QA или создай одну, если её нет.
Несколько legacy QA сведи в одну через просмотренный diff, сохрани источники,
ссылки и подтверждения. Конфликты дат/исполнителей покажи аналитику; не складывай
проценты и не изобретай общий фактический интервал. QA охватывает все неотменённые
FE/BE-работы независимо от наличия QA-оценок.

## Сбор

Для новых сеансов выполни `config-status` и его stop gate, уточни провайдер и
область, затем используй обычный `begin` с `--adaptive`. Существующий run не
заменяй: без `collection_mode: adaptive` он продолжает прежний протокол.

При `collect-tracker-data` основной агент изучает описания доступных MCP-инструментов
этой установки и выбирает чтение, реализующее `selection`. Названия инструментов
и аргументов не зашиты. Нельзя расширять область, фильтровать завершённые задачи,
менять провайдера без решения аналитика или выполнять запись в трекер.
Не спрашивай имя инструмента у аналитика: это задача агента. Если возможности
нет, сообщи ограничение, не подменяй запрос старой выгрузкой.

Сразу запрашивай общую и все AN/BE/FE/QA-оценки, используя актуальную схему полей
установки. Незапрошенное поле не означает отсутствующей оценки. Не жди ошибки
генератора для дополнительного сбора; не переноси поздние ответы в реестр в обход
проверенного результата. Старые утверждения «во втором трекере 404» не расширяй
на новые карточки и не выдавай за проверку текущего сеанса.

Сохрани полный ответ MCP вне run. Передай его в `ingest` вместе с `--call-file`:

```json
{
  "provider": "jira",
  "tool": "имя из текущего описания MCP",
  "arguments": {},
  "operation": "read-only",
  "capability_source": "ссылка на изученное описание инструмента",
  "captured_at": "2026-09-16T09:00:00+03:00",
  "selection": "точное значение selection.query_semantics"
}
```

Записывай только реально выполненный вызов. Не сохраняй токены, cookies и
заголовки авторизации. Если они передаются аргументами, требуется безопасный
коннектор; не записывай такой вызов. Проверки ключей, склейки по Объект Jira,
конфликтов и полных ответов остаются. Неизвестная структура карточек блокируется,
а не пересказывается моделью. Автоматическое объединение страниц карточек в этой
версии не поддерживается: ограничения полноты остаются видимыми.

После `reconcile` и дословного `result-status` выполни `execution-preview`
(для релиза — `release-preview` с решениями о новых владельцах).
При блокировке разбирай владельцев. При `collect-history` читай историю всех
FE/BE-задач выбранных фич, не только карточек с оценкой QA. Исключение: для релиза
обязательна история только его участников; остальные карточки читаются для
разбиения QA без актуализации их строк по `core/tracker-release.md`. Используй доступное
чтение истории, включая отдельную карточку, если этого требует инструмент.
Это тот же run; чтение не делегируется. Старый запрет на per-key вызовы здесь
не действует. Провайдера истории согласуй, не выбирай замену молча.

## Манифест истории

Агент готовит внешний JSON и вызывает возвращённую команду:

```text
python3 scripts/trackerctl.py history-review --run-id RUN --project-root PROJECT --manifest FILE
```

Манифест содержит ссылки на полные ответы, SHA256, реальные вызовы и JSON-пути,
а не переписанную моделью историю. Роли и словарь статусов должны быть подтверждены
аналитиком; используй существующие решения, иначе задай содержательный вопрос.
Роль человека независима от роли карточки: AN на FE-задаче остаётся AN.
Не переклассифицируй аналитика в разработчика из-за префикса задачи. Совмещение
ролей требует отдельного подтверждения; неизвестная роль остаётся неизвестной.

```json
{
  "schema_version": 1,
  "analyst_confirmed": true,
  "decision_source": "ссылка на подтверждение ролей и статусов",
  "feature": "example",
  "provider": "jira",
  "participants": {"developer-id": "FE", "tester-id": "QA"},
  "status_rules": {"not_started": ["todo"], "development_review": ["review"], "qa_completed": ["ready-uat", "done"], "cancelled": ["cancelled"]},
  "responses": [{
    "provider": "jira", "key": "EXAMPLE-1", "role": "FE",
    "response_file": "/absolute/path/full-response.json",
    "sha256": "SHA256 полного файла",
    "status_aliases": {"Done": "done"},
    "call": {
      "provider": "jira", "tool": "актуальный инструмент истории", "arguments": {},
      "operation": "read-only", "capability_source": "описание MCP",
      "captured_at": "2026-09-16T09:00:00+03:00"
    }
  }]
}
```

Вместо `feature` допускается `quarter`. Один манифест использует один провайдер:
ID людей и статусов разных систем не смешиваются. Для подтверждённых dirty-реестров
передай `reviewed_registries` (путь -> SHA256) и `expected_head` из предпросмотра.

Jira по умолчанию: `/key`, `/assignee/key`, `/status/name`, `/changelogs`;
в событии `/created`, `/items`; в изменении `/field`, `/from_id`, `/to_id`.
Для другой структуры response содержит `mapping` с JSON Pointer к исходным
данным: `events`, `at`, `field`, `from`, `to`. `changes` нужен только для вложенного
массива изменений; без него каждое событие само является изменением.
`assignment_field` и `status_field` задают разные точные значения типа изменения.
`key` указывает ключ в ответе; если ответ его не содержит, `request_key` указывает
ключ в **реальных** `call.arguments` (не в дописанных моделью аргументах).
Указатель может проходить через JSON-строку MCP. Модель выбирает пути, но значения
извлекает программа. `status_aliases` сопоставляет исходные значения с
подтверждёнными кодами; нельзя придумывать ID участников или статусов.

### Раздельные источники и текстовая история

Сохраняй полный исходный ответ до извлечения данных, включая описания и прочие
поля, не участвующие в расчёте. Не пересобирай его под `mapping`, не заменяй
объекты строками и не добавляй `total`, `start`, даты или параметры вызова.
SHA256 фиксирует байты файла, но сам по себе не доказывает, что файл был ответом
MCP. Источник должен быть настоящим файлом MCP либо дословным захватом ответа.

Текущую карточку разрешено читать отдельно от истории. В элемент `responses`
добавь `snapshot` с собственными `response_file`, `sha256`, `call` и `mapping`
(`key`, `assignee`, `status`). Это тот же выбранный провайдер и та же задача.
При раздельных источниках снимок не дописывается в историю; время наблюдения
берётся из вызова карточки. События позднее снимка требуют свежую карточку.
Если снимок уже есть в полном сохранённом ответе, используй его с реальным
вызовом и путями к выбранной карточке, а не читай повторно без необходимости.

Если MCP вернул JSON с человекочитаемой историей, например `{"output": "History ..."}`,
сохрани JSON целиком; используй `mapping: {"request_key": "/key", "text": "/output"}`,
если именно `/key` был в реальном вызове. Для чистого текста без JSON-оболочки
сохрани текст дословно, укажи `format: "text"` и `mapping.text: ""`.
Другие пути выбираются по настоящему ответу. Не превращай текст в выдуманный
JSON-массив. Без явного описания формата этот вариант только сохраняет свидетельство.

Если формат изменился или regex неудобен, используй `mapping.text_extraction`
по `core/tracker-history-extraction.md`: LLM размечает источник, программа извлекает
значения по проверяемым позициям и цитатам. Не проси аналитика выбирать regex или
вручную подтверждать даты ради обхода технической ошибки. Смена формы MCP-ответа
не требует правки обвязки; смысловые ограничения остаются явными.

Альтернативно, если текст содержит датированные записи, добавь в `mapping` объект `text_parser`:
`schema_version: 1`, `record_start_pattern`, `record_pattern`, `header_pattern`
и `value_format` (`json`, `python-literal` или `text`). Это описание фактического
формата ответа, не привязка к имени MCP-инструмента. Пример для одного наблюдаемого
формата: `templates/tracker-history-text-mapping.json`; проверь его соответствие
текущему ответу, путям идентификаторов и кодов статуса до использования.
`record_pattern` должен целиком распознавать каждую запись и иметь именованные
группы `at`, `field`, `before`, `after`. Нераспознанные записи запрещено пропускать.
Программа извлекает значения из неизменного исходника; `python-literal` использует
безопасный разбор литералов, не выполнение кода. Внутренние пути значений:
`/before`, `/after`; вложенные идентификаторы задаются через `assignment_from/to`,
а статусы через `status_from/to`. Поля выбираются через `assignment_field` и
`status_field`, отдельно от отображаемых подписей.

Заголовок может доказать полноту только при распознанных `count`, `page`, `has_next`:
число записей совпадает с `count`, страница равна нулю, продолжения нет (`False`).
Это проверенные данные ответа, а не утверждение LLM. Для иных форматов полнота
остаётся недоказанной; не подменяй заголовок или исходные метаданные.
Голый `CREATE` с автором записи не является событием назначения исполнителя.
Не выводи начало разработки из автора, даты создания или текущего исполнителя.
Передача разработчик → QA может доказать окончание при неизвестном начале.
Роли участников в `participants` — AN/BE/FE/QA, не ресурс QA1/QA2;
они не должны противоречить роли или ресурсу участника в конфигурации.
Подтверждённая роль задачи определяется отдельно, по префиксу или решению аналитика.
В `status_rules.qa_completed` допустимы только подтверждённые состояния после QA:
«Готов к тестированию» и «Тестирование» не означают завершения QA. Проверяй реальные
коды и `status_aliases`, не навязывай инструменту фиксированный словарь статусов.

Текстовая история без описания разбора или событие жизненного цикла без даты возвращают
`pending_history_dates` и `next_action: collect-history`. Самостоятельно проверь
текущие capabilities MCP: доступен ли полный ответ, экспорт или другой способ
получить историю с датами. Не выдумывай инструмент, параметры или API и не
переключай провайдера. Новый настоящий ответ сохраняй отдельным файлом и
передавай в том же run. Если доступного источника дат нет, зафиксируй
`unavailable_history_dates: {"KEY/BE": "что проверено и какое ограничение обнаружено"}`.
Тогда разрешено обсуждение состояния по снимку и неизвестных сроков, но не
подстановка дат из статуса, порядка строк или времени захвата. Не называй
историю недоступной лишь потому, что её текст не подошёл парсеру. Если часть
переходов не датирована, датированные переходы не используются отдельно:
неизвестное положение возврата может отменять прежнее завершение.

Ошибка JSON содержит путь, строку и столбец. Исправляй манифест/пути извлечения
отдельно; исходный ответ нельзя «починить». Повторно полученный настоящий ответ
имеет новый файл и реальный вызов. Неполнота истории и полнота состава релиза
проверяются независимо: получение истории не доказывает состав релиза.

Необязательные `mapping.total` и `mapping.start` указывают метаданные пагинации.
Возможен также `mapping.has_next` с булевым признаком продолжения, с началом
из ответа или реального вызова (`request_start`, `request_cursor`), как описано
в `core/tracker-release.md`. Полнота требует доказанного покрытия всего списка:
start=0 и total=число событий либо доказанное начало и отсутствие продолжения.
Один флаг последней страницы без начала/общего количества недостаточен. Иначе сохраняется
`history-completeness-not-proven`: доступны состояния и границы, но не доказанные
точные даты. Не дописывай в ответ метаданные, события или фиктивные ID.
ID нормализованного события — SHA256 исходного события, не серверный ID.
Разрыв цепочки назначений/статусов или несовпадение со снимком отражаются
в limitations и evidence; точные даты при таком разрыве не выдаются. Повторная
передача тому же тестировщику не переносит первое завершение разработки.
Подтверждённый возврат продолжает QA, не открывая разработку заново. Повторный
выход из посттестового состояния отменяет завершение QA до нового завершения.
Неоднозначный порядок/одновременные противоречивые события блокируют расчёт.
Никогда не удаляй события и не меняй снимок/исходный статус ради валидатора:
ответы истории и отдельного снимка закрепляются по checksum до разбора,
при первом просмотре, даже неуспешном.
Новый настоящий ответ сохраняется новым файлом с новым реальным вызовом;
решения аналитика существуют отдельно от исходной истории.
При раздельных страницах покажи
ограничение: ручное слияние и выдача части за полную историю запрещены.

## Сверка и применение

### Перенос подтверждённых дат QA

Сначала найди исходный ответ аналитика в текущем разговоре/сохранённом протоколе.
Не задавай повторный вопрос о уже явно подтверждённом точном интервале. Но общее
«принять сроки» при показанных границах не превращает их в точные даты.
В манифест `history-review` добавь `qa_confirmations`, например:

```json
{
  "qa_confirmations": [{
    "feature": "example", "task_id": "QA-EXAMPLE", "analyst_confirmed": true,
    "kind": "exact-interval",
    "fields": {"Actual Start": "2026-07-31", "Actual Finish": "2026-08-24"},
    "source": {"file": "/absolute/path/analyst-answer.txt", "sha256": "SHA256", "quote": "дословный ответ аналитика"}
  }]
}
```

Это пример формата, не подтверждение этих дат. Файл содержит исходный ответ,
а не придуманный моделью пересказ. `exact-interval` требует оба Actual-поля;
`exact-start`/`exact-finish` — одно соответствующее поле; `completed-by` — только
`Completed By`. Источник, цитата и checksum проверяются. Значение `kind` должно
соответствовать смыслу реального ответа; нельзя обозначать границу как точный
интервал. Подтверждение может быть старым: новая неполная история его не отменяет.
Для явного решения ничего не менять используй `kind: keep-current`, `fields: {}`
с тем же проверяемым источником подтверждения.
Для принятого набора полей QA используй `kind: reviewed-fields`: `fields` содержит
только явно принятые Actual Start, Actual Finish, Completed By, Status, Progress %,
Estimate строками в формате реестра. Проверяются все шесть полей, остальные
сохраняются. Этот формат не разрешает превращать границы в точные даты или
переписывать оценку без отдельного принятия показанной суммы.

`qa_application` возвращает `fields_to_write` и полное ожидаемое состояние дат.
После просмотра/разрешения применения перенеси эти поля в указанную QA-строку,
сохрани основание в контексте и выполни:

```text
trackerctl.py qa-application-check --project-root PROJECT --review-file SAVED_HISTORY_REVIEW
```

Проверка не пишет файлы. Пустой `Actual Finish` при принятом точном интервале
блокирует успешное завершение, даже если `Completed By` заполнен. При принятой
границе проверка запрещает самовольно менять Actual-поля. Проверяется исходный
проект, HEAD и неизменность сохранённого отчёта. Затем обязательны actual-only,
проверка конкретной QA-полосы и Confluence. Для `expected_rendering: actual-interval`
ожидаются starts/ends, не happens-at; при границе маркер не означает однодневную
работу. Не путай серый PLAN с TASK и называй точные даты проверенного файла,
не «24 или 27». Команда не подтверждает сама визуальный результат.
Отсутствие `qa_confirmations` не освобождает от проверки: оформи уже полученное
подтверждение и повтори history-review. Не объявляй применение завершённым и
не сохраняй результат как проверенный при непройденном QA-гейте.

### Общая сверка

`comparison.required_qa_application_checks` обязателен для каждой фичи, даже
если обычные задачи не изменились. Перед заявлением «правок не требуется»
отдельно сопоставь сохранённую QA с рассчитанным началом, завершением, статусом,
процентом и суммой оценки. `start_change_required` запрещает такое заявление
без явного решения оставить прежнее начало. Совпадение BE/FE не закрывает QA.
После решения аналитика примени разрешённые поля к единственной QA-строке,
заново прочитай её и проверь Гант после actual-only. В execution-контексте
укажи по QA «изменено», «совпадает», «оставлено по решению» или «заблокировано»
с прежними/новыми значениями и причиной. Не заявляй QA применённой только
по обновлению контекста. Выбор «только сроки» не меняет её статус/процент/оценку;
выбор «оставить текущее» сохраняет QA тоже. Неприменимые поля не заполняются
догадками. Отдельное подтверждение даты QA имеет приоритет до пересмотра.

После выбора сроков разработки пересчитай начало общей QA как минимум принятых
`Actual Finish` неотменённых BE/FE-задач фичи, включая сохранённые подтверждённые
даты. Это начало тестирования после первой законченной разработки, не после
закрытия последней карточки. Не оставляй QA без начала только потому, что новая
история неполная, если дата разработки уже принята. Не используй плановый конец,
`Completed By` или SP как точную дату. Противоречие отдельному подтверждению
начала QA и неизвестные окончания уже завершённых работ вынеси в сверку.

После истории покажи `comparison.table` целиком: сохранённые даты, статусы,
проценты и основания рядом с результатами истории. Даже ранее подтверждённые
факты входят в сравнение. Пустая точная дата означает неизвестность, а не
разрешение подставить `started_by`/`completed_by`. Отсутствие пагинации или
назначения в снимке — существенное ограничение доказательств, не «косметика».

Используй четыре варианта из `comparison.choices` для показанной выборки:
1. Принять сроки выбранного трекера для всех задач (статусы и проценты сохранить).
2. Принять сроки и статусы выбранного трекера для всех задач.
3. Оставить текущие сроки и статусы для всех задач.
4. Свой вариант по задачам и полям.

Принять сроки означает принять только доказанные точные даты; неизвестные поля
не очищаются и границы не становятся точными. Для принятия границы как точной
даты требуется отдельное явное решение аналитика с перечислением таких дат.
Если решение меняет прежние подтверждения, перечисли их явно и сохрани новое
решение вместе с прежним источником. Эти варианты не разрешают менять оценку,
исполнителя, состав задач или удалять их без просмотра соответствующих правок.
Ответ запиши с идентификатором/хешем проверенного отчёта и областью решения в
execution-контекст при применении. Исходная команда актуализации не является
подтверждением, а подтверждение ролей не является согласием изменить даты.

Показывай реальные `status_rules` из отчёта, не придумывай второе противоречащее
пояснение. Используй уже согласованный словарь: названия/коды после тестирования
относятся к завершению QA, не к началу. Не переопределяй его молча при новой фиче.

Поля истории можно настраивать раздельно: `status_from`/`status_to` для статусов,
`assignment_from`/`assignment_to` для назначений. Они перекрывают старые `from`/`to`.
Например, статусы `/from_string`/`/to_string`, назначения `/from_id`/`/to_id`.
Снимок и события статусов должны иметь согласованные значения через `status_aliases`;
ID исполнителей сохраняются. Не заменяй ID именами для обхода проверки статусов.

`history-review` проверяет run, владельцев, роли, состав FE/BE из реестров,
SHA256 ответов и неизменность HEAD/источников. Результат со сведениями о вызовах
сохраняется в `tracker-runs/RUN/history/`, без сырых ответов и правок проекта.
Идентичный повтор возвращает тот же файл.

Покажи фичи по приоритетам: новые даты и проценты, основания, ограничения,
рядом прежние факты и подтверждения. Расчёт не отменяет решения аналитика и
не разрешает запись. После поправок и команды применения повтори history-review
для проверки актуальности источников, затем выполни `core/tracker-actualization.md`:
обнови источники в допустимой ветке и режиме, запусти `--actual-only`, проверь
неизменность планов и Confluence. Применение выполняет агент после просмотра.
