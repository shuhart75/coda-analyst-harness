# Профиль компактной спецификации функциональности

## Назначение

Профиль определяет формат единственного авторского документа
`features/<feature>/requirements.md`. Документ должен читаться как связное описание
изменения и одновременно быть достаточным входом для разработческой SDD, которая
сверит его с кодом и создаст собственные технические спецификации.

Аналитический `requirements.md` не является техническим `spec.md`. Он фиксирует
предметный результат, наблюдаемое поведение, ограничения и примеры. Классы, файлы,
таблицы и порядок реализации попадают в него только как подтверждённая часть
контракта, а не как предположение аналитика.

## Основные правила

- Корневой `requirements.md` является единственным авторским документом требований.
- Обвязка не создаёт срезы, отдельные пакеты клиентской и серверной частей или
  предварительные задачи разработки.
- Требования пишутся по-русски. Английский сохраняется только в точном коде,
  путях, идентификаторах, форматах, названиях продуктов и необходимых терминах.
- Документ должен быть компактным: неприменимые разделы не добавляются, одинаковые
  сведения не повторяются в паспортах, таблицах и сценариях.
- Устойчивые `REQ-*` обеспечивают трассировку, но не превращают документ в реестр
  атомарных строк без связного объяснения.
- Каждая формулировка проходит правила контролируемого русского языка и проверку
  изолированного читателя из `core/requirements-wording.md`.

## Обязательная структура

Документ содержит только пять обязательных разделов:

1. `Назначение` — проблема, пользователи, причина изменения и законченный результат.
2. `Границы` — что входит и что явно не входит.
3. `Требования` — правила в естественном порядке процесса и вложенные сценарии.
4. `Влияние на соседние функциональности` — включённые доработки либо явное
   подтверждение отсутствия влияний.
5. `Источники и открытые вопросы` — основания решений, предположения и вопросы.

При необходимости между границами и требованиями добавляются:

- `Как будет работать` — связное описание процесса и PlantUML;
- `Данные и состояния` — только значимые предметные объекты и переходы;
- `Ошибки и особые случаи` — общие исключения, не относящиеся к одному требованию;
- другие короткие разделы, действительно улучшающие понимание.

Не нужно создавать раздел только ради отметки `неприменимо`.

Если требований много, после вводного заголовка `Требования` допускаются главы
второго уровня по этапам пользовательского или системного процесса. Область
требований продолжается до раздела `Влияние на соседние функциональности`.
Заголовки глав должны описывать предметный этап, например `Список Реестра` или
`История согласования`; названия `Дополнительные требования` и `Прочее` не
используются. Нормативные `REQ-*` остаются заголовками третьего уровня внутри этой
области.

## Требование

Каждое нормативное правило оформляется заголовком третьего уровня:

```markdown
### REQ-REG-001. Отображение действующих записей

Система должна показывать в реестре только действующие записи, доступные
пользователю с учётом его полномочий.
```

Правило:

- имеет уникальный устойчивый `REQ-*`;
- содержит человекочитаемый заголовок;
- использует `должен`, `должна`, `должно`, `должны` либо явный запрет;
- описывает наблюдаемый результат, а не способ написания кода;
- допускает отдельное выполнение, откладывание и проверку;
- не смешивает текущее и требуемое поведение;
- не использует оценочные слова без измеримого смысла.

Если несколько правил могут получить разные результаты реализации, им нужны
отдельные `REQ-*`. Связный поясняющий текст без нормативного смысла допускается
между требованиями.

## Сценарии

У каждого `REQ-*` есть хотя бы один вложенный проверяемый сценарий:

```markdown
#### Сценарий: пользователь видит доступные записи

**Когда** пользователь открывает реестр.

**Тогда** система показывает только доступные ему действующие записи.
```

Сценарий использует русские ключевые слова `Когда`, `Тогда` и при необходимости
`И`. Сценарий конкретизирует требование, но не вводит новое правило. Несколько
сценариев добавляются только для действительно разных основных, альтернативных
или ошибочных ветвей.

Отдельные идентификаторы сценариев не обязательны: связь задаётся вложенностью под
соответствующий `REQ-*`. Если проекту нужен устойчивый идентификатор проверки, его
можно указать после слова `Сценарий`, не создавая отдельной таблицы трассировки.

## Диаграммы

PlantUML используется только когда схема сокращает текст или выявляет пробелы:

- диаграмма деятельности — для общего процесса;
- диаграмма состояний — для жизненного цикла;
- диаграмма последовательности — для значимого взаимодействия систем.

Диаграмма не заменяет нормативный текст и не создаёт самостоятельных требований.
Подписи пишутся по-русски, точные имена полей, методов и статусов не переводятся.

## Влияния и завершение перехода

Раздел `Влияние на соседние функциональности` обязателен. Каждая необходимая
доработка соседней функциональности входит в объём текущего изменения и связывается
с соответствующими `REQ-*`.

При замене поведения здесь же или в соответствующем требовании перечисляются
удаляемые либо заменяемые поля, статусы, маршруты, подписи, проверки, прототипы и
прежние правила. Необъяснённый остаток блокирует передачу.

## Трассировка

Полный текст требования не дублируется в отдельной сводной таблице. Базовая цепочка
строится по устойчивым идентификаторам:

```text
REQ-* -> техническое изменение локальной SDD
      -> returns/tasks.md
      -> отчёт задачи
      -> returns/summary.md
      -> решение аналитика по требованиям, плану и исходному состоянию
```

Источники решения указываются компактно в последнем разделе или непосредственно
рядом с требованием, если без этого правило трудно проверить.

## Переход со старых форматов

Прежние опубликованные редакции неизменяемы и остаются читаемой историей. Перед
следующей передачей живой `requirements.md` переводится в компактный профиль.

При явно порученной одноразовой миграции ISO-подобный документ можно сохранить
рядом как `requirements_iso.md`. Он не редактируется, не становится вторым
источником требований и не передаётся разработчикам.

## Аудит перед передачей

Перед публикацией выполняется отдельный трёхуровневый аудит по
`core/requirements-audit.md`. Формальная проверка файла не заменяет смысловой аудит.
Редакция обмена создаётся только после устранения блокирующих замечаний, итогового
полного прохода и явного подтверждения аналитика.
