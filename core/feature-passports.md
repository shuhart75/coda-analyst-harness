# Человекочитаемый паспорт фичи

Применяется к проектам с `delivery-index.json`. Физический корень
`features/<feature_id>/` описывает долгоживущую возможность продукта. Квартал
остаётся основной рабочей областью; паспорт собирает понимание фичи между поставками.

## Состав

- `README.md`: русское название, назначение, подтверждённая доступность в ПРОМ,
  текущие работы, ближайшая поставка, ограничения, ссылки и история обновлений.
- `requirements.md`: связное сводное описание фичи целиком с раздельными разделами
  действующего поведения, согласованных изменений и неподтверждённого объёма.
  Примеры описывают конкретное событие и наблюдаемый результат.
- `backlog.md`: только известные идеи и остаток вне согласованной поставки,
  с основаниями. Отсутствие сведений не означает отсутствие дальнейшей работы.
- `deliveries.md`: производный список поставок из реестра, без бизнес-выводов.

## Источники и границы

Текущее внедрённое поведение подтверждается baseline и решениями о внедрении.
Будущий объём берётся из требований соответствующей поставки с сохранением
состояния согласования. Черновик не становится утверждённым при пересказе.
Завершение задач, дата в календаре и наличие файла не доказывают внедрение.
Установленную, но выключенную возможность описывай отдельно от доступной пользователям.

Сводные требования — авторское объяснение с точными ссылками на источники,
а не ещё один независимый контракт для передачи. Полные правила, устойчивые
REQ-идентификаторы, критерии приёмки, аудит, редакции и возвраты принадлежат поставке.
При расхождении останавливай перенос спорного утверждения и фиксируй пробел;
не выбирай автоматически новейший текст и не повторяй нормативный документ целиком.
Не придумывай требования для кандидата, у которого согласована только идея.

Исторические операционные псевдонимы не доказывают наличие разных бизнес-фич.
Показывай известную связь между карточками, не объединяй их реестры молча.
Служебный контейнер исполнения явно обозначай как служебный.

## Обновление

При согласовании или изменении поставки обновляй её паспорт в той же рабочей ветке.
После актуализации задач отражай проверенный срез исполнения; после подтверждения
релиза согласуй паспорт с обновлённым baseline. Сохранение паспорта входит в область
владеющей поставки; межфичевая редакционная миграция требует явного поручения аналитика.
В режиме release-finalization разрешено сводить паспорта по уже принятым источникам,
не меняя исходные требования и факты задач.

В README указывай дату содержательного обновления документа, что изменилось,
основание и квартал/поставку/релиз. Различай дату документа, дату снимка задач
и дату внедрения. Не используй mtime, дату миграционного коммита или сегодняшнюю
дату как дату продуктового события. Неизвестный релиз и дата остаются неизвестными.
Существующую историю сохраняй, новые события добавляй с источником.

## Инструменты и проверка

`layoutctl.py` обновляет только производный список `deliveries.md`, создаёт
первичную заготовку README и не перезаписывает авторский паспорт.
Стандартные `feature_root`, `project_path` и `artifact_glob` сохраняют прежнее
значение путей для исторических проверок и передачи: корень поставки.
Паспорт читается по явному физическому пути, не через legacy-resolver.
Его нельзя передавать через requirements-exchange вместо контракта поставки.

Проверь ссылки, русский текст, согласованность фактов с источниками и отсутствие
изменений исходного исполнения, утверждённых планов и истории обмена.
Автоматическая проверка структуры не подтверждает бизнес-содержание.
