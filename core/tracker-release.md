# Актуализация по релизу

Это вариант адаптивной актуализации, а не сравнение трекеров и не публикация релиза.
Работай только с указанным трекером; эпики необязательны. Сохраняй порядок фич,
утверждённые PLAN, исторические подтверждения и обычные stop gates.

## Область

После config-status используй `begin --scope-kind release --scope-provider PROVIDER
--scope-id RELEASE --label LABEL --scope-source SOURCE --intent update-planning`.
Один запрос задаёт один релиз. Уточни проект/ID, если имя неоднозначно.
Jira использует семантику `fixVersion`; для SberTrek `release-members:"..."`
является описанием отбора, НЕ TQL и НЕ именем API. Подбери read-only инструмент
и способ отбора по возможностям текущей установки. Членство может быть полем,
связью или результатом запроса участников релиза. Не угадывай TQL-поле по слову
«релиз» и не закрепляй имя MCP-инструмента в сценарии. Запиши фактический вызов,
а в `selection` — возвращённую семантику. Сохраняй полный исходный ответ без
дописанных полей; пропуски и ограничения выдачи не означают полный состав.
Не фильтруй завершённые задачи. Роли вне AN/BE/FE/QA пропускаются после чтения
и показываются отдельно, в любом сценарии, не только релизном.

После reconcile/result-status выполни `release-preview --run-id RUN --project-root PROJECT`.
Для каждого участника сначала используй точные ключи реестров, затем привязанные
эпики. Название может дать предложение владельца, но не автоматическую запись.
Неоднозначную/неустановленную принадлежность уточни у аналитика. Покажи предложения
одной таблицей; для нового владельца сохрани решение отдельно от реестра.
Используй `ownership_table`: показывай название стори/задачи, отдельные ключи
SberTrek и Jira, роль, предложенную фичу и основание связи. Один ключ другого
трекера не является «владельцем» задачи. Нельзя просить выбрать фичу по одним
номерам, включая `proposed_registrations`: поле `summary` обязательно показывается
аналитику. Если названия недостаточно, добавь краткое описание смысла стори
из реального ответа; при отсутствии описания дочитай его по текущим MCP-capabilities,
не придумывай содержание. Предположения по названию явно отделяй от доказанной связи.
Проверяй историю до записи новых строк; не записывай planned/0 из todo.
Повтори preview; дубли владения и несовпадающий префикс требуют исправления.
Межфичевые записи выполняй последовательно в допустимых collaboration-сессиях,
не объявляй разрешение одной ветки разрешением для всех владельцев.

### Доказательства членства

Если карточки сами содержат релиз, прежний ingest остаётся достаточным.
Иначе в файл фактического вызова карточек добавь отдельное описание
`release_membership: {"schema_version": 1, "sources": [...]}`. Это служебный
манифест, а НЕ правка ответа MCP. Каждый источник содержит `response_file`,
`sha256`, реальный `call`, `basis` и `mapping`. Инструмент, аргументы, названия
полей и вложенность выбираются по текущим capabilities, не по примеру ниже.

- `basis: selected-query`: полный ответ запроса именно участников этого релиза;
  `call.selection` совпадает с семантикой отбора текущего шага. `mapping.records`
  указывает RFC 6901 JSON-путём на массив, `member_key` — на ключ внутри элемента.
- `basis: links`: ответ со связями. Дополнительно нужны пути `relation`,
  `release_key` внутри связи или `release_root` в корне ответа и реальное
  `relation_value`, означающее членство. Не принимай произвольную связь за релиз.
- Полнота: пути `total` и `start` в ответе, если сервер возвращает эти
  сведения. Поддерживается также `has_next`: булев признак следующей страницы.
  Начало можно связать с реальным вызовом через `request_start` (путь в arguments)
  либо `request_cursor` (null/пустая строка для первой страницы по контракту API).
  При `has_next: false` и `total`, равном длине полного массива, offset не требуется.
  Один `has_next: false` без доказанного начала/общего количества недостаточен:
  это может быть только последняя страница. Не придумывай offset или cursor.
  Страницы сохраняются отдельными источниками с фактическими вызовами;
  проверяются непрерывное покрытие и уникальность ключей. Не придумывай total/start.
  Для links пагинация относится ко ВСЕМ связям до фильтрации по типу: четыре
  связи, из которых три релизные, не означают расхождение total с тремя задачами.
  Без доказательства полноты сбор и обсуждение продолжаются с ограничением,
  применение полного состава и разбиения QA остаётся заблокированным.
- Если API по контракту возвращает весь список без пагинации, не требуй
  выдуманных числовых полей. Для единственного ответа допустим
  `unpaginated_contract: {response_file, sha256, quote}`: полный JSON описания
  capabilities и дословный фрагмент о полной выдаче без пагинации; путь совпадает
  с `call.capability_source`. Агент проверяет смысл контракта, программа — источник
  и неизменность. Наличие поля «список» само по себе не доказывает полноту.

Названия путей относятся только к внутреннему манифесту. Например, реальный
ответ может хранить массив по `/result/edges`, ключ задачи по `/target/code`,
тип связи по `/kind`, релиз по `/source/code`. При другом формате меняется
описание путей, а не серверный ответ и не код обвязки. Для текстового JSON внутри
обёртки пути поддерживают декодирование строки. Набор доказанных ключей обязан
совпасть с набором собранных карточек, включая пропущенные по ролям.
Противоречащие заполненные поля релиза требуют разбора, а не тихой подмены.

Если подтверждение полноты получено после reconcile, не переписывай старый ответ
или run. Передай новое описание источников через `release-preview --membership FILE`
и тот же объект как `release_membership` в history-review. Проверка сверит ключи
со всеми исходными карточками, включая пропущенные по ролям, и сохранит основания
в отдельном review. Снимается только доказанное ограничение полноты членства;
другие ограничения сохраняются. Ответ аналитика не превращается в метаданные сервера:
для него используется отдельное основание полноты, описанное ниже.
Если обнаружены дополнительные участники, изменение состава требует отдельного
разбора; не выдавай прежнюю выборку за полную.

### Подтверждение полного состава аналитиком

Если источник не доказывает полноту, покажи аналитику весь полученный состав,
включая задачи пропущенных ролей, и задай один вопрос: является ли этот список
полным составом конкретного релиза в выбранном трекере. Не требуй повторного
подтверждения уже явно согласованного полного списка. Согласование оценок, QA
или разрешение продолжить сами по себе не подтверждают полноту состава.

В новый манифест `release_membership` рядом с неизменными `sources` добавь:

```json
{
"analyst_confirmation": {
  "run_id": "<current-run>",
  "provider": "sbertrek",
  "release": "<release-key>",
  "member_keys": ["<all-collected-keys>"],
  "complete": true,
  "analyst_confirmed": true,
  "source": {"file": "<dialogue-file>", "sha256": "<sha256>", "quote": "<verbatim-confirmation>"}
}
}
```

Источник содержит дословное решение и контекст вопроса с полным списком; он
хранится вне каталога run. SHA-256 вычисляется по реальным байтам. Агент проверяет
смысл ответа, программа — источник, цитату, привязку к run/трекеру/релизу и точное
совпадение уникальных ключей со всеми собранными карточками. Нельзя удалить
неудобного участника, проигнорировать роль DEV в составе или выдать подмножество
за весь релиз. Доказанные пропуски страниц и противоречия источников остаются
блокерами; это не разрешение игнорировать известные дополнительные задачи.

Повтори `release-preview --membership FILE` и `history-review` в том же run.
Review сохраняет `complete=true`, но `source_complete=false` и
`completeness_basis=analyst-confirmed`, а также исходное подтверждение. Ограничение
источника остаётся видимым как `release-membership:source-completeness-unproven:analyst-confirmed`.
Снимается только `membership-completeness-not-proven`, не лимиты выдачи, пробелы
истории, ошибки владения, оценки и прочие QA partition blockers. Не переписывай
reconciled.json, completion-status или raw-ответы. Подтверждение состава не
подтверждает даты, оценки или завершение тестирования.

Если применение было `paused`, по команде аналитика продолжить сначала запиши
`application-state pending` с причиной и `--analyst-confirmed`. `pending` означает
ожидание применения, а не паузу и не завершение. Затем новый review с отдельными
QA-подтверждениями, успешный `qa-application-check`, actual-only, проверка диаграммы
и `save-preview`; только потом единый save. Само подтверждение состава не закрывает run.

### Новая фича в исполнении

Отсутствие фичи на Ганте или execution-реестра не запрещает собирать карточки.
Существующий `features/<feature>/requirements.md` не нужно создавать заново.
Предпросмотр показывает `registration`, известных аналитических владельцев и
неподтверждённые связи. Чужие оценки не блокируют поиск ключей; повреждённая
структура таблицы остаётся блокером, если нельзя исключить дубли владения.
Не предлагай чинить чужую фичу или прерывать сбор вместо обсуждения новых задач.

1. Покажи все карточки релиза, включая пропущенные по ролям, и предложения
   владельцев. Явное указание аналитика выше догадки по названию/эпику.
   Несовпадение с существующим реестром показывается как конфликт, не молча
   переносится. Задаче без префикса можно дать AN/BE/FE/QA только по отдельному
   решению аналитика; не путай тип Story с ролью работы.
2. Для проверяемого решения используй `release-preview --decisions FILE`.
   Файл содержит `schema_version: 1`, `provider`, `release`, `analyst_confirmed: true`,
   `source: {file, sha256, quote}` с дословным ответом и
   `tasks: [{key, feature, role}]`. `role` можно опустить при явном префиксе;
   менять явный префикс таким решением нельзя. Этот же объект передай как
   `release_scope_decisions` в манифест history-review. Исходная сверка не меняется.
3. Повтори preview с решениями. `proposed_registrations` представляет новые
   BE/FE только в памяти: это предложения, а не существующие строки и не запись
   аналитики. Собери историю в том же run и выполни history-review с решениями.
   Существование execution-реестра, строки QA или Ганта для этого не требуется.
   Пустые оценки не равны нулю и не блокируют историю. Новые задачи входят в
   обязательную историю и расчёт QA наряду с существующими.
4. Покажи единое сравнение BE/FE и QA с ограничениями, получи поправки и команду
   применения. Только затем после `application-preflight` в collaboration-сессии
   владельца создай/обнови `execution/tasks.md`: Task ID, Jira, SberTrek, Kind,
   Role, Summary, Estimate (дн), Status, Progress %, Actual Start, Actual Finish.
   Реальные FE/BE — отдельные строки; AN/QA относятся к фиче. Неподтверждённые
   оценки/даты — `-`, состояние/процент — `unknown`, не todo/0. Локальный QA-ID
   находится в Task ID, не в Jira. Не создавай срезы. Новую QA и её оценку согласуй
   по сравнению; после регистрации повтори review с теми же исходными ответами
   и текущими хешами просмотренных реестров, затем проверь QA-применение.
   Не требуй выдумать оценку ради отображения подтверждённого завершения BE/FE:
   при `done/completed`, 100% и полном фактическом интервале либо `Completed By`
   генератор показывает факт с неизвестной оценкой. Для прогнозного размещения
   оценка по-прежнему нужна. Сначала проверь ролевую оценку в исходной карточке;
   общую оценку не распределяй по ролям без основания/решения аналитика.
   Фактические календарные даты и длительность не превращай в SP или трудозатраты.
   `qa_application_blockers` не мешают сбору/сравнению, но запрещают объявлять
   применение завершённым или генерировать Гант «с оговоркой». При недоказанной
   полноте продолжай сбор; не предлагай частичную запись как обход проверки.
5. Для вывода на Гант отдельно согласуй квартал, название и место новой фичи.
   Сохрани относительный порядок прежних разделов и PLAN. Проверь источники
   baseline: при подтверждённом отсутствии используй `Baseline State = absent`
   в `planning/actualization.md` по шаблону, с реальными связями задач и без
   выдуманной полосы PLAN. Обнови только подтверждённый actual-progress scope/layout,
   затем выполни QA-проверку и `--actual-only`. Наличие в релизе само по себе не
   утверждает приоритет, ресурс или календарную дату.

Если активна чужая collaboration-сессия, чтение и решения можно продолжать,
но запись не разрешена. Не переключай ветку с незавершённой работой и не
закрывай чужую сессию автоматически.

Для согласованной актуализации нескольких фич используй одну рабочую сессию:
`collaboration.py set-execution-scope` с подтверждёнными фичами, кварталами и run
по `core/collaboration.md`. Один общий пересчёт actual-only и один проверенный
набор исходников/includes/Confluence сохраняются в одной ветке. Не разводи
сдвиги квартального расписания по ветке на каждый FEATURE-файл.

### Остановка применения

После reconciliation сбор уже завершён; `abandon-run` к нему неприменим.
По явной просьбе остановиться выполни
`application-state --run-id RUN --state paused --reason REASON --analyst-confirmed`.
Сверка и исходные ответы сохраняются, применения не происходит. Возобновление
того же результата — та же команда с `--state pending` только по просьбе аналитика.
Нельзя удалять run, перезаписывать его ради исправленного формата или объявлять
актуализацию завершённой по статусу `tracker-read-reconciled`.

## Полный состав QA

Область чтения шире области применения. Для каждой затронутой фичи нужны карточки
всех её FE/BE-задач, в том числе не вошедших в релиз: они нужны для полного состава
и пропорционального разделения QA. Это не разрешает актуализировать их строки.
`release-preview` возвращает недостающие ключи.
Прочитай их тем же провайдером и в том же run. Передай history-review в манифесте
`supplemental_responses`: список объектов `keys`, `response_file`, `sha256`, `call`.
`call` следует tracker-adaptive; его `selection` — точный `key IN (...)` для Jira
или `unit = "..." or ...` для SberTrek, с порядком `keys`. Сохрани реальные ответы
вне run; команда проверяет контрольные суммы, ключи и полноту каждого дополнения.
Не переписывай reconciled.json: дополнения привязываются к отдельному history-review.
Обязательна история FE/BE-участников текущего релиза. Она передаётся обычным
`responses`; отсутствие объясняется `unavailable_history`, не превращаясь в даты.
Для задач вне релиза историю дополнительно собирать не требуется. Уже собранные
ответы сохраняются, но не дают предложений факта и не расширяют область применения.
Просьба «не трогать задачи вне релиза» запрещает менять их строки, а не читать
карточки для QA. Не удаляй их из реестра и не подменяй членство релиза.

Одна реальная задача принадлежит одному релизу. Несколько релизов — аномалия.
Спроси единственного владельца; запиши ответ в `decision_source` и
`release_decisions: {"TASK-KEY": "RELEASE"}` подтверждённого манифеста.
Нельзя копировать задачу или дважды учитывать её оценку. Изменение уже принятого
состава/владельца требует отдельного просмотра и исправления групп, не тихой миграции.

## Разбиение и применение

При частичном релизе сохрани ID прежней QA для вошедших задач, создай стабильный
ID QA остатка. Оценка делится пропорционально количеству уникальных неотменённых
FE/BE-карточек, не их SP. Сумма частей равна прежней общей оценке; остаток округления
остаётся в остаточной группе. Начало, конец и прогресс группы текущего релиза считаются
только по её участникам: первое окончание разработки, последнее окончание QA,
доля прошедших тестирование. Оценка не определяет фактическую календарную длину.
Не наследуй done/100 и даты общей QA обеим частям. AN остаётся работой фичи.

В релизном review `application_scope` задаёт участников и защищённые строки.
Карточки вне релиза имеют `proposed_action: reference-only` и исключены из таблицы
обновления разработки. QA других релизов и остатка имеют
`application_mode: partition-only`: допускается только разделение оценки,
без обновления сроков, статуса или прогресса. Существующий факт сохраняется.
Для новой остаточной QA факт не наследуется: даты `-`, статус и прогресс `unknown`
в присутствующих колонках реестра. Это неизвестность, не утверждение «не начата».
В `qa_confirmations` для такой группы разрешены только поля оценки либо
`keep-current`, если оценка уже соответствует разбиению. Команда применения
проверяет неизменность остальных задач и факта остаточной QA. Старый release-review
без `application_scope` нужно повторить в том же run, не редактировать вручную.

`feature_qa_proposals[].partition` содержит предлагаемые группы и документ для
`features/<feature>/execution/qa-groups.json` (`schema_version: 1`, `provider`,
`total_estimate`, `groups`: `task_id`, `members` внутренних ID, `release`, `estimate`).
Это execution-источник, не план. Группы непустые, не пересекаются и покрывают весь
активный FE/BE-состав. Повторный запрос обновляет те же ID. Другие релизы отделяются
от остатка; обычная актуализация фичи/квартала сохраняет принятое разбиение.
