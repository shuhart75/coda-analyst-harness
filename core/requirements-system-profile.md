# Человекочитаемая системная спецификация

Новый авторский `requirements.md` использует маркер
`Формат: **системная спецификация функциональности**` и шаблон
`templates/requirements/feature-requirements.template.md`.
Прежний компактный профиль поддерживается без изменения проверок. Переход
существующего документа выполняется при явной переработке в его рабочей ветке
с сохранением REQ и регистрацией происхождения изменения. Старые редакции,
аудиты и возвраты не переписываются; новый маркер автоматически не подставляется.

## Назначение и источники

Один документ содержит цель, согласованное поведение и необходимые системные
контракты. `sdd/` является производным представлением по `core/sdd-input.md`;
паспорт фичи остаётся обзором. Независимые «человеческая» и «техническая» версии
требований не создаются.

Глубина зависит от задачи. Для интеграции нужны входы, выходы, источники полей,
преобразования и ошибки; изменение подписи кнопки не требует описывать БД.
Классы, внутреннее устройство и технические задачи принадлежат разработке.
Факты реализации подтверждаются ограниченной проверкой кода. Отсутствующие
поля, API и бизнес-решения становятся вопросами, а не догадками в нормативном
тексте. Упоминание кода или макета в полученном документе не доказывает проверку.

## Структура и согласование

Перед первым разделом: название, `Редакция`, `Формат`, `Функциональность`.
Поля `Статус` нет; состояния остаются в существующих реестрах.
Обязательны непустые разделы второго уровня:

1. `Назначение`.
2. `Границы`, с маркером этапа и дословными title/goal по `core/delivery-stages.md`.
3. `Критерии приёмки`.
4. `Влияние на соседние функциональности`.
5. `Источники и открытые вопросы`.

Между границами и приёмкой добавляй применимые предметные разделы: текущее
поведение и изменение, доработки фронта, доработки бэка, API и интеграции,
данные и совместимость, ошибки. Пустые разделы ради шаблона не добавляются.
При запросе разделения FE/BE соблюдай его. Это ответственности внутри одной
поставки, не отдельные этапы, задачи или пакеты.

При просьбе согласовывать по разделам покажи один содержательный раздел,
получи обратную связь и затем продолжай зависимый шаг. Предметные вопросы
задавай по одному. Не выдавай весь документ за согласованный.
Явный запрос другого формата имеет приоритет; объясни несовместимость
с проверками до передачи, не подменяй запрос привычным шаблоном.

## Правила и таблицы

REQ описывает наблюдаемое правило с уникальным устойчивым идентификатором.
Короткие правила оформляй таблицей из трёх колонок:

```markdown
| Требование | Название | Правило |
|---|---|---|
| REQ-DOC-001 | Выбор документа | Пользователь выбирает ровно один документ радиокнопкой. |
```

Длинное правило может иметь прежний заголовок `### REQ-DOC-002. Результаты поиска`
с текстом под ним. Формы можно сочетать. Текст правила пишется один раз;
ссылка на REQ не создаёт второго определения. В таблицах внутренний символ
вертикальной черты экранируется обратной косой чертой. REQ в примерах кода
и комментариях не являются авторскими определениями.

Таблицы полей, состояний и переходов описывают точные источники, типы,
обязательность, пустые значения, условия и результат. Новые обязательства
получают REQ; таблица деталей связывается с владеющим REQ. Не превращай
каждую ячейку в отдельное требование и не дублируй текст ради трассировки.

Для UI указывай прямую ссылку на фрейм и состояние/элемент. Общая ссылка на
файл дизайна не заменяет ссылку на экран. Недоступный макет отмечай как
непроверенный. Для API допустима ссылка на проверенный контракт с точным
перечнем изменений вместо полного копирования.

## Общие критерии приёмки

Каждый REQ покрывается хотя бы одним критерием. Один критерий может проверять
несколько REQ в одном процессе. Вложенный «Когда / Тогда» под каждым коротким
правилом не обязателен. Не повторяй правило словами сценария.

Раздел `Критерии приёмки` содержит таблицу из четырёх колонок:

```markdown
| Критерий | Условие и действие | Ожидаемый результат | Требования |
|---|---|---|---|
| AC-001 | Найдены два документа; пользователь выбирает второй | Выбран только второй документ | REQ-DOC-001, REQ-DOC-002 |
```

AC-id уникален и устойчив. Условие называет конкретное состояние и событие,
результат наблюдаем. Последняя колонка перечисляет полные REQ через запятую,
без диапазонов и сокращений. Общий список REQ вне таблицы не доказывает
покрытия. Основной процесс, альтернативы, ошибки и границы проверяются по смыслу.

Груминг использует AC-id в существующем поле `scenarios` для каждого связанного
REQ. Производная задача сохраняет правило и выбранный общий критерий. Ссылки
на остальные REQ критерия относятся к полному договору, не расширяют задачу.
Изменение критерия меняет source hash. Аудит проверяет покрытие в производном
SDD; исходные и SDD-сценарии не обязаны иметь одинаковые заголовки. Receiver
получает новый parser при штатной передаче. Не понижай формат ради обхода
ошибки устаревшего receiver.

## Проверки

Проверить профиль, формулировки, язык, ссылки и соответствие запросу аналитика.
Смысловой аудит по `core/requirements-audit.md` дополнительно проверяет:

- понятность изменений фронта/бэка и совместимость их API;
- идентичность объекта, источники и преобразования данных;
- повторные действия, ошибки, пределы и старые записи;
- основания решений и проверенные ссылки на макеты;
- сохранение всех REQ, общих критериев и ограничений в SDD.

Профильная проверка подтверждает структуру и покрытие ссылками, но не смысл
и не готовность реализации. Неизвестные решения блокируют затронутую передачу
по обычным правилам; маркер нового формата не утверждает документ.
