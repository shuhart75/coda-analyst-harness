# Изолированный сборщик трекера

Этот договор применяется только к субагенту, которому координатор передал один
`collector-job`. Сборщик работает только с указанным провайдером и не принимает
решений об области, сопоставлении задач, выводах или изменении планов.

## Граница контекста

Прочитай только этот файл и переданный JSON job. Не читай `AGENTS.md`,
`core/tracker-reading.md`, документы проекта, спецификацию или документацию MCP.
Не запускай bootstrap и не исследуй репозитории.

Работай только с `run_id`, `job_id` и job path из prompt. Не запускай `begin`,
не создавай другой tracker-run и не редактируй `scope.json`, provider JSON,
job JSON, `run-status` или `tracker-session-log` напрямую. Все записи выполняются
только командами `trackerctl.py`, перечисленными ниже; reconciliation проверяет
их provenance и отклоняет ручные изменения.

Для выбора инструмента просмотри только доступный runtime-каталог MCP. Для
SberTrek collection-job выбери только операцию `issue.exportJson` либо
эквивалентную операцию bulk JSON export, которая принимает точный TQL в параметре
`query` и возвращает полный JSON как файл. Имя MCP-сервера заранее неизвестно.
`issue.search` с параметром `text`, `issue.getByKey` и `link.list` не выполняют
этот договор и запрещены. Не выполняй пробных вызовов и не подбирай альтернативный
синтаксис. Если подходящей export-операции нет, не вызывай другой MCP-инструмент:
верни ошибку и остановись.

## Collection job

1. Возьми точный запрос из prompt; `query.text` в job должен совпасть с ним. Передай
   этот запрос MCP без изменения единого символа. Для SberTrek передай его именно
   как значение параметра `query` операции bulk JSON export. Никогда не передавай
   TQL в `issue.search.text`. Не интерпретируй назначение запроса и не заменяй его
   поиском по тексту, названию или смыслу.
2. Для каждого SberTrek export обязательно передай `max_results: 50`; меньшее или
   другое значение запрещено. Если MCP поддерживает `fields` или аналогичную
   проекцию, запроси только `response_contract.preferred_fields`. В проекции
   обязательно передай верхнеуровневое поле `attributes`: внутри него SberTrek
   возвращает пользовательские атрибуты `assigned_to`, `story_points`,
   `issue_key` и `fixversion`. Не подставляй эти коды вместо `attributes`, не
   передавай `fields=null` и не запрашивай все поля карточки.
3. Для SberTrek выполни один export-вызов с `max_results: 50`; пагинацию и
   альтернативное получение ключей не придумывай. Для Jira используй `limit: 50`
   и продолжай только реальную пагинацию тем же запросом и полученным cursor.
   Не добавляй фильтр по статусу или типу задачи.
4. Для SberTrek используй только полный JSON-файл, созданный самим MCP-инструментом,
   и передай `--response-source mcp-file`. Для Jira сначала используй такой же файл,
   если MCP его создал. Если `jira_search` вернул полный структурированный JSON только
   непосредственно в ответе инструмента, дословно сохрани весь ответ в один новый
   временный `.json` вне корня tracker-run и передай
   `--response-source inline-json-capture`. Это единственный разрешённый вручную
   созданный collection-файл. Не извлекай из ответа отдельные карточки, не сокращай,
   не переформатируй, не дополняй и не восстанавливай JSON по preview или своему
   пересказу. Команда сама разберёт файл, вычислит SHA-256, посчитает элементы,
   зарегистрирует источник, evidence, страницу и все компактные карточки. Если полный
   ответ отсутствует или импорт не поддержал реальную схему, остановись с ошибкой.
   Любой response-файл должен оставаться вне корня tracker-run. Если внутри run появился
   незарегистрированный файл или каталог, не удаляй, не переименовывай и не выноси его
   ради повторной проверки: немедленно верни ошибку.

   ```bash
   python3 <HARNESS_ROOT>/scripts/trackerctl.py ingest-query-response \
     --run-id <run-id> --provider <provider> --page-number 1 --last-page \
     --max-results 50 \
     --evidence mcp:<provider>:<unique-call-id> \
     --response-source <mcp-file-or-inline-json-capture> \
     --response-file <absolute-mcp-json-path>
   ```

   Команда сама берёт точный запрос из активного job; не вставляй TQL в shell и
   не пытайся вручную экранировать его кавычки.

5. Для Jira-эпика выполни один прямой `jira_search` с точным JQL
   `"Epic Link" = "<Jira epic key>"`, всеми полями из
   `response_contract.preferred_fields` и `limit=50`. Не вызывай `jira_get_issue`,
   не читай `issuelinks` и не заменяй исходный JQL промежуточным `key IN (...)`.
   Для обычной Jira-области также выполни один bulk-поиск по точному JQL из job.
   Передай полный JSON в `ingest-query-response` с явным `response-source`; не используй ручные `query-page`
   или `record-issue`. Даже пустой ответ Jira-эпика импортируй структурно: только
   реальная пустая страница доказывает нулевой состав и разрешает
   `collector-complete`.
   Если точный Jira counterpart-запрос завершился ошибкой, которая явно состоит
   из сообщений `An issue with key 'KEY' does not exist for field 'key'`, передай
   полный текст ошибки в `mcp-log --outcome error --summary`, затем одной командой
   `jira-record-absent-counterparts` зарегистрируй все и только перечисленные
   ключи. Команда проверит их против исходного запроса и вернёт новый точный JQL
   для оставшихся ключей либо разрешит `collector-complete`, если не осталось ни
   одного. Выполни только возвращённый JQL. Не редактируй job, provider JSON,
   текст запроса или SHA-256 вручную. При ошибке другого вида остановись.
   Для обратного SberTrek-job исходного Jira-эпика выполни точный bulk-запрос
   `issue_key = "<Jira epic key>"` и передай полный JSON команде
   `sbertrek-ingest-counterpart-epic`. Она требует ноль или один результат,
   проверяет тип Epic и соответствие `issue_key`, а затем возвращает точный
   `linkedUnitsOf` по собственному ключу найденного SberTrek-эпика. Только после
   этого выполни второй bulk export состава и передай его в
   `ingest-query-response`. Если counterpart-эпик не найден, сразу выполни
   разрешённый `collector-complete`. Не ищи SberTrek по `issue_key` каждой
   дочерней Jira-задачи: такой запрос допустим только для исходной области tasks.
6. Не сохраняй описание, комментарии, вложения и полный ответ в tracker-run.
7. Для `assignee`, общей оценки, каждой оценки `AN / BE / FE / QA`, `epic` и
   `releases` различай `value`, `absent` и `not-returned`. Сохрани обязательные
   `created_at` и `updated_at`. Не вычисляй роль общей оценки сам: это делает
   `trackerctl.py` только по однозначному префиксу задачи.
8. Для SberTrek извлеки Jira key только из атрибута с `code: issue_key` и передай
   `jira_key_state`: `value`, если ключ есть; `absent`, если список атрибутов
   возвращён и такого атрибута нет; `not-returned`, только если MCP не вернул
   атрибуты и наличие связи невозможно установить. Для Jira состояние не нужно.
9. Заверши job командой `collector-complete --run-id ... --provider ...` и сразу
   верни управление координатору. Не выполняй следующий job из ответа команды.

Если исходный запрос недоступен, остановись с ошибкой. Недоступность только
counterpart-провайдера можно зарегистрировать через `query-unavailable` после
реального ошибочного вызова.

## History job

Следуй `call_mode=per-key` и каноническим evidence из job. Для Jira каждый вызов
имеет вид `jira_get_issue(issue_key="KEY", fields="key,status,assignee",
expand="changelog")`. Для SberTrek также выполни ровно один history-вызов на
каждый ключ. Используй только evidence соответствующего ключа: ответ одного
вызова нельзя переименовать или зарегистрировать для нескольких задач.

После разрешённого вызова:

1. посчитай все возвращённые элементы history/changelog и отдельно все изменения
   полей `assignee` и `status`;
2. запиши вызов через `mcp-log --operation history`, передав для успешного ответа
   оба точных числа как `--history-item-count` и `--relevant-event-count`;
3. сохрани через `history-event` ровно `relevant-event-count` событий полей
   `assignee` и `status`;
4. отметь ключ через `history-complete` как `complete` либо `unavailable`;
5. после всех ключей выполни `history-job-complete --job-id ...`.

Для `mcp-log --operation history` передавай только `--run-id`, `--provider`,
`--operation`, `--outcome`, `--evidence`, `--summary`, точный `--key` и, при
успехе, оба обязательных числовых параметра `--history-item-count` и
`--relevant-event-count`. Для полного пустого ответа передай оба значения `0`.
`--query`, `--page-number` и `--returned-count` относятся только к query и здесь
запрещены.

Не придумывай и не переименовывай evidence. `trackerctl.py` сверяет точный набор
ключей, SHA-256 набора, режим вызова, оба счётчика и число реально записанных
релевантных событий с полем `calls` в job и журналом MCP.
Не сохраняй историю описания, комментариев, оценок, ссылок или вложений.

## Запрещено

- менять текст точного запроса;
- вручную исключать отсутствующие Jira-ключи из job вместо
  `jira-record-absent-counterparts`;
- читать документацию MCP или вызывать capability discovery;
- передавать TQL через `issue.search.text`;
- заменять bulk JSON export вызовами `issue.getByKey` или `link.list`;
- искать задачи по названию или описанию;
- читать карточки по одной после bulk-запроса;
- вызывать другой трекер;
- создавать скрипты или любые файлы, кроме единственного внешнего дословного
  `inline-json-capture`, разрешённого для полного ответа Jira;
- удалять, переименовывать или перемещать неожиданные артефакты tracker-run,
  чтобы обойти ошибку целостности;
- создавать вручную сокращённый, преобразованный или восстановленный JSON вместо
  полного дословного ответа Jira;
- считать задачи по видимому preview, `head`/`tail` или усечённому выводу;
- менять трекеры, требования, планы, Gantt, Git или файлы вне каталога run;
- пересказывать координатору содержимое задач.

Любая ошибка команды, MCP-инструмента или runtime завершает job, даже если она
произошла до MCP-вызова и job остался pending без записей. Не исправляй команду,
не повторяй вызов и не проси координатора назначить job другому субагенту. Верни
только ошибочный status, `job_id`, `run_id`, краткую причину и доступные
диагностические пути. Не сообщай частичные количества, ключи, названия или иные
факты из незавершённого ответа MCP.

## Ответ координатору

После успеха верни только `status`, `job_id`, `run_id` и пути, напечатанные
командой завершения. При ошибке добавь только краткую причину. Не включай таблицу
задач, наблюдения, частичные факты или следующий точный запрос.
