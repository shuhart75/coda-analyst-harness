# Чтение, сверка и применение данных трекеров

## Назначение

`targeted-tracker-v3` разделяет работу на независимые контексты:

1. координатор определяет область и создаёт run;
2. изолированный сборщик читает один провайдер;
3. отдельные history-сборщики читают ограниченные пакеты ключей;
4. `trackerctl.py` детерминированно склеивает результаты;
5. основной агент читает только `reconciled.json` и применяет его к планам лишь
   при явном intent `update-planning`.

Команда «прочитай» всегда имеет intent `read-only` и не разрешает менять задачи,
требования, планы, Gantt или `actual-progress`. Команда «актуализируй задачи/Гант»
имеет intent `update-planning`, но применение разрешено только после успешной
сверки и только в артефактах режима исполнения.

## Стоп-барьер

До MCP и делегирования координатор выполняет отдельно:

```bash
python3 scripts/trackerctl.py config-status
```

Команду нельзя передавать в `head`, `tail`, `grep`, `jq` или иной pipeline: код
выхода является частью fail-closed договора.

Код `3` и `must_stop: true` разрешают только дословно задать
`response_contract.text`. Не выполнять discovery, поиск, bootstrap, делегирование
или предварительную сводку.

## Область

Run получает один эпик либо явный набор ключей и явно известный исходный трекер.
Jira и SberTrek используют одинаковую форму ключа, поэтому провайдер не выводится
из `PROJECT-123`. При неоднозначности задать один вопрос.

Примеры:

```bash
python3 scripts/trackerctl.py begin \
  --scope-kind epic --scope-provider sbertrek \
  --scope-id RSCON-6607 --label 'Когорты' \
  --scope-source 'Ответ аналитика' --intent read-only

python3 scripts/trackerctl.py begin \
  --scope-kind tasks --scope-provider jira \
  --scope-id RSCON-2905 --scope-id RSCON-2906 \
  --label 'Когорты' --scope-source 'features/cohorts/actual-progress.md' \
  --intent update-planning
```

`begin` создаёт `run_id` и первый job. Одновременно существует только один
незавершённый tracker-run: повторный `begin` блокируется. Если аналитик явно
решил не продолжать его, координатор фиксирует отказ через `abandon-run`, не
удаляя диагностические файлы. Координатор не выполняет напечатанный TQL/JQL сам.
Он получает готовый prompt:

```bash
python3 scripts/trackerctl.py collector-brief --run-id <run-id>
```

и создаёт отдельного субагента с этим prompt. Если runtime не поддерживает
субагентов, операция блокируется: нельзя возвращаться к чтению в основном
контексте.

Prompt жёстко связывает сборщик с существующими `run_id`, `job_id` и job path.
Сборщик не запускает `begin`, не создаёт новый run и не редактирует runtime JSON
или журнал напрямую. Каждая записанная страница, карточка и history-запись имеет
provenance успешной команды `trackerctl` и SHA-256; `reconcile` проверяет их до
выдачи официального результата.

## Collection jobs

Job хранится в `jobs/collection-<provider>.json` и содержит точный запрос и его
SHA-256. `collector-brief` передаёт субагенту сам точный запрос в первой короткой
команде без названия фичи, смысла эпика, исходного пользовательского текста и
иного аналитического контекста. Сборщик следует только этой команде,
`core/tracker-collector.md` и job-файлу. Он не читает общие правила проекта или
документацию MCP.

Обвязка строит только следующие запросы:

```text
SberTrek epic:
unit IN linkedUnitsOf("unit = 'RSCON-6607'", "Состоит из")

SberTrek tasks:
unit = "RSCON-6848" or unit = "RSCON-6849"

SberTrek by Jira counterparts:
issue_key = "RSCON-2905" or issue_key = "RSCON-2906"

SberTrek epic counterpart for a Jira epic:
issue_key = "RSCON-2911"

SberTrek members after the counterpart epic is found:
unit IN linkedUnitsOf("unit = 'RSCON-6854'", "Состоит из")

Jira tasks:
key IN ("RSCON-2905", "RSCON-2906")

Jira epic members:
"Epic Link" = "RSCON-2911"
```

Для Jira-эпика выполняется один прямой bulk `jira_search` с точным JQL
`"Epic Link" = "<Jira epic key>"`, всеми полями из job и `limit=50`. Переход через
`jira_get_issue(..., fields="issuelinks")` и промежуточный `key IN (...)` запрещён.
Фильтр по типу или статусу запрещён: завершённые элементы нужны, чтобы увидеть
факт закрытия. Нулевой состав эпика считается доказанным только после структурного
импорта полного пустого ответа `jira_search`; `collector-complete` без такой
страницы блокируется.

Обратный путь из Jira-эпика в SberTrek не строится по ключам найденных Jira-задач.
Сначала отдельный bulk-запрос ищет ноль или один объект SberTrek, у которого
`issue_key` равен ключу самого исходного Jira-эпика. `trackerctl.py` проверяет,
что единственный найденный объект подтверждает тот же `issue_key`; если тип
возвращён, он обязан быть Epic. Не возвращённый экспортом тип фиксируется как
limitation. Затем программа подставляет собственный ключ найденного SberTrek-
эпика в стандартный запрос `linkedUnitsOf` и читает его состав. Если counterpart-
эпик не найден, Jira-задачи остаются в результате, а SberTrek-ветка считается
пустой. Поиск SberTrek по `issue_key` каждой Jira-задачи применяется только когда
исходная область была явным набором Jira-задач.

Поисковый ответ нормализуется без detail-вызовов каждой задачи. Для SberTrek
сборщик использует только `issue.exportJson` либо эквивалентную bulk JSON export
операцию: точный TQL передаётся в параметре `query`, а имя MCP-сервера может
отличаться. Каждый export выполняется с максимальным поддержанным значением
`max_results: 50`; меньший лимит, пагинация и альтернативный сбор ключей не
используются. `issue.search.text`, `issue.getByKey` и `link.list` запрещены и не
являются проверкой поддержки TQL. Сборщик не читает отображаемый preview: большой
ответ может быть показан только частично, хотя MCP вернул все элементы. Если
инструмент поддерживает проекцию, он запрашивает только поля из job, включая
верхнеуровневый контейнер `attributes`, и никогда не использует `fields=null`.
Коды `assigned_to`, `story_points`, `issue_key` и `fixversion` извлекаются из
`attributes`, а не передаются экспортёру как замена этого контейнера. Полный JSON
ответа передаётся в `trackerctl.py ingest-query-response`: MCP-файл использует
`--response-source mcp-file`, а полный inline-ответ дословно сохраняется вне
tracker-run и использует `--response-source inline-json-capture`. Программа
структурно находит массив задач, вычисляет SHA-256, считает карточки и атомарно
регистрирует источник ответа, evidence, страницу и компактные записи. Ручные `mcp-log`,
`query-page` и `record-issue` не могут завершить collection-job ни одного
провайдера. Оба провайдера импортируются только из полного JSON bulk-ответа. Если
MCP не создал файл, но вернул полный структурированный JSON непосредственно в ответе
инструмента, коллектор может дословно сохранить весь ответ в единственный внешний
временный `.json` и импортировать его с `--response-source inline-json-capture`.
Извлекать, сокращать, переформатировать или вручную восстанавливать карточки
запрещено. Metadata `total`, `start_at` и `max_results`, если она возвращена,
проверяется машинно. Порядковый номер импортируемой страницы вычисляет сам
`trackerctl.py`; коллектор не передаёт `--page-number` и не подставляет Jira
`start_at` вместо номера. У SberTrek нет пагинации: его единственный ответ
регистрируется как страница 1. Успешный collection-вызов не требует и не допускает
предварительный `mcp-log`. Правило одинаково для Jira и SberTrek.

Provider-файл хранит только ключи, название, тип, статус, исполнителя, общую и
ролевые оценки `AN / BE / FE / QA`,
эпик, релизы, даты создания/обновления, состояния `value/absent/not-returned`,
evidence, число элементов и SHA-256 исходной страницы. При этом описания, комментарии, вложения
и полный MCP-ответ в tracker-run не сохраняются. Отсутствие полного
JSON-ответа, неподдержанная схема, пустые `pages`, несовпадение машинного числа
карточек или карточка без evidence блокируют `collector-complete` и `reconcile`.
Для SberTrek наличие `issue_key` фиксируется отдельно: `absent` является
нормальным отсутствием связи, а `not-returned` означает неполное чтение и
блокирует переход к Jira и reconciliation.

Если точный Jira counterpart-запрос явно сообщает, что перечисленные `issue_key`
не существуют, сборщик сохраняет полный текст ошибки и регистрирует эти ключи
через `jira-record-absent-counterparts`. Только `trackerctl.py` строит повторный
JQL по оставшимся ключам; job и SHA-256 вручную не изменяются. SberTrek-задача с
таким подтверждённо отсутствующим Jira-контрагентом исключается из итоговых задач,
оценок, статусов, группировок и history jobs. Она остаётся в исходном снимке и в
отдельном списке исключений с evidence. SberTrek-задача с `jira_key_state=absent`
не исключается и продолжает обрабатываться как самостоятельная задача.

Если SberTrek вернул ровно 50 карточек, reconciliation сохраняет limitation
`sbertrek-export-limit-reached:50`: результат остаётся доступен, но полнота свыше
поддерживаемого лимита не утверждается.
Если Jira вернула 50 карточек без `total/start_at/max_results` или другой
машинной гарантии конца списка, аналогично сохраняется
`jira-search-limit-reached:50`.

После `collector-complete` субагент обязан остановиться. Команда сама создаёт
counterpart-job либо history-jobs; запускать их должен координатор в новых
контекстах.

Несколько account ID одного человека в одном или разных провайдерах могут быть
явно связаны с одним roster `team_id`. Точное совпадение полного имени используется
только как подсказка в следующем вопросе, но не как автоматическое сопоставление.
Обвязка не требует и не предлагает создавать новый `team_id` для технического alias.

Любая ошибка collection- или history-сборщика терминальна для текущего run. Это
включает отсутствие shell/MCP-инструмента, временный runtime-сбой, ошибку до
первого MCP-вызова и pending job без единой записи. Координатор не проверяет,
«воспроизводится» ли сбой, не делегирует тот же job повторно тому же или новому
субагенту и не продолжает run вручную. Он сразу выполняет известную команду
`fail-run --run-id <run-id> --reason <краткая-причина>` без `--help`, shell pipeline
и синтаксических проб, может один раз прочитать `run-status`, сообщает только
сохранённые статус, причину и `allowed_next_action=stop-and-report-failure` и
останавливается. Частичные
количества, ключи, названия и другие факты из MCP-ответа при
`final_response_allowed: false` сообщать запрещено. Для нового прогона failed run
закрывается через `abandon-run` только по отдельному явному решению аналитика,
но не как продолжение того же запроса чтения.

Коллектор не создаёт, не копирует и не перемещает MCP-ответы или вспомогательные
файлы внутрь корня tracker-run: `--response-file` получает исходный внешний путь,
созданный MCP, либо внешний дословный `inline-json-capture` провайдера. Если проверка нашла
неожиданный артефакт, удалять, переименовывать
или переносить его ради повторного `collector-complete` запрещено. Такая ошибка
целостности переводит run в `tracker-read-failed`; текущий запрос завершается
действием `stop-and-report-failure`. Последующий явный отказ от failed run
фиксируется отдельно через `abandon-run`.

## History jobs

История разбивается на job не более восьми ключей. Каждый job относится к одному
провайдеру. Для каждого ключа Jira сборщик вызывает
`jira_get_issue(issue_key="KEY", fields="key,status,assignee", expand="changelog")`;
для SberTrek также выполняется ровно один history-вызов на ключ. Канонический
evidence, ключ и его SHA-256 записываются в `calls` job и сверяются с MCP-журналом.
Один ответ нельзя переименовывать или использовать как evidence другого ключа.
Сохраняются только события `assignee` и `status`.

Для `mcp-log --operation history` нельзя передавать `--query`, `--page-number`
или `--returned-count`. Успешный вызов обязан передать точное число всех элементов
ответа через `--history-item-count` и точное число изменений `assignee/status`
через `--relevant-event-count`. `history-complete` сверяет второе число с реально
записанными `history-event`; неопределённое «history call ok» без счётчиков не
является доказательством полного чтения. Ошибка любой команды записи терминальна
для run; исправить аргументы и повторить вызов в том же run нельзя.

По истории вычисляются:

- `assigned_at` — первое возвращённое назначение на исполнителя;
- `work_started_at` — первое возвращённое назначение участнику с ролью developer;
- завершение по передаче — последнее доказанное назначение developer → известная
  не-developer роль, если явный статус не означает завершение или исключение.

Для единицы разработки `in-progress` допустим только при текущем назначении
известному developer либо при истории, доказавшей назначение developer без более
поздней передачи. При полном пустом history и отсутствии исполнителя состояние
`not-started`; при неполной истории или недостаточных доказательствах — `unknown`.

Отсутствующая или недоступная история даёт `null` и явное limitation; дата не
угадывается по `updated_at`.

## Сопоставление и склейка

Пары образуются только так:

```text
SberTrek.issue_key == Jira.key
```

Для каждого поля заполненный SberTrek имеет приоритет. Jira заполняет пропуск.
Это правило применяется отдельно к `AN`, `BE`, `FE`, `QA` и общей оценке.
Два разных заполненных значения сохраняют SberTrek и создают discrepancy.
Эпик и релиз остаются независимыми группировками. `1 SP = 1 человекодень`, другие
единицы молча не преобразуются.

Если ни одной ролевой оценки нет, но есть общая оценка, она становится ролевой
только при одном однозначном префиксе `AN`, `BE` или `FE` в названии задачи.
Несколько префиксов и отсутствие префикса дают limitation
`general-estimate-role-unresolved`, а не догадку. Если заполнена хотя бы одна
ролевая оценка, общая не создаёт дополнительную работу и не суммируется повторно.

Подтверждённо отсутствующий `Jira.key` не создаёт пару: связанная через
`SberTrek.issue_key` задача исключается с причиной `jira-counterpart-absent`.
Отсутствующий у SberTrek атрибут `issue_key` не является причиной исключения.

Неизвестные account id запрашиваются по одному во время `reconcile`. Аналитик
указывает `AN1`, `BE2`, `FE1`, `QA1`; алиасы `A/B/F/Q` нормализуются. Несколько
account id могут указывать на один `team_id`. Если полное имя уже имеет одно
однозначное соответствие, вопрос показывает этот `team_id` как существующий alias.

После сопоставления участников `reconcile` отдельно проверяет конфликт ЖЦ у
склеенной единицы разработки. Вопрос нужен только когда текущие исполнители в
обоих трекерах известны, в одном трекере это developer, в другом — не-developer,
а вычисленные отдельно по каждому провайдеру состояния различаются. Явный
завершающий или исключающий статус основного SberTrek имеет приоритет и такого
вопроса не создаёт. Разные account id двух разработчиков либо двух
не-разработчиков сами по себе конфликтом ЖЦ не являются.

Конфликты выдаются строго по одной задаче. Вопрос показывает ключи, исполнителей,
`team_id`, роли и состояния обоих провайдеров и всегда предлагает пять вариантов:

1. приоритет SberTrek только для текущей задачи;
2. приоритет SberTrek для текущей и всех последующих конфликтующих задач run;
3. приоритет Jira только для текущей задачи;
4. приоритет Jira для текущей и всех последующих конфликтующих задач run;
5. пользовательское состояние `completed`, `in-progress`, `not-started` или
   `unknown` только для текущей задачи.

Ответ сохраняется только командой `set-development-decision` для точного
ожидающего ключа. Вариант «для всех последующих» действует только в текущем
tracker-run, не переносится в конфигурацию и не влияет на будущие сверки.
Пользовательское состояние нельзя массово применить. JSON решений связан с
журналом команды и SHA-256; ручная подмена блокирует reconciliation.

## Координатор

Последовательность основного агента:

```text
config-status
-> begin
-> collector-brief -> isolated collection agent -> run-status
-> collector-brief -> isolated counterpart agent -> run-status
-> collector-brief -> isolated history agent(s) -> run-status
-> reconcile -> один вопрос об участнике или конфликте ЖЦ -> сохранить ответ -> reconcile
-> result-status
```

Координатор не вызывает tracker MCP, не читает provider-файлы и не пересказывает
ответы субагентов. После `config-status` он не запускает `--help`, команды без
обязательных аргументов, shell pipeline, redirection, цепочки команд или пробные
вызовы: каждая команда должна соответствовать протоколу и текущему
`allowed_next_action`. Между job он читает только `run-status` и не сообщает
пользователю количества карточек, факты задач, догадки о следующем job или
содержание ответа сборщика. После любого сбоя
субагента он без вспомогательных команд сразу фиксирует `fail-run`, не создаёт
заменяющего субагента и не сообщает частичные данные. Итог разрешён
только при одновременном выполнении:

```json
{
  "status": "tracker-read-reconciled",
  "workflow_complete": true,
  "final_response_allowed": true
}
```

После успешного `reconcile` координатор выполняет только отдельный
`result-status --run-id <run-id>`. Он не читает `report.md`, `reconciled.json`,
provider-файлы или ответы сборщиков для подготовки финала. `result-status`
проверяет SHA-256 итоговых артефактов и возвращает `response_contract` с режимом
`emit-verbatim`; координатор выводит `response_contract.text` дословно и ничего
больше. Это исключает ручной пересчёт и смысловую трактовку конфликтов: нельзя
объявлять их «ожидаемыми», объявлять состав полным или согласованным, приравнивать
разные ключи эпиков, объяснять даты часовыми поясами или переопределять исполнителя
по памяти либо сырым данным.

Для изменения Ганта дополнительно требуется:

```json
{"planning_application_allowed": true}
```

При `false` допускается только отчёт без изменений. Даже при `true` основной
агент сначала читает компактный `reconciled.json`, проверяет предлагаемые новые
эпики/релизы и соблюдает режим, ветку и правила сохранения аналитического проекта.
Каждая заполненная ролевая оценка материализуется отдельной строкой execution и
отдельной полосой Ганта. У одной задачи tracker key повторяется, а внутренний
идентификатор имеет вид `<tracker-key>/<role>`; название полосы начинается с
`AN`, `BE`, `FE` или `QA`. Ссылка actualization на базовый tracker key раскрывается
во все его ролевые полосы.

## Артефакты

Успешный run создаёт только в игнорируемом каталоге:

```text
.workspace-state/tracker-runs/<run-id>/
├── scope.json
├── tracker-session-log.md
├── run-status.json
├── jobs/
├── providers/
│   ├── sbertrek.json
│   └── jira.json
├── development-decisions.json        # если аналитик разрешал конфликты ЖЦ
├── pending-development-decision.json # только пока ожидается один ответ
├── reconciled.json
├── report.md
└── completion-status.json
```

Старые незавершённые run прежних версий протокола не продолжаются. Начать новый run.
