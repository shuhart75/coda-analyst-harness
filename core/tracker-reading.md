# Прямое чтение SberTrek и Jira

## Назначение

Протокол `direct-tracker-v1` получает корректный результат коротким линейным
маршрутом. Основной агент сам выполняет каждый MCP-вызов. Дополнительные
оркестраторы, ручные evidence и отдельные этапы сбора не используются.

Протокол поддерживает четыре области:

- один эпик Jira;
- явный набор задач Jira;
- один эпик SberTrek;
- явный набор задач SberTrek.

Провайдер обязателен. Если аналитик не назвал Jira или SberTrek, задай один вопрос
и не запускай `begin`. По синтаксису ключа провайдер не определяется.

## Обязательная последовательность

Перед любым tracker MCP-вызовом отдельно выполни:

```bash
python3 scripts/trackerctl.py config-status
```

Код `3` и `must_stop: true` разрешают только дословный вывод
`response_contract.text`. После готовой конфигурации создай run:

```bash
python3 scripts/trackerctl.py begin \
  --scope-kind <epic|tasks> \
  --scope-provider <jira|sbertrek> \
  --scope-id <KEY> \
  --label <label> \
  --scope-source <source> \
  --intent <read-only|update-planning>
```

Для набора задач повтори `--scope-id`. Один незавершённый run обслуживает один
пользовательский запрос. Повторный `begin` с теми же kind, provider, ids и intent
возвращает его же независимо от формулировок label и source, в том числе после
неудачного ingest. Исправленный полный ответ передаётся тому же `step_id`, после
чего тот же run продолжает маршрут. Другая область блокируется до явной команды
аналитика прекратить текущий run. Только после неё допустим
`abandon-run --analyst-confirmed`; модель никогда не добавляет этот флаг сама.
Не удаляй `tracker-active-run.json` вручную. `begin` сам убирает только осиротевший
маркер, для которого каталога run уже не существует; существующий run всегда
продолжается по его машинному действию.

Далее повторяй только машинный цикл:

1. прочитай `next_action` из ответа `begin`, `ingest` или `run-status`;
2. при `type=mcp-query` вызови указанные `provider`, `tool` и `arguments` без
   изменения параметров;
3. передай полный JSON-ответ в указанную `ingest_command`, заменив только путь и
   `response_source`;
4. выполни следующий возвращённый `next_action`;
5. при `type=reconcile` выполни возвращённую команду;
6. если reconciliation вернул `type=resolve-conflict`, выведи его
   `response_contract.text` дословно и дождись одного решения аналитика;
7. запиши выбранный вариант возвращённой командой `resolve-conflict` и повторяй
   этот шаг по одной задаче, пока снова не будет разрешён `reconcile`;
8. завершённая сверка вернёт `type=result-status`; выполни эту команду и выведи
   `response_contract.text` дословно.

Не запускай `--help`, пробные команды, shell pipeline или альтернативный поиск.
Не отвечай пользователю данными прямого MCP-вызова. До
`final_response_allowed: true` итог запрещён.

## Полный ответ MCP

Оба провайдера используют один полный JSON на шаг. Предпочитай файл, созданный
MCP, с `--response-source mcp-file`. Если JSON вернулся только inline, дословно
сохрани весь ответ во внешний временный файл и используй
`--response-source inline-json-capture`. Файл должен находиться вне каталога run.

Не извлекай карточки вручную, не сокращай ответ и не восстанавливай его по
preview. `ingest` сам определяет провайдера и запрос по `step_id`, считает
карточки, вычисляет SHA-256 и сохраняет компактный снимок. Идентичный повтор
ответа является no-op. Другой ответ для завершённого `step_id`, повреждённый JSON
или ответ не текущего шага переводят run в состояние ошибки, но не уничтожают
его. Ошибка не разрешает ручной итог и не разрешает новый run: исправь полный
ответ и повтори ingest того же pending step. Успешный повтор очищает ошибку и
продолжает обычный маршрут. Отсутствующие `created_at` и `updated_at` сохраняются
как `null` с наблюдением и видимым limitation, а не блокируют сбор.

Каждый запрос использует максимум 50 результатов. Результат ровно из 50 карточек
остаётся пригодным, но получает видимое ограничение
`<provider>-result-limit-reached:50`. Если Jira явно сообщает `total` больше
возвращённого количества, добавляется `jira-result-incomplete:<received>-of-<total>`.
Пагинация в этой версии протокола не моделируется.

## Точные маршруты

Исходный Jira-эпик:

```text
jira_search: "Epic Link" = "KEY"
-> SberTrek issue.exportJson: issue_key = "KEY"
-> если найден ровно один Epic: issue.exportJson по linkedUnitsOf его ключа
-> при необходимости Jira key IN (...) для дополнительных SberTrek-контрпар
-> reconcile
```

Исходные Jira-задачи:

```text
jira_search: key IN ("KEY1", "KEY2")
-> SberTrek issue.exportJson: issue_key = "KEY1" or issue_key = "KEY2"
-> reconcile
```

Исходный SberTrek-эпик:

```text
issue.exportJson: unit IN linkedUnitsOf("unit = 'KEY'", "Состоит из")
-> Jira jira_search по всем заполненным issue_key
-> reconcile
```

Исходные SberTrek-задачи:

```text
issue.exportJson: unit = "KEY1" or unit = "KEY2"
-> Jira jira_search по всем заполненным issue_key
-> reconcile
```

Не добавляй фильтр по статусу или типу. Завершённые задачи нужны для фактической
актуализации.

Для Jira `next_action` всегда задаёт `jira_search`, точный JQL, полный явный
список стандартных и оценочных полей и `limit=50`. Не заменяй его
`jira_get_issue`, `issuelinks` или промежуточным запросом.

Для SberTrek `next_action` всегда задаёт `issue.exportJson`, точный TQL,
`max_results=50` и проекцию с верхнеуровневым `attributes`. Не передавай TQL в
`issue.search.text` и не заменяй export на `issue.getByKey` или `link.list`.

## Отсутствующие Jira-контрпары

Только для шага Jira counterpart допустим `ingest-error`. Передай ему полный
ошибочный ответ. Если Jira явно перечисляет сообщения
`An issue with key 'KEY' does not exist for field 'key'`, программа:

1. подтверждает, что каждый ключ был запрошен текущим шагом;
2. фиксирует отсутствующие ключи;
3. возвращает уменьшенный точный JQL для остальных ключей либо разрешает
   reconciliation, если ключей не осталось.

SberTrek-задача с заполненным `issue_key`, подтверждённо отсутствующим в Jira,
исключается из результата. SberTrek-задача без `issue_key` остаётся. Отсутствие
карточки в успешном поиске само по себе не доказывает удаление и даёт limitation.

Любая другая ошибка исходного или counterpart-запроса завершает run с ошибкой.
Новый run не создаётся автоматически.

## Склейка и оценки

Пара образуется только по правилу:

```text
SberTrek.issue_key == Jira.key
```

Собственные ключи, название и смысл задачи не используются для сопоставления.
Для исполнителя, общей оценки и каждой оценки `AN / BE / FE / QA` Jira заполняет
пропуск SberTrek. Два разных заполненных значения создают значимый
`field-conflict` и останавливают reconciliation на одной задаче. Разные внутренние
идентификаторы одного исполнителя при совпадающем нормализованном ФИО конфликтом
не являются. Конечный служебный маркер Jira `[B]` при сравнении ФИО игнорируется.
Различия ключей связанных эпиков, словарей статусов и служебных дат
не требуют пользовательского выбора и не включаются в `field-conflict`.

Для текущей конфликтующей задачи аналитик выбирает один из вариантов:

- SberTrek только для этой задачи либо также для всех следующих конфликтующих
  задач текущего run;
- Jira только для этой задачи либо также для всех следующих конфликтующих задач
  текущего run;
- собственный вариант по каждому перечисленному полю. Он может выбрать источник
  отдельно для каждого поля или задать явное значение.

Не переноси общий выбор в будущие tracker-run. Пользовательский вариант не
распространяется автоматически на следующие задачи. До разрешения всех значимых
конфликтов `workflow_complete` и `final_response_allowed` остаются `false`.

Действует `1 SP = 1 человекодень`. Другие единицы не преобразуются. Если ролевых
оценок нет, общая оценка становится `AN`, `BE` или `FE` только по одному
однозначному префиксу названия. При наличии хотя бы одной ролевой оценки общая не
создаёт дополнительную полосу. Общий итог равен сумме ролевых work item и только
тех общих оценок, роль которых осталась неразрешённой; разложенная общая оценка
повторно не учитывается.

Каждая заполненная ролевая оценка создаёт отдельный work item и полосу Ганта с
идентификатором `<tracker-key>/<role>`. Название начинается с `AN`, `BE`, `FE`
или `QA`. Ролевые квадратные скобки удаляются: `[FE] Списковая форма` превращается
в `FE Списковая форма`.

## История и состояние

`direct-tracker-v1` не читает историю. Явные конечные и исключающие текущие
статусы используются как подтверждённые. Состояние, для которого нужна история
назначений, остаётся `unknown`, а результат содержит `history-not-collected`.

## Результат

`reconcile` создаёт только машинные результаты:

```text
.workspace-state/tracker-runs/<run-id>/
├── scope.json
├── run.json
├── run-status.json
├── providers/
│   ├── sbertrek.json
│   └── jira.json
├── reconciled.json
├── report.md
└── completion-status.json
```

`result-status` перепроверяет контрольные суммы `reconciled.json`, `report.md` и
готового текста. Только его `response_contract.text` является итогом для
пользователя. В итоговом тексте каждая заполненная ролевая оценка перечисляется
отдельной задачей `<tracker-key>/<role>`; QA не скрывается внутри общей карточки.
