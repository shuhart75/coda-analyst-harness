# Чтение SberTrek

SberTrack (в CLI и сохранённых идентификаторах — `sbertrek`, в колонках —
`SberTrek`) является единственным трекером. Выбор провайдера не требуется.
Используй собственный ключ карточки. Внешние ссылки и служебные атрибуты
`issue_key`, включая `REMOVED_BY_CLONING`, не определяют идентичность,
включение карточки в выборку, владельца или оценки.

## Последовательность

Перед любым поиском MCP-инструментов трекера или чтением отдельно выполни:

```bash
python3 scripts/trackerctl.py config-status
```

Код `3` с `must_stop: true` разрешает только дословный вывод
`response_contract.text` и ожидание ответа. Не выполняй другие команды,
не показывай факты и не делегируй сбор до сохранения ответа и готовности gate.
Сохраняются настройки проектов, типов разработки и статусов SberTrek.
При первом чтении старой конфигурации программа сохраняет её резервную копию
и переносит настройки SberTrek в схему 5; подтверждённые настройки не спрашиваются заново.

Область задаёт текущий запрос аналитика: задачи, один/несколько эпиков,
их объединение или релиз. Если область не задана, используй `scope-preview`
и подтверди её по `core/tracker-adaptive.md`. Не ищи задачи по названию.
Для релиза следуй `core/tracker-release.md`; intent обязателен.

```bash
python3 scripts/trackerctl.py begin --adaptive \
  --scope-kind epic --scope-id PROJECT-123 \
  --label "Эпик" --scope-source "решение аналитика" --intent update-planning
```

`--scope-provider sbertrek` допускается для совместимости и необязателен.
`begin` возвращает `direct-tracker-v1` и одно `next_action`.
Основной агент выполняет сбор сам; tracker work не делегируется.
Адаптивный сбор использует актуальные MCP-capabilities и сохраняет реальный
вызов в `--call-file` по `core/tracker-adaptive.md`.
Legacy-сбор использует только `issue.exportJson`, TQL в `query`, проекцию с
`attributes` и `max_results=50`. Эпик: `unit IN linkedUnitsOf("unit = 'KEY'", "Состоит из")`;
задачи: `unit = "KEY1" or unit = "KEY2"`. Не фильтруй по статусам или типам:
закрытые карточки тоже нужны. Не подменяй запрос поиском по тексту или полным
инвентарём проекта.

Цикл: `begin -> next_action -> ingest -> reconcile -> result-status`.
Только `result-status` с `tracker-read-reconciled`, `collection_complete: true`
и `report_allowed: true` разрешает дословный отчёт из `response_contract.text`.
Для update-planning это промежуточное сообщение: `final_response_allowed: false`,
`response_contract.must_continue: true`; сразу выполни верхнеуровневый `next_action`
(он совпадает с `planning_update.next_action`). Не заканчивай ход на отчёте чтения.
Для read-only разрешён финальный ответ. Не составляй сводку из сырых ответов вручную.

## Полный ответ и повтор

Один запрос обслуживает один незавершённый run. Повторный `begin` с той же
областью и intent возвращает его. После ошибки повтори импорт того же pending
`step_id`; не создавай замену и не удаляй active-marker. `abandon-run` допустим
только по явной команде аналитика. `begin` убирает осиротевший маркер только
при отсутствии его каталога.

Предпочитай полный файл MCP (`mcp-file`); полный inline JSON сохрани дословно
вне run (`inline-json-capture`). Не реконструируй и не правь сырой ответ.
`ingest` сохраняет происхождение, SHA256, размер и компактные карточки.
Идентичный повтор — no-op; другой ответ для завершённого шага, чужой step_id,
неполный JSON или выход за область блокируют импорт. Ошибка сохраняет run и
pending step для повторения. Отсутствующие служебные даты — `null` с ограничением.
Ровно 50 карточек дают `sbertrek-result-limit-reached:50`; заявленные ограничения
полноты нельзя скрывать. Автоматическое объединение страниц не поддерживается.

Неполученная карточка не доказывает удаление. Для задачи из явной области
используй `retry-missing` либо `confirm-absence` с доказательством и явным
решением аналитика. Отсутствие в эпике не разрешает удалять локальную работу.

## Оценки и применение

`reconcile` нормализует только SberTrek. Пустые значения не равны нулю.
Роли определяются префиксами AN/BE/FE/QA, а не специализацией исполнителя.
В adaptive неподдерживаемые роли видны в `skipped`. Один BE/FE-разработчик
может выполнять обе роли. Действует `1 SP = 1 человекодень`; другие единицы
не преобразуются. Общая оценка становится AN/BE/FE только по одному
однозначному префиксу и при отсутствии всех ролевых оценок. Не учитывай её дважды.

Каждая заполненная ролевая оценка показана отдельным `<sbertrek-key>/<role>`
в отчёте. Удали скобки префикса из подписи: `[FE] Форма` -> `FE Форма`.
Это источник оценки, а не разрешение создавать отдельные AN/QA-полосы каждой
карточки. Сначала подтверди владельцев и сопоставление с исполнением.

Сбор не меняет аналитику. Read-only заканчивается отчётом. Для update-planning
после отдельного дословного отчёта продолжи `planning_update.next_action`
по `core/tracker-actualization.md`. Обязательны `application-preflight`,
`execution-preview`/`release-preview`, история и `history-review` до применения
статусов и дат, а затем `qa-application-check`. Текущий статус не задаёт даты.
Неизвестные факты остаются `unknown` с ограничением `history-not-collected` до сбора истории. QA релиза группируется
по `core/tracker-release.md`; общая оценка сохраняется.

## Сохранённое состояние

Незавершённый однотрекерный сеанс SberTrek продолжается с прежними run_id,
step_id, областью и исходными ответами. Старые многотрекерные сеансы не
переинтерпретируются: их продолжение блокируется без изменения файлов.
Исторические ответы, завершённые отчёты, реестры и обменные пакеты не переписывай.
Новые результаты используют схему 2. Применение завершённых результатов прежней
схемы блокируется; их файлы остаются доступны как архивные свидетельства.
Старые внешние ключи не считай ключами SberTrek; отсутствие подтверждённого
ключа требует решения аналитика. Новые реестры содержат `Task ID` и `SberTrek`.

Run сохраняет `scope.json`, `run.json`, `run-status.json`,
`providers/sbertrek.json`, `reconciled.json`, `report.md`, `completion-status.json`.
Проверка результата связывает область, нормализованные факты и контрольные суммы;
изменённый отчёт не разрешает применение.

## Проверка полей оценок

Перед вызовом проверь актуальную схему MCP. В проекцию экспорта включи `attributes`
либо подтверждённые схемой эквивалентные поля оценок; название аргумента проекции
определяется текущим инструментом, а не старым call-file. Не запрашивай `issue_key`.
После ответа проверь наличие полей, а не только число карточек. Явный `null` и
неполученное поле различаются; отсутствие всех полей оценок требует проверки
проекции и формата ответа, а не вывода «оценок в трекере нет».
`result-status.collection_diagnostics` показывает такие карточки, в том числе
для ранее собранных run. Не правь их raw/reconciled и не создавай замену run.
Новый adaptive update-planning импорт issue.exportJson без полей оценок у ролевых
карточек останавливается с `estimate-projection-not-returned`: проверь проекцию,
повтори полный экспорт и ingest в тот же pending step. Явные null и возвращённый
пустой attributes допустимы. Для уже reconciled run диагностика не переписывает
результат: сохраняй ограничение оценок и продолжай проверку владельцев и истории.
Отдельный snapshot истории подтверждает статус/назначения, но не дополняет оценки
reconciled; не обещай восстановить их через history-review.
Нулевое число `work_items` означает отсутствие положительных ролевых оценок,
а не отсутствие задач для actualization или истории. `execution-preview` читает
исходные `issues`; сбор истории обязателен и для created/todo без оценок.

## Исторические реестры

Таблицы прежнего формата с колонками `Jira`, `Summary`, `Kind`, `Role` читаются
без изменения файла. `Jira` используется только как прежний локальный `Task ID`;
это не ключ SberTrack, не провайдер и не основание сопоставления. Собственный ключ
берётся исключительно из явно заполненной колонки `SberTrek`. Диагностика
`legacy-local-identities` сохраняет видимость таких таблиц. Их наличие в соседней
поставке не требует массовой миграции перед чтением истории текущей поставки.
Повреждённые таблицы по-прежнему блокируют проверку; совпадение локального ID
с текущим ключом вызывает `unconfirmed-internal-id-collision` и требует разбора.
Нельзя копировать старые ключи в SberTrek по формату, номеру или названию.

В проверенной установке `issue.exportJson` параметр `fields` возвращал только
базовые поля, а `attributes` — полный набор оценок. Legacy-команда использует
`attributes`; adaptive возвращает `export_hint`, который надо сверить с текущими
capabilities. Не путай имя аргумента проекции с полем `attributes` внутри ответа.

Новые файлы execution-реестров обязаны содержать `Task ID` и `SberTrek`,
непустой локальный `Task ID` каждой строки и не содержать колонку `Jira`.
Историческую таблицу нельзя копировать как шаблон нового файла. Проверка
сравнивает наличие файла с HEAD, поэтому staging и подтверждение SHA256
не разрешают старый формат нового реестра. Используй канонический шаблон
`templates/execution/tasks.template.md`. При исправлении уже созданного файла
сохраняй локальные идентичности строк и связи QA; не меняй их на внешние ключи.

Защищённые строки старых реестров без локального идентификатора сверяются
по полному содержимому и числу повторений. Это не регистрация ключей трекера
и не миграция соседних таблиц. Удаление, изменение или изменение количества
одинаковых защищённых строк блокирует применение, генерацию и сохранение.
