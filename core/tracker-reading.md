# Чтение и сверка трекеров

## Назначение

Этот договор разрешает только чтение фактических данных разработки. Он не разрешает
изменять задачи, комментарии, статусы, исполнителей, оценки, эпики и релизы, а также
требования, планы, Gantt и `actual-progress`.

Рабочий протокол — `active-inventory-v2`. Он сначала получает ограниченные списки
незавершённых задач из обоих трекеров, затем отбирает относящиеся к фиче задачи и
только для выбранных задач читает дополнительные карточки и историю. Старые
schema-8/schema-9 снимки и completion-envelope не продолжаются и не разрешают
показывать результат: после обновления обвязки требуется новый `begin`.

## Стоп-барьер

До обнаружения MCP и любого чтения выполнить отдельную команду:

```bash
python3 scripts/trackerctl.py config-status
```

Её запрещено передавать в `head`, `tail`, `grep`, `jq` и другие фильтры: код
возврата является частью договора. Код `3` и `must_stop: true` разрешают ровно одно
следующее действие: дословно вывести `response_contract.text`. Запрещены вступление,
пояснение, примеры, MCP-вызовы, поиск ключей в проекте и предметная сводка.

MCP разрешён только после готовой конфигурации и успешного `begin`. Все вызовы
выполняет основной агент; делегирование чтения трекеров запрещено. Итог разрешён
только после `reconcile`, вернувшего одновременно:

```json
{
  "status": "tracker-read-reconciled",
  "workflow_complete": true,
  "final_response_allowed": true
}
```

Прямые ответы MCP не являются отчётом. После ошибки или оборванного запуска нельзя
пересчитывать или пересказывать их вручную.

## Настройка

SberTrek — основной источник. Jira — дополнительный и постепенно выводимый из
эксплуатации источник. Имя MCP-сервера не фиксируется: LLM находит доступные
инструменты по возможностям поиска, чтения карточки и истории. Имена серверов,
токены и credentials в Git не записываются.

Локальная конфигурация находится в `.workspace-state/tracker-config.json` и хранит:

- проекты каждого провайдера;
- доступность Jira;
- типы объектов, считающиеся единицами разработки;
- однозначно завершённые и исключающие статусы каждого провайдера;
- соответствие provider account id командным идентификаторам.

При неполной настройке вопросы задаются по одному через `config-status`. Используются
команды `set-projects`, `set-jira-mode`, `set-issue-types`, `set-statuses` и в конце
`complete-config`.

Командный идентификатор одновременно является стабильным id и ролью. Полные формы:
`AN1`, `BE2`, `FE1`, `QA1`; синонимы `A1`, `B2`, `F1`, `Q1` автоматически
нормализуются. `OTHER1`/`O1` допустим только после прямого ответа аналитика.
Один `team_id` не может обозначать несколько account id одного провайдера.

## Алгоритм

### 1. Начало

Определить фичу и известные реальные ключи `PROJECT-123` из её фактических
артефактов. Текстовый поиск не превращает задачу в известный ключ. Для каждого
ключа сохранить источник:

```bash
python3 scripts/trackerctl.py begin \
  --feature cohorts \
  --known-key RSCON-6845=features/cohorts/actual-progress.md
```

`begin` сразу создаёт `run-status.json`, входные снимки и расположенный рядом
`tracker-session-log.md`. Поэтому даже оборванный сеанс диагностируется машинно и
не выглядит как необъяснимая пара JSON-файлов.

### Диагностический журнал MCP

Сразу после каждого реального MCP-вызова и до преобразования его ответа LLM
записывает вызов в журнал:

```bash
python3 scripts/trackerctl.py mcp-log \
  --run-id <run-id> --provider sbertrek \
  --operation inventory --outcome success \
  --evidence mcp:sbertrek:active-search:page-1 \
  --page-number 1 --returned-count 25 \
  --summary 'Получена первая страница незавершённых задач RSCON'
```

Допустимые операции: `capability-discovery`, `inventory`, `issue-detail`,
`history`. Исход `success` означает реально полученный ответ, `error` — реально
выполненный неуспешный вызов. Нельзя регистрировать планируемый или выдуманный вызов.
Имена MCP-серверов, credentials и полные ответы в журнал не записываются.

`inventory-page`, `inventory-unavailable`, `record-issue` и `history-complete`
принимают только evidence, уже зарегистрированный через `mcp-log`. Сам
`trackerctl` автоматически дописывает в тот же журнал результат каждой своей
команды, включая остановку и ошибку. Поэтому журнал различает три ситуации:

- MCP не вызывался;
- MCP-ответ получен, но ещё не преобразован в снимок;
- преобразование было выполнено либо отклонено guarded-проверкой.

### 2. Две активные инвентаризации

Сначала запросить у SberTrek все незавершённые задачи настроенных проектов, затем
таким же отдельным запросом — у Jira. Запрос должен быть ограничен проектами из
конфигурации и явно исключать завершённые задачи. Для страницы записываются все
вернувшиеся ключи и одно предварительно зарегистрированное evidence реального
MCP-вызова:

```bash
python3 scripts/trackerctl.py inventory-page \
  --run-id <run-id> --provider sbertrek \
  --query '<ограниченный запрос незавершённых RSCON>' \
  --scope-project RSCON --unfinished-confirmed \
  --page-number 1 --last-page \
  --evidence mcp:sbertrek:active-search:page-1 \
  --key RSCON-6845 --key RSCON-6893 \
  --jira-link RSCON-6845=RSCON-2902
```

Для непоследней страницы задаётся `--next-cursor`, для следующей — `--cursor`.
Пагинация завершается только `--last-page`. Один MCP-вызов нельзя записывать как
несколько страниц. Число нормальных MCP-вызовов на этом этапе равно числу страниц,
а не числу задач.

Из каждой страницы SberTrek обязательно записать все возвращённые значения поля
`Объект Jira` как `--jira-link SBER_KEY=JIRA_KEY`. Только это поле устанавливает
связь между задачами. Собственные ключи задач могут совпадать или различаться — это
не влияет на сопоставление.

SberTrek обязателен. Если Jira недоступна после реальной попытки, записать
`inventory-unavailable` с причиной и evidence и продолжить с явным ограничением
полноты.

### 3. Отбор задач

Из полных активных инвентарей выбрать кандидатов:

1. уже известные ключи;
2. стороны явных связей `SberTrek.Объект Jira -> Jira.key`;
3. задачи с предметным совпадением названия или описания;
4. соседей по эпику как кандидатов, но не как автоматически относящиеся к фиче.

Не требуется читать и записывать подробную карточку каждой задачи инвентаря.
`record-issue` используется только для выбранных, сомнительных и сознательно
проверенных кандидатов. Если поисковая страница уже содержит полную карточку, её
evidence допустим для этой задачи; отдельный exact-key вызов не нужен. Если данных
страницы недостаточно, выполнить один точный detail-вызов только для этой задачи.

Для каждого поля `assignee`, `estimate`, `epic`, `releases` различаются:

- `value` — значение реально возвращено;
- `absent` — провайдер подтвердил отсутствие;
- `not-returned` — использованный ответ не содержит этого поля.

SberTrek `assigned_to` нормализуется в `assignee`, `story_points` — в `estimate`.
`SP`, story points и человекодни нормализуются в `story-points` по принятому
соотношению `1 SP = 1 человекодень`. Другие единицы молча не преобразуются.

Основание выбора задаётся одним из значений: `known-key`, `linked-counterpart`,
`description-match`, `same-epic`, `ambiguous`. Релевантность: `relevant`,
`ambiguous`, `irrelevant`.

Сомнительная задача блокирует `selection-complete`. LLM выводит только один точный
`next_question`, сохраняет ответ через `decide-relevance` и повторяет проверку.
Вопросы задаются последовательно, а не списком.

`selection-complete` также проверяет замыкание явных связей: если выбранная активная
задача SberTrek имеет активный Jira counterpart, обе стороны должны быть выбраны.
Обратное правило действует для Jira-задачи, на которую указывает активная задача
SberTrek. Название, описание, исполнитель, эпик, релиз и семантическая похожесть
никогда не создают пару.

### 4. История только выбранных задач

История читается только для `relevant` задач после отбора. Для каждой выбранной
задачи выполнить один ограниченный history-вызов, записать нужные события через
`history-event`, затем состояние через `history-complete`. Пустая реально
возвращённая история является `complete`; отсутствие возможности или прав —
`unavailable` с evidence и причиной. Пропуск вызова не является недоступностью.

Правило завершения по передаче исполнителя применяется только теперь, а не при
построении активного инвентаря. Оно относится только к настроенным типам единиц
разработки, включая Story, если Story настроен. Явный завершённый или исключающий
статус основного источника имеет приоритет. Иначе завершение выводится только из
последнего события history, доказывающего передачу от участника с ролью developer
участнику с другой известной ролью.

Неизвестные account id запрашиваются только у выбранных релевантных единиц
разработки и их истории. `reconcile` возвращает ровно одного участника; ответ
сохраняется только guarded-командой:

```bash
python3 scripts/trackerctl.py set-participant \
  --run-id <run-id> --provider sbertrek \
  --account-id 22028314 --team-id B2
```

Затем `reconcile` повторяется и при необходимости задаёт следующий вопрос.
Исполнитель нерелевантной задачи не попадает в эту очередь.

### 5. Финализация и склейка

После завершения выбора и истории финализировать каждый включённый снимок:

```bash
python3 scripts/trackerctl.py snapshot-finalize --run-id <run-id> --provider sbertrek
python3 scripts/trackerctl.py snapshot-finalize --run-id <run-id> --provider jira
python3 scripts/trackerctl.py run-status --run-id <run-id>
python3 scripts/trackerctl.py reconcile --run-id <run-id>
python3 scripts/trackerctl.py result-status --run-id <run-id>
```

Финализированный снимок неизменяем. `run-status` перечисляет машинные gaps.

Склейка выполняется только по `SberTrek.Объект Jira == Jira.key`. Для каждого поля
действует поэлементное правило:

1. использовать заполненное значение SberTrek;
2. если SberTrek не вернул или не содержит значение, дополнить из Jira;
3. если заполненные значения конфликтуют, сохранить SberTrek и явно записать
   расхождение.

Это правило обязательно как минимум для `epic`, `assignee` и `estimate` и также
применяется к остальным склеиваемым полям. Истории объединяются без молчаливой
подмены источника. Эпик и релиз остаются независимыми группировками. Эпик не
считается аналитической фичей без явного решения аналитика.

Успешный запуск создаёт:

- `tracker-session-log.md` — создаётся на `begin` и содержит хронологию MCP и
  guarded-команд;
- `run-status.json` — существует с момента `begin`;
- `input/sbertrek.json` и при включённой Jira `input/jira.json`;
- `reconciled.json`;
- `report.md`;
- `completion-status.json`.

Итоговые counts и limitations берутся только из `completion-status.json` и
`report.md`. Нельзя пересчитывать их вручную. Все runtime-файлы находятся только в
игнорируемом `.workspace-state/tracker-runs/`; Git и аналитические артефакты не
изменяются.
