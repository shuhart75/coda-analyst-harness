# Чтение и сверка трекеров

## Назначение

Этот договор разрешает только чтение фактических данных разработки. Он не разрешает
изменять задачи, комментарии, статусы, исполнителей, оценки, эпики, релизы,
требования, планы, Gantt или `actual-progress`.

Рабочий протокол — `targeted-tracker-v1`. Он получает только явно заданную область:
один эпик либо набор ключей задач в известном трекере. Обвязка сама строит точные
TQL/JQL и не разрешает LLM заменять их полнотекстовым, семантическим или общим
поиском проекта.

## Стоп-барьер

До обнаружения MCP и любого чтения выполнить отдельную команду:

```bash
python3 scripts/trackerctl.py config-status
```

Команду нельзя передавать в `head`, `tail`, `grep`, `jq` или pipeline. Код `3` и
`must_stop: true` разрешают только дословный вывод `response_contract.text`.
Запрещены пояснения, MCP-вызовы, поиск ключей и предварительная сводка.

MCP разрешён только после готовой конфигурации и успешного `begin`. Все вызовы
выполняет основной агент. Имена MCP-серверов не фиксируются: инструменты находятся
по возможности выполнить точный TQL/JQL, прочитать карточку и историю.

Итог разрешён только после `reconcile`, вернувшего одновременно:

```json
{
  "status": "tracker-read-reconciled",
  "workflow_complete": true,
  "final_response_allowed": true
}
```

Прямой ответ MCP не является отчётом. После ошибки или оборванного запуска нельзя
пересказывать полученные данные вручную.

## Определение области

Запрос аналитика сводится к одному из вариантов:

1. известен эпик и известно, в каком трекере находится этот идентификатор;
2. известны ключи задач и известно, какому трекеру принадлежат эти ключи.

Ключи Jira и SberTrek имеют одинаковую форму `PROJECT-123`, поэтому трекер нельзя
угадывать по виду ключа. Если из запроса и фактических артефактов провайдер не
следует однозначно, задать аналитику один вопрос: Jira или SberTrek. Не запускать
оба варианта «на пробу».

Фраза «актуализируй задачи по фиче» сама по себе не разрешает глобальный поиск.
Сначала взять уже сохранённые реальные ключи или явное соответствие эпика этой
фиче. Если подходящей области нет или есть несколько разных областей, уточнить
один эпик либо набор ключей и их провайдера.

Начало для задач:

```bash
python3 scripts/trackerctl.py begin \
  --scope-kind tasks --scope-provider sbertrek \
  --scope-id RSCON-6849 --scope-id RSCON-6848 \
  --label 'Когорты' \
  --scope-source 'features/cohorts/actual-progress.md'
```

Начало для эпика:

```bash
python3 scripts/trackerctl.py begin \
  --scope-kind epic --scope-provider jira \
  --scope-id RSCON-2911 \
  --label 'Когорты' \
  --scope-source 'Ответ аналитика'
```

`begin` создаёт `scope.json`, `run-status.json`, входные снимки и
`tracker-session-log.md`. В ответе `next_query` находится единственный разрешённый
поисковый запрос.

## Точные запросы

### Эпик SberTrek

Использовать только TQL, сформированный обвязкой:

```text
unit IN linkedUnitsOf("unit = 'RSCON-6607'", "Состоит из")
```

### Задачи SberTrek

Использовать один TQL для всех входных ключей:

```text
unit = "RSCON-6848" or unit = "RSCON-6849"
```

### Задачи Jira

Использовать один JQL для всех входных ключей:

```text
key IN ("RSCON-2905", "RSCON-2906")
```

### Эпик Jira

Начать с контролируемого JQL:

```text
parent = "RSCON-2911"
```

Если реальный MCP-вызов завершился ошибкой из-за неподдерживаемого способа связи,
зарегистрировать ошибку и выполнить `jira-epic-fallback`. Только после этого
разрешён второй вариант:

```text
"Epic Link" = "RSCON-2911"
```

Произвольный JQL, текстовый поиск и поиск по названию эпика запрещены.

## Регистрация MCP

Сразу после каждого реального MCP-вызова и до преобразования ответа выполнить
`mcp-log`. Для поискового вызова обязательно передать точный запрос из
`next_query`:

```bash
python3 scripts/trackerctl.py mcp-log \
  --run-id <run-id> --provider sbertrek \
  --operation query --outcome success \
  --evidence mcp:sbertrek:query:page-1 \
  --query 'unit = "RSCON-6848" or unit = "RSCON-6849"' \
  --page-number 1 --returned-count 2 \
  --summary 'Получены две полные карточки SberTrek'
```

`mcp-log` отклонит запрос, который отличается от машинного `next_query`. Нельзя
регистрировать планируемый вызов, имя MCP-сервера, credentials или полный ответ.

После регистрации записать страницу:

```bash
python3 scripts/trackerctl.py query-page \
  --run-id <run-id> --provider sbertrek \
  --query 'unit = "RSCON-6848" or unit = "RSCON-6849"' \
  --page-number 1 --last-page \
  --evidence mcp:sbertrek:query:page-1 \
  --key RSCON-6848 --key RSCON-6849
```

При пагинации непоследняя страница требует `--next-cursor`, следующая — точно этот
`--cursor`. Один evidence нельзя использовать для двух страниц.

## Карточки и связь трекеров

Каждый целевой запрос должен вернуть полные карточки. Каждую карточку записать через
`record-issue`; пропуск хотя бы одного возвращённого ключа блокирует продолжение.
Карточка обязательна для каждого возвращённого ключа.
Если конкретный MCP не возвращает полную карточку в поиске, допускается один
точный detail-вызов для этого ключа.

В карточке SberTrek найти атрибут с `code: issue_key`. Его `value` записать как
`--jira-key`. Это единственный источник связи:

```text
SberTrek.issue_key == Jira.key
```

Запрещено связывать задачи по собственному ключу SberTrek, одинаковым ключам,
названиям, описаниям, исполнителям, эпикам, релизам или смысловому сходству.

Для `assignee`, `estimate`, `epic`, `releases` различать:

- `value` — значение возвращено;
- `absent` — ответ подтвердил отсутствие;
- `not-returned` — использованный MCP-ответ не содержит поле.

SberTrek `assigned_to` нормализуется в `assignee`, `story_points` — в `estimate`.
`SP`, story points и человекодни нормализуются в `story-points` при соотношении
`1 SP = 1 человекодень`. Другие единицы молча не преобразуются.

## Counterpart-запрос

После карточек исходного запроса выполнить `collection-advance`. Обвязка сама
строит один второй запрос.

Если исходными были Jira-задачи либо дочерние задачи Jira-эпика, выполнить только:

```text
issue_key = "RSCON-2905" or issue_key = "RSCON-2906"
```

Это TQL SberTrek по Jira-идентификаторам. Для каждой возвращённой карточки значение
`code: issue_key` должно указывать на один из ключей исходной Jira-области.

Если исходными были SberTrek-задачи либо дочерние задачи SberTrek-эпика, собрать
непустые `issue_key` из карточек и выполнить один JQL:

```text
key IN ("RSCON-2905", "RSCON-2906")
```

Если связанных ключей нет, counterpart-запрос помечается `skipped`. Недоступность
вторичного трекера после реального вызова можно записать через `query-unavailable`;
это создаёт явное ограничение полноты. Недоступность исходного трекера блокирует
запуск.

После записи всех counterpart-карточек повторить `collection-advance`. Только этот
успешный вызов разрешает чтение истории.

## История и команда

Для каждой вошедшей в целевую коллекцию задачи прочитать историю. Пустой реально
полученный список является `complete`; ошибка прав или возможности — `unavailable`
с evidence и причиной. Пропуск вызова не является недоступностью.

Правило завершения по передаче исполнителя применяется только к настроенным типам
единиц разработки. Явный завершённый или исключающий статус SberTrek имеет
приоритет. Иначе завершение выводится только из последнего события, доказывающего
передачу от участника с ролью developer участнику с другой известной ролью.

Неизвестные account id запрашиваются по одному во время `reconcile`. Ответом служит
командный идентификатор `AN1`, `BE2`, `FE1`, `QA1`; синонимы `A1`, `B2`, `F1`,
`Q1` нормализуются. Один `team_id` нельзя назначить двум аккаунтам одного трекера.

## Финализация и склейка

Последовательность протокола:

```text
config-status
-> begin
-> (exact MCP query -> mcp-log -> query-page -> record-issue)
-> collection-advance
-> (exact counterpart MCP query -> mcp-log -> query-page -> record-issue)
-> collection-advance
-> (history MCP -> mcp-log -> history-complete)
-> snapshot-finalize
-> run-status
-> reconcile
-> result-status
```

Склейка выполняется только по `SberTrek.issue_key == Jira.key`. Для каждого поля:

1. использовать заполненное значение SberTrek;
2. если SberTrek не вернул значение, дополнить из Jira;
3. при конфликте сохранить SberTrek и записать расхождение.

Это относится как минимум к `epic`, `assignee`, `estimate`, а также к остальным
склеиваемым полям. Истории объединяются с сохранением источника. Эпик и релиз —
независимые группировки; эпик не равен аналитической фиче без явного решения.

Успешный запуск создаёт в `.workspace-state/tracker-runs/<run-id>/`:

- `tracker-session-log.md`;
- `scope.json`;
- `run-status.json`;
- `input/sbertrek.json` и, когда включена, `input/jira.json`;
- `reconciled.json`;
- `report.md`;
- `completion-status.json`.

Итоговые counts и limitations брать только из `completion-status.json` и
`report.md`. Runtime-файлы игнорируются Git; аналитические артефакты не меняются.
