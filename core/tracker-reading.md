# Чтение трекеров задач

## Назначение

Этот договор описывает только чтение и сверку фактических данных разработки через
доступные LLM MCP-инструменты. Он не разрешает создавать или изменять задачи,
комментарии, исполнителей, оценки, статусы, эпики и релизы и не разрешает
автоматически менять аналитические требования, планы или baseline.

SberTrek является основным трекером. Jira используется как временный дополнительный
источник, пока она доступна. Отсутствие Jira не является ошибкой; отчёт явно
указывает уменьшенную полноту сверки.

## Обнаружение MCP

LLM не зашивает имя MCP-сервера и не просит пользователя каждый раз указывать его.

1. Просмотреть доступные MCP-инструменты и найти возможности поиска задач, чтения
   карточки, истории, связей, эпика и релизов.
2. Классифицировать кандидатов по логическому провайдеру: SberTrek или Jira.
3. Если для провайдера найден ровно один подходящий набор инструментов, использовать
   его независимо от имени сервера.
4. Если найдено несколько кандидатов одного провайдера, задать один вопрос о выборе.
5. Если SberTrek недоступен, не подменять его данными Jira как основным состоянием:
   показать диагностический отчёт и остановить предметную сверку.
6. Если Jira недоступна, продолжить по SberTrek и отметить, что дообогащение и
   контроль рассинхронизации не выполнены.

Имена MCP-инструментов, токены и учётные данные не записываются в Git. Локальная
настройка проектов, явных пар задач, типов единиц разработки, участников и
статусных исключений хранится в
`.workspace-state/tracker-config.json`.

## Ограничение выборки

До запроса LLM определяет ограниченный набор проектов, эпиков, релизов, ключей либо
поисковый фильтр. Нельзя читать весь доступный трекер без прямого указания аналитика.

При первом чтении LLM по одному запрашивает только недостающие настройки:

- проекты SberTrek;
- соответствующие проекты Jira, пока Jira используется;
- способ однозначного сопоставления ключей, если синхронизация не сохраняет связь;
- явные конечные и исключающие статусы, специфичные для команды;
- типы объектов трекера, являющиеся единицами разработки;
- соответствие учётных записей обоих трекеров единому участнику и его роли.

Пустая настройка не является допустимым режимом чтения. Порядок обязателен:

1. Если `tracker-config.json` отсутствует, выполнить `trackerctl.py init-config`.
2. Выполнить `trackerctl.py config-status`.
3. Задать аналитику ровно `next_question`, сохранить ответ соответствующей
   командой `set-projects`, `set-jira-mode`, `set-issue-types` или `set-statuses`
   и снова выполнить `config-status`.
4. После заполнения базовых полей запросить подтверждение сохранённой настройки и
   только после ответа выполнить `trackerctl.py complete-config`.
5. `trackerctl.py begin` обязан завершиться ошибкой, пока настройка не подтверждена.
   LLM запрещено обходить ошибку продолжением сверки с пустыми значениями.

Примеры внутренних команд:

```bash
python3 scripts/trackerctl.py set-projects --provider sbertrek RSCON
python3 scripts/trackerctl.py set-jira-mode enabled
python3 scripts/trackerctl.py set-projects --provider jira RSCON
python3 scripts/trackerctl.py set-issue-types story task
python3 scripts/trackerctl.py set-statuses --kind completed done resolved
python3 scripts/trackerctl.py set-statuses --kind excluded cancelled deleted
python3 scripts/trackerctl.py complete-config
```

Маппинг участника содержит отдельные account id SberTrek и Jira и одну роль:
`developer`, `tester`, `analyst` или `other`. Роль не выводится из имени, статуса,
эпика либо факта назначения. LLM запрашивает роль только для встреченного в текущей
выборке неизвестного участника, по одному участнику за вопрос. До ответа account id
остаётся `unknown`.

Обе учётные записи связываются через единый `canonical_id`. Для участника из
`PROJECT_ROOT/planning/team.md` используется его устойчивая дорожка, например `B1`
или `Q1`. Одинаковый `canonical_id` не может иметь разные роли в двух трекерах.

После чтения снимков `reconcile` проверяет участников настроенных типов разработки.
При неизвестной учётной записи он блокируется и сообщает ровно одного участника.
LLM задаёт аналитику один вопрос, сохраняет ответ и повторяет `reconcile`:

```bash
python3 scripts/trackerctl.py set-participant \
  --provider sbertrek --account-id 123 --canonical-id B1 --role developer
```

Молча назначать роль запрещено.

## Нормализованный снимок

Каждый провайдер преобразуется в JSON схемы 1:

```json
{
  "schema_version": 1,
  "provider": "sbertrek",
  "captured_at": "2026-08-26T00:00:00+00:00",
  "scope": {
    "projects": ["PROJECT"],
    "query": "ограниченный запрос",
    "seed_keys": ["PROJECT-1"],
    "seed_evidence": [
      {"key": "PROJECT-1", "source": "features/example/actual-progress.md"}
    ],
    "expected_epic_keys": [],
    "expected_release_keys": []
  },
  "collection": {
    "history": {"state": "complete", "reason": null},
    "epic_links": {"state": "complete", "reason": null},
    "release_links": {"state": "complete", "reason": null},
    "counterpart_lookup": {"state": "not-applicable", "reason": null},
    "epic_neighbors": {"state": "complete", "reason": null},
    "not_found_keys": [],
    "expanded_epic_keys": ["EPIC-1"]
  },
  "issues": [
    {
      "key": "PROJECT-1",
      "counterpart_key": "JIRA-1",
      "summary": "Название",
      "description": "Описание и ожидаемый результат",
      "issue_type": "development-task",
      "status": "В разработке",
      "assignee": {"id": "u1", "name": "Имя"},
      "estimate": {"value": 3, "unit": "days"},
      "epic": {"key": "EPIC-1", "name": "Эпик"},
      "releases": [{"key": "REL-1", "name": "Релиз"}],
      "discovery": "seed",
      "updated_at": "2026-08-26T00:00:00+00:00",
      "history": [
        {
          "at": "2026-08-25T12:00:00+00:00",
          "field": "assignee",
          "from": {"id": "dev"},
          "to": {"id": "qa"}
        }
      ]
    }
  ]
}
```

`begin` сам создаёт оба шаблона с состояниями `pending`. LLM заменяет каждое такое
состояние на:

- `complete`, если соответствующая возможность действительно вызвана для всей
  ограниченной выборки;
- `unavailable` с непустой причиной, если MCP не предоставляет возможность или
  вызов завершился ошибкой;
- `not-applicable` только для `counterpart_lookup` снимка SberTrek.

Ни одного `pending` перед `reconcile` оставаться не может. Значение `complete`
запрещено ставить только на основании наличия поля в поисковой выдаче: история,
прямые пары и соседи эпика должны быть реально дочитаны. Временные метки копируются
из ответа провайдера без замены часового пояса или повторной интерпретации смещения.
Если `epic_neighbors=complete`, каждый найденный эпик обязан присутствовать в
`expanded_epic_keys`; противоречащий снимок блокируется.

`scope.seed_keys` берётся из уже известных реальных задач аналитической фичи.
Каждый ключ обязан иметь запись `seed_evidence` с путём аналитического источника.
Результат текстового поиска без такого источника не может стать `seed`: он получает
`discovery: feature-search-candidate` и классификацию релевантности.
Эпики и релизы, уже известные из actual-progress, записываются в
`expected_epic_keys` и `expected_release_keys`: если MCP-снимок их не подтвердит,
результат получит явное ограничение полноты.

Точные значения `issue_type` зависят от трекера. В
`development_issue_types` локальной политики перечисляются типы, для которых
действует правило завершения разработки. Туда могут входить `Task`, `Story`,
`Bug` и другие типы проекта. Тип не классифицируется по названию задачи.

Эпик и релизы являются независимыми измерениями. У задачи может отсутствовать эпик,
может быть один эпик и может быть несколько релизов. Эпик не приравнивается к
`features/<feature>` автоматически: соответствие фиксируется отдельно только при
наличии явного решения аналитика.

## Сопоставление задач

SberTrek-задача связывается с Jira только однозначно, в порядке:

1. явная пара из `tracker-config.json`;
2. `counterpart_key` из SberTrek;
3. обратный `counterpart_key` из Jira;
4. полностью совпадающий ключ.

Совпадение названия, исполнителя, эпика или релиза недостаточно.

Каждый явный `counterpart_key` из SberTrek обязательно читается в Jira прямым
запросом по ключу, даже если общий Jira-поиск его не вернул. При полном обходе
отсутствующий ключ записывается в `collection.not_found_keys`. Результат различает:

- `jira-pair-not-found` — прямой запрос выполнен, Jira подтвердила отсутствие;
- `jira-pair-not-read` — прямой запрос недоступен или не завершён;
- `jira-pair-unmapped` — однозначная связь не найдена;
- `jira-only` — Jira-задача не сопоставлена ни с одной SberTrek-задачей.

## Дообогащение

Для каждого поля действует один договор:

- заполненное значение SberTrek является эффективным;
- Jira заполняет только отсутствующее значение;
- ноль, `false` и пустая оценка имеют разный смысл: ноль не считается отсутствием;
- разные заполненные значения не объединяются молча: сохраняется SberTrek и
  создаётся `field-conflict`;
- история не выбирается целиком из одного трекера: события объединяются,
  одинаковые события дедуплицируются, источники сохраняются;
- более свежая Jira не заменяет текущее значение SberTrek автоматически, а
  отражается как расхождение для анализа.

Технически одинаковые типы задач сравниваются без учёта регистра: `story` и
`Story` не являются конфликтом. Статусы разных трекеров не считаются эквивалентными
без отдельного подтверждённого правила.

Оценка сохраняет исходную единицу. Часы, дни и story points не пересчитываются.

## Расширение выборки по эпику

Начальная выборка `seed` строится по уже известным ключам реальных задач. После её
чтения LLM получает каждый найденный эпик и ограниченно читает остальные задачи
этого эпика. Новая задача получает `discovery: epic-neighbor`.

Каждая задача с `discovery: epic-neighbor` или `feature-search-candidate` обязана
иметь `feature_relevance` (`proposed`, `ambiguous`, `confirmed-relevant`,
`confirmed-not-relevant` либо `reviewed-not-relevant`) и непустое
`relevance_basis`. Снимок без этой классификации блокируется.

Для каждой новой задачи LLM сопоставляет название, описание, связи, компоненты,
метки и предметный результат с выбранной аналитической функциональностью:

- при наличии прямой связи с функциональностью, `REQ-*`, переданной декомпозицией
  или известной задачей показывается обоснованное предложение включить задачу;
- при смысловом сходстве без прямой связи задаётся один вопрос аналитику;
- нерелевантная задача остаётся в группе эпика как просмотренная, но не предлагается
  для actual-progress.

Совпадение эпика само по себе не доказывает принадлежность к функциональности.
На этапе чтения найденные задачи только показываются; аналитические файлы не
изменяются.

## Обнаружение релизов

Релизы собираются для начальных и найденных через эпик задач. LLM сравнивает их с
релизами и вехами actual-progress. Отсутствующий релиз показывается как предложение
добавить его в диаграмму с доступными датами и ссылкой на источник. Добавление
выполняется только будущей отдельной операцией применения фактов.

`trackerctl` формирует `release_proposals` детерминированно: это релизы из задач,
которых нет в `scope.expected_release_keys`. LLM показывает этот список без
самостоятельного изменения actual-progress.

## Состояние разработки

Правило переназначения применяется ко всем типам, явно перечисленным в
`development_issue_types`. Поэтому tracker Story может участвовать в правиле, если
в этом проекте она является реальной единицей разработки. Наша аналитическая
planning story не получает такой статус непосредственно: она актуализируется через
связанные реальные объекты трекера.

Порядок определения:

1. Явный исключающий статус, включая настроенные `Отменена` и `Удалена`,
   даёт `excluded` и имеет приоритет над историей исполнителей.
2. Явный настроенный конечный статус даёт `completed-by-status`.
3. Текущий исполнитель с ролью `developer` даёт `in-development`.
4. Если объединённая история подтверждает, что последнее относящееся к
   разработке переназначение выполнено с `developer` на `non-developer` и
   после него задача не возвращалась разработчику, результат равен
   `development-completed-handoff`.
5. При недостаточной истории или неизвестных ролях результат равен `unknown`.

Для любого типа вне `development_issue_types` переназначение исполнителя не означает
завершение. Обвязка показывает его состояние без самостоятельного вывода, кроме
явно настроенного конечного или исключающего статуса.

## Две группировки

Каждая сверка показывает один и тот же набор задач двумя независимыми разрезами:

- по эпикам, включая `Без эпика`;
- по релизам, включая `Без релиза`.

Задача нескольких релизов присутствует в каждой соответствующей группе. Эти
группировки не меняют связи с аналитическими функциональностями.

## Выполнение команды

Команды `прочитай задачи из трекеров`, `проверь задачи в трекерах`,
`сверь SberTrek и Jira`, `покажи текущее состояние по трекерам` и близкие
формулировки означают:

1. проверить этот договор и локальную настройку;
2. обнаружить MCP по возможностям;
3. завершить пошаговую базовую настройку и получить успешный `config-status`;
4. определить seed-ключи и известные эпики/релизы из аналитической фичи;
5. выполнить `trackerctl.py begin` и получить `run_id` и заполненные шаблоны;
6. прочитать ограниченную выборку сначала из SberTrek, затем из Jira, включая
   историю, связи, прямые counterpart-ключи и соседей найденных эпиков;
7. сохранить нормализованные входы только по возвращённым путям под
   `.workspace-state/tracker-runs/<run-id>/input/`;
8. выполнить `trackerctl.py reconcile --run-id <run-id>`; при неизвестном участнике
   задать один вопрос, сохранить роль и повторить команду;
9. показать без ручного пересчёта сводку из `counts`, `limitations` и `report.md`,
   обе группировки, дообогащённые поля, конфликты и неизвестные состояния.

LLM не должна объявлять сверку завершённой после ошибки `begin`, валидации снимка
или `reconcile`. Числа в финальном сообщении копируются из `counts`; запрещено
пересчитывать или пересказывать их по памяти. Если `limitations` непустой, фраза
«ограничений полноты нет» запрещена.

Весь результат остаётся в игнорируемой `.workspace-state/tracker-runs/`.
Команда не переключает режим, не создаёт рабочую ветку и не изменяет
`PROJECT_ROOT`. Применение фактов к actual-progress будет отдельным процессом и
не входит в текущий договор чтения.
