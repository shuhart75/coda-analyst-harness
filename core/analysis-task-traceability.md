# Связь коммитов с задачами SberTrack

Правило действует для аналитического проекта и его передач. Отдельный Git-репозиторий
обвязки и его worktree исключены. Каждому новому аналитическому коммиту нужны
подтверждённый владелец и ключи соответствующих задач SberTrack.
Следуй `core/commit-task-resolution.md`: аналитик выбирает эпик, GigaCode находит
или создаёт в нём задачу типа `suit="task"` нужного вида.

## Виды работ

- Поставка: `[SA][PR] <название поставки>` в её эпике.
- Планирование: `[PLANNING_QUARTER] YYYY-QN` в отдельном эпике этого квартала.
- Baseline и закрытие релиза: `[BASELINE] <название поставки>` в эпике каждой
  затронутой поставки. Вне поставок: `[BASELINE] YYYY-QN` в квартальном эпике.
- Контекст: `[CONTEXT] <название поставки>` либо `[CONTEXT] YYYY-QN` по тому же правилу.

Общие работы не имеют отдельного «общего эпика»: используй эпики реальных владельцев.
Смешанное изменение требует всех ключей. AN/BE/FE/QA остаются ролями исполнения,
но прежнее требование роли AN для задач коммитов заменено классификацией выше.

## Формат связи

Пример, не реальная задача:

```json
{
  "schema_version": 2,
  "provider": "sbertrek",
  "key": "RSCON-1234",
  "suit": "task",
  "kind": "delivery",
  "summary": "[SA][PR] Название поставки",
  "epic": "RSCON-1000",
  "owner": {"type": "delivery", "id": "delivery-key"},
  "confirmation": "Подтверждение эпика аналитиком и ссылка на проверенный результат MCP"
}
```

Для планирования `kind=planning`, `owner.type=quarter`, `owner.id=YYYY-QN`;
название строго `[PLANNING_QUARTER] YYYY-QN`. Для baseline/context kind совпадает
с названием вида, а owner явно определяет поставку или квартал.
Старые связи схемы 1 и роль AN не доказывают соответствие новому правилу:
перед следующим коммитом проверь задачу через процедуру разрешения и сохрани схему 2.
Исторические коммиты, архивы и опубликованные пакеты не переписывай.

## Где хранить

Для поставки: `analysis-task.json` в корне, разрешённом через `project_layout.feature_root`.
Для планирования: `planning/task-bindings.json`, схема реестра 1:

```json
{
  "schema_version": 1,
  "epics": {
    "2027-Q1": {"provider": "sbertrek", "key": "RSCON-1000", "confirmation": "Цитата аналитика"}
  },
  "quarters": {},
  "shared_paths": {"planning/team.md": "2027-Q1"}
}
```

Сначала регистрируется эпик, затем в `quarters[YYYY-QN]` сохраняется полный binding
задачи `[PLANNING_QUARTER]`. До этого коммит планирования запрещён. Эпик и задача
хранятся в одном реестре, но это разные сущности. Пустой `quarters` в примере
означает незавершённую регистрацию, не готовое разрешение на коммит.
Текущий и последующие кварталы связываются со своими эпиками при начале планирования.
Не выводи квартал общего файла по сегодняшней дате; явно укажи его в shared_paths.
Материалы квартала и каталоги planning и execution внутри поставки используют одну
существующую квартальную задачу. Сюда относятся реестр исполнения, QA-группы,
оценки, Ганты и план релизов. Для этих изменений задача [SA][PR] поставки
не требуется. Изменение требований вместе с планированием требует обоих ключей.

Для baseline/context с одним владельцем допустим `baseline/analysis-task.json`
или `context/analysis-task.json` в проекте или внутри поставки. Для нескольких
владельцев и точной области используй корневой `work-task-bindings.json`:

```json
{
  "schema_version": 1,
  "tasks": {},
  "paths": {"baseline/current/": ["delivery-a-baseline", "delivery-b-baseline"]}
}
```

Каждое значение в tasks должно быть полным binding схемы 2. В paths указывай точный
файл или каталог с завершающим `/`; наиболее точная запись имеет приоритет.
Каждый перечисленный владелец требует своего ключа. Не назначай поставки по
содержимому файла автоматически. Для переноса релиза в baseline используй
подтверждённый состав поставок релиза. Категория baseline не подменяется `[SA][PR]`.

## Сохранение

До коммита разреши задачи через `core/commit-task-resolution.md`, проверь изменения
и допустимость записи в текущем режиме. Включи metadata и материалы в один проверенный
коммит. `save-preview` и managed commit-msg hook сверяют обязательные ключи;
hook читает индекс Git, нестадированный binding не удовлетворяет проверке.
Не обходи hook и не подставляй чужую задачу ради сохранения. Отсутствие задачи
означает поиск/создание в известном эпике, отсутствие эпика требует вопроса аналитику.

Ключи обязательны в первой строке каждого нового коммита, включая автоматические,
merge и squash, вместе со смысловым описанием. Пример:
`RSCON-1234, RSCON-5678: Обновить baseline по принятому релизу`.
PR/MR связывается со всеми задачами из коммитов; ключи в его заголовке или описании
необязательны. Используй смысловой `merge_request_title`.

Передачи в разработку несут тот же binding в `manifest.analysis_task`; разработчик
сохраняет его ключ в своих коммитах вместе с дополнительными техническими ссылками.
Проверка локального сообщения не доказывает работу внешней интеграции SberTrack.
