# Задачи SberTrack для поставок и квартального планирования

Каждая поставка связана с задачей SberTrack на аналитику, с ролью AN.
Это правило заменяет прежний запрет номеров задач в коммитах и PR.
Задача относится к конкретной поставке, а не автоматически ко всем кварталам
долгоживущей фичи. Общую задачу для нескольких поставок может подтвердить аналитик.

## Область действия

Правило привязки к SberTrack применяется к аналитическому проекту и его передачам в разработку. Отдельный Git-репозиторий обвязки (HARNESS_ROOT) и его worktree исключены: для их коммитов и PR задача не требуется.
Исключение определяется идентичностью Git-репозитория обвязки, а не именем
каталога или наличием локального конфигурационного файла.

## Хранение и подтверждение

В корне выбранной поставки, разрешённом через `project_layout.feature_root`,
храни `analysis-task.json`. Для legacy-проекта это `features/<feature>/analysis-task.json`.
Пример формата, не реальная привязка:

```json
{
  "schema_version": 1,
  "provider": "sbertrek",
  "key": "RSCON-1234",
  "role": "AN",
  "confirmation": "Точная цитата решения аналитика о задаче для этой поставки"
}
```

Не копируй пример в действующие поставки. Запроси конкретный ключ и подтверждение,
что это задача на аналитику данной поставки. Не определяй роль по исполнителю.
Если требуется прочитать трекер, соблюдай config-status и tracker-протокол;
регистрация связи не разрешает обходить application-preflight или менять исполнение.

Файл создаётся или меняется в рабочей ветке владельца поставки в её текущем режиме,
вместе с соответствующей аналитической работой. Он является метаданными связи,
не реестром исполнения и не вторым документом требований. Для актуализации
сохраняются границы execution scope и обязательные проверки записи.
Связь должна быть зарегистрирована до сохранения и передачи поставки.
Смена задачи требует нового явного решения аналитика. Чтение старых материалов
не блокируется, исторические коммиты и опубликованные входы не переписываются.
Старые поставки без связи требуют её регистрации перед следующей записью/передачей.

## Одна задача планирования на квартал

Планирование каждого квартала имеет ровно одну подтверждённую задачу SberTrack
на аналитику. Все его коммиты используют этот ключ. Задача отдельной
поставки не заменяет квартальную задачу планирования.

Храни связи в `planning/task-bindings.json` аналитического проекта:

```json
{
  "schema_version": 1,
  "quarters": {
    "2026-Q4": {
      "schema_version": 1,
      "provider": "sbertrek",
      "key": "RSCON-5678",
      "role": "AN",
      "confirmation": "Точная цитата аналитика о задаче планирования квартала"
    }
  },
  "shared_paths": {
    "planning/team.md": "2026-Q4"
  }
}
```

Это пример, а не готовая привязка. Квартальный ключ хранится один раз в `quarters`.
`shared_paths` задаёт квартал для общих материалов и legacy-планирования, где
квартал нельзя однозначно получить из пути или `delivery-index.json`.
Не назначай квартал по сегодняшней дате или по исполнителю. Запроси его у аналитика.
Для файла оценки с кварталом в имени используй именно этот квартал, включая архивные
оценки; существующие запреты изменения утверждённых планов и истории сохраняются.

Материалы квартала в `quarters/<quarter>/` и `planning/<quarter>/`, включая планы,
Гант и прогнозы, относятся к задаче квартального планирования. Материалы самой
поставки сохраняют её задачу; её каталог `planning/` относится к планированию
квартала поставки. Чистый коммит планирования не требует задачи поставки только
из-за того, что рабочая ветка названа по фиче. Смешанный коммит требует ключи всех
затронутых поставок и кварталов. Для общих файлов укажи квартал в `shared_paths`.

## Обязательный вопрос перед коммитом

До индексирования при управляемом сохранении проверь связи всех изменённых
материалов. Если у поставки нет корректной связи, спроси: «Какую задачу SberTrack
на аналитику связать с поставкой <поставка>?» Если нет связи планирования, спроси:
«Какую задачу SberTrack связать с планированием квартала <квартал>?»
При нескольких пробелах задавай вопросы последовательно и сохраняй уже полученные
ответы. Ответ о квартальной задаче действует для всего квартала; повторно её
не запрашивай, пока аналитик не меняет связь.

До ответа не коммить, не отправляй ветку и не подставляй номер из текста сообщения
вместо сохранённой связи. После ответа зарегистрируй точный ключ и подтверждение
в рабочей ветке, повтори проверки и включи файл связи в тот же проверенный коммит.
`save-preview` также проверяет связи и выдаёт обязательные ключи в команде сохранения.
Git hook повторно проверяет индекс и блокирует прямой коммит с отсутствующей связью
или неправильным ключом. Нестадированный файл связи не удовлетворяет проверке.

## Коммиты и PR/MR

Формат заголовка: `RSCON-1234: Уточнить правила согласования`.
При нескольких поставках: `RSCON-1234, RSCON-5678: Обновить прогноз поставок`.
Ключ должен быть в заголовке, а не только в теле или названии ветки.
Используй точный ключ SberTrack в верхнем регистре. Ключи BE/FE/QA разрешены
как дополнительные ссылки, но не заменяют обязательный ключ AN.

Правило действует для каждого нового коммита, включая merge, squash,
передачу требований, обратную заплату и очистку обмена. Для общих изменений,
не принадлежащих поставке, аналитик указывает задачу AN этой работы;
служебный характер изменения не освобождает от ключа в заголовке.
Не придумывай связь ради прохождения проверки.

`commit_message_policy.py` проверяет заголовок. Managed Git hook дополнительно
сверяет ключи затронутых поставок и квартального планирования с **индексом Git**, включая файлы связи и
манифесты обмена. `collaboration.py save` определяет связи по изменённым материалам до индексирования.
Создающие сообщения команды берут ключ из связи поставки; без неё останавливаются.
Обратная заплата читает связь из проверенного целевого дерева; для общей работы
вне поставок принимает повторяемый `--analysis-task` с подтверждённым ключом.

Команды подготовки/submit возвращают смысловой `merge_request_title` без обязательных ключей.
PR/MR автоматически связывается со всеми задачами, указанными в его коммитах.
Повторять ключи в заголовке или описании PR не требуется. При merge или squash
сохрани все обязательные ключи в заголовке создаваемого коммита.
Создание и принятие PR остаются отдельными действиями согласно правилам совместной работы.
Hook проверяет сообщения локально, но не доказывает наличие внешней связи в SberTrack.

## Передача разработчикам

Новые манифесты несут `analysis_task` с тем же объектом, что и файл поставки.
Разработчик включает этот ключ в заголовки своих коммитов вместе
с нужными ему ссылками на технические задачи. Отсутствие связи требует уточнения
у аналитика. Старые неизменяемые пакеты не дописываются задним числом.
При очистке старого пакета команда берёт текущую подтверждённую связь поставки,
сохраняя архив без изменений.
