# Режим требований

## Назначение

Режим создаёт и изменяет один авторский документ `features/<feature>/requirements.md`, проверяет его качество и по явной команде передаёт неизменяемую редакцию через `requirements-exchange/`.

## Граница записи

В обычной работе режим изменяет только:

- `features/<feature>/requirements.md`;
- `features/<feature>/requirements-state.json`;
- вспомогательные `context-summary.md`, `artifact-map.md` и результаты исследования, когда они действительно нужны.

Режим не создаёт и не обновляет срезы, пакеты клиентской или серверной части, предварительные задачи разработки и файлы `returns/`.

## Авторский документ

- Используй `templates/requirements/feature-requirements.readable.template.md`.
- Следуй `core/requirements-profile.md`.
- Излагай требования по ходу пользовательского или системного процесса.
- В каждой функциональной главе сохраняй порядок: результат, условия, основной ход, правила, исключения, примеры приёмки, влияния.
- Каждое нормативное правило оформляй отдельным `REQ-*` с человекочитаемым заголовком.
- Диаграммы встраивай в тот же Markdown только в PlantUML.
- Таблицы применяй для сравнений, данных и трассировки, но не превращай весь документ в реестр атомарных строк.
- Пиши по-русски; английский оставляй только для точного кода, путей, идентификаторов и необходимых специальных терминов.

## Обычное изменение

1. Выполни `requirementsctl.py status`.
2. Если обнаружена незарегистрированная разница, выясни её источник до новых правок.
3. Измени только корневой `requirements.md`.
4. Проверь текущую реализацию точечно и только для фактов, необходимых требованиям.
5. Проверь влияния и устаревшие хвосты.
6. Выполни языковую, ссылочную и профильную проверки.
7. Запиши источник через `requirementsctl.py record-change`.
8. Не создавай редакцию обмена без явной команды передачи.

## Источник изменения

- `analyst` — изменение по инициативе аналитика. Если требования уже передавались, один раз предложи новую редакцию. После отказа не повторяй предложение до явной команды.
- `developer-result` — принятое уточнение из возврата разработческой SDD. Укажи `return_id`. Такое изменение не создаёт и не предлагает новую редакцию.

## Команда передачи

Каноническая команда: `сформируй пакет для разработки`.

Равнозначны:

- `передаём в разработку`;
- `передаем в разработку`;
- `отдаём требования разработчикам`;
- `отдаем требования разработчикам`;
- `подготовь требования для разработки`;
- `собери пакет для разработчиков`;
- `отправь требования в разработку`;
- `передай требования разработчикам`;
- `передай разрабам`;
- `отдай требования разрабам`;
- `отправь разрабам`;
- `отдаём в разработку`.

В многопользовательской рабочей области сначала заверши принятую рабочую ветку и докажи, что требования находятся в актуальной `analytics/main`.

Далее:

1. Выполни `requirementsctl.py begin-preparation`. Команда только начинает обязательный аудит и не разрешает публикацию.
2. Проведи полный аудит по разделу «Обязательный аудит перед передачей» в `core/requirements-profile.md`.
3. Выполни точечную сверку с кодом, если без неё нельзя подтвердить текущее состояние. Принимающая SDD повторит сверку по своей актуальной ветке.
4. Исправляй автоматически только однозначные ошибки без изменения предметного смысла.
5. Если требуется предметное решение, задавай аналитику по одному вопросу. Не придумывай ответ и не переходи к публикации.
6. Запусти `validate-requirements-profile.py`, `validate-language.py`, проверку ссылок и `git diff --check`.
7. Запиши итог через `requirementsctl.py record-audit`. Блокирующие замечания должны иметь ненулевой `--blocking-finding-count` и запрещают подтверждение.
8. Покажи в чате итог, проверенные направления, таблицу замечаний, остаточные риски, предположения и контрольную сумму. Заверши вопросом: `Подтверждаете результат аудита и отправку требований в разработку?`
9. Остановись и дождись явного ответа. Исходная команда передачи не считается подтверждением аудита.
10. После положительного ответа выполни `requirementsctl.py confirm-audit`. Если документ изменился, команда заблокирует продолжение: повтори аудит.
11. Выполни `requirements-exchange.py prepare <project> <feature>`. Скрипт независимо проверяет подтверждение и контрольную сумму.
12. Скрипт сам выберет существующий доступный каталог в роли `code` либо резервный каталог в роли `analytics`.
13. Выполни `requirementsctl.py mark-published` с манифестом, редакцией и фактической ролью из результата.
14. Сообщи абсолютный путь, роль размещения, функциональность и редакцию.

После подтверждения редакция сразу получает состояние `sent`. До подтверждения редакции обмена нет; состояние аудита не является промежуточным пакетом `ready`. ZIP не создаётся.

## Новые результаты разработки

Команды `проверь результаты разработки`, `проверь возвраты разработчиков`, `есть ли новые результаты` запускают:

```text
requirements-exchange.py scan <project>
```

По умолчанию показываются результаты текущего аналитика. Команды `покажи все новые результаты разработки` и `посмотрим, что пришло другим аналитикам` добавляют `--all`.

Перед изменением требований:

1. покажи новые результаты и выбери один;
2. сопоставь его с `REQ-*`;
3. отдельно реши, что меняется в требованиях, baseline и оставшейся работе;
4. зарегистрируй обработку через `record-processed`;
5. если требования изменились, вызови `record-change --origin developer-result --return-id ...`.

Другой аналитик может просмотреть чужие результаты без смены владельца. Обработку чужого результата начинай только после его явной команды.

## Запреты

- Не создавать срезы и отдельные требования по контурам.
- Не формировать предложения или черновики задач за разработчиков.
- Не записывать что-либо в `returns/`.
- Не изменять старые редакции требований.
- Не изменять код или обычный рабочий клон роли `code`.
- Не создавать `requirements-exchange/` в роли `code`, если разработчики не создали его заранее.
- Не объявлять передачу успешной, не указав фактическое место размещения.
