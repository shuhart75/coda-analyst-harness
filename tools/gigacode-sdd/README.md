# GigaCode SDD Runner

Локальный контроллер GigaCode для Mac: отдельные headless-сессии выполняют задачи по существующей SDD-обвязке, свежие сессии проверяют результат, замечания возвращаются исполнителям. Независимые задачи идут параллельно в отдельных Git-копиях. Контроллер сохраняет текущую работу над PoC и собирает проверенные изменения в собственной интеграционной копии.

Требуются Python 3.10+, Git и уже установленный, авторизованный GigaCode CLI с `stream-json`, `--prompt` и `--approval-mode`. Python-библиотеки устанавливать не нужно. Этот пакет сам ничего не скачивает.

## Обычный запуск на Mac

1. Распакуйте архив и дважды щёлкните `Start-GigaCode-SDD.command`. Он сам выбирает рабочий каталог; открывать Terminal и вводить пути не нужно.
2. Выберите продолжение сохранённой работы или новый запуск. Для нового запуска программа предложит найденные проекты. Если нужного каталога нет среди найденных, укажите его через окно выбора папки.
3. Программа проверит установленное ПО и работающие сервисы. Если старый GigaCode держит стенд или связь процессов не удалось установить, запуск остановится с отчётом. **Не завершайте старую сессию по одному лишь совету в промпте.**
4. Выберите пакет требований из найденных вариантов или через окно выбора. Подтвердите показанные проект и пакет. Дальше runner сам выполнит проверку разрешений, составит план и запустит исполнение с независимым ревью. Оставьте открывшееся окно Terminal работающим.

Хеш требований, каталог состояния и `config.json` создаются автоматически. В обычном сценарии сотрудник не вводит их вручную. Выбор пакета остаётся содержательным решением: программа фиксирует выбранные файлы, но не считает самый новый по дате каталог правильной редакцией.

Если работа началась в прежнем чате GigaCode, выберите сохранённый экспорт JSONL как дополнительный контекст или пункт «Без журнала». Это необязательный шаг. История помогает найти уже принятые решения и незаконченные действия, но не заменяет выбранные требования, фактический код и результаты проверок. Утверждение прежнего агента «готово» проверяется заново; старая редакция и команды из истории не становятся новым заданием.

Автопоиск сопоставляет точный каталог проекта; журнал из другого каталога требует отдельного подтверждения связи с PoC, которое фиксирует выбор и SHA журнала, но не подтверждает его происхождение или приёмку результата.

Состояние запусков на Mac хранится в `~/Library/Application Support/GigaCode SDD/runs/`. При повторном запуске выберите сохранённую работу, если нужно её продолжить. Для новой редакции требований нужен новый запуск. Программа не заменяет вход старого запуска другим пакетом.

Если не хватает Python 3.10+, Git или авторизованного GigaCode CLI, программа сообщит, чего именно не хватает. Сама она ничего не устанавливает и не скачивает. Разрешения, доверие к папкам и корпоративные ограничения проверяются на этой машине, а не считаются настроенными по результатам тестов разработчика.

## Если GigaCode уже поднял собственный стенд

Сначала передайте **текущему** агенту текст из `SAFE-HANDOFF-PROMPT.txt`. Он просит прекратить дальнейшее изменение кода, сохранить сведения о работающем стенде и не завершать процессы. Для нового чата используйте `MAC-PROMPT.txt` после выяснения зависимостей стенда.

Закрытие сессии может завершить PostgreSQL, backend или frontend, если они принадлежат её группе процессов или управляются её фоновыми задачами. Отвязавшийся процесс, наоборот, может остаться работать. Сам факт, что сервис сейчас отвечает, не доказывает возможность безопасно закрыть агента.

Встроенная диагностика читает доступные процессы текущего пользователя, их рабочие каталоги и слушающие TCP-порты. Процессы PostgreSQL учитываются и без TCP-порта. Диагностика ничего не останавливает, не переподчиняет процессы и не переносит их в `launchd`. Неполный снимок остаётся явным ограничением. Даже полный снимок не заменяет проверку способа запуска, сохранности данных и восстановления сервиса; он не охватывает все возможные зависимости.

Для отдельной диагностики выберите «Только диагностика» при повторном запуске или выполните:

```bash
python3 bootstrap.py --diagnose --repo '<каталог текущего PoC>'
```

Отчёт сохраняется с правами `0600`; полный список аргументов процессов и значения переменных окружения в него не попадают. На Mac каталог отчётов находится в `~/Library/Application Support/GigaCode SDD/diagnostics/`. Отчёт описывает наблюдаемые процессы, но не даёт разрешения их завершить.

Перенос управления стендом требует отдельной проверки его существующих скриптов и данных. Пока этого нет, исходный агент и зависимые сервисы сохраняют. Runner не принимает уже работающий стенд под своё управление автоматически.

## Что сохраняется при переходе

Runner работает с отдельной Git-копией текущего PoC и сохраняет незакоммиченный код. Исходный каталог и зарегистрированный основной code-клон остаются защищёнными. Существующие SDD-инструкции в `backend/` и `frontend/` обязательны; другая методика вместо них не устанавливается.

Во время работы контроллера исходный PoC и защищённый code-клон должны оставаться неизменными. Если другой агент продолжит их редактировать, проверка снимков остановит дальнейшую работу. Не удаляйте каталог состояния после ошибки: там остаются исходный снимок, рабочие копии, частичные результаты и логи.

## Ручная настройка для технического специалиста

Следующие команды нужны для диагностики и нестандартного окружения. При обычном запуске через `Start-GigaCode-SDD.command` вводить их не требуется.

Распакуйте полученный архив в отдельный каталог и перейдите в него. Здесь и далее значения в угловых скобках нужно заменить фактическими значениями; это не готовые пути вашего Mac.

```bash
cd '<каталог распакованного gigacode-sdd>'
python3 --version
git --version
gigacode --version
python3 sdd-runner.py --help
```

Проверьте хеш выбранного документа и сопоставьте его с переданным пакетом:

```bash
shasum -a 256 '<пакет>/<относительный путь требований>'
```

Создайте новый запуск. `--state-dir` должен указывать на ещё не существующий каталог вне исходного PoC и защищённых репозиториев. `--commit-prefix` содержит реальный ключ задачи или другой префикс, который разрешают действующие правила и Git hooks данного проекта. Контроллер не подбирает ключ за аналитика.

```bash
python3 sdd-runner.py init \
  --repo '<текущий отдельный Git-каталог PoC>' \
  --packet '<каталог новой редакции пакета>' \
  --requirements-file '<относительный путь требований внутри пакета>' \
  --requirements-sha256 '<подтверждённый SHA256>' \
  --state-dir '<новый каталог состояния вне репозиториев>' \
  --protected-root '<зарегистрированный основной code-клон>' \
  --commit-prefix '<подтверждённый префикс коммитов>' \
  --nexus-host 'nexus-ci.delta.sbrf.ru' \
  --npm-registry '<фактический HTTPS Nexus npm endpoint>' \
  --jobs 8
```

Если npm-загрузки не нужны, уберите `--npm-registry`. Без Nexus endpoint, выбранного аргументом или переменной окружения, npm работает offline. Для загрузок через pip передайте `--pip-index-url '<HTTPS Nexus endpoint>'`; без endpoint, выбранного аргументом или окружением, pip получает `PIP_NO_INDEX=1`. Унаследованный публичный URL реестра вызывает блокер, а не молча принимается. Допускаются несколько `--nexus-host` и `--protected-root`. Не придумывайте endpoints по имени сервера.

`--cli` позволяет указать фактический путь GigaCode CLI. `--session-timeout` задаёт предельную длительность одной сессии в секундах, по умолчанию 3600. Это ограничение зависшего процесса, а не общий лимит работы или токенов.

`init` выводит путь `config.json`. Сохраните его для следующих команд:

```bash
SDD_CONFIG='<каталог состояния>/config.json'
```

При подготовке контроллер:

- копирует текущий PoC в `work/main`, не меняя исходные файлы и индекс;
- сохраняет незакоммиченный код в локальном базовом коммите собственной копии;
- переносит SDD-контекст и разрешения, сохраняя `ask` и `deny`;
- сохраняет переносимые Git hooks и выполняет локальные коммиты с ними;
- фиксирует входной пакет и хеши файлов.

Игнорируемые build artifacts, `node_modules`, локальные секреты и настройки подключения не являются переносимым исходным кодом. Их отсутствие в новой копии может потребовать подготовки окружения через Nexus. Просмотрите `clone_report` в `config.json`, особенно список `skipped`. Не отключайте hooks ради прохождения `init`; непереносимый hook требует отдельного решения.

Изменённые отслеживаемые секретные файлы и защищённые файлы инструкций вызывают блокер при создании исходного снимка или его базового коммита. Runner не отбрасывает эти изменения молча: исходный каталог остаётся неизменным, уже созданная рабочая копия сохраняется для разбора. Не удаляйте изменения ради запуска. Устраните причину согласно правилам проекта и выберите новый каталог состояния для повторного `init`.

## Проверка разрешений

```bash
python3 sdd-runner.py preflight --config "$SDD_CONFIG"
```

Начальный preflight параллельно запускает реальные headless-сессии в отдельных пробных копиях корня, backend и frontend, с учётом `jobs`. Для исполнения проверяются чтение, запись, shell и синхронный субагент с полученным ответом. Для ревью проверяются чтение, shell и субагент в режиме `plan`. В backend/frontend обе роли дополнительно вызывают установленный SDD skill в режиме чтения или справки; в корне наличие такого skill не требуется. Наличие инструмента в списке CLI не считается успешной проверкой: нужны события фактического вызова и возврата.

Исполнители работают с `auto-edit` и подготовленным списком разрешённых инструментов. Ревьюеры работают с `plan`. `auto-edit` сам по себе не даёт безусловных разрешений на shell, skills, агентов и MCP. Глобальные правила, доверие к папке, `ask`, `deny`, shell security policy и подтверждения MCP сохраняются. Если они блокируют обязательный инструмент, runner останавливается с диагностикой вместо бесконечных запросов в чат.

Смотрите `preflight.json` и соответствующие `logs/*/stdout.jsonl`, `stderr.log`. Исправьте именно обнаруженную настройку штатным способом и повторите preflight. Не обходите отказ альтернативным shell-синтаксисом. Успех пробной копии не гарантирует, что политика доверия конкретной версии CLI автоматически распространится на каждую новую рабочую копию; отказ при исполнении также останется видимым блокером.

## План и выполнение

Основная команда запускает недостающий preflight, готовит план и выполняет работу:

```bash
python3 sdd-runner.py start --config "$SDD_CONFIG"
```

При необходимости этапы можно вызвать отдельно:

```bash
python3 sdd-runner.py plan --config "$SDD_CONFIG"
python3 sdd-runner.py run --config "$SDD_CONFIG"
```

Планировщик читает закреплённые требования, текущий PoC и существующую SDD-обвязку. План включает зависимости, область изменяемых файлов, разделяемые ресурсы и команды проверок. Подготовка SDD design/tasks становится явной предпосылкой разработки, если этого требует местная обвязка. Существующая нарезка согласованных задач сохраняется. Отдельный ревьюер проверяет план против полного входа. Замечания возвращаются планировщику на исправление; внешние блокеры и необходимые решения аналитика остаются явными остановками.

`--jobs 8` задаёт восемь параллельных заданий контроллера. Внутри задания последовательны исполнение, проверки и независимое ревью. Зависимые задачи, пересекающиеся области записи и одинаковые метки разделяемых ресурсов сериализуются. При наличии подходящих независимых задач число можно увеличить через новый запуск. Число внутренних субагентов GigaCode этим параметром отдельно не ограничивается.

После каждого исполнения запускаются команды проверок из закреплённого плана. Свежий ревьюер получает отдельную копию результата, проверяет код и свидетельства выполнения требований. При замечаниях исполнитель продолжает работу с сохранёнными изменениями. После сборки всех задач проходит общий цикл интеграционных проверок и независимого ревью.

Лимита токенов и общего числа исправлений нет. Внешний блокер, необходимость бизнес-решения, нарушение границ записи, отказ разрешения или повторяющаяся одинаковая ошибка без прогресса требуют устранения причины. Контроллер не ослабляет требования ради завершения. Запись `complete` означает завершение проверок этого запуска; приёмка аналитиком, работа на реальном стенде и внедрение подтверждаются отдельно.

## Наблюдение, остановка и продолжение

В другом терминале:

```bash
python3 sdd-runner.py status --config "$SDD_CONFIG"
```

`Ctrl+C` запрашивает остановку runner и сохраняет его состояние. Перед завершением принадлежащей ему группы процессов runner проверяет, нет ли в ней слушающего сервиса. Если сервис найден или состояние живой группы не удалось проверить, группа сохраняется, а дальнейшие задачи и возобновление блокируются. Причина и сведения о процессах остаются в приватном отчёте. Не обходите такой блокер повторной командой остановки или очисткой файлов состояния.

После сессии также проверяются новые слушающие сервисы, которые удалось связать с её рабочей копией. Обнаруженный отдельно запущенный сервер требует разбора, даже если основная сессия уже закончилась. Эта проверка не является полной изоляцией ОС: произвольно отвязавшийся процесс со скрытой связью может остаться незамеченным. Уже работающий внешний стенд runner автоматически не принимает под управление.

Когда причина остановки устранена, для продолжения используйте прежний `config.json`:

```bash
python3 sdd-runner.py run --config "$SDD_CONFIG"
```

При состоянии `blocked` сначала прочитайте причину в status и логах. Если нужно решение аналитика, запишите его в `<каталог состояния>/decision.md`. Этот файл уточняет исполнение, но не заменяет закреплённые требования и не снимает проверки. После устранения причины:

```bash
python3 sdd-runner.py start --config "$SDD_CONFIG" --retry-blocked
```

Изменение конфигурации требует повторного preflight. Новая редакция требований требует нового запуска; `input/` и закреплённый план вручную не переписывают. Если применение патча или hook прервали интеграционный коммит, не делайте `reset --hard`: сначала проверьте сохранённую интеграционную копию и причину отказа. Применение патча и коммит фиксируются в журнале интеграции. После устранения причины отказа hook продолжайте через `start --retry-blocked`: runner использует журнал, чтобы не применять уже внесённый патч повторно. Не изменяйте журнал вручную и не обходите hook.

Логи содержат полный вывод инструментов и могут включать чувствительные сведения. Они создаются с ограниченными правами. Не публикуйте их без проверки.

## Результат

После `complete`:

```bash
python3 sdd-runner.py export \
  --config "$SDD_CONFIG" \
  --output '<новый путь вне исходного PoC>/poc-result.patch'
```

Рядом появится JSON с базовым и итоговым коммитами, SHA256 патча и требований. Патч содержит изменения **относительно сохранённого состояния PoC при `init`**, включая его тогдашнюю незакоммиченную работу в базовом снимке. Это не патч от исходного чистого коммита продукта. Полная итоговая копия находится в `<каталог состояния>/work/main`.

Перед переносом сверьте базу, состояние получателя и выполните `git apply --check` в выбранной отдельной копии. Сам runner не применяет результат к исходному PoC, не переключает работающий стенд, не делает push или merge. Пока перенос не выполнен, текущий стенд продолжает использовать прежний код.

## Ограничение Nexus

Каждая сессия получает прямой запрет публичных скачиваний и fallback. Проверяются поддерживаемые package manifests, lock-файлы и конфигурации зависимостей. pip fallback отключается; без явно выбранных Nexus endpoints npm/pip не должны использовать публичные endpoints по умолчанию.

Это **инструкции, настройки и статическая проверка, а не сетевая песочница ОС**. Shell-скрипт может переопределить окружение; редиректы, все возможные загрузчики и глобальные настройки Maven/npm не охвачены. Для технической гарантии запрета внешних скачиваний нужна корпоративная сетевая политика с разрешением необходимых LLM-сервисов и Nexus. Нельзя объявлять её наличие по успешному preflight. Maven-аудит консервативен: публичный repository URL может блокироваться даже при настроенном Nexus mirror.

## Промпты для передачи работы

- `SAFE-HANDOFF-PROMPT.txt` предназначен для текущего агента, который мог запустить стенд. Это только обследование и сохранение сведений без остановки сервисов.
- `MAC-PROMPT.txt` предназначен для нового чата. Он направляет к обычному запуску через `Start-GigaCode-SDD.command` и запрещает агенту создавать ещё один стенд ради подготовки.

## Локальные тесты runner

```bash
python3 -m unittest discover -v
```

Тесты используют временные репозитории, имитацию CLI и подставные ответы диалогов. Они проверяют контроллер и обработку событий. Запуск двойным щелчком в Finder и реальные диалоги macOS здесь, на Linux, не проверялись; первый запуск и preflight установленного GigaCode нужно проверить на Mac.
