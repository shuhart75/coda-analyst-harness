# GigaCode SDD Runner

Локальный контроллер для Windows, macOS и Linux. Отдельные headless-сессии выполняют задачи по существующей SDD-обвязке, свежие сессии проверяют результат, замечания возвращаются исполнителям. Независимые задачи идут параллельно в отдельных Git-копиях. Контроллер сохраняет текущую работу над PoC и собирает проверенные изменения в собственной интеграционной копии.

Требуются Python 3.10+ (64-разрядный в Windows), Git и установленный, авторизованный GigaCode CLI с `stream-json`, `--prompt` и `--approval-mode`. Используется стандартная библиотека Python. Runner ничего не скачивает и не устанавливает.

## Обычный запуск

Код получают через принятый в организации Git или Nexus. Для переписки достаточно текстовой инструкции `START-PROMPT.txt`. Отдельных файлов запуска `.com`, `.command`, `.bat`, `.ps1` и `.exe` в пакете нет.

1. Обновите установленную обвязку через разрешённый канал. Откройте самостоятельный терминал: PowerShell в Windows, Terminal в macOS или терминал Linux.
2. Из корня обвязки выполните одну команду установленным Python:

   ```text
   python tools/gigacode-sdd/bootstrap.py
   ```

   Если установленный интерпретатор вызывается как `python3` или `py -3`, используйте это имя. Для запуска из любого каталога подходит полный путь к `bootstrap.py` в кавычках. Текст `START-PROMPT.txt` просит GigaCode найти существующие пути и дать одну точную команду под вашу оболочку.
3. Выберите продолжение или новую работу. Консольный мастер предложит найденные проекты и пакеты требований. Выбор делается номером; если нужного варианта нет, введите полный путь. Для отмены введите `q`.
4. Мастер проверит работающие сервисы. Если старый GigaCode держит стенд или связь процессов неизвестна, запуск остановится с отчётом. Текущую сессию и сервисы сохраняют до выяснения причины.
5. Подтвердите показанные проект и пакет. Хеш требований, рабочие копии и конфигурация создаются автоматически. Далее выполняются проверка разрешений, планирование, исполнение и независимое ревью. Оставьте терминал работать.

Пакет не выбирается автоматически по дате или номеру редакции. Это остаётся решением аналитика. Прежний тред можно выбрать как необязательную справку в JSONL или пропустить. Текущие требования, код и результаты проверок имеют приоритет над историей; старые команды не становятся новым заданием. Для журнала из другого каталога мастер отдельно запрашивает подтверждение связи и фиксирует его SHA256.

Состояние хранится вне проекта:

| ОС | Каталог |
| --- | --- |
| Windows | `%LOCALAPPDATA%\GigaCode SDD`, при отсутствии переменной: `~/AppData/Local/GigaCode SDD` |
| macOS | `~/Library/Application Support/GigaCode SDD` |
| Linux | `$XDG_STATE_HOME/gigacode-sdd` или `~/.local/state/gigacode-sdd` |

Внутри находятся `runs/` и `diagnostics/`. При повторном запуске можно продолжить сохранённую работу с тем же входом. Новая редакция требований требует нового запуска.

## Если прежний GigaCode уже поднял стенд

Передайте текущему агенту `SAFE-HANDOFF-PROMPT.txt`. Он останавливает дальнейшую разработку и просит сохранить сведения о стенде, сохраняя процессы. Новый чат получает `START-PROMPT.txt`.

Закрытие сессии может завершить PostgreSQL, backend или frontend. Работающий порт и один только PPID не доказывают независимость сервиса. Диагностика читает доступные процессы, рабочие каталоги и слушающие TCP-порты. PostgreSQL учитывается и без TCP-порта. Недоступные данные остаются ограничением, запуск при неполной проверке блокируется.

Отдельная диагностика из корня обвязки:

```text
python tools/gigacode-sdd/bootstrap.py --diagnose --repo "<полный путь к PoC>"
```

Диагностика ничего не останавливает и не переподчиняет процессы. Полные аргументы и переменные окружения не включаются в отчёт. На POSIX файлы создаются с правами `0600`; в Windows доступ зависит также от ACL пользовательского каталога. Снимок процессов не подтверждает сохранность данных и способ восстановления. Перенос управления стендом требует проверки существующих скриптов и данных; runner не принимает стенд под управление автоматически.

Контроллер запускают в отдельном терминале вне дерева процессов GigaCode. Его нельзя запускать фоновой задачей LLM-сессии.

## Сохранение работы и SDD

Runner создаёт отдельную Git-копию текущего PoC, включая незакоммиченный код, и работает в ней. Исходный каталог и явно зарегистрированный основной code-клон защищены. Обвязки `backend/` и `frontend/` обязательны; согласованная нарезка задач сохраняется.

Запуск использует сохранённую копию кода и закреплённый вход. Синхронизация, коммиты и локальные изменения во внешних репозиториях не меняют эту копию и не блокируют продолжение. Их начальные снимки остаются в конфигурации как история; обновлять их не нужно, в том числе у ранее созданных запусков. Runner не должен писать во внешние репозитории, экспорт в них запрещён. Проверки закреплённого входа, кандидата и рабочих копий запуска сохраняются. Каталог состояния после ошибки не удаляют: там остаются снимок, рабочие копии, частичные результаты и логи.

Игнорируемые build artifacts, `node_modules`, секреты и настройки подключения не являются переносимым кодом. Список пропусков находится в `clone_report` конфигурации. Подготовка окружения допускается только через Nexus. Изменённые отслеживаемые секретные файлы и защищённые инструкции вызывают блокер; они не отбрасываются молча.

Переносимые Git hooks сохраняются и выполняются. Не отключайте hook ради запуска. Если он требует ключ задачи или отдельную настройку, причина решается по правилам проекта. Префикс `SDD PoC` в мастере не заменяет обязательную связь с задачей.

## Разрешения и выполнение

Preflight запускает реальные headless-сессии в пробных копиях корня, backend и frontend. Для исполнителей проверяются чтение, запись, shell и синхронный субагент с ответом. Для ревью проверяются чтение, shell и субагент в режиме `plan`. В backend/frontend обе роли дополнительно вызывают установленный SDD skill в режиме чтения или справки. Список инструментов сам по себе не подтверждает успешную проверку.

Исполнители используют `auto-edit` и подготовленный список инструментов, ревьюеры используют `plan`. Глобальные правила, доверие к папкам, `ask`, `deny`, shell policy и подтверждения MCP сохраняются. Если они запрещают обязательный инструмент, runner сообщает конкретный блокер. Он не запрашивает бесконечно одно и то же и не обходит отказ другим синтаксисом. Пробная копия не гарантирует доверия каждой будущей копии в установленной версии CLI.

Планировщик сопоставляет требования, PoC и SDD. План содержит зависимости, области записи, общие ресурсы и команды проверок. Если обвязка требует design/tasks, они становятся предпосылкой разработки. Независимый ревьюер проверяет план целиком. Бизнес-решения остаются за аналитиком.

По умолчанию разрешено восемь параллельных заданий. Зависимые задачи, пересекающиеся области записи и одинаковые ресурсы выполняются последовательно. Внутри задания последовательно идут исполнение, проверки и свежее ревью. Замечания возвращаются исполнителю с сохранением сделанного. После сборки проводится общий цикл интеграционных проверок и ревью.

Лимита токенов и общего числа исправлений нет. Внешний блокер, необходимость решения аналитика, нарушение границ, отказ разрешения или повторяющаяся ошибка без прогресса требуют устранения причины. `complete` означает завершение проверок запуска; приёмка, работа на реальном стенде и внедрение подтверждаются отдельно.

## Команды для технического специалиста

Для обычного запуска достаточно мастера. Команды ниже выполняются из корня обвязки установленным Python; значения в угловых скобках заменяются фактическими путями. Все примеры даны одной строкой и не требуют Bash.

```text
python tools/gigacode-sdd/sdd-runner.py --help
python tools/gigacode-sdd/sdd-runner.py init --help
python tools/gigacode-sdd/sdd-runner.py preflight --config "<каталог состояния>/config.json"
python tools/gigacode-sdd/sdd-runner.py start --config "<каталог состояния>/config.json"
python tools/gigacode-sdd/sdd-runner.py status --config "<каталог состояния>/config.json"
```

Ручной `init` требует точных `--repo`, `--packet`, `--requirements-file`, `--requirements-sha256` и нового `--state-dir` вне исходного и защищённых репозиториев. Для защищённых клонов передают `--protected-root`; `--commit-prefix` должен соответствовать действующим правилам проекта. `--cli` задаёт установленный GigaCode. `--jobs` меняет параллелизм; `--session-timeout` ограничивает зависшую сессию (по умолчанию 3600 секунд), но не общую работу.

Nexus hosts и endpoints передаются через `--nexus-host`, `--npm-registry`, `--pip-index-url` или подтверждённое окружение. Не придумывайте endpoints по имени сервера. Без endpoint npm работает offline, pip получает `PIP_NO_INDEX=1`; унаследованный публичный URL вызывает блокер.

## Остановка и продолжение

`Ctrl+C` запрашивает остановку и сохраняет состояние. Перед завершением принадлежащих runner процессов проверяется наличие сервисов. Если сервис найден или проверка неполна, процессы сохраняются, дальнейшие задачи и возобновление блокируются. После сессии также проверяются новые сервисы, связанные с её рабочей копией. Не обходите отказ повторным завершением процессов или удалением состояния.

Это не полная изоляция ОС: отвязавшийся процесс со скрытой связью может остаться незамеченным. Уже работающий внешний стенд автоматически не принимается под управление.

После устранения причины используйте прежний `config.json`. При необходимости решения аналитика сохраните его в `decision.md` каталога состояния. Решение уточняет исполнение и не подменяет требования:

```text
python tools/gigacode-sdd/sdd-runner.py start --config "<каталог состояния>/config.json" --retry-blocked
```

Конфигурационные изменения требуют повторного preflight. Закреплённые `input/` и план вручную не переписывают. Если применение патча или hook прервали коммит, не выполняйте `reset --hard`. Сначала устраните причину; журнал интеграции позволит продолжить без повторного применения патча. Журнал вручную не изменяют.

Логи содержат полный вывод инструментов и могут включать чувствительные сведения. Не публикуйте их без проверки.

## Получение результата

После `complete`:

```text
python tools/gigacode-sdd/sdd-runner.py export --config "<каталог состояния>/config.json" --output "<новый путь вне исходного PoC>/poc-result.patch"
```

Рядом появится JSON с базовым и итоговым коммитами, SHA256 патча и требований. Патч строится относительно снимка PoC при `init`, в котором уже сохранена тогдашняя незакоммиченная работа. Полная итоговая копия находится в `<каталог состояния>/work/main`.

Перед переносом сверьте базу, состояние получателя и выполните `git apply --check` в отдельной копии. Runner не применяет результат к исходному PoC, не переключает стенд, не делает push или merge.

## Запрет публичных скачиваний

Каждая сессия получает запрет публичных скачиваний и fallback. Проверяются поддерживаемые manifests, lock-файлы и конфигурации зависимостей, отключается pip fallback. В мастере разрешён `nexus-ci.delta.sbrf.ru`; неизвестные endpoints не подставляются.

Инструкции, настройки и статический аудит не являются сетевой песочницей. Произвольный shell-скрипт способен переопределить окружение; все загрузчики, редиректы и глобальные настройки не охвачены. Техническую гарантию даёт корпоративная сетевая политика с доступом к необходимым LLM-сервисам и Nexus. Успешный preflight не подтверждает её наличие.

## Проверки переносимости

Из каталога `tools/gigacode-sdd`:

```text
python -m unittest discover -v
```

Тесты проверяют контроллер, консольный выбор и обработку событий. ОС-проверки используют отдельные платформенные реализации; имитация Windows на Linux не заменяет запуск на Windows. Первый запуск установленного GigaCode, корпоративные разрешения и доступность локального стенда проверяет preflight на машине сотрудника.

### Отображение прогресса

В интерактивном терминале активные операции показаны обновляемыми строками:
`hh:mm:ss  название операции`. Время отсчитывается от начала операции по
монотонным часам и обновляется раз в секунду отдельным потоком. Для параллельных
операций используются отдельные строки; итоговые сообщения остаются в истории.
Длинные названия обрезаются по ширине терминала, время остаётся видимым.
При перенаправлении stdout в файл или TERM=dumb используются обычные строки
без ANSI-кодов и сообщения ожидания раз в 30 секунд. Таймер показывает прошедшее
время, не процент готовности и не прогноз завершения. Зависимостей не требуется.

## Один текстовый файл диагностики

После работы под блокировкой запуска, включая остановку с ошибкой, runner собирает
`diagnostics/latest-diagnostics.txt` в общем каталоге GigaCode SDD и печатает полный путь.
На Mac это `~/Library/Application Support/GigaCode SDD/diagnostics/latest-diagnostics.txt`.
Следующая сборка атомарно заменяет текстовый файл; исходные журналы запусков сохраняются.
В разделах файла находятся `summary.json`, состояние и конфигурация, планы, закреплённый
вход, все журналы запуска и версия Python-обвязки. Рабочие копии кода не включены.
Файл записывается в UTF-8, содержит исходные данные без гарантированного удаления секретов.
Автоматической отправки нет. Ошибка сборки не подменяет исходный результат запуска.
Отказ до получения блокировки не пересобирает пакет, поэтому проверяйте время и
идентификатор запуска в `summary.json`.

Для уже остановленного запуска выполните `bootstrap.py --diagnostics-config
"<каталог запуска>/config.json"` одной строкой. Команда берёт блокировку,
собирает текстовый файл без агентов и не меняет состояние запуска. При ручном сборе
`summary.json.error` равен `null`; причины ищут в приложенных отчётах и журналах.

Каждый раздел указывает исходное имя и длину текста в символах. Бинарные файлы
и файлы с нетекстовыми управляющими символами не встраиваются и не кодируются
в base64: в сводке остаются путь, размер, SHA256 и причина пропуска.
Ранее созданные ZIP не удаляются, новые диагностические архивы не создаются.
