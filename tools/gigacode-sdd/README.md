# GigaCode SDD Runner

Локальный контроллер для Windows, macOS и Linux. Отдельные headless-сессии разных моделей предлагают планы, выполняют задачи по существующей SDD-обвязке и независимо проверяют результат. Контроллер сравнивает варианты по обязательным проверкам, разбирает спорные замечания и возвращает подтверждённые дефекты на исправление. Независимые задачи и варианты работают параллельно в отдельных Git-копиях, если не используют общие изменяемые ресурсы. Текущая работа над PoC сохраняется; проверенные изменения собираются в собственной интеграционной копии.

Требуются Python 3.10+ (64-разрядный в Windows), Git и установленный, авторизованный GigaCode CLI с `stream-json`, `--prompt` и `--approval-mode`. Используется стандартная библиотека Python. Runner ничего не скачивает и не устанавливает.

## Обычный запуск

Код получают через принятый в организации Git или Nexus. Для переписки достаточно текстовой инструкции `START-PROMPT.txt`. Отдельных файлов запуска `.com`, `.command`, `.bat`, `.ps1` и `.exe` в пакете нет.

1. Обновите установленную обвязку через разрешённый канал. Откройте самостоятельный терминал: PowerShell в Windows, Terminal в macOS или терминал Linux.
2. Из корня обвязки выполните одну команду установленным Python:

   ```text
   python tools/gigacode-sdd/bootstrap.py
   ```

   Если установленный интерпретатор вызывается как `python3` или `py -3`, используйте это имя. Для запуска из любого каталога подходит полный путь к `bootstrap.py` в кавычках. Текст `START-PROMPT.txt` просит GigaCode найти существующие пути и дать одну точную команду под вашу оболочку.
3. Выберите продолжение или новую работу. Консольный мастер предложит найденные проекты и пакеты требований. Выбор делается номером; если нужного варианта нет, введите полный путь. Для отмены введите `q`.
4. Мастер проверит работающие сервисы. Если старый GigaCode держит стенд или связь процессов неизвестна, запуск остановится с отчётом. Текущую сессию и сервисы сохраняют до выяснения причины.
5. Подтвердите показанные проект и пакет. Хеш требований, рабочие копии и конфигурация создаются автоматически. Далее выполняются проверка разрешений, планирование, исполнение и независимое ревью. Оставьте терминал работать.

Пакет не выбирается автоматически по дате или номеру редакции. Это остаётся решением аналитика. Прежний тред можно выбрать как необязательную справку в JSONL или пропустить. Текущие требования, код и результаты проверок имеют приоритет над историей; старые команды не становятся новым заданием. Для журнала из другого каталога мастер отдельно запрашивает подтверждение связи и фиксирует его SHA256.

Состояние хранится вне проекта:

| ОС | Каталог |
| --- | --- |
| Windows | `%LOCALAPPDATA%\GigaCode SDD`, при отсутствии переменной: `~/AppData/Local/GigaCode SDD` |
| macOS | `~/Library/Application Support/GigaCode SDD` |
| Linux | `$XDG_STATE_HOME/gigacode-sdd` или `~/.local/state/gigacode-sdd` |

Внутри находятся `runs/` и `diagnostics/`. При повторном запуске можно продолжить сохранённую работу с тем же входом. Новая редакция требований требует нового запуска.

## Если прежний GigaCode уже поднял стенд

Передайте текущему агенту `SAFE-HANDOFF-PROMPT.txt`. Он останавливает дальнейшую разработку и просит сохранить сведения о стенде, сохраняя процессы. Новый чат получает `START-PROMPT.txt`.

Закрытие сессии может завершить PostgreSQL, backend или frontend. Работающий порт и один только PPID не доказывают независимость сервиса. Диагностика читает доступные процессы, рабочие каталоги и слушающие TCP-порты. PostgreSQL учитывается и без TCP-порта. Недоступные данные остаются ограничением, запуск при неполной проверке блокируется.

Отдельная диагностика из корня обвязки:

```text
python tools/gigacode-sdd/bootstrap.py --diagnose --repo "<полный путь к PoC>"
```

Диагностика ничего не останавливает и не переподчиняет процессы. Полные аргументы и переменные окружения не включаются в отчёт. На POSIX файлы создаются с правами `0600`; в Windows доступ зависит также от ACL пользовательского каталога. Снимок процессов не подтверждает сохранность данных и способ восстановления. Перенос управления стендом требует проверки существующих скриптов и данных; runner не принимает стенд под управление автоматически.

Контроллер запускают в отдельном терминале вне дерева процессов GigaCode. Его нельзя запускать фоновой задачей LLM-сессии.

## Сохранение работы и SDD

Runner создаёт отдельную Git-копию текущего PoC, включая незакоммиченный код, и работает в ней. Исходный каталог и явно зарегистрированный основной code-клон защищены. Обвязки `backend/` и `frontend/` обязательны; согласованная нарезка задач сохраняется.

Запуск использует сохранённую копию кода и закреплённый вход. Синхронизация, коммиты и локальные изменения во внешних репозиториях не меняют эту копию и не блокируют продолжение. Их начальные снимки остаются в конфигурации как история; обновлять их не нужно, в том числе у ранее созданных запусков. Runner не должен писать во внешние репозитории, экспорт в них запрещён. Проверки закреплённого входа, кандидата и рабочих копий запуска сохраняются. Каталог состояния после ошибки не удаляют: там остаются снимок, рабочие копии, частичные результаты и логи.

Игнорируемые build artifacts, `node_modules`, секреты и настройки подключения не являются переносимым кодом. Список пропусков находится в `clone_report` конфигурации. Подготовка окружения допускается только через Nexus. Изменённые отслеживаемые секретные файлы и защищённые инструкции вызывают блокер; они не отбрасываются молча.

Переносимые Git hooks сохраняются и выполняются. Не отключайте hook ради запуска. Если он требует ключ задачи или отдельную настройку, причина решается по правилам проекта. Префикс `SDD PoC` в мастере не заменяет обязательную связь с задачей.

## Разрешения и выполнение

Preflight запускает реальные headless-сессии в пробных копиях корня, backend и frontend. Для исполнителей проверяются чтение, запись, shell и синхронный субагент с ответом. Для ревью проверяются чтение, shell и субагент в режиме `plan`. В backend/frontend обе роли дополнительно вызывают установленный SDD skill в режиме чтения или справки. Список инструментов сам по себе не подтверждает успешную проверку.

Исполнители используют `auto-edit` и подготовленный список инструментов, ревьюеры используют `plan`. Глобальные правила, доверие к папкам, `ask`, `deny`, shell policy и подтверждения MCP сохраняются. Если они запрещают обязательный инструмент, runner сообщает конкретный блокер. Он не запрашивает бесконечно одно и то же и не обходит отказ другим синтаксисом. Пробная копия не гарантирует доверия каждой будущей копии в установленной версии CLI.

Планировщики разных моделей сопоставляют требования, PoC и SDD. Каждый кандидат содержит зависимости, области записи, общие ресурсы и команды проверок. Если обвязка требует design/tasks, они становятся предпосылкой разработки. Сохранённый или импортированный кандидат сначала проходит независимое ревью; повторное планирование без причины не запускается. Если исправления нужны, модели параллельно предлагают альтернативы. Бизнес-решения остаются за аналитиком.

По умолчанию разрешено восемь независимых заданий через `jobs`. Это число задач, а не общий предел LLM-сессий: для одного задания могут одновременно работать две модели. Зависимые задачи, пересекающиеся области записи и одинаковые метки `resources` выполняются последовательно. Внутри каждого варианта последовательно идут исполнение, команды проверок и свежее ревью другой моделью. Если задача объявляет общий ресурс, его очередь охватывает исполнение и обязательные проверки одного варианта. Перед независимым ревью ресурс освобождается, поэтому другой исполнитель может работать одновременно с ревью. Ревью использует файлы своей копии и доказательства проверок контроллера; повторные сборки и обращения к общим БД, кешам и сервисам ему не поручаются. Это правило инструкций и проверок, а не изоляция ОС. Отдельные Git-копии сами по себе не изолируют БД, порт или внешний Maven-кеш. После сборки проводится общий цикл интеграционных проверок и ревью.

После первого варианта, прошедшего обязательные проверки и независимое ревью, контроллер сообщает о готовом обязательном результате и ждёт конкурента ещё не более `execution_comparison_seconds` (по умолчанию 120 секунд, плюс время остановки процесса). Среди проверенных вариантов выбирается вариант с меньшим числом подтверждённых необязательных замечаний; при равенстве используется порядок настроенных моделей. Это явный критерий выбора, а не доказательство абсолютного превосходства реализации. Голосование, размер патча и самооценка модели не используются. Если готов только один вариант, выбирается он. Оставшиеся варианты останавливаются отдельно от других задач; их файлы и журналы сохраняются. При продолжении сохранённые принятые варианты сравниваются без повторного исполнения. Нарушение границ или разрешений не скрывается наличием удачного варианта.

Лимита токенов нет. Приоритетом служит время до проверенного результата. Повторы одной стратегии ограничены; при отсутствии измеримого продвижения меняются технические инструкции и способ исправления. Внешняя зависимость или необходимое решение аналитика переводят задачу в ожидание ответа; независимая работа продолжается. Нарушение границ или исчерпание разных стратегий без результата блокирует задачу с сохранением материалов. `complete` означает завершение обязательных проверок запуска; приёмка, работа на реальном стенде и внедрение подтверждаются отдельно.

## Команды для технического специалиста

Для обычного запуска достаточно мастера. Команды ниже выполняются из корня обвязки установленным Python; значения в угловых скобках заменяются фактическими путями. Все примеры даны одной строкой и не требуют Bash.

```text
python tools/gigacode-sdd/sdd-runner.py --help
python tools/gigacode-sdd/sdd-runner.py init --help
python tools/gigacode-sdd/sdd-runner.py preflight --config "<каталог состояния>/config.json"
python tools/gigacode-sdd/sdd-runner.py start --config "<каталог состояния>/config.json"
python tools/gigacode-sdd/sdd-runner.py status --config "<каталог состояния>/config.json"
```

Ручной `init` требует точных `--repo`, `--packet`, `--requirements-file`, `--requirements-sha256` и нового `--state-dir` вне исходного и защищённых репозиториев. Для защищённых клонов передают `--protected-root`; `--commit-prefix` должен соответствовать действующим правилам проекта. `--cli` задаёт установленный GigaCode. `--jobs` меняет параллелизм; `--session-timeout` ограничивает зависшую сессию (по умолчанию 3600 секунд), но не общую работу.

Nexus hosts и endpoints передаются через `--nexus-host`, `--npm-registry`, `--pip-index-url` или подтверждённое окружение. Не придумывайте endpoints по имени сервера. Без endpoint npm работает offline, pip получает `PIP_NO_INDEX=1`; унаследованный публичный URL вызывает блокер.

## Остановка и продолжение

`Ctrl+C` запрашивает остановку и сохраняет состояние. Перед завершением принадлежащих runner процессов проверяется наличие сервисов. Если сервис найден или проверка неполна, процессы сохраняются, дальнейшие задачи и возобновление блокируются. После сессии также проверяются новые сервисы, связанные с её рабочей копией. Не обходите отказ повторным завершением процессов или удалением состояния.

Это не полная изоляция ОС: отвязавшийся процесс со скрытой связью может остаться незамеченным. Уже работающий внешний стенд автоматически не принимается под управление.

После обычного `Ctrl+C` продолжите сохранённый запуск через `bootstrap.py` или прежний `config.json`:

```text
python tools/gigacode-sdd/sdd-runner.py start --config "<каталог состояния>/config.json"
```

Прерывание пользователем не расходует число неудачных попыток. Проверенные результаты, завершённые проверки, рабочие копии и незавершённые изменения сохраняются. Контроллер восстанавливает пригодные квитанции завершённых сессий, проверяя их привязку и целостность. Незавершённый текст используется только как черновик. Это не восстановление внутреннего состояния модели или продолжение GigaCode через `--resume`: новый вызов может повторить часть анализа.

После устранения настоящего блокера исполнения добавьте `--retry-blocked` к команде `start`. Простая остановка пользователем этого флага не требует. Обычный перезапуск не сбрасывает исчерпанные стратегии и не выдаёт повтор прежней ошибки за продвижение.

Для общего уточнения задания, затрагивающего весь результат, остановите запуск, сохраните уточнение в `decision.md` каталога состояния и продолжите его. Решение уточняет исполнение и не подменяет закреплённые требования, проверки или разрешения. Каждая версия сохраняется в `operator-instructions/` с исходным текстом и хешем. Изменение файла во время сессии запрещает приёмку её результата под старыми инструкциями.

После нового решения ранее выполненные задачи и коммиты сохраняются. Для принятого плана контроллер заново проверяет общий интегрированный результат по всем требованиям: он не пытается угадать затронутые задачи из свободного текста. Новая проверка также сохраняет свою рабочую копию при остановке. Старое состояние готовности и экспорт недоступны до её завершения. Завершённый запуск старой версии без привязки к инструкциям тоже требует такой проверки перед новым подтверждением готовности.

Конфигурационные изменения требуют повторного preflight. Закреплённые `input/` и план вручную не переписывают. Если применение патча или hook прервали коммит, не выполняйте `reset --hard`. Сначала устраните причину; журнал интеграции позволит продолжить без повторного применения патча. Журнал вручную не изменяют.

Логи содержат полный вывод инструментов и могут включать чувствительные сведения. Не публикуйте их без проверки.

## Прогресс и вопросы во время работы

Пока есть вопрос без ответа, статус печатает полную команду для отдельного окна
терминала. Она не обрезается по ширине экрана и повторяется вместе со сводкой раз
в минуту. В окне ответа показываются вопрос, нужный контекст, варианты и последствия
решения. Сырые отчёты моделей, дублирующий JSON и технические доказательства остаются
в указанном файле подробностей. Команда, каталог и порты запускаемого сервиса
показываются перед его разрешением.


Вопрос модели распознаётся и внутри обычного отчёта с отдельными блоками кода или
патча. Поддерживаются поля `question`/`request`/`message` и `topic`/`subject`.
Неоднозначный явный запрос передаётся пользователю для уточнения. При продолжении
запуска контроллер восстанавливает пропущенный вопрос из сохранённого результата,
проверив исходный журнал и снимок файлов. Повторять исполнение ради вопроса не нужно.

Если нужен ремонт файла ранее принятой задачи или существующего файла, который
не закреплён ни за одной задачей плана, модель может вернуть `scope_request`
с точными `paths` и `reason`. Контроллер проверяет все области записи плана, зависимость и исходную
версию файла, затем предлагает отдельное разрешение. Только выбор
«Разрешить исправление этих файлов» добавляет перечисленные файлы в область текущей
задачи. Отказ и произвольный текст разрешения не дают. Защищённые файлы, каталоги,
маски и файлы независимых задач таким способом не разрешаются. План остаётся
неизменным; решение привязано к задаче и её исходной версии. Патч из ответа модели
автоматически не исполняется. Исправления проходят проверки и независимое ревью,
а разрешение повторно проверяется перед интеграцией. При продолжении контроллер
повторно проверяет старый неотвеченный запрос, отклонённый только из-за отсутствия
владельца файла. Если файл действительно не закреплён ни за одной задачей, появляется
новый вопрос с вариантами разрешения и отказа. Ранее сохранённые ответы не трактуются
как согласие на новое разрешение.


Основной экран отвечает на четыре вопроса: требуется ли вмешательство, сколько
задач принято, какой этап выполняется и как долго, сколько задач осталось.
В интерактивном терминале сводка обновляется на месте. При перенаправлении вывода
она печатается при изменениях и раз в минуту для обновления времени.

```text
В работе. Запросов на вмешательство нет.
Принято: 4 из 9 задач.
Сейчас: 00:18:19 · backend-modular-its · разработка · DeepSeek-V4.1-Flash-1017
Осталось: 5 задач и итоговая проверка. Оценки времени пока нет.
```

Свежие события не означают успешной проверки. Вопрос, блокировка, отсутствие новых
событий более пяти минут и приближение к лимиту этапа меняют первую строку.
Количество оставшихся задач не преобразуется в выдуманный прогноз времени.
Даже после приёмки всех задач итоговая проверка остаётся обязательной.

Подробные сообщения, карта зависимостей и причины повторов сохраняются в
`logs/controller.log`, путь печатается при запуске. Полный вывод моделей и проверок
остаётся в отдельных каталогах `logs/`. Инструкции моделей в консоль не выводятся.
`progress.json` содержит карту задач; `console-status.json` содержит последние
таймеры активных операций. Сводка из второго окна сообщает, если эти данные устарели.
`readiness.json` подтверждает итог только после интеграционных проверок и ревью
всех требований.

Для вопроса контроллер печатает полную команду с фактическими абсолютными путями:
`python3 ".../tools/gigacode-sdd/bootstrap.py" --answers-config ".../config.json"`.
Скопируйте именно напечатанную команду в другое окно терминала. Обычный повторный
запуск мастера тоже обнаруживает работающий контроллер и открывает прогресс и
вопросы, не создавая второй процесс исполнения. В остановленном запуске для этого
есть пункт «Прогресс и ответы на вопросы».

Мастер показывает вопрос и варианты, принимает свой текст и необязательное
пояснение, затем просит подтвердить сохранение. Можно ответить позже. Ответы
хранятся в `operator-questions/` отдельно от состояния контроллера и привязаны
к закреплённому плану и требованиям. Вопросы двух моделей с одной задачей и темой
объединяются, пояснения сохраняются. Молчание не считается ответом.

Ожидание освобождает рабочий слот и ресурсы задачи, не расходует бюджет исправлений.
Контроллер подхватывает ответ и продолжает зависимую работу; независимые задачи
идут дальше. Если другой вариант уже прошёл проверки и решает задачу, ненужный
вопрос закрывается с этой причиной. После остановки вопросы и ответы сохраняются.
Ответ не является доказательством прохождения проверки и не отменяет требования,
корпоративные разрешения или обязательные проверки.

Для просмотра состояния без запуска моделей используйте тот же фактический путь
к мастеру и параметр `--status-config` с путём к `config.json`. Это доступно во время
работы. `--diagnostics-config` по-прежнему предназначен для остановленного запуска.

## Приёмка результата отдельной задачи

Новый план явно задаёт `acceptance.deliverables` и `deferred_evidence`: какое
обязательное доказательство, по какому требованию и какая последующая задача
должна получить. Для старого закреплённого плана источником остаются его инструкции
задач; план и его хеш не переписываются. Ревью оценивает вклад текущей задачи,
выполнение её проверок и соблюдение SDD. Оно не требует от реализации доказательства,
которое план явно назначил зависимой задаче с ещё не запущенным стендом.

Отложенное доказательство сохраняется в результате ревью, отображается в сводке
и передаётся задаче-владельцу вместе с идентификатором требования. Владелец должен
быть достижим по зависимостям. Итоговая проверка не допускает отсрочек. Неизвестный
дефект реализации нельзя выдать за будущую проверку, а обязательный живой сценарий
или снимок нельзя заменить компиляцией либо объявить необязательным.

При первом продолжении на этой версии сохранённые внешние блокировки проходят
повторное ревью с новыми правилами границ задачи. Код, контрольные суммы, прошедшие
проверки и прежние замечания сохраняются. Блокировка не превращается в успех
автоматически. Принятые задачи повторно не исполняются.

## Управляемый локальный стенд

Исполнитель может запросить необходимый сервис через `service_request`: точный
массив аргументов, рабочий каталог, локальные порты, проверку готовности, перечень
готовых артефактов и назначение с областью тестовых данных. Он не запускает
фоновый сервер из shell. Для неизвестного запуска мастер один раз показывает
конкретную команду, пути и артефакты и получает разрешение оператора. Секреты
следует передавать через разрешённое окружение, не писать в вопросах и аргументах.

Контроллер сохраняет отдельную копию сервиса и хеши артефактов, запускает его,
проверяет HTTP-ответ или TCP-доступность и принадлежность портов своему процессу.
Готовый сервис доступен следующим задачам. Запрос `service_action` с действием
`restart` перезапускает ранее согласованный сервис с теми же артефактами, без
пересборки. Изменение артефактов требует нового согласования запуска.
Действие `stop` явно освобождает свой сервис перед заменой; файлы сохраняются,
старый сервис больше не восстанавливается автоматически. Внутри закреплённого
эксперимента без пересборки замена артефактов не разрешается.

При обычной остановке контроллер завершает только сервисы, которые сам запустил;
их рабочие каталоги и журналы сохраняются. При продолжении согласованные сервисы
восстанавливаются из сохранённых копий. Занятый порт, неизвестный оставшийся
процесс или неполная проверка владельца не разрешают захват или завершение
чужого сервиса. После аварийного завершения может понадобиться сверка процессов.

Это управление жизненным циклом, а не песочница ОС. Команда и конфигурация сервиса
должны использовать изолированные тестовые данные. Существующий PoC и его база
не становятся стендом автоматически. MDM-запрет браузера не обходится: если
снять страницу разрешённым способом нельзя, задача запрашивает помощь оператора,
а требование остаётся открытым до появления проверяемого доказательства.

## Получение результата

`readiness.json` показывает число принятых задач, текущую интеграционную копию и привязку к плану, требованиям, коду и версии инструкций. До завершения обязательных проверок это только частичная работа, даже если отдельные функции уже можно осмотреть.

Сообщение «Основная задача проверена, результат можно смотреть» появляется после завершения всех обязательных задач, интеграционных проверок и независимого ревью. Если остаются доказательно необязательные улучшения, `readiness.json` получает `preview-ready` и их список. Невыполненное обязательное требование нельзя переименовать в улучшение. Общий запуск при этом завершён; отдельное выполнение необязательных улучшений не запускается автоматически. Место просмотра: `<каталог состояния>/work/main`.

После `complete` в состоянии запуска:

```text
python tools/gigacode-sdd/sdd-runner.py export --config "<каталог состояния>/config.json" --output "<новый путь вне исходного PoC>/poc-result.patch"
```

Рядом появится JSON с базовым и итоговым коммитами, SHA256 патча и требований. Патч строится относительно снимка PoC при `init`, в котором уже сохранена тогдашняя незакоммиченная работа. Полная итоговая копия находится в `<каталог состояния>/work/main`.

Перед переносом сверьте базу, состояние получателя и выполните `git apply --check` в отдельной копии. Runner не применяет результат к исходному PoC, не переключает стенд, не делает push или merge.

## Запрет публичных скачиваний

Каждая сессия получает запрет публичных скачиваний и fallback. Проверяются поддерживаемые manifests, lock-файлы и конфигурации зависимостей, отключается pip fallback. В мастере разрешён `nexus-ci.delta.sbrf.ru`; неизвестные endpoints не подставляются.

Инструкции, настройки и статический аудит не являются сетевой песочницей. Произвольный shell-скрипт способен переопределить окружение; все загрузчики, редиректы и глобальные настройки не охвачены. Техническую гарантию даёт корпоративная сетевая политика с доступом к необходимым LLM-сервисам и Nexus. Успешный preflight не подтверждает её наличие.

## Проверки переносимости

Из каталога `tools/gigacode-sdd`:

```text
python -m unittest discover -v
```

Тесты проверяют контроллер, консольный выбор и обработку событий. ОС-проверки используют отдельные платформенные реализации; имитация Windows на Linux не заменяет запуск на Windows. Первый запуск установленного GigaCode, корпоративные разрешения и доступность локального стенда проверяет preflight на машине сотрудника.

### Отображение прогресса

В интерактивном терминале активные операции показаны обновляемыми строками:
`hh:mm:ss  название операции`. Время отсчитывается от начала операции по
монотонным часам и обновляется раз в секунду отдельным потоком. Для параллельных
операций используются отдельные строки; итоговые сообщения остаются в истории.
Длинные названия обрезаются по ширине терминала, время остаётся видимым.
В истории показаны модели, причина повтора, выбранная стратегия, результат
ревью и адресной проверки замечаний, выбор варианта и число принятых задач.
Окончание сессии само по себе не означает приёмку задачи.
При перенаправлении stdout в файл или TERM=dumb используются обычные строки
без ANSI-кодов и сообщения ожидания раз в 30 секунд. Таймер показывает прошедшее
время, не процент готовности и не прогноз завершения. Зависимостей не требуется.

## Один текстовый файл диагностики

После работы под блокировкой запуска, включая остановку с ошибкой, runner собирает
`diagnostics/latest-diagnostics.txt` в общем каталоге GigaCode SDD и печатает полный путь.
На Mac это `~/Library/Application Support/GigaCode SDD/diagnostics/latest-diagnostics.txt`.
Следующая сборка атомарно заменяет текстовый файл; исходные журналы запусков сохраняются.
По умолчанию это компактный отчёт размером не более 2 МиБ. В нём находятся
текущая ошибка, состояние, кандидат плана, требования, решение аналитика,
сокращённая конфигурация и выбранные попытки текущих циклов. Для планирования
и ревью, как и для исполнения, выбираются до трёх последних циклов;
точно названный в ошибке цикл имеет приоритет. Экспортируются до 24 записей на
категорию и до восьми связанных сессий, включая две последние.
Сессии, указанные в текущих ошибках задач, получают приоритет. Их краткие
сводки с отказами разрешений, ошибками инструментов и аргументами связанных
вызовов записываются до исторических материалов. Большие тела записываемых
файлов сокращаются с указанием размера и хеша. Если план уже принят, экспорт
показывает выбранный кандидат вместо старого корневого файла.
Записи выбираются поочерёдно из разных циклов, включая результаты генерации
планов и ошибки подготовки. Один активный кандидат не вытесняет все остальные.

Ответы моделей сохраняются один раз по хешу, а повторные вхождения ссылаются
на этот раздел. Из потока событий исключены рассуждения модели и содержимое
успешных чтений; остаются вызовы, ошибки, итоги и метаданные результатов.
Полный prompt включается только для первой приоритетной сессии. Снимки рабочих копий,
старые циклы и исходники обвязки не переносятся; для версии обвязки остаются
хеши файлов. Проекции, пропуски и сокращения отмечены явно. Крупный раздел
заменяется началом и концом с размером и хешем оригинала; общий лимит не превышается.
Этот отчёт служит для разбора ошибки и не является исходным журналом для
повторной проверки доказательств. Восстановление использует неизменённые локальные файлы.
Файл записывается в UTF-8, содержит исходные данные без гарантированного удаления секретов.
Автоматической отправки нет. Ошибка сборки не подменяет исходный результат запуска.
Отказ до получения блокировки не пересобирает пакет, поэтому проверяйте время и
идентификатор запуска в `summary.json`.

Для уже остановленного запуска выполните `bootstrap.py --diagnostics-config
"<каталог запуска>/config.json"` одной строкой. Команда берёт блокировку,
собирает текстовый файл без агентов и не меняет состояние запуска. При ручном сборе
`summary.json.error` равен `null`; причины ищут в приложенных отчётах и журналах.

Для полного текстового отчёта добавьте `--diagnostics-full` к той же команде.
Он собирается только по явному запросу в отдельный `full-diagnostics.txt` и
заменяет предыдущий полный отчёт, не увеличивая `latest-diagnostics.txt`.
Автоматических копий отчётов с датами не создаётся; журналы и контрольные точки
самого запуска не удаляются, поскольку нужны для возобновления.

Каждый раздел указывает исходное имя и длину текста в символах. Бинарные файлы
и файлы с нетекстовыми управляющими символами не встраиваются и не кодируются
в base64: в сводке остаются путь, размер, SHA256 и причина пропуска.
Ранее созданные ZIP не удаляются, новые диагностические архивы не создаются.

## Модели и выбор варианта

По умолчанию используются `DeepSeek-V4.1-Flash-1017` и `GLM-5.3-Flash`.
Фактическая модель проверяется по метаданным CLI, а не по тексту её ответа.
Конфигурация поддерживает отдельные списки:

| Поле `config.json` | Назначение | Допустимый состав |
| --- | --- | --- |
| `planning_models` | Альтернативные планы | Не менее двух разных моделей |
| `plan_review_models` | Независимое ревью плана и адресная проверка замечаний | Ровно две разные модели |
| `execution_models` | Альтернативы реализации и перекрёстное ревью | Ровно две разные модели |

При отсутствии `planning_models` или `execution_models` используется
`plan_review_models`, а при отсутствии всех списков используются две модели
по умолчанию. Не добавляйте model/fallback-флаги в общий `cli`. Изменять
конфигурацию можно только у остановленного запуска; изменённая конфигурация
потребует нового preflight.

Существующие конфигурации и импортированные кандидаты не требуют пересоздания.
Продолжение использует прежний закреплённый вход. Успешный preflight неизменённой
конфигурации сохраняется. Если кандидат уже импортирован, сначала проверяется
он; варианты планировщиков запускаются при подтверждённой необходимости
доработки. Новый импорт не означает принятия плана.

Для каждого плана две модели работают в разных копиях одного входа. Для каждой
реализации другая модель проверяет фактический код и результаты команд. Первый
вариант, удовлетворивший обязательным критериям, может быть выбран без ожидания
полной доработки остальных. Среди пока непригодных планов число подтверждённых
дефектов помогает выбрать основу следующей доработки, но не разрешает принять
дефектный план.

## Замечания, исправления и повторные попытки

Замечание ревьюера сначала считается проверяемой гипотезой. Перед переделкой
проводится отдельная адресная проверка с исходным замечанием, текущим кандидатом
или кодом и закреплёнными требованиями. Результат указывает, подтверждён ли дефект,
опровергнут ли он, относится ли к необязательному улучшению или требует внешнего
решения. Для выводов обязательны проверяемые пути, ссылки на содержание и объяснение.
Пробел обязательного покрытия остаётся дефектом. Голосование не используется;
необязательность оценивается по доказательствам и не выводится из длительности
доработки.

Ссылки на содержание оцениваются моделями по смыслу. Контроллер не требует
буквального совпадения цитат: пересказ, опечатки и Markdown не вызывают повтор.
Он проверяет существование файлов в закреплённой копии, чтение кандидата,
полноту покрытия требований и согласованность решений с вердиктом. Фрагменты
помечены как `semantic-reference`, а не как проверенные дословные цитаты.
При отказе следующая попытка получает конкретную причину через
`previous-review-error.json`. Готовый структурированный черновик сохраняется
вместо более позднего обещания начать работу или прерванного ответа.

Для ревью предпочтительны специальные инструменты чтения и поиска. Shell и
другие универсальные инструменты нежелательны, но их вызов сам по себе не
отклоняет результат и не создаёт предупреждение. Успешное чтение полного
закреплённого плана через shell тоже подтверждает ознакомление с кандидатом.
Команды из журнала не исполняются и не классифицируются по текстовому списку.
Проверяются результат, модель, покрытие требований, целостность рабочей копии,
Git, сервисов и исходных данных. Явный отказ CLI или файлового guard остаётся
отказом; разрешения не меняются. Аудит известных аргументов путей сохраняется,
но произвольная shell-команда не позволяет доказать все прочитанные пути.

Лимиты повторов привязаны к SHA256 рабочего Python-кода обвязки. Обновление
кода даёт новый ограниченный бюджет ревью, подготовки плана и исполнения;
простой перезапуск, изменение документации или тестов бюджет не сбрасывают.
Старые попытки и счётчики остаются в истории, успешные результаты проходят
проверку перед повторным использованием. Исходные файлы, контрольные точки,
подтверждённые внешние блокеры и остановки безопасности не сбрасываются.

Контроллер отдельно обрабатывает ошибки транспорта, формата JSON, путей,
подтверждения модели, команд проверок и содержательные замечания. Технические
поправки выбираются из ограниченного набора инструкций; причина, поправка и
результат сохраняются. Текст ошибки не может добавить новую политику или ослабить
требования, границы записи, разрешения и проверки. Повторяется нужный шаг,
пригодные результаты соседних сессий сохраняются.

Один полный JSON-объект можно разобрать и с вводной фразой вокруг него,
в том числе внутри Markdown-блока. Несколько объектов, несколько блоков и оборванный JSON остаются
ошибкой. При продолжении контроллер повторно проверяет сохранённые ответы,
ранее отклонённые по протоколу, до проверки лимита попыток. Восстановление
требует неизменных журнала, рабочей копии, входа и подтверждённой модели;
лимит не сбрасывается, проверки содержания и покрытия сохраняются.

Пути инструментов могут быть относительными или абсолютными внутри выданной
рабочей копии: некоторые версии CLI требуют абсолютный путь для просмотра
каталога. Контроллер передаёт точный корень. Однозначный отказ аргумента до
чтения локального файла не обнуляет отчёт, но не считается доказательством
чтения. В JSON-отчёте пути доказательств остаются относительными.

Планирование меняет стратегию после двух раундов без уменьшения числа
подтверждённых дефектов: сначала точечное исправление, затем сверка покрытия,
затем пересмотр дефектных групп зависимостей и владения. Для технически
непригодного ответа одного планировщика предусмотрено до трёх попыток в раунде.
Исполнение тоже использует три стратегии: исправление дефекта, поиск минимального
воспроизведения, пересмотр локального способа реализации. Снижение числа ошибок
учитывается как продвижение; одинаковые неудачи не повторяются бесконечно.
Число раундов зависит от результатов проверок и продвижения выбранной стратегии.

Ревью плана и адресная проверка имеют две технические стратегии, до двух
завершённых неудачных попыток на каждую. Для неподтверждённой модели предел
составляет две попытки: исследовательская инструкция не исправляет настройку CLI.
Каждая такая сессия ограничена 15 минутами либо меньшим `session_timeout`.
Повторная попытка получает до 512 КиБ наблюдений из последних четырёх попыток
той же модели по тому же кандидату. Перед передачей проверяются хеш журнала,
неизменность рабочей копии, модель и закреплённый вход. Материалы находятся в
`.review-input/previous-research.json`; сокращения отмечены явно. При наличии
материалов инструкция требует завершить ревью, проверяя только оставшиеся
пробелы. Это черновые свидетельства: итоговый JSON всё равно проходит все проверки.
Строки статуса содержат короткий SHA кандидата, этап и номер попытки, чтобы
параллельные проверки не выглядели повторами одной сессии.
Остановка пользователя не считается неудачей. После исчерпания вариантов
контроллер сообщает конкретную причину отсутствия пригодного результата и
сохраняет материалы для продолжения с новыми данными или указаниями.

Контроллер связывает ревью с SHA прочитанного кандидата сам. Ошибка модели при
переписывании SHA не меняет привязку. Подтверждённый пустой поиск или конкретный
ответ об отсутствующем файле не означает чтения чужих данных и не обнуляет
готовое ревью. Непустое чтение вне рабочей копии и недоказанный исход вызова
не допускаются как доказательство. Изменение защищённых файлов или разрешений
и неясная принадлежность сервисов требуют безопасной остановки.
Старые журналы без проверяемой квитанции целостности используются только как
черновики, не как автоматически принятый результат.

После проверок целостности `session_outcome.py` определяет следующий шаг одинаково
для новой сессии и восстановления по квитанции. Отказ инструмента сам по себе
не становится постоянной блокировкой. Завершённое исполнение с ошибками отдельных
вызовов, а также частичное исполнение после таймаута или переполнения контекста
может передать сохранённый код обязательным проверкам и независимому ревью другой
модели. Для частичного исполнения нужны непустой журнал без повреждённых событий,
завершённый процесс и подтверждение модели. Незавершённый текст ответа не доказывает
готовности задачи. Неудачные проверки или замечания ревью запускают ограниченную
доработку; отказ инструмента и таймаут одной модели не отменяют второй вариант.
Ревьюер получает `.review-input/execution-limitations.json`: отклонённые команды
не считаются выполненными проверками. Разрешения не меняются, повтор запрещённой
операции другим инструментом не допускается. Для preflight это исключение
не действует. В ревью отказ не обнуляет готовый ответ только при явном подтверждении
CLI, что команда не выполнялась. Вердикт, покрытие требований, модель и целостность
входа проверяются как обычно; отклонённый вызов не служит доказательством проверки.

Старая блокировка именно из-за такого отказа может быть восстановлена по
неизменённой квитанции той же попытки, модели, рабочей копии и входа. Исходный
`fatal.json` архивируется, сохранённая сессия возвращается к проверкам либо исправлению,
а проверки и ревью остаются обязательными. Другие причины блокировки автоматически
не снимаются. Диагностика
прослеживает ссылки на `fatal.json`, чтобы повторный запуск не скрывал исходный отказ.

Завершённое ревью или проверка замечаний также восстанавливается по квитанции:
должны совпадать кандидат, пакет требований, задача, результаты проверок, модель,
инструкция и исходный журнал. Повторять уже завершённые стадии не требуется.
Непроверенные ссылки в необязательных предложениях сохраняются отдельно и не
обнуляют обязательные замечания. Цитаты оцениваются по смыслу, без посимвольного
сравнения; это не позволяет объявлять обязательное требование необязательным.

Системный сбой и нарушение целостности обрабатываются отдельно. Ошибка остановки
процесса сохраняет его идентификатор, причину и частичный журнал. Контроллер не
применяет другой способ остановки и не считает очистку успешной. При продолжении
он заново проверяет процессы; такая остановка не становится вечным `fatal.json`.
Возобновление через bootstrap повторно проверяет заблокированные задачи, даже
если общий статус запуска был `interrupted`.

Для прежнего системного отказа восстановление возможно при наличии неизменённого
кандидата с завершённым ревью и квитанцией. Проверяются исходный пакет, задача,
контрольные проверки, модель, журнал, Git, контекст, разрешения, область изменений
всех вариантов и отсутствие оставшихся процессов. Незавершённые варианты
сохраняются отдельно со статусом `quarantined`, без автоматического принятия или
повторного запуска. Старый отказ архивируется с записью проверок восстановления.
Без достаточных доказательств отказ остаётся видимым. Новые ошибки содержат тип,
код ОС и стек вызовов без локальных переменных, чтобы следующий разбор не зависел
от одной строки `Operation not permitted`.

Сверка кандидата с копией для ревью учитывает различия, создаваемые Git при
клонировании. Время изменения файла и права чтения/записи не заменяют проверку
содержимого; признак исполняемости и цели ссылок должны совпадать. Для файлов,
чьё содержимое скрыто в снимке (например, `.npmrc`), выполняется отдельное
сравнение байтов без записи значений или их хешей в диагностику. Проверка
неизменности каждой отдельной копии относительно её квитанции остаётся точной.
Несовпадения сохраняются в `recovery-binding.json`, а причины отказа от старых
квитанций в `recovery-attempts.json`; компактная диагностика включает эти записи.

История вариантов и решений находится в `planning-portfolio.json`,
`planning-cycles/`, `review-ledger.json`, `review-cycles/` и `execution-cycles/`.
Уточнения аналитика хранятся в `operator-instructions/`, готовность в
`readiness.json`. Эти текстовые материалы входят в `latest-diagnostics.txt`.
Механизм не привязан к именам задач, классов или идентификаторам требований
конкретного PoC. Локальные тесты с fake CLI проверяют протокол и восстановление;
они не доказывают качество ответов или доступность моделей установленного
корпоративного GigaCode.

### Активность текущих сессий

Строка с таймером показывает число событий, время без новой записи в журнале
и число вызовов инструментов без ответа. Это активность CLI, не процент готовности
и не доказательство полезного прогресса. Ограниченная сводка обновляется в
`logs/<session>/activity.json` и включается в компактную диагностику без
аргументов инструментов и содержимого ответов.

`session_idle_timeout` в конфигурации задаёт допустимое время без записи stdout
(по умолчанию 900 секунд). При превышении выполняется обычная защищённая остановка
процесса, сохраняются изменения и частичный журнал, а повтор получает причину
`Session journal idle timeout`. Долгая молчащая команда тоже подпадает под этот
лимит; это граница ожидания, а не утверждение о зависании. Общий `session_timeout`
сохраняется и ограничивает сессии с непрерывной активностью. Значения должны быть
положительными. Существующий запущенный процесс получает новые правила только
после остановки и продолжения обновлённой обвязкой.

### Отказ инструмента и сбой контекста ревью

После проверок рабочей копии, источников и сервисов непригодный ответ ревьюера
возвращается к ограниченному исправлению этапа ревью. Это относится к таймаутам,
переполнению контекста и отказам инструментов, в том числе в старых квитанциях.
Неполный ответ не может дать принятие. Изменения защищённых файлов, нарушение
целостности квитанции и незавершённая безопасная остановка процессов по-прежнему
блокируют восстановление. Отмена пользователем сохраняет прогресс и не считается
неудачной попыткой. Проверка доступности разрешений в preflight остаётся обязательной.

При `COMPRESSION_FAILED_API_ERROR` и аналогичном сообщении API о лимите контекста
повтор получает отдельную причину `review-context`: новая сессия, поиск нужных
символов, короткие фрагменты вместо полных генерированных файлов и краткая таблица
доказательств для всех требований. Уже пройденные исполнение и проверки не
повторяются. Старые квитанции перепроверяются по исходному журналу; неполное ревью
можно вернуть в исправление протокола, но нельзя принять как завершённое.

## Восстановление отдельного шага

Ошибки проверок реализации, протокола ревью и adjudication используют отдельные
бюджеты. Каждый бюджет ограничен шестью неудачами, общий предел варианта в одной
версии обвязки составляет 24. Повтор ревью сохраняет исполнение и проверки,
передаёт ограниченный непроверенный черновик и меняет техническую инструкцию
по мере исчерпания стратегий. Пауза не расходует попытку; обычный перезапуск
не снимает исчерпанный лимит. Подробности, источники подхода и ограничения:
[ORCHESTRATION-AUDIT.md](ORCHESTRATION-AUDIT.md).

### Успешное чтение диагностических файлов

Текст ответа инструмента считается данными. Упоминания прежних отказов доступа
в успешно прочитанном файле не создают новый отказ. Текстовая классификация
применяется только к `tool_result` с `is_error: true`; структурированные
`permission_denials` проверяются независимо.

При восстановлении оркестратор повторно разбирает исходный журнал после проверки
его хеша и привязки к входам. Старый ложный отказ снимается только при точном
совпадении с результатом прежнего алгоритма. Журналы и записи сессий сохраняются;
реальные отказы, ошибки процесса, прерывания и проверки результата не отменяются.

### Ожидание ресурсов и временных сбоев

Ожидание общего ресурса сохраняется в `candidate.json`: `resource_wait`
показывает владельца, позицию, билет и время начала ожидания. При продолжении
порядок восстанавливается; запись не даёт права запускать второй процесс поверх
оставшегося первого. Освобождение ресурса будит следующий вариант. Ожидание
не расходует лимит неудачных попыток и не вызывает модель.

Для временных транспортных сбоев срок повтора сохраняется в `recovery_wait`
кандидата или `next_attempt_at` записи ревью плана. Задержки по умолчанию:
5, 10, 20, 40, затем не более 60 секунд. Параметр `recovery_retry_seconds`
задаёт начальную задержку от 0 до 60 секунд. Простой перезапуск не переносит
сохранённый срок. Ctrl+C прерывает ожидание с сохранением состояния.
Транспортный повтор не меняет техническую инструкцию и не повторяет успешные
этапы. Ошибки ответа исправляются отдельно. При исчерпании лимита сохраняется
остановка; ожидание не обнуляет бюджет.

Компактная диагностика сначала сохраняет `compact/current-execution/`: текущий
этап и модель, последние шесть ошибок, остаточное состояние повторов и фрагмент
черновика ревью. Для активных задач приоритетны последние две сессии каждой
задачи. Исторические планы не могут вытеснить эти сводки; общий лимит остаётся
2 МБ. Проекции не заменяют исходные журналы и не служат доказательством приёмки.

Ошибка проверки adjudication сохраняет отвергнутый ответ как непроверенный
черновик для следующей попытки. Для некорректной ссылки ошибка указывает поле,
путь и причину: отсутствующий файл, пустую ссылку, нарушение границы или ошибку
чтения. Противоречие итогового вердикта детальным решениям сообщает ожидаемый
вердикт и состав подтверждённых замечаний. Проверки обязательных требований
не отменяются; исправленный ответ проверяется полностью.

### Поиск файлов и восстановление ответа ревью

Если известный путь не найден, ревьюер ищет файл и нужный символ внутри
закреплённой копии ревью, проверяет совпадения по модулю и содержимому и ссылается
на найденный путь. Поиск в соседних запусках и обход запретов shell не разрешены.
Завершённые ошибки штатного чтения/поиска сохраняются как `tool_warnings`,
но сами по себе не отменяют итоговый ответ. Полнота покрытия, замечания,
обязательные проверки и целостность копии проверяются отдельно. Неизвестные
ошибки shell/записи, незавершённые вызовы и сбои транспорта требуют восстановления.

Замечания в виде `{id, text}` приводятся к списку текстов с сохранением исходного
представления. В adjudication связь замечаний определяется проверенными
`issue_dispositions`, а не дословным повторением текста в `findings`.
Противоречие вердикта решениям по замечаниям остаётся причиной точечного ремонта.

### Сохранённые группы процессов

Новая запись сохранённой группы связывает PID и PGID со временем запуска каждого
наблюдавшегося процесса. При возобновлении блокируется только совпавшая живая
идентичность. Это исключает ложную остановку после повторного использования PID
или PGID операционной системой.

Для старой записи без времени запуска свежий полный снимок должен видеть в этой
группе GigaCode, сервис или один из ранее записанных PID. Один лишь существующий
номер группы не считается доказательством. Если свежий снимок неполный, запуск
останавливается. Процессы при такой сверке не завершаются, а историческая запись
не удаляется.

### Маршрут и число сессий

Краткий статус показывает оставшиеся задачи с понятными названиями и отметкой
`▶` у текущих. Независимые ветви выводятся со своими зависимостями, а не как
последовательная цепочка. Для новых планов доступно необязательное поле `title`;
сохранённые планы не переписываются, инструкции моделей в статус не попадают.

Для текущих задач видны состояния обоих вариантов, включая ожидание ресурса
или ответа. Число активных LLM-сессий считается по работающим операциям и
показывается по моделям; проверки и ожидающие варианты в него не входят.
Отдельный счётчик показывает попытки запуска по сохранённым журналам прогона,
включая повторы и неудачные запуски. Это не число уникальных диалогов.
При устаревшей или неполной телеметрии текущее число обозначается как неизвестное.

Две модели не означают глобальный предел в две сессии: `jobs` ограничивает
одновременные задачи, а зависимости и общие ресурсы ограничивают фактическое
исполнение. Варианты одной задачи являются альтернативными решениями;
субагенты для параллельных сессий не требуются. Планировщик эта доработка не меняет.
Если сводка не помещается в терминал, она печатается целиком с ограниченной
частотой вместо обрезания строк. Подробности остаются в журнале.

### Расхождение снимков процессов и портов

Если TCP-listener отсутствует в исходном `ps` или имеет другого владельца,
обвязка адресно сверяет его между двумя свежими снимками процессов. Исчезновение
подтверждается отсутствием в обоих снимках и промежуточном запросе `lsof`.
Новый процесс учитывается только при стабильной идентичности и текущем UID.
Ошибки чтения, смена владельца или идентичности остаются блокерами. PID, порты
и результат сверки сохраняются без произвольных аргументов процессов.

Неполный снимок останавливает работу как восстанавливаемая проблема окружения.
Консоль показывает причину и путь к отчёту; компактная диагностика включает
последние отчёты сервисов без полной таблицы процессов. Обнаруженный новый сервис
по-прежнему требует проверки и никогда не завершается автоматически.
Старая `fatal.json` именно этого типа архивируется только после свежей полной
проверки и проверки сохранённых процессов. Другие ошибки безопасности не снимаются.
