# Короткая памятка аналитика

Все фразы ниже пишутся прямо в чат. Пути к программам и репозиториям LLM определяет сама.

## Работа над функциональностью

- `начинаю работу над фичей <feature>`
- `пишем требования по фиче <feature>`
- `сохрани изменения`
- `обнови мою ветку`
- `требования готовы к объединению`
- `запрос на слияние принят`

## Требования

- `делаем требования`
- `актуализируй требования`
- `проверь полноту и непротиворечивость требований`
- `проведи аудит требований`
- `проанализируй требования`
- `сходи в код и уточни текущее поведение`
- `проверь русский язык требований`
- `проверь формулировки требований`
- `проверь однозначность требований`
- `найди плохо составленные требования`

Требования ведутся одной компактной спецификацией `features/<feature>/requirements.md`: назначение, границы, правила `REQ-*` со сценариями, влияния, источники и вопросы. Формулировки должны проходить проверку изолированного читателя: точные количества и ссылки, конкретное `Когда`, наблюдаемый результат в `Тогда`. Обвязка не создаёт срезы, отдельные пакеты по контурам и предварительные задачи разработки.

## Передача разработчикам

Равнозначные команды:

- `сформируй пакет для разработки`
- `отправь требования в разработку`
- `передай требования разработчикам`
- `отдаём требования разработчикам`
- `передай разрабам`
- `отдай требования разрабам`
- `отправь разрабам`
- `передаём в разработку`
- `отдаём в разработку`
- `подготовь требования для разработки`
- `собери пакет для разработчиков`

LLM отдельно проверяет каждое правило, затем взаимодействие всего набора и готовность к передаче. Она исправляет только однозначное, задаёт по одному вопросу для предметных решений и после исправлений повторяет полный аудит. Затем показывает отчёт с замечаниями, решениями, рисками и контрольной суммой и просит подтвердить результат аудита и отправку. До явного подтверждения пакет не создаётся. После подтверждения передаются только неизменившийся `requirements.md` и `manifest.json`.

Если разработчики заранее создали доступный `requirements-exchange/` в кодовом репозитории, используется он. Иначе создаётся `requirements-exchange/` в аналитическом репозитории. Итоговый ответ всегда содержит фактическое место и номер редакции.

Фразы про нарезку требований на срезы устарели и ничего не создают.

## Результаты разработки

- `проверь результаты разработки`
- `есть ли новые результаты`
- `покажи все новые результаты разработки`
- `покажи все результаты разработки`
- `обработай результат <return-id>`

По умолчанию LLM показывает новые результаты текущего аналитика. Просмотр чужих результатов не меняет владельца. Их обработка начинается только по явной команде.

`returns/tasks.md` уже содержит согласованную разработчиками декомпозицию. Аналитик её не подтверждает. Каждая задача относится к одному контуру и ссылается на локальное изменение SDD и `REQ-*`; клиентская и серверная работа не смешиваются. Отчёты по задачам и итоговый отчёт возвращают фактическую реализацию.

## Трекеры задач

- `прочитай задачи из трекеров`
- `проверь задачи в трекерах`
- `сверь SberTrek и Jira`
- `покажи текущее состояние по трекерам`

Это только чтение: SberTrek является основным источником, Jira заполняет пропуски
и дополняет историю. Отчёт отдельно группирует задачи по эпикам и релизам и ничего
не изменяет в трекерах или аналитическом репозитории.

При первом запуске LLM сначала задаёт недостающие вопросы по одному. До завершения
настройки она не читает трекеры и не показывает предварительные данные. Статусы
завершения и исключения задаются отдельно для SberTrek и Jira. Итоговая сводка
появляется только после записи каждого MCP-ответа командами `snapshot-*`, успешного
`run-status` и полного машинно проверенного цикла чтения. Каждый известный ключ
должен быть найден или получить доказанный результат `not-found`; пропущенный
MCP-вызов не считается недоступной возможностью. Для всех неизвестных участников
LLM последовательно спрашивает только командный идентификатор из `planning/team.md`.

## Репозитории

- `синкани репы`
- `обнови код`
- `сделай обратный дифф`
- `прими изменения из documents`

Обычное `обнови` во время работы над функциональностью обновляет рабочую ветку. `Обнови код` выполняет только защищённый `git pull --ff-only`.

## Ограничения

- Не изменять продуктовый код.
- Не создавать `requirements-exchange/` в кодовом репозитории, если разработчики не создали его заранее.
- Не использовать `git add -A` и `git add .` в аналитическом репозитории.
- Не создавать ZIP без прямого требования; разрешённое место — только `~/Downloads`.
- Не менять утверждённые планы задним числом.
