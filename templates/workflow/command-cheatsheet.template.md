# Короткая памятка аналитика

Все фразы ниже пишутся прямо в чат. Пути к программам и репозиториям LLM определяет сама.

## Работа над функциональностью

- `сохрани локальные коммиты main в рабочую ветку для <feature>`
  требует проверки истории и подтверждения коммита; LLM выполняет
  `recover-main`, а не повторную миграцию. Дальше нужны проверка и PR/MR.

- `начинаю работу над фичей <feature>`
- `пишем требования по фиче <feature>`
- `сохрани изменения`
- `обнови мою ветку`
- `требования готовы к объединению`
- `запрос на слияние принят`

## Требования

- `делаем требования`
- `актуализируй требования`
- `проверь полноту и непротиворечивость требований`
- `проведи аудит требований`
- `проанализируй требования`
- `сходи в код и уточни текущее поведение`
- `проверь русский язык требований`
- `проверь формулировки требований`
- `проверь однозначность требований`
- `найди плохо составленные требования`

Требования ведутся одной компактной спецификацией `features/<feature>/requirements.md`: назначение, границы, правила `REQ-*` со сценариями, влияния, источники и вопросы. Формулировки должны проходить проверку изолированного читателя: точные количества и ссылки, конкретное `Когда`, наблюдаемый результат в `Тогда`. Обвязка не создаёт срезы, отдельные пакеты по контурам и предварительные задачи разработки.

## Этапы поставки

- `готовим первый этап по <feature>`
- `готовим следующий этап по <feature>`
- `закрыть этап по <feature>`

Каждый этап нацелен на законченный полезный результат. В корневом документе
ведётся текущий утверждённый объём; будущие предложения остаются предварительным
бэклогом или архивом без обещания исполнения. Регистрация названия и цели сохраняет
намерение аналитика, но не утверждает весь документ и не подтверждает аудит.

Следующий этап требует закрытого предыдущего и нового решения аналитика.
Остаток не включается автоматически; зависимости проверяются по фактам.
Отсутствие прежнего требования не отменяет внедрённое поведение. Параллельных
этапов нет. Исправление требований передаётся новой редакцией того же этапа.

Закрытие требует текущего подробного разбора каждого требования и явной судьбы
всего остатка. Неизвестные результаты и незавершённое исследование блокируют его.
Можно закрыть даже нулевое выполнение с явным решением по всему объёму;
полнота отчёта, приёмка, внедрение и закрытие являются разными событиями.

Авторская проверка доступна в рабочей ветке; аудит для передачи выполняется
только после принятия ветки в main и завершения рабочей сессии. Служебные вызовы
обвязка выполняет сама. Для прежних публикаций она просит явно подтвердить,
что вся история редакций относится к одному этапу. Привязка сохраняется локально,
старые манифесты, входы и возвраты не переписываются. Историю нескольких этапов
обвязка не группирует самостоятельно. Прежние результаты проходят обычный разбор
и закрытие; новая публикация требует собственного аудита.

## Передача разработчикам

Равнозначные команды:

- `сформируй пакет для разработки`
- `отправь требования в разработку`
- `передай требования разработчикам`
- `отдаём требования разработчикам`
- `передай разрабам`
- `отдай требования разрабам`
- `отправь разрабам`
- `передаём в разработку`
- `отдаём в разработку`
- `подготовь требования для разработки`
- `собери пакет для разработчиков`

LLM отдельно проверяет каждое правило, затем взаимодействие всего набора и готовность к передаче. Она исправляет только однозначное, задаёт по одному вопросу для предметных решений и после исправлений повторяет полный аудит. Затем показывает отчёт с замечаниями, решениями, рисками и контрольной суммой и просит подтвердить результат аудита и отправку. До явного подтверждения пакет не создаётся. После подтверждения передаются только неизменившийся `requirements.md` и `manifest.json`.

Для кода LLM отправляет отдельную ветку и сообщает «ожидает слияния».
Человек создаёт и принимает PR/MR в целевую ветку. После сообщения
`проверь передачу требований по <feature>` LLM повторяет `prepare` для прежнего
подтверждённого документа и фиксирует передачу только после доказанного слияния.
Резервное размещение в аналитическом проекте не означает доставку в код.

Если разработчики заранее создали доступный `requirements-exchange/` в кодовом репозитории, используется он. Иначе создаётся `requirements-exchange/` в аналитическом репозитории. Итоговый ответ всегда содержит фактическое место и номер редакции.

Фразы про нарезку требований на срезы устарели и ничего не создают.

## Результаты разработки

- `проверь результаты разработки`
- `есть ли новые результаты`
- `покажи все новые результаты разработки`
- `покажи все результаты разработки`
- `обработай результат <return-id>`

По умолчанию LLM показывает новые результаты текущего аналитика. Просмотр чужих результатов не меняет владельца. Их обработка начинается только по явной команде.

При обработке итога аналитик решает по каждому требованию, какую проверенную
часть принять и что делать с остатком: продуктовый бэклог, дефект, технический
долг, архив или исследование. Принятое отклонение и следующая доработка могут
сосуществовать. В baseline попадают подтверждённые факты внедрения, а не сам
отчёт о завершении разработки.

`returns/receipt.json` подтверждает, что разработка приняла точную редакцию и её
контрольную сумму. Без собственной квитанции новая редакция считается новой и не
обработанной. `returns/tasks.md` уже содержит согласованную разработчиками
декомпозицию. Аналитик её не подтверждает. Каждая задача относится к одному контуру
и ссылается на локальное изменение SDD и `REQ-*`; клиентская и серверная работа не
смешиваются. Отчёты по задачам и итоговый отчёт возвращают фактическую реализацию.

## Трекеры задач

- `прочитай задачи из трекеров`
- `проверь задачи в трекерах`
- `сверь SberTrek и Jira`
- `покажи текущее состояние по трекерам`

При чтении трекеры и аналитический репозиторий не изменяются. Аналитик обязательно
указывает Jira или SberTrek и либо один эпик, либо конкретные ключи задач.

При первом запуске LLM сначала задаёт недостающие вопросы по одному. До завершения
настройки она не читает трекеры и не показывает предварительные данные. Статусы
завершения и исключения задаются отдельно для SberTrek и Jira. Затем LLM определяет
один эпик либо набор ключей и их провайдера; при неоднозначности задаёт один вопрос.
Обвязка возвращает один точный `next_action`: основной агент выполняет указанный
MCP-вызов, передаёт полный JSON в `ingest` с его `step_id` и повторяет цикл.
Полный инвентарь проекта и поиск по названию не выполняются. Пары устанавливаются
только по `SberTrek.issue_key == Jira.key`. SberTrek заполняет каждое доступное
поле первым, Jira дополняет пропуски; ролевые оценки `AN / BE / FE / QA` остаются
раздельными. История в этом протоколе не читается.

После `reconcile` нужно выполнить возвращённый `result-status`. Только его
проверенный `response_contract.text` является пользовательской сводкой; модель не
составляет её вручную.
## Планирование

- `новая фича`
- `занимаемся планированием`
- `спланируй фичу`
- `утверждаю квартальный план`
- `актуализируй реальное положение дел`
- `актуализируй задачи по фиче <feature> из Jira`
- `актуализируй текущие задачи квартала 2026-Q3 из SberTrek`

Актуализация по трекерам включает сверку, обновление подтверждённых фактов и
проверку actual-progress. Если ключи не заданы, LLM покажет локальный
предпросмотр по фиче или кварталу и уточнит область. Неизвестные даты,
исполнители и принадлежность задач не заполняются автоматически.

## Репозитории

- `синкани репы`
- `обнови код`
- `сделай обратный дифф`
- `прими изменения из documents`

Обычное `обнови` во время работы над функциональностью обновляет рабочую ветку. `Обнови код` выполняет только защищённый `git pull --ff-only`.

`Синкани репы` предлагает изменения `source` отдельной веткой в `documents`.
Человек проверяет и принимает PR/MR в `main`, затем повторяет `синкани репы`.
До подтверждённого слияния импорт ожидает рассмотрения и блокирует обратную заплату.

## Ограничения

- Не изменять продуктовый код.
- Не создавать `requirements-exchange/` в кодовом репозитории, если разработчики не создали его заранее.
- Не использовать `git add -A` и `git add .` в аналитическом репозитории.
- Не создавать ZIP без прямого требования; разрешённое место — только `~/Downloads`.
- Не менять утверждённые планы задним числом.
