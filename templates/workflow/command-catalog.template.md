# Каталог коротких команд

Команды являются обычными фразами в чате. Пользователь не указывает пути обвязки: LLM разрешает `HARNESS_ROOT`, `PROJECT_ROOT` и роли репозиториев по настройке рабочей области.

## Работа над функциональностью

| Намерение | Фразы | Действие |
|---|---|---|
| Начать работу | `начинаю работу над фичей <feature>`, `пишем требования по фиче <feature>`, `работаем с фичой <feature>`, `беру фичу <feature> в работу` | Выполнить bootstrap, проверить совместную работу, при необходимости провести одноразовую миграцию и создать ветку функциональности. |
| Сохранить | `сохрани`, `зафиксируй изменения`, `закоммить`, `сделай коммит` | Проверить изменения, сохранить только точные пути и отправить рабочую ветку. |
| Обновить ветку | `обнови`, `синкани`, `подтяни изменения`, `обнови мою ветку` | Влить актуальную основную ветку в рабочую ветку защищённой командой совместной работы. |
| Отправить на слияние | `требования готовы к объединению`, `отправь требования на проверку`, `вливаем в основную ветку` | Проверить, сохранить и отправить ветку; вернуть ссылку на форму создания запроса на слияние, не заявляя, что запрос создан. |
| Завершить слияние | `запрос на слияние принят`, `PR принят`, `ветка влита в main` | Доказать наличие отправленного коммита в основной ветке и завершить рабочую сессию. |

## Требования

| Намерение | Фразы | Действие |
|---|---|---|
| Создать или изменить | `делаем требования`, `пишем требования`, `актуализируй требования` | Работать только с `features/<feature>/requirements.md` по компактному профилю со сценариями. |
| Проверить качество | `проверь требования`, `проверь полноту требований`, `проведи аудит требований`, `проанализируй требования`, `проверь русский язык требований` | Без публикации выполнить применимые уровни аудита: отдельные правила, взаимодействие всего набора и готовность; показать замечания и задать по одному предметному вопросу. |
| Проверить формулировки | `проверь формулировки требований`, `проверь однозначность требований`, `найди плохо составленные требования`, `убери неоднозначные формулировки` | Запустить проверку контролируемых формулировок, затем применить проверку изолированного читателя. Однозначные редакционные дефекты исправить; для выбора предметного смысла задать один вопрос. Пакет не создавать. |
| Посмотреть код | `сходи в код`, `посмотри в коде`, `сверь с кодом` | Выполнить ограниченное чтение зарегистрированного кодового репозитория с проверкой неизменности. |
| Передать разработчикам | `сформируй пакет для разработки`, `передаём в разработку`, `отдаём требования разработчикам`, `подготовь требования для разработки`, `отправь требования в разработку`, `передай требования разработчикам`, `передай разрабам`, `отдай требования разрабам`, `отправь разрабам`, `отдаём в разработку` | Провести обязательный аудит, по одному закрыть предметные вопросы, показать отчёт и запросить явное подтверждение. Только после подтверждения передать неизменившийся `requirements.md` и `manifest.json`. |

Команды `разложи требования на срезы`, `нарежь требования на срезы`, `подготовь требования по срезам` и похожие больше не являются командами обвязки. Не создавай по ним файлы. Сообщи, что срезы исключены из процесса, и уточни, требуется ли изменить структуру глав в едином `requirements.md` или передать требования разработчикам.

## Размещение передачи

Для команды передачи:

1. Заверши принятую рабочую ветку и проверь актуальность `analytics/main`, если включена совместная работа.
2. Выполни `requirementsctl.py begin-preparation`.
3. Проведи все три уровня из `core/requirements-audit.md`, исправь однозначное и по одному закрой предметные вопросы.
4. После исправлений повтори затронутые связи, затем все три уровня по всему документу.
5. Выполни проверки из `modes/requirements.md`, включая `validate-requirements-wording.py`, и запиши итог через `requirementsctl.py record-audit`.
6. Покажи отчёт аналитику, задай установленный вопрос подтверждения и остановись.
7. Только после явного положительного ответа выполни `requirementsctl.py confirm-audit`.
8. Выполни `requirements-exchange.py prepare`; программа проверит подтверждение, метод, три уровня и контрольную сумму.
9. Если в роли `code` существует доступный корневой `requirements-exchange/`, защищённая операция использует его.
10. Если репозитория, каталога или доступа нет, операция создаёт `PROJECT_ROOT/requirements-exchange/`.
11. Выполни `requirementsctl.py mark-published` для резервного размещения в `analytics` или подтверждённой передачи в `code` (`publication_confirmed=true`). При `awaiting-merge` сообщи ветку и необходимость человеческого PR/MR; после его принятия повтори `prepare` для неизменного подтверждённого документа и только затем фиксируй передачу.
12. Сообщи роль, номер редакции, состояние и место: ветку запроса, целевую ветку и путь для кода либо абсолютный резервный путь.

`проверь передачу требований по <feature>` означает повторить `prepare` с прежней
целевой веткой и неизменным подтверждённым документом. При `awaiting-merge` не
переоткрывай аудит и не создавай новую редакцию. При `publication_confirmed=true`
выполни `mark-published`. Это не команда `collaboration.py finish` рабочей ветки.

Не создавай ZIP и промежуточный пакет `ready`. Ожидание подтверждения аудита не создаёт редакцию обмена.

## Результаты разработки

| Намерение | Фразы | Действие |
|---|---|---|
| Проверить свои | `проверь результаты разработки`, `проверь возвраты разработчиков`, `есть ли новые результаты` | Найти новые файлы функциональностей текущего аналитика и показать машинную стадию `new / accepted / decomposed / in-progress / completed` через `requirements-exchange.py scan`. |
| Посмотреть все | `покажи все новые результаты разработки`, `покажи все результаты разработки`, `посмотрим, что пришло другим аналитикам` | Запустить поиск с `--all`, ничего не обрабатывать автоматически. |
| Обработать выбранное | `обработай результат <id>`, `разбери возврат <id>` | Сопоставить результат с точной входной редакцией и её сценариями, получить решения аналитика по каждому `REQ-*`, отдельно учесть внедрение и остаток, затем зарегистрировать обработку. |

Чужой результат можно просмотреть без смены владельца. Его обработка начинается только после явной команды аналитика.

Для итогового `summary.md` следуй `core/developer-handoff.md`: разделяй полноту,
соответствие, проверку, принятие и внедрение. Содержательные вопросы задавай по
одному. Подготовь внутренний файл по `templates/exchange/result-review.template.json`
и запиши согласованные решения через `record-processed --decision reviewed --review-file ...`.
Команда записывает решения, но не переносит документы автоматически. Изменения
требований, релиза, baseline и адресатов остатка выполняй в режиме-владельце;
изменение требований требует сессии совместной работы. Ссылки в решении должны
указывать на уже существующие записи. Сохранение работы следует обычному
протоколу `core/collaboration.md`.

## Трекеры задач

| Намерение | Фразы | Действие |
|---|---|---|
| Прочитать и сверить | `прочитай задачи из трекеров`, `проверь задачи в трекерах`, `сверь SberTrek и Jira`, `покажи текущее состояние по трекерам` | Уточнить провайдер, если он не указан. Начать один `direct-tracker-v1` run с intent `read-only`; основной агент сам выполняет каждый точный `next_action`, импортирует полный JSON и завершает через `reconcile -> result-status`. Ничего не изменять. |
| Актуализировать планы | `актуализируй задачи`, `актуализируй задачи по фиче`, `актуализируй Гант`, `актуализируй Гант с текущими делами` | Выполнить тот же прямой линейный сбор с intent `update-planning`. Применять компактный `reconciled.json` только после `planning_application_allowed: true`; tracker-run планы не меняет. |

Команда чтения не означает `актуализируй реальное положение дел`: она не меняет
execution-задачи и actual-progress. Применение прочитанных фактов вводится отдельно.

## Планирование

| Намерение | Фразы | Действие |
|---|---|---|
| Новая функциональность | `новая фича` | Выполнить приём и сравнение с baseline до создания структуры. |
| Планирование | `занимаемся планированием`, `спланируй фичу` | Подготовить плановые истории, оценки `AN / BE / FE / QA`, зависимости, риски и расписание. |
| Утверждение | `утверждаю квартальный план`, `апрувь план` | Только по явной команде пользователя зафиксировать утверждённый неизменяемый план. |
| Фактическое состояние | `актуализируй реальное положение дел`, `обнови фактический план` | Использовать фактические задачи и подтверждённый `returns/tasks.md`, не менять утверждённый план. |

## Репозитории

| Намерение | Фразы | Действие |
|---|---|---|
| Полный обмен | `синкани репы`, `синхронизируй репозитории`, `обнови репы` | Выполнить зарегистрированный обмен. Входящий `source` предложить отдельной веткой для человеческого PR/MR в `documents/main`; до принятия не объявлять синхронизацию и не создавать обратную заплату. Повтор продолжает незавершённый импорт. |
| Обновить код | `обнови код`, `обнови coda`, `обнови репу с кодом` | Выполнить только защищённый `git pull --ff-only` роли `code`. |
| Обратная заплата | `сделай обратный дифф`, `собери обратную заплату` | Создать и проверить локальную пару обратной заплаты без её применения. |
| Отложить импорт | `отложи импорт source`, `отклони этот импорт source` | После явного решения аналитика и удаления человеком удалённой ветки отклонённого PR/MR выполнить `repository-exchange.py defer-source-import --analyst-confirmed`. Сохранить квитанцию, ждать новую версию source; обратная заплата остаётся заблокированной. |

Короткая фраза `обнови` во время работы над функциональностью означает обновление рабочей ветки. Фразы с `репы`, `репозитории`, `code` или `coda` сохраняют специальные значения из таблицы.
