# База продуктового знания

Проект использует `coda-analyst-harness` для планирования, требований, прототипов, передачи в разработку, QA, план-факта и финализации релизов.

## Источники истины

- `baseline/current/` - текущее реализованное состояние системы и доменная модель.
- `features/` - изменения относительно текущего состояния, требования и срезы.
- `planning/` - входящие заметки, квартальные планы, план-факт и ретроспективы.
- `releases/` - поставленные пакеты перед переносом в текущее состояние.
- `context/source-materials/` - исходные материалы и свидетельства, но не каноническое состояние.

Корневой `features/<feature>/requirements.md` является главным документом требований. Карточки срезов, пакеты требований к клиентской и серверной части, входные редакции, техническая декомпозиция и результаты тестирования являются производными.

## Сквозной процесс

Репозиторий хранит продуктовое знание. Код может лежать рядом или в отдельных репозиториях. Требования не нужно копировать в кодовые репозитории как второй источник истины.

### 1. Текущее состояние

`baseline/current/` описывает уже реализованную систему:

- доменную модель и словарь;
- текущие правила и ограничения;
- текущие данные, API и интерфейсы;
- зафиксированные решения.

Новая доработка сначала живёт в `features/` как изменение. В `baseline/current/` она попадает только после финализации релиза.

### 2. Планирование

`planning/` хранит входящие заметки, квартальные планы, командирские планы, приоритеты, закрытые интервалы, состав команды и план-факт. Функциональность планируется как законченный пользовательский или системный результат. Для неё создаются ролевые плановые истории AN, BE, FE и QA, если роль участвует.

После утверждения квартальный и командирский планы не меняются. Поздно обнаруженная работа отражается на диаграмме фактического выполнения через черновики задач и фактические задачи. Это сохраняет возможность честного сравнения квартальной оценки с реальным выполнением.

### 3. Требования

`features/<feature>/requirements.md` является главным документом требований по функциональности. Он описывает изменение относительно `baseline/current/`: пользовательский результат, системное поведение, правила, изменения данных, API, интерфейсов, проверки и доработки затронутых соседних функциональностей.

Новые корневые документы создаются по `.workflow/requirements-profile.md`, основанному на ISO/IEC/IEEE 29148:2018. Профиль задаёт практические критерии качества и трассировки, но не заявляет полного соответствия стандарту. Существующие документы переводятся на профиль только при существенной переработке или по явному решению пользователя.

Срезы в `features/<feature>/slices/<slice>/` производны от корневых требований. Они нужны для аналитической проверки целостных пользовательских сценариев, прототипов и проверок и остаются основной единицей тестирования.

Аналитик не определяет окончательную техническую нарезку. Карточки будущих задач Jira создают разработчики внутри общего пакета после сверки требований с актуальным кодом и локальными SDD нужных контуров.

### 4. Передача в разработку

Перед технической декомпозицией аналитик создаёт редакцию общего пакета:

- `features/<feature>/handoffs/<package-id>/handoff.json` - состояние редакций и единственное следующее действие SDD;
- `revisions/NNN/package/request.md` - краткий паспорт в форме «Цель / Ограничения / Контекст / Примеры / Критерии приёмки»;
- `revisions/NNN/package/manifest.json` - состав, способ трассировки, идентификаторы и контрольные суммы;
- `revisions/NNN/package/requirements.md` и `package/slices/` - полный документ, карточки срезов и их подробные требования по контурам;
- `revisions/NNN/returns/` - техническая декомпозиция и независимые результаты реализации и тестирования.

Разработчики создают самодостаточные карточки `DEV-BE-*` и `DEV-FE-*`. Одна карточка относится к одному контуру и одному законченному техническому результату. Целевой размер - 1-3 рабочих дня одного исполнителя; максимум 5 дней для серверной и 10 дней для клиентской задачи. Оценка и ключ Jira необязательны.

`returns/development-tasks/index.md` постоянно показывает порядок работы, действующие будущие задачи Jira и основные команды. Каждая карточка создаётся по шаблону пакета, заполняется полностью и сохраняет весь блок `Короткие команды разработчика` после каждой правки. Обвязка не подтверждает карточку с пропущенным разделом, заглушкой, потерянным идентификатором или сокращённой инструкцией.

Новые требования трассируются по `REQ-*` и `SCN-*`. Для прежнего документа `traceability.mode = legacy-sections` явно назначает единицей результата раздел с устойчивым идентификатором и ссылкой на карточку среза. SDD не придумывает отсутствующие идентификаторы.

После решения разработчиков SDD создаёт неизменяемый снимок декомпозиции и автоматически делает его доступным аналитику. Аналитик не разрешает начало разработки и сам решает, какие карточки отразить в фактическом плане. Новая декомпозиция создаёт следующий снимок, а не переписывает предыдущий.

Если требования изменились после передачи, аналитик формирует новую входную редакцию и явно меняет состояние прежней. Подтверждённые карточки разработчиков задним числом не редактируются.

### 5. Взаимодействие с кодом

Кодовый репозиторий указывается в `.workflow/code-repos.json`. На машине аналитика `documents/` и `coda/` являются независимыми соседними клонами. Общая рабочая область создаётся командами `code-inspect.py doctor` и `code-inspect.py setup`; пути к коду в обычных запросах не указываются.

Рекомендуемая первоначальная настройка:

```bash
mkdir -p ~/work/rscon
cd ~/work/rscon
git clone ssh://git@stash.delta.sbrf.ru:7999/rscon/documents.git documents
git clone ssh://git@stash.delta.sbrf.ru:7999/rscon/coda.git coda
cd documents
python .workflow/tools/code-inspect.py doctor .
python .workflow/tools/code-inspect.py setup .
```

Аналитическая LLM может по явной команде или автоматически при необходимости проверить фактический API, данные, статусы, роли и уже реализованное поведение. Она фиксирует ветку и коммит, исследует один контур, читает только найденные модули и соседние проверки, а затем подтверждает, что `coda` не изменился. Значимые выводы сохраняются как вспомогательные доказательства и переносятся в требования только после отделения фактов от предметных решений.

Идеальная модель такая:

- этот репозиторий остаётся главным источником требований и план-факта;
- общий каталог передачи хранится в `features/<feature>/handoffs/<package-id>/` и доступен аналитической и разработческой сторонам по одному пути;
- `handoff.json` указывает единственную редакцию, разрешённую к обработке, каталоги возврата и необходимость продолжения, ожидания либо остановки;
- пакет редакции автономен и фиксирует контрольные суммы входных файлов; разработчику не требуется читать остальные требования репозитория;
- языковая модель читает активную редакцию, компактные задание и манифест, затем только связанные требования одного контура, локальную SDD этого контура, найденные модули и соседние проверки;
- если код показывает, что ожидаемое техническое устройство неуместно, разработчик выбирает подходящее решение и фиксирует отличие в квитанции;
- если входное требование неоднозначно, зависимый пункт остаётся невыполненным, а независимая работа продолжается;
- пакет не переписывается во время разработки: декомпозиция фиксируется снимками, а фактическая поставка и дополнительный объём возвращаются в квитанциях реализации;
- тестировщик работает по срезам той же редакции и сохраняет независимые квитанции тестирования.

Разработчику передаётся ссылка на общий каталог пакета. SDD читает `handoff.json`, берёт только разрешённую редакцию, сохраняет карточки в `returns/development-tasks/`, подтверждённые снимки в `returns/decomposition-snapshots/`, а квитанции в `returns/implementation-results/`. Тестировщик сохраняет результаты в `returns/test-results/`.

SDD не загружает весь `coda`, оба контура или все локальные спецификации одновременно. Второй контур читается только по обнаруженной и записанной зависимости. Пути исходного аналитического репозитория и абсолютные пути машины аналитика в полном документе являются сведениями о происхождении материала, а не обязательными входами разработчика.

#### Команда аналитика для передачи

Команда `сформируй пакет для разработки` и её естественные варианты `передаём в разработку` и `отдаём требования разработчикам` запускают полный проход готовности. LLM проверяет полноту, однозначность, непротиворечивость, проверяемость, границы, данные, состояния, ошибки, влияния, срезы, трассировку, устаревшие остатки и русский язык. Однозначные исправления без изменения смысла выполняются автоматически.

Если требуется предметное решение, LLM задаёт ровно один вопрос и ждёт ответа; оставшиеся вопросы рассматриваются последовательно. Пока есть содержательная неопределённость или блокирующая ошибка, пакет не создаётся. После успешной проверки обвязка сразу публикует редакцию как `sent` с действием SDD `process`. ZIP создаётся только по явному требованию и только в `~/Downloads`; внутри репозитория архивы запрещены. Аналитик проверяет требования, а не внутренние файлы пакета, поэтому промежуточного `ready` нет.

### 6. Реализация и возврат факта

Рабочий цикл общего пакета:

1. SDD принимает одну неизменяемую редакцию и исследует код нужного контура.
2. Разработчики подтверждают карточки будущих задач Jira. Снимок фоново поступает аналитику, но разработка ответа не ждёт.
3. Каждая карточка реализуется отдельно; обвязка переносит в заготовку квитанции точные идентификаторы, номер снимка и необязательный ключ Jira, после чего SDD фиксирует фактическое состояние, отклонения, остаток, коммиты и проверки.
4. Для тестировщика обвязка создаёт по срезу заготовку с номером снимка, точным составом требований и сценариев, связанными карточками и зарегистрированными квитанциями реализации; тестировщик заполняет фактический результат.
5. Аналитик сам решает, какие карточки материализовать в фактическом плане и как обработать полученные результаты.
6. По аналитическому решению обновляются требования, релиз и затем `baseline/current/`; невыполненное оставляется, откладывается, переносится или отменяется.
7. Утверждённый квартальный план не меняется.

## Начало работы

1. Прочитать `AGENTS.md`.
2. Сформировать минимальный контекст сессии:

```bash
python .workflow/tools/harnessctl.py session-brief .
```

3. Перед широкими изменениями проверить обвязку:

```bash
python .workflow/tools/harnessctl.py doctor .
```

4. Использовать ролевые команды из `.workflow/command-cheatsheet.md`.

## Планирование

Функциональность является результатом уровня квартала. У неё может быть не более одной плановой истории на роль: `AN`, `BE`, `FE`, `QA`. Утверждённые квартальный и командирский планы неизменяемы; поздний объём работ появляется на диаграмме фактического выполнения.

Черновой план пересобирается командой:

```bash
python .workflow/tools/sync-planning-gantt.py . <YYYY-QN>
```

Утверждение выполняет только владелец проекта:

```bash
python .workflow/tools/harnessctl.py plan-approve . <YYYY-QN> --by <owner>
```

## Требования

Требования пишутся на русском языке. Английская форма допускается для кода, путей, API, БД, значений перечислений, протокольных статусов, закреплённых названий внешних систем и технических сокращений.

Проверка изменённых требований:

```bash
python .workflow/tools/harnessctl.py language-check . --feature <feature>
python .workflow/tools/harnessctl.py requirements-check . --feature <feature>
```

## Проверки

Базовая диагностика:

```bash
python .workflow/tools/harnessctl.py doctor .
```

Проектные сценарии проверки:

```bash
python .workflow/tools/evaluate-harness.py .
```
