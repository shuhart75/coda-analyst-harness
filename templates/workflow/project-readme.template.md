# Аналитические материалы проекта

Этот репозиторий хранит только проектные данные: текущее состояние системы, требования, планы, пакеты передачи, результаты разработки и сведения о выпусках. Инструкции LLM, режимы, программы и шаблоны находятся во внешней аналитической обвязке уровнем выше.

## Структура

- `baseline/current/` - подтверждённое текущее состояние системы;
- `baseline/versions/` - сохранённые версии текущего состояния;
- `context/source-materials/` - исходные материалы;
- `context/project-rules/` - особенности проекта;
- `context/evals/` - проектные проверочные сценарии;
- `planning/team.md` - состав команды, закрытые интервалы и коэффициенты;
- `planning/approved-plans/` - контрольные снимки утверждённых планов;
- `planning/<YYYY-QN>/` - квартальные планы и фактическое выполнение;
- `features/<feature>/requirements.md` - корневые требования функциональности;
- `features/<feature>/development-results-state.json` - решения по полученным результатам разработки;
- `requirements-exchange/` - резервный каталог передачи, когда публикация в кодовый репозиторий недоступна;
- `releases/` - материалы завершённых выпусков.

В отслеживаемом Git-дереве не должно быть копий `.workflow`, `.vscode` или `AGENTS.md` аналитической обвязки. Местный `AGENTS.md` с маркером `analyst-harness-local-entrypoint:v1` создаётся программой развёртывания, исключается через `.git/info/exclude` и не входит в проект.

## Работа через внешнюю обвязку

Из корня `coda-analyst-harness`:

```bash
python3 scripts/harnessctl.py session-brief documents
python3 scripts/harnessctl.py doctor documents
python3 scripts/harnessctl.py wording-check documents --feature <feature>
python3 scripts/code-inspect.py doctor documents
```

LLM должна получать правила из корня обвязки, а изменять проектные материалы только в этом репозитории. Роль `code` используется для ограниченного чтения. Единственное исключение — защищённая публикация в заранее созданный разработчиками `requirements-exchange/**`; она выполняется из временной копии и не изменяет обычный клон кода.

## Источники истины

- утверждённый план после утверждения неизменяем;
- фактическое выполнение отражается отдельно от утверждённого плана;
- корневые требования являются единственным авторским документом и ведутся как компактная бизнес-спецификация с `REQ-*` и вложенными сценариями; срезы и отдельные пакеты по контурам не создаются;
- перед передачей выполняется трёхуровневый аудит отдельных правил, их взаимодействия и готовности документа; форматная проверка его не заменяет;
- каждое правило и сценарий проходят проверку однозначности: явные количества и ссылки, конкретное событие в `Когда`, наблюдаемый результат в `Тогда`;
- принимающая SDD сверяет бизнес-контракт с кодом и создаёт собственные технические изменения отдельно по контурам;
- обычная правка требований не создаёт редакцию передачи, а её источник фиксируется в `requirements-state.json`;
- реализованное поведение переносится в `baseline/current/` только после обработки результата разработки;
- изменения соседних функциональностей входят в объём текущих требований отдельным разделом;
- известные несогласованные хвосты фиксируются в `planning/consistency-backlog.md`.

## Язык

Требования и пользовательская документация пишутся по-русски. Английский используется только для кода, путей, API, имён полей, статусов, форматов, названий продуктов и необходимых специальных терминов.
