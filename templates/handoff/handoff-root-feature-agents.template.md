# Контракт SDD для пакета `<package-id>`

## Область действия и приоритет

Этот файл является обязательным договором обработки общего пакета функциональности.

- Правила этого файла действуют для `handoff.json`, `.control/` и `revisions/` данного пакета.
- При изменении файлов `coda/backend` или `coda/frontend` SDD ОБЯЗАНА выполнять локальные инструкции соответствующего контура `coda`.
- Локальные инструкции `coda` определяют способ реализации кода. Этот файл определяет только приём требований, декомпозицию и возврат результатов.
- Отправленная редакция в `revisions/<revision>/package/` неизменяема.

## Обязательный порядок начала работы

После команды `Обработай активную редакцию пакета.` SDD ОБЯЗАНА:

1. Найти корень пакета по `handoff.json` с `package_kind = feature-delivery`.
2. Прочитать `handoff.json` и проверить, что `agent_contract.path` указывает на этот `AGENTS.md`.
3. Выполнить только действие из `next_sdd_action`.
4. При действии `process` выполнить `claim` до создания или изменения возвратных материалов.
5. Взять номер редакции, `package_path` и `returns_path` только из `next_sdd_action`.
6. Прочитать `request.md`, `manifest.json` и `README.md` активной входной редакции.
7. Прочитать `<returns_path>/development-tasks/README.md` перед технической декомпозицией.

## Действия по состоянию

| `next_sdd_action.action` | Обязательное поведение |
|---|---|
| `wait` | Не изменять пакет. Сообщить причину из `next_sdd_action.reason`. |
| `no-action` | Не изменять пакет. Сообщить, что редакция не требует обработки. |
| `process` | Выполнить `claim` и начать техническую декомпозицию активной редакции. |
| `continue` | Продолжить ранее принятую редакцию, не выполняя повторный `claim`. |
| `stop-and-report` | Остановить изменения и зафиксировать доступный фактический результат. |

SDD ЗАПРЕЩЕНО выбирать другую редакцию или путь, не указанный в `next_sdd_action`.

## Ограничение контекста

SDD ОБЯЗАНА обрабатывать серверный и клиентский контуры отдельными последовательными проходами.

Для каждого прохода порядок чтения следующий:

1. связанные идентификаторы и срезы из `manifest.json`;
2. относящиеся к контуру разделы `requirements.md` и подробные требования срезов;
3. локальная SDD выбранного контура в `coda`;
4. поиск точных сущностей, полей, маршрутов и символов;
5. только найденные модули и соседние проверки.

SDD ЗАПРЕЩЕНО загружать весь `coda`, оба контура или все локальные спецификации без зафиксированной зависимости. Второй контур открывается только отдельным проходом.

## Техническая декомпозиция

Во время технической декомпозиции SDD ЗАПРЕЩЕНО изменять код.

SDD ОБЯЗАНА:

1. Создавать каждую карточку только по `.control/templates/development-task-card.template.md`.
2. Создавать только карточки `DEV-BE-*` для `backend` и `DEV-FE-*` для `frontend`.
3. Описывать в карточке одну будущую задачу Jira и один законченный технический результат.
4. Помещать в карточку полные требования, сценарии, влияния, границы, зависимости, состояние кода, доказательства и проверки.
5. Сохранять полный раздел `Короткие команды разработчика` после каждой правки.
6. Пересобирать `index.md` после каждого изменения карточек.
7. Явно показывать непокрытые `REQ-*`, `SCN-*` и `IMP-*`.
8. Не придумывать оценку, ключ Jira, состояние кода или предметное решение при отсутствии доказательств.

Целевой размер карточки составляет 1-3 дня одного исполнителя. Оценка необязательна. Оценка свыше 5 дней для `backend` или свыше 10 дней для `frontend` требует заполненного обоснования.

## Подтверждение декомпозиции

После команды `Декомпозиция подтверждена разработкой.` SDD ОБЯЗАНА:

1. Оставить в `decomposition-receipt.json` только действующие задачи.
2. Установить каждой действующей задаче `decomposition_status = confirmed-by-development`.
3. Установить в каждой действующей карточке строку `| Состояние декомпозиции | подтверждена разработкой |`.
4. Установить в `index.md` строку `Состояние декомпозиции: **подтверждена разработкой**`.
5. Заполнить `confirmed_by`, `confirmed_at`, `source_revisions`, задачи, оценки, зависимости и необязательные ключи Jira. Неизвестные значения оставить `null`.
6. Вычислить `coverage` как точную разность между составом `manifest.json` и распределением по действующим карточкам.
7. Выполнить `confirm-decomposition`.

SDD НЕ ДОЛЖНА считать пример команды в карточке подтверждением её состояния. При ошибке проверки SDD исправляет только указанную структурную ошибку и НЕ ДОЛЖНА менять предметный смысл без решения разработчика или аналитика.

Успешное подтверждение создаёт неизменяемый снимок в `decomposition-snapshots/`. Получение ответа аналитика не требуется для начала реализации.

## Реализация

После команды `Возьми <DEV-id или ключ Jira> в разработку.` SDD ОБЯЗАНА:

1. Найти карточку в подтверждённом снимке декомпозиции.
2. Выполнить `prepare-implementation` до изменения кода.
3. Применить локальную SDD соответствующего контура `coda`.
4. Сверить карточку с текущими спецификациями, кодом и проверками.
5. Продолжить независимый однозначный объём, даже если часть поведения уже реализована, реализована иначе или заблокирована.
6. Заполнить созданную квитанцию фактическим результатом каждого требования и сценария, доказательствами, проверками, остатком и ревизиями кода.
7. Заменить `draft` итоговым состоянием и выполнить `register-implementation`.

SDD НЕ ДОЛЖНА объявлять уже реализованное или реализованное иначе поведение ошибкой всего пакета. Фактическое поведение и отклонение фиксируются в квитанции.

## Тестирование

После команды `Возьми срез <slice-id> в тестирование.` SDD ОБЯЗАНА:

1. Выполнить `prepare-test` для выбранного среза и актуального подтверждённого снимка.
2. Проверить точный состав требований и сценариев среза.
3. Использовать карточки и зарегистрированные квитанции реализации только как дополнительный контекст.
4. Заполнить результат каждого требования и сценария, доказательства, находки и заблокированный объём.
5. Заменить `draft` итоговым состоянием и выполнить `register-test`.

## Возвратные материалы

SDD ОБЯЗАНА записывать создаваемые материалы только в каталог из `next_sdd_action.returns_path`:

- `development-tasks/` — рабочая декомпозиция;
- `decomposition-snapshots/` — подтверждённые неизменяемые снимки;
- `implementation-results/` — квитанции реализации;
- `test-results/` — квитанции проверки срезов.

Человек не редактирует служебный JSON. SDD ОБЯЗАНА самостоятельно заполнять его по шаблонам и вызывать служебные команды.

## Служебные команды

Команды выполняются из корня общего пакета:

```bash
python .control/handoffctl.py status .
python .control/handoffctl.py claim . <revision> --by "<идентификатор-сеанса>"
python .control/handoffctl.py confirm-decomposition . <revision>
python .control/handoffctl.py prepare-implementation . <revision> <DEV-BE-*|DEV-FE-*> --decomposition-revision <decomposition-revision>
python .control/handoffctl.py register-implementation . <revision> <DEV-BE-*|DEV-FE-*> --decomposition-revision <decomposition-revision>
python .control/handoffctl.py prepare-test . <revision> <slice-id> --decomposition-revision <decomposition-revision>
python .control/handoffctl.py register-test . <revision> <slice-id> --decomposition-revision <decomposition-revision>
python .control/handoffctl.py validate .
```

## Запреты

SDD ЗАПРЕЩЕНО:

- изменять файлы в `package/` отправленной редакции;
- создавать или хранить ZIP внутри репозитория;
- создавать транспортный ZIP без явного требования аналитика;
- использовать транспортный ZIP вместо общего каталога для штатной работы;
- просить разработчика вводить доступные SDD пути или вручную составлять JSON;
- копировать аналитический репозиторий или требования в `coda`;
- переносить пакет целиком в `openspec/changes`;
- скрывать непокрытые требования, сценарии или влияния;
- останавливать независимые задачи только из-за частичного расхождения с ожиданиями;
- изменять локальные спецификации или код без выполнения правил SDD соответствующего контура `coda`.
