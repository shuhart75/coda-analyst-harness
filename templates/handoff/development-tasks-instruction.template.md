# Инструкция SDD по технической декомпозиции

Разработчик сообщает короткое намерение и не указывает пути. SDD сама находит общий каталог передачи и активную редакцию.

## Обязательный порядок чтения

1. Сначала прочитать `handoff.json` и выполнять только `next_sdd_action`.
2. Затем прочитать `package/request.md`, `package/manifest.json` и этот файл.
3. Выбрать только один контур: серверный или клиентский.
4. По идентификаторам из `manifest.json` открыть только относящиеся к выбранному контуру разделы `package/requirements.md`, карточки срезов и их подробные требования.
5. Открыть локальную SDD выбранного контура в `coda`.
6. Поискать точные сущности, поля, маршруты и символы; после этого читать только найденные модули и соседние проверки.

Не загружать весь репозиторий `coda`, оба контура одновременно или все локальные спецификации. Второй контур открывается только при обнаруженной зависимости, которую нужно явно записать.

Пути внутри `package/` доступны. Пути из исходного аналитического репозитория и абсолютные пути машины аналитика в тексте требований являются только сведениями о происхождении материала: не пытаться открывать их и не считать их обязательными входами. Фактическое состояние проверяется по локальной SDD, коду и проверкам `coda`.

## Правила карточек

- Карточка описывает одну будущую задачу Jira и только один контур: `backend` или `frontend`.
- Карточка самодостаточна: полные требования, сценарии, влияния, данные, границы, проверки и доказательства состояния кода находятся внутри.
- Каждую новую карточку создавать только по `.control/templates/development-task-card.template.md`, заполнять все разделы и сохранять блок `Короткие команды разработчика` без сокращений. Этот блок должен оставаться перед глазами разработчика после любой правки карточки.
- В `index.md` всегда сохранять краткий порядок работы, все основные команды и ссылки на действующие карточки.
- Оценка в днях одного исполнителя и ключ Jira необязательны.
- Состояния декомпозиции: `предложена`, `подтверждена разработкой`, `заменена`, `разделена`, `объединена`, `отменена`.
- Состояния выполнения и тестирования в поле состояния карточки не записываются.
- Подтверждённая декомпозиция не изменяется задним числом. Следующее подтверждение создаёт новый снимок.
- Подтверждение декомпозиции не ждёт аналитика и не запрещает сразу начинать реализацию.
- После каждого изменения пересобрать `index.md` и проверить полное распределение требований, `SCN-*` и `IMP-*` из `manifest.json`. При `legacy-sections` требования имеют секционные идентификаторы без префикса `REQ-`.
- Код не менять во время технической декомпозиции. Реализация начинается отдельной короткой командой.
- При расхождении кода с входными требованиями зафиксировать фактическое поведение и остаток в карточке. Уже реализованный или иначе реализованный пункт не останавливает декомпозицию и независимые задачи.

## Порядок подтверждения декомпозиции

После команды `Декомпозиция подтверждена разработкой.` SDD обязана:

1. Оставить в `decomposition-receipt.json` только действующие задачи и установить для них `decomposition_status = confirmed-by-development`.
2. В каждой действующей карточке установить строку `| Состояние декомпозиции | подтверждена разработкой |`. Наличие этих слов только в блоке коротких команд подтверждением не является.
3. В `index.md` перенести действующие карточки в подтверждённый состав и установить строку `Состояние декомпозиции: **подтверждена разработкой**`.
4. Заполнить `confirmed_by`, `confirmed_at`, `source_revisions`, оценки, зависимости и необязательные ключи Jira. Неизвестные значения оставить `null`, не придумывать их.
5. Вычислить `coverage` как точную разность между полными списками идентификаторов из `manifest.json` и распределением по действующим карточкам. Непокрытые идентификаторы не скрывать.
6. Выполнить `confirm-decomposition`. Если проверка не прошла, исправить только указанные структурные ошибки; предметный смысл без решения разработчика или аналитика не менять.

Успешная команда создаёт неизменяемый снимок в `decomposition-snapshots/`. После этого разработчик может сразу начинать реализацию подтверждённой карточки.

## Толкование коротких команд

| Команда | Действие SDD |
|---|---|
| `Подготовь декомпозицию серверной части.` | Исследовать серверный контур и создать или обновить предложенные `DEV-BE-*`. |
| `Подготовь декомпозицию клиентской части.` | Исследовать клиентский контур и создать или обновить предложенные `DEV-FE-*`. |
| `Проверь декомпозицию.` | Проверить карточки, размеры, зависимости и покрытие; содержательные решения не принимать. |
| `Уточни <задача> по коду.` | Повторно проверить фактическое состояние, границу и остаток задачи. |
| `Измени состав <задача>: <что изменить>.` | Изменить объём и повторно проверить покрытие и зависимости. |
| `Объедини <задача> и <задача>.` | Сохранить одну действующую карточку, вторую оставить в истории. |
| `Раздели <задача>: <граница>.` | Создать отдельную карточку и перераспределить содержание. |
| `Перенеси <идентификатор> в <задача>.` | Перенести полное правило и связанные проверки. |
| `<задача> уже реализована. Проверь.` | Подтвердить кодом и тестами и оставить только фактический остаток. |
| `Отмени <задача>: <причина>.` | Сохранить историю и показать непокрытый объём. |
| `Покажи непокрытые требования.` | Вывести отчёт без изменения файлов. |
| `<задача> подтверждена разработкой.` | Зафиксировать решение разработчика по одной карточке. |
| `Декомпозиция подтверждена разработкой.` | Подтвердить действующие карточки и автоматически создать снимок для аналитика. |
| `Подготовь список для Jira.` | Вывести подтверждённые карточки; Jira не изменять. |
| `Свяжи <задача> с <ключ Jira>.` | Записать необязательную внешнюю связь. |
| `Возьми <задача или ключ Jira> в разработку.` | Начать локальный процесс реализации без ожидания аналитика. |
