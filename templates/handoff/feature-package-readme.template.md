# Пакет функциональности `<package-id>`, редакция `<revision>`

Этот пакет передаёт разработке требования по функциональности целиком. Он не содержит заранее утверждённой технической декомпозиции.

## Порядок работы

1. Сначала прочитать корневой `handoff.json`, затем `request.md`, `manifest.json` и эту инструкцию.
2. Выбрать один контур. По идентификаторам манифеста прочитать только относящиеся к нему разделы требований, срезы и подробные требования срезов.
3. Прочитать локальную SDD выбранного контура, найти точные сущности в коде и открыть только найденные модули и соседние проверки. Не загружать весь `coda` и оба контура одновременно.
4. Сформировать предложенные карточки будущих задач Jira в `returns/development-tasks/` строго по вложенному шаблону и сохранить в каждой карточке все короткие команды.
5. Обсудить и изменить декомпозицию короткими командами из карточек.
6. После решения разработчиков выполнить `confirm-decomposition`. Команда создаёт неизменяемый снимок для аналитика и не блокирует начало разработки.
7. Реализовывать подтверждённые карточки по правилам разработческой SDD.
8. Для каждой карточки автоматически подготовить квитанцию с точными идентификаторами, заполнить фактический результат и зарегистрировать её в `returns/implementation-results/`.
9. Тестировщики работают по исходным срезам; обвязка автоматически подготавливает связанную со снимком декомпозиции квитанцию в `returns/test-results/`.

Пути внутри пакета доступны принимающей стороне. Упомянутые в полном документе пути исходного аналитического репозитория и абсолютные пути машины аналитика являются только сведениями о происхождении материала. Их не нужно открывать; фактическое состояние определяется по локальной SDD, коду и проверкам `coda`.

Оценка задачи и ключ Jira необязательны. Их отсутствие не мешает подтверждению декомпозиции, реализации или тестированию.

## Важные границы

- Декомпозиция определяется разработчиками по фактическим техническим границам.
- Подтверждение декомпозиции автоматически делает её доступной аналитику, но аналитик не согласовывает начало разработки.
- Карточка хранит состояние декомпозиции. Выполнение, передача аналитику и тестирование имеют отдельные состояния.
- Тестировщик получает тот же пакет, но основной единицей проверки остаётся срез, а карточки и квитанции реализации служат контекстом.
- Уже реализованное или реализованное иначе поведение фиксируется доказательствами и не останавливает независимую работу.
- Поле `traceability.mode = legacy-sections` означает допустимую секционную трассировку прежнего документа. Единицей результата тогда служит раздел с устойчивым идентификатором; SDD не должна придумывать отсутствующие `REQ-*`.
