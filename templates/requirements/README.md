# Шаблоны требований

Этот каталог является проектным источником шаблонов для режима требований.

## Профиль требований

Новые корневые документы используют профиль АС КОДА, основанный на ISO/IEC/IEEE 29148:2018. Это практическая адаптация критериев качества, структуры и трассировки, а не заявление полного соответствия стандарту. Полное описание находится в `core/requirements-profile.md`.

Облегчённый и подробный форматы используют одинаковое обязательное ядро: назначение и границы, текущее состояние, участников, термины и данные, атомарные `REQ-*`, сценарии `SCN-*`, нефункциональные требования, влияния, зависимости, критерии завершённости и трассировку. Форматы различаются только объёмом представления.

Старые документы без маркера профиля остаются допустимыми. Они переводятся на профиль при существенной переработке или по явному решению пользователя, но не ради формального изменения заголовков.

## Язык требований

- Основной язык требований — русский.
- Англоязычные слова в обычном описательном тексте необходимо заменять русскими формулировками.
- Английская форма допустима внутри кода, путей, точных API/БД-идентификаторов, значений перечислений и закреплённых названий внешних систем.
- Если специальный термин без английской формы неоднозначен, сначала используется русское объяснение, затем точный термин в скобках или обратных кавычках.
- Не следует использовать англицизмы только потому, что они короче русской формулировки.
- Перед завершением работы запускается `scripts/validate-language.py` по изменённой функциональности.

Примеры предпочтительных замен:

| Не использовать в обычном тексте | Предпочтительная формулировка |
|---|---|
| scope | объём работ, границы |
| baseline | текущее или базовое состояние |
| feature | функциональность |
| slice | срез |
| workflow | процесс, рабочий контур |
| developer task | задача разработки |
| task candidate | черновик задачи реализации |
| handoff | передача в разработку |
| impact | влияние |
| acceptance criteria | критерии приёмки |
| draft / approved | черновик / утверждён |
| frontend / backend | клиентская / серверная часть |

Пути вроде `baseline/current/`, идентификаторы `REQ-*`, `ApprovalChain`, HTTP-методы и названия таблиц не переводятся.

## Доступные форматы

- `feature-requirements.template.md` — подробный корневой документ.
- `slice.template.md` — подробная карточка среза.
- `frontend.template.md` — подробный пакет требований к клиентской части.
- `backend.template.md` — подробный пакет требований к серверной части.
- `feature-requirements.readable.template.md` — облегчённый корневой документ.
- `slice.readable.template.md` — краткая карточка среза.
- `frontend.readable.template.md` — краткий пакет требований к клиентской части.
- `backend.readable.template.md` — краткий пакет требований к серверной части.
- `developer-task-index.template.md` — прежний индекс аналитически подготовленных задач; сохраняется только для совместимости существующих проектов.
- `developer-task.template.md` — прежний пакет одной задачи; для новых передач используйте общий пакет функциональности из `templates/handoff/`.

## Выбор формата

| Формат | Когда применять |
|---|---|
| Новый облегчённый | новая функциональность, краткие срезы, удобство чтения человеком |
| Старый подробный | пользователь явно запросил подробный формат или функциональность уже ведётся в нём |

Внутри одной функциональности форматы не смешиваются без явного запроса. Корневые требования, карточки срезов и детальные пакеты должны использовать единый стиль.

## Источник истины

- `features/<feature>/requirements.md` — главный авторский документ требований.
- Карточки срезов и пакеты клиентской/серверной части являются производными.
- Входные редакции общего пакета являются неизменяемыми производными снимками требований и срезов.
- Подтверждённые карточки в возвратах пакета принадлежат разработчикам и не переписываются при изменении требований.
- Новое правило, найденное при детализации, сначала вносится в корневой документ.
- Контекстные сводки и исследовательские материалы не заменяют требования.

## Порядок работы

1. Проверить текущий активный режим.
2. Прочитать `baseline/current/`, исходные материалы и существующие требования функциональности.
3. Создать или обновить корневой документ.
4. Зафиксировать порядок и границы срезов.
5. Синхронизировать карточки срезов.
6. Обновить пакеты требований к клиентской и серверной части.
7. Зафиксировать влияние на соседние функциональности, модель предметной области и прототипы.
8. Выполнить проверку хвостов и языковой контроль.
9. Выполнить `scripts/validate-requirements-profile.py <project> --feature <feature>`.
10. По отдельной команде сформировать новую входную редакцию общего пакета функциональности. Если предыдущая редакция уже отправлена, не менять её файлы.

## Проверка хвостов

После изменения необходимо повторно проверить:

- старые маршруты API;
- прежние названия полей;
- устаревшие роли и статусы;
- старые подписи интерфейса;
- отменённые правила и решения;
- соседние функциональности и текущее состояние;
- прототипы, входные редакции пакетов и проверки.

Локальный необъяснённый хвост блокирует завершение. Межрежимное влияние фиксируется в `planning/consistency-backlog.md`.
