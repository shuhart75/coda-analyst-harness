# Обмен требованиями и результатами разработки

Версия договора: `5`

Каталог связывает требования аналитиков с фактической работой разработчиков.

Для GigaCode начни с `GIGACODE.md` в этом каталоге. Там указаны правила
подключения к корневой инструкции разработчика и необязательной команды
`delivery-sdd.command.md`. Автоматическая загрузка вложенных инструкций
не предполагается; корневые настройки кодового репозитория обвязка не меняет.

Начало работы: `AGENTS.md` задаёт договор, `SDD-WORKFLOW.md` — порядок работы
в одном или нескольких репозиториях. Рядом поставляются шаблоны квитанции,
декомпозиции, результата задачи и общего итога. Они не являются возвратами:
заполняет их разработка только внутри `returns/` выбранной редакции.

На одну редакцию существует один канонический каталог обмена и один ответственный
за общий результат. Независимая рассылка и автоматическое объединение возвратов
нескольких репозиториев текущим транспортом не поддерживаются.

Принятая функциональность поставляется последовательными бизнес-этапами; каждый
нацелен на законченный полезный результат. Аналитик утверждает объём текущего
этапа, SDD определяет техническую декомпозицию. Параллельные этапы не поддерживаются.
В манифесте новая редакция имеет `stage_id`, `stage_revision`, снимок `stage`
(`stage_id`, `number`, `title`, `goal`) и `stage_sha256`. Глобальный номер
`revisions/<NNN>/` и `return_id` сохраняются. В `Границы` входного файла находятся
обычный маркер `Этап поставки: stage-1` с текущим идентификатором и дословные
однострочные название и цель. Исправление передаётся новой редакцией того же этапа.

Следующий этап требует закрытия предыдущего и отдельного решения аналитика.
Остаток и предварительный бэклог автоматически не включаются; зависимости
проверяются по фактам. Отсутствие прежнего `REQ-*` не отменяет внедрённое поведение:
его изменение или удаление должно быть явно задано. Legacy сохраняет историю:
аналитик может явно связать все редакции точного последнего опубликованного
манифеста с одним этапом через `adopt-legacy-stage`. Локальный `legacy_overlay`
не меняет старые манифесты, входы, returns и их идентификаторы. Прежние returns
проходят обычный reviewed и закрытие; новый вход требует маркера в авторском корне
и своего аудита. Смешанная история нескольких этапов не группируется автоматически.

Пакет из отдельной ветки `requirements/**` сначала проходит человеческий PR/MR
в согласованную целевую ветку кода. До слияния это предложение, а не вход разработки:
состояние `sent` в предлагаемом манифесте ещё не разрешает создание возвратов.
Резервный каталог в аналитическом проекте означает только местное размещение.

Для каждой поставки входом служат:

- `manifest.json`;
- одна активная редакция `revisions/<NNN>/requirements.md`;
- для `openspec-spec-driven-v1` — `revisions/<NNN>/sdd/package.json` и готовые
  `sdd/<backend|frontend>/<change-id>/{.openspec.yaml,proposal.md,specs/<capability>/spec.md}`.

В манифесте схемы 5 `sdd_input` связывает профиль и хеши всех файлов. Корневые
`sdd-receive.py` и `sdd_bundle.py` проверяют и размещают вход на стороне разработки;
первый запуск без `--apply` ничего не изменяет.

Разработческая SDD читает формальный договор из `AGENTS.md`. При первом принятии
редакции она создаёт `revisions/<NNN>/returns/receipt.json` по корневому
`receipt.template.json` для версии 1 или `receipt-sdd.template.json` для версии 2,
а затем записывает остальные результаты в тот же `returns/`.

`requirements.md` остаётся единственным авторским бизнес-контрактом. В SDD-профиле
аналитик готовит из него proposal/delta specs, разработка сверяет готовый вход с
кодом и main specs, принимает его без повторной генерации и создаёт design/tasks.
Перенос разрешается разработчиком отдельно; аналитическая обвязка не пишет в
рабочие OpenSpec-каталоги. Для прежнего входа без `sdd_input` сохраняется прежний
порядок самостоятельного создания дельты разработкой.

Входные редакции требований неизменяемы. Новые вводные передаются новой редакцией. Возвраты одной редакции не переносятся в другую автоматически.

Объём текущей поставки утверждает аналитик с полномочиями владельца продукта.
SDD определяет техническую декомпозицию и сообщает о невыполненной части.
Квитанция получения, фактическая реализация, её проверка, аналитическая приёмка
и внедрение являются разными событиями. Подробные решения аналитика хранятся в
аналитическом проекте, а не в разработческом `returns/`.

Файл `returns/tasks.md` содержит уже согласованную разработчиками разбивку. Аналитическая сторона не участвует в её согласовании и не подтверждает её.

Состояние обработки определяется по файлам активной редакции:

- нет `receipt.json` — новая редакция ещё не принята;
- есть только квитанция — редакция принята, идёт сверка с кодом;
- появился `tasks.md` — согласованная декомпозиция записана;
- появились `tasks/<task-id>.md` — реализация выполняется;
- появился полный `summary.md` — редакция обработана.

Каждая новая редакция требует собственной квитанции. Для `returns_contract_version: 2`
квитанция содержит также `sdd_sha256` из манифеста. Результаты прежней редакции
не означают, что новая редакция уже принята или обработана.

`completed` у полного итога не закрывает бизнес-этап. Закрытие требует решения
аналитика по текущему подробному `reviewed` итогу каждого `REQ-*` и всему остатку;
`unknown` и `investigate` блокируют его. Нулевое выполнение допускается при явном
решении судьбы всего объёма, но не считается успешной поставкой. Приёмка,
внедрение и закрытие учитываются отдельно.

## Квартальные поставки: схема 4

`delivery_binding.feature_id` — постоянная бизнес-фича; `delivery_id` и `quarter`
обозначают её поставку. `delivery_key` совпадает с историческим полем `feature`
и именем каталога: это транспортный ключ, а не новая бизнес-фича. Проверяй одну
точную поставку и активную редакцию. Не объединяй входы разных поставок и не
перепривязывай `return_id`; номер редакции имеет смысл внутри своего каталога.

В каждой новой редакции привязка совпадает с манифестом. При сохранённой старой
истории `legacy_revision_ceiling` ограничивает записи без этой привязки; они не
переписываются. Схемы 1/2/3 читаются по прежнему договору, схема 4 требует клиента
с поддержкой поставок. Схема 5 требует поддержки SDD-входа; историю схем 1–4
не изменяй. Новые поля не добавляются в старые квитанции. Общий бизнес-идентификатор не разрешает автоматически
включать отложенный объём или пропускать предыдущую реализацию при сверке кода.
