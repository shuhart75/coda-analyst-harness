# Новый обмен через documents

Для manifest schema 6 действует этот порядок. Прежние инструкции о receipt и
returns применяются только к старым редакциям с returns_contract_version 0–2.

1. Прочитать точный пакет в documents: редакция, requirements, tasks, sdd, materials.
   Проверить опубликованный коммит и контрольные суммы. Не менять входные файлы.
2. Сверить указанные исходные code_commit, context_files, base_specs со своим
   кодом и текущими specs. При расхождении затронутых правил разобрать изменения.
3. Для OpenSpec использовать поставленный sdd-receive.py; его --apply выполняется
   только в разработческом процессе. Принимать готовые proposal/specs без повторной
   генерации, затем готовить design/tasks. Технические шаги сохраняют согласованную
   нарезку tasks/grooming.json; одна задача может охватывать несколько changes.
4. Следовать местным правилам SDD, тестирования и Git. Использовать номера задач,
   обозначенных после груминга. Ссылка на исходную редакцию в proposal полезна,
   но отдельная квитанция и отчёты в documents не требуются.
5. Сохранять обычные технические артефакты SDD и результаты проверок согласно
   местному процессу. Аналитическая обвязка самостоятельно сверяет результаты
   с требованиями по Git, OpenSpec и коду. Архивация не означает внедрения.

Аналитик не копирует папку обмена, инструкции или helper-файлы в coda. Разработка
читает их из documents. Архивный change не заменяет действующие main specs;
требования новой поставки сопоставляются с закреплённой исходной базой.
