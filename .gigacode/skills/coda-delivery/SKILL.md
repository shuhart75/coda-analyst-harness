## Новые передачи через documents

Для всех новых передач следуй `core/documents-exchange.md`: публикация только
в documents, manifest schema 6, собственный анализ по задачам груминга вместо
обязательных квитанций и returns. Указания ниже о публикации в code и обязательных
returns относятся только к прежним редакциям. Новый процесс не пишет в code.
Текущие исходные specs закрепляются до разработки; результат ищется после неё
по номерам согласованных задач. Архивация не подтверждает тесты или внедрение.


# Поставка и возвраты

**RULE:** Это skill аналитической стороны. Разработческий вход поставляется
в `requirements-exchange/GIGACODE.md` и `SDD-WORKFLOW.md`; он использует
локальные skills SDD разработчиков. Не запускай реализацию через этот skill.
Шаблон `delivery-sdd.command.md` подключает разработчик в своём репозитории;
prepare не меняет его корневой `GIGACODE.md` и `.gigacode/`.

**DOCS:** Прочитай `GIGACODE.md`, `core/delivery-stages.md`,
`core/developer-handoff.md`, `core/sdd-input.md`, `core/requirements-audit.md` и
`modes/requirements.md`.

**RULE:** Определи операцию по запросу: регистрация/закрытие этапа, передача,
проверка прежней публикации, чтение или обработка возврата. Не выполняй
остальные операции автоматически. Входы и разрешённые записи задаёт её договор.
Оформление задач по `core/delivery-stories.md` входит в операцию передачи;
после публикации пакета продолжи его без отдельной команды аналитика.

**RULE:** Новая подготовка явно выбирает `begin-preparation --input-profile
openspec-spec-driven-v1`. В рабочей ветке требований до принятия в main подготовь
`<delivery-root>/sdd/package.json`, proposal и delta specs затронутых backend/frontend
по `core/sdd-input.md`. Requirements остаётся единственным авторским бизнес-контрактом.
Исходный code commit, config/context, main specs и покрытие REQ/сценариев проверяются
через зарегистрированное чтение; отсутствие источников блокирует готовность.
Не генерируй design/tasks и не вызывай opsx-propose/opsx-ff. Аналитик не запускает
sdd-receive.py --apply и не пишет в рабочие OpenSpec roots кода.

**RULE:** Перед передачей нужны актуальная принятая main, завершённая сессия
и `require-main-for-delivery`. Выполни три уровня аудита, проверки и record-audit,
покажи отчёт и получи отдельное явное подтверждение аудита и отправки.
Только после этого confirm-audit и prepare неизменного requirements и всего SDD-пакета.
Аудит связывает все байты и источники; изменение любого входа требует повтора.
При awaiting-merge сообщи ожидание принятия PR/MR; mark-published
для documents допустим только при publication_confirmed=true.

**RULE:** Публикуй только через requirements-exchange.py prepare. Новые
отдельные ветки ограничены 48 байтами; полная идентичность остаётся в
манифесте по core/naming.md. Не собирай имя вручную. Отказ серверного hook
не разрешает отправку или слияние напрямую в целевую ветку. Повторный
prepare проверяет прежнюю ветку, включая старый длинный формат.

**RULE:** Для возврата используй scan и точную редакцию; reviewed требует
решения по каждому REQ и остатку. Различай реализацию, проверку, приёмку,
внедрение и закрытие этапа. Прежние входы и returns неизменяемы.

**RULE:** При проверке возврата самостоятельно исследуй доступный код по
core/code-inspection.md и разделу «Самостоятельная проверка возврата аналитической
обвязкой» в core/developer-handoff.md. Используй
templates/exchange/analyst-return-review.template.md для собственного разбора.
Ветка отчёта и движение develop/main не требуют нового отчёта разработчика.
Проверь каждый сценарий, отдели вклад разработчика от последующих изменений.
Не переноси непроверенные оценки в reviewed. Предлагай аналитику также принятие
реализации с изменением требований; сроки и судьбу остатка согласуй отдельно.
К разработке готовь только сводный запрос за недоступными доказательствами,
после самостоятельного исследования; отправка требует разрешения аналитика.
Независимые части работы продолжай. Решения применяй штатными операциями в
режиме-владельце, с существующими ссылками на остаток и точным return_id.

**PROHIBITED:** Не создавай design/tasks и техническую декомпозицию за разработчиков;
proposal/delta specs аналитика являются согласованным входом SDD.
Не включай остаток в следующий этап автоматически. ZIP запрещён; используй
обычные файлы и каталоги. Сообщи фактическое место и номер редакции.

**DOCS:** Для квартальной структуры прочитай `core/quarter-deliveries.md`.
Путь авторских требований и исполнения получи через `scripts/project_layout.py`
по выбранной поставке; legacy slug является операционным псевдонимом, а не новой
бизнес-фичей. Не дублируй авторский текст в корневом каталоге `features/`.

**DOCS:** Корневой паспорт фичи описан в `core/feature-passports.md`.
Читай его по физическому пути `features/<feature_id>/`; контракт для передачи
бери только из выбранной поставки. Сводные требования не являются второй
передаваемой редакцией. При изменении поставки, актуализации задач или
подтверждении релиза обновляй разрешённые режимом разделы паспорта с датой,
содержанием изменения и источником; не выводи внедрение из завершения задач.

## Передача по явному решению аналитика

Если аналитик явно просит передать текущий пакет без аудита и сверки с кодом,
приоритет имеет `core/analyst-decision-delivery.md`: одна команда
`requirements-exchange.py send-by-decision`, без предварительных main gate,
record-change, аудитов и отмены прежнего кандидата. Разрешение повторно не
запрашивать. Обычный маршрут остаётся для передачи без такого решения.

## Передача после груминга

Для новой передачи сначала проверь согласованный груминг по `core/grooming.md`.
При его отсутствии вернись к согласованию через `coda-requirements`. Схема 3 SDD
включает `tasks/` в общий хеш; принимай его вместе с требованиями и proposal/spec.
Принимающая SDD сохраняет согласованные story, а технические шаги создаёт внутри
них. Старые незавершённые публикации продолжаются без переписывания входа.
После подтверждённой публикации в documents выполни `core/delivery-stories.md`:
номера из запроса или груминга найди и обнови; для задач без номера создай Story.
Запрос передачи разрешает обработать согласованный состав без отдельных вопросов
о записи каждой карточки. Сохрани остальные поля существующих задач.

Для каждой задачи проверь эпик фичи, RSCON_dev, КЭ «ПКАП1200 АС КОДА
(CI07642362)», «Архитектурные изменения: Не влияет на архитектуру» и
«Требуется НТ: Нет». Добавь описание, критерии, три пояснённые ссылки на корень
редакции, общие requirements.md и папку задачи, а также промпт SDD и ссылку
на всю редакцию как его вход. Оценки опциональны. Перед MCP выполни config-status;
используй preview/status/resolve/claim/bind и фактическое чтение после записи.
Полный успех передачи сообщай только с отдельным итогом обработки задач.
