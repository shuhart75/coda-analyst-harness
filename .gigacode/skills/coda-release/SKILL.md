# Финализация выпуска

**RULE:** Обработка внедрённого релиза объединяет разбор результатов, baseline
и очистку обмена. Обязательно проверь актуальность доменной модели: сущности,
связи, правила, жизненные циклы, процессы и диаграммы. Зафиксируй по каждому
аспекту `updated` либо `unchanged` с основанием в `domain_review`; при влиянии
релиза обнови модель до продвижения baseline. Отсутствие изменений тоже требует
проверки. Формат review и команды — в `core/quarter-deliveries.md`.

**RULE:** После продвижения baseline выполни `baselinectl.py review-exchange`
по полному составу релиза. Полностью завершённые поставки архивируются в
`releases/<release-id>/exchange-archive/<delivery-key>/`; частичные остаются
активными. Решение связано с `packet_hash` всех входов и возвратов после их
разбора. Новые факты требуют новой проверки, а не автоматического согласия.
После принятия архива вместе с baseline в analytics/main запускай
`baselinectl.py cleanup-exchange`. Для code используется изолированная ветка
удаления и человеческое слияние; обычный checkout неизменен. Для analytics
удаление сохраняется обычным порядком. Повтор команды подтверждает принятие
удаления; до этого очистка остаётся видимой. Не повторяй продвижение baseline
из-за ошибки очистки и не удаляй пакет вручную.

**DOCS:** Прочитай `GIGACODE.md`, `modes/release-finalization.md`,
`core/developer-handoff.md` и `core/delivery-stages.md`.

**RULE:** Режим `release-finalization`; входы: точная переданная редакция,
подробные reviewed результаты и решения аналитика о приёмке, внедрении
и остатке. Не считай completed доказательством внедрения или закрытия.
Результат: разрешённые режимом записи выпуска и baseline в PROJECT_ROOT.

**RULE:** Переноси в baseline подтверждённые внедрённые факты, сохраняя
ограничения и отвергнутые отклонения; проверь соседние функциональности,
ссылки, структуру, контекст и согласованность. Неизвестное требует решения.

**PROHIBITED:** Не редактируй прежние входы и возвраты, не закрывай этап
без явного решения и полной судьбы остатка, не объявляй поставку по статусу
задачи или факту подготовки пакета.

**DOCS:** Для квартальной структуры прочитай `core/quarter-deliveries.md`.
Путь авторских требований и исполнения получи через `scripts/project_layout.py`
по выбранной поставке; legacy slug является операционным псевдонимом, а не новой
бизнес-фичей. Не дублируй авторский текст в корневом каталоге `features/`.

**RULE:** Каждый подтверждённо внедрённый релиз требует версии baseline.
Проверяй влияние на domain, requirements, ui, api, data и decisions; сохраняй
неизменённые разделы. Домен — связное человекочитаемое объяснение сущностей,
отношений, ЖЦ, процессов и диаграмм. Решения не удаляются при замене. Используй
проверенный кандидат и реестр `releases/baseline-status.json` через внутренний
`scripts/baseline_releases.py`; закрытие задач лишь предлагает обработать релиз,
но не разрешает автоматическое продвижение. Отсрочка не скрывает кандидата.

**DOCS:** Корневой паспорт фичи описан в `core/feature-passports.md`.
Читай его по физическому пути `features/<feature_id>/`; контракт для передачи
бери только из выбранной поставки. Сводные требования не являются второй
передаваемой редакцией. При изменении поставки, актуализации задач или
подтверждении релиза обновляй разрешённые режимом разделы паспорта с датой,
содержанием изменения и источником; не выводи внедрение из завершения задач.
