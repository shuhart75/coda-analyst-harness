# Требования

**DOCS:** Прочитай `GIGACODE.md`, `modes/requirements.md`,
`core/requirements-profile.md`, `core/requirements-system-profile.md`, `core/requirements-wording.md` и
`core/requirements-audit.md` в HARNESS_ROOT.

**RULE:** Режим `requirements`; входы: baseline, исходные материалы и соседние
функциональности в PROJECT_ROOT. До чтения существующей функциональности
проверь её рабочую сессию по `core/collaboration.md`. Перед правкой выполни
`requirementsctl.py status`; происхождение незарегистрированной разницы
выясни у аналитика.

**RULE:** Авторский результат: один `features/<feature>/requirements.md`,
его состояние и необходимые вспомогательные записи. После правки зарегистрируй
источник через `record-change`. Выполни профильную, языковую, ссылочную проверку,
`validate-requirements-wording.py` и проверку изолированного читателя; проверь
взаимодействие всех REQ и влияния на соседние функциональности.

**PROHIBITED:** Не создавай срезы, технические задачи или редакции обмена из
обычной правки. Skill не утверждает требования и не разрешает передачу.

**DOCS:** Для квартальной структуры прочитай `core/quarter-deliveries.md`.
Путь авторских требований и исполнения получи через `scripts/project_layout.py`
по выбранной поставке; legacy slug является операционным псевдонимом, а не новой
бизнес-фичей. Не дублируй авторский текст в корневом каталоге `features/`.

**DOCS:** Корневой паспорт фичи описан в `core/feature-passports.md`.
Читай его по физическому пути `features/<feature_id>/`; контракт для передачи
бери только из выбранной поставки. Сводные требования не являются второй
передаваемой редакцией. При изменении поставки, актуализации задач или
подтверждении релиза обновляй разрешённые режимом разделы паспорта с датой,
содержанием изменения и источником; не выводи внедрение из завершения задач.

## Груминг

По явному запросу «грумим <фичу>» следуй `core/grooming.md`. Разреши поставку
и этап, согласуй по одной задачи с названиями требований своего FE/BE-контура,
определённого префиксом. Оценки всегда в человеко-днях. Подготовь согласованный
`tasks/` и SDD, проверь покрытие. Далее используй `coda-delivery` для аудита
и передачи, затем создания story по договору груминга. Skill не заменяет
подтверждения конкретного состава, аудита или внешних записей.

## Читаемая системная спецификация

Основной документ, обсуждение с аналитиком и требования задач для разработчиков
пиши прямо, без лишних технических конструкций: действие, условие при необходимости,
наблюдаемый результат. Применяй раздел «Прямой язык требований для людей» из
`core/requirements-wording.md`. Для производного SDD сохраняй техническую точность
по `core/sdd-input.md`, не перенося его формальный язык обратно в человеческий текст.

Для новых документов применяй системный профиль: разделение FE/BE по запросу,
применимые API/данные, таблицы правил и общие критерии с полными REQ-ссылками.
Согласовывай разделы последовательно, если аналитик просил такой порядок.
Не заполняй неизвестные поля и решения догадками. Существующий компактный
формат не мигрирует автоматически; опубликованные редакции не меняются.
